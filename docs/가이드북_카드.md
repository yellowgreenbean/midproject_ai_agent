## 0. 한눈에 보기

### 0-1. 카드 목록 조회 기능의 목적
- **내 카드를 한곳에서 본다.** 토스의 「내 카드」처럼, 로그인한 회원이 가진 카드(체크·신용)를 한 화면에 모아 이번 달 쓴 돈·낼 돈·결제일을 바로 알 수 있게 한다(기획서 1-1-1).
- **카드 한 장을 깊게 본다.** 결제 계좌·결제일·연회비, 그리고 **어떤 혜택을 어떤 조건으로 받는지**와 지난달 실적으로 지금 혜택을 받을 수 있는지를 보여 준다(1-1-2).
- **어디에 얼마 썼는지 본다.** 카드별 이용 내역을 달·업종·일시불/할부로 걸러 본다(1-1-3). 이 데이터가 나중에 실적(1-1-6)·예측(1-4)·추천(1-5)의 원재료가 된다.
- **낼 돈을 놓치지 않는다.** 모든 카드의 청구서를 결제일별로 묶은 결제 캘린더, 결제 계좌 잔액 부족 경고, 결제일 3일 전·당일 알림(1-1-4).
- **본인 것만 본다.** 과제 필수 조건 「인증된 사용자가 본인에게 허용된 정보만 이용」 — 모든 카드 조회는 로그인한 회원의 카드로만 거른다.
- 1차는 기획서대로 **모의 카드사 서버 없이 `data/dummy/cards/` 더미**를 읽는다. 마이데이터 동기화(1-1-0)는 2차다.

### 0-3. 왜 「py 파일 하나 실행」이 아니라 「서버 API」인가
```
 [브라우저 화면 frontend :5173]  ──HTTP 요청(쿠키 sid)──▶  [FastAPI 서버 backend :8010]  ──SQL──▶  [PostgreSQL (Docker) :5433]
     「내 카드」를 연다                      ① 쿠키로 회원 확인                      user_cards · card_transactions
                                           ② 그 회원의 카드만 골라 계산               card_bills · card_benefits …
```
- **누구의 카드인지는 서버만 정할 수 있다.** 화면이 「user_001 의 카드를 줘」라고 보내면 누구나 남의 아이디를 넣을 수 있다. 서버는 화면이 보낸 값이 아니라 **로그인 쿠키(sid) → 세션 → 회원**으로 주인을 정하고, 그 회원의 카드만 DB 에서 꺼낸다.
- **브라우저는 DB 에 직접 붙을 수 없다.** 브라우저 코드는 누구나 열어 볼 수 있어서 DB 비밀번호를 넣으면 그대로 드러난다.
- **금액 판정은 한 곳에서.** 「낼 돈」·「이번 기간 사용액」·「잔액 부족」·「실적 구간」 계산을 서버가 하고 화면은 받은 숫자를 묶어 보여 주기만 한다(`frontend/src/cardRules.ts` 첫 줄 주석). 챗봇(자연어 요청)이 같은 API 를 부르면 화면과 같은 답이 나온다.
- 버튼을 누를 때마다 실행돼야 하므로 계속 켜져 있는 **서버의 API** 여야 한다. 반대로 `scripts/crawl_card_benefits.py`(크롤링)·`scripts/load_dummy.py`(DB 채우기)는 「처음에 데이터를 준비하는」 일회용 도구라 스크립트로 둔다. 결제일 알림은 사람이 누르는 게 아니라 하루 한 번 도는 일이라 `app/jobs.py` 함수다.

## 1. 로그인한 회원의 카드만 — 「본인 확인」은 어떻게 하나

> 카드 조회 기능을 만들기 **전에** 먼저 확인하고 테스트로 고정한 부분이다.

### 1-1. 서버가 회원을 정하는 순서 (`backend/app/deps.py`, 원래 있던 코드)
```
쿠키 sid ─▶ sessions 행 (id = 쿠키의 해시) ─▶ 끊김·최대 12시간·유휴 10분 검사 ─▶ users 행 ─▶ 상태 검사
   없음 → 401 UNAUTHORIZED           만료 → 401 SESSION_EXPIRED                    WITHDRAWN → 401
                                                                                  PENDING_VERIFICATION → 403 SIGNUP_INCOMPLETE
```
라우터는 회원을 직접 찾지 않고 `CurrentUserId` 만 받는다.
```python
@router.get("/cards", response_model=list[CardOut])
def list_cards(db: DB, user_id: CurrentUserId):      # ← 로그인 회원 id (위 검사를 통과해야 들어옴)
    ...
```

### 1-2. 「그 회원의 카드만」 거르는 곳 (`backend/app/routers/cards.py`)
목록·상세는 `_load()`, 이용 내역·해지·결제는 `_owned()` 를 거친다. 둘 다 **WHERE 에 `user_id = 로그인 회원`** 이 들어 있다.
```python
q = (select(UserCard, CardProduct, CardCompany.name, Account)
     ...
     .where(UserCard.user_id == user_id, UserCard.source == "TOSS_ISSUED"))
```
- 남의 카드 id 를 넣으면 이 조건에 걸려 행이 0개 → `card_not_found()` → **404**. 없는 카드 id 와 응답이 글자 하나까지 같다.
- 청구서 상세(`/card-bills/{billId}`)는 청구서 → 카드(`user_cards`)를 JOIN 해서 카드 주인을 본다(청구서 표에는 `user_id` 가 없다).

### 1-3. 테스트로 고정한 것 (`backend/tests/test_cards.py` 앞부분)
**진짜 쿠키 로그인**(`POST /auth/login`)으로 시험한다 — 개발용 `X-User-Id` 헤더는 쓰지 않는다.
| 시험 | 기대 |
|---|---|
| 로그인 없이 `/cards`·`/cards/card_001`·`/cards/card_001/transactions`·`/card-bills` | 401 `UNAUTHORIZED` (화면 `api.ts` 는 이걸 `UNAUTHENTICATED` 로 묶어 손님 화면을 띄움) |
| 엉터리 쿠키 + 남의 `X-User-Id` | 401 — 쿠키가 있으면 쿠키가 우선 |
| 가입 마무리 중(user_028) | 403 `SIGNUP_INCOMPLETE` |
| user_001 로그인 | `card_001`·`card_002`·`card_003` 만, 전부 주인이 user_001 |
| user_003 → 로그아웃 → user_002 | 카드가 바뀌고, 로그아웃 직후는 401 |
| 카드 없는 user_005 | `200 []` |
| user_001 이 `card_004`·`card_006`·`card_006/termination-check` | 404 `CARD_NOT_FOUND`, **`card_999`(없는 카드)와 응답이 같다** |

## 2. DB 의 어떤 표를 쓰나 (`docs/sql/05_card_products.sql`, `docs/sql/06_card_usage.sql`)

### 2-1. 카드 더미가 DB 에 들어갔는지 확인한 결과
`data/dummy/cards/` 의 세 파일은 `scripts/load_dummy.py` 가 아래 표로 옮긴다(기획서 Part 6 C-2 변환 규칙).
| 더미 파일 | 개수 | DB 표 | 확인 결과 (2026-11-10) |
|---|---|---|---|
| `cards.json` | 30장 | `user_cards` | 30행 · 주인 15명 · 카드 번호·상품·상태·한도·연결 계좌 **불일치 0** |
| `card_approvals.json` | 132건(취소 5) | `card_transactions` (`id = 'ctx_' + 승인번호`) | 132행 · 카드·금액·취소 금액·상태 **불일치 0** |
| `card_billing.json` | 30건 | `card_bills` (`id = 'bill_' + 카드 + '_' + 결제 연월`) | 30행 · 청구 금액 **불일치 0** |

비교는 JSON 과 DB 를 한 칸씩 맞춰 보는 짧은 파이썬으로 했다. 주의: JSON 의 `credit_limit` 은 문자열(`"1000000"`), DB 는 숫자라서 **형식을 맞추고** 비교해야 한다(처음에 15건이 「다름」으로 나온 이유).
```bash
docker exec midproject-postgres psql -U app -d midproject -c "SELECT count(*) FROM user_cards" -c "SELECT count(*), count(*) FILTER (WHERE status='CANCELED') FROM card_transactions" -c "SELECT count(*) FROM card_bills"
```

### 2-3. 스키마에 더한 것 (기획서 3장 #19~21)
| 대상 | 추가한 칸 | 뜻 · 예 |
|---|---|---|
| `card_benefits` | `limit_group_id` | 같은 그룹끼리 통합 월 한도를 함께 씀 |
| 〃 | `merchant_names` | 이 가맹점에서만 (쉼표로) — `스타벅스,폴바셋` |
| 〃 | `payment_channel` | `ONLINE` 온라인만 / `OFFLINE` 매장만 |
| 〃 | `pay_methods` | 이 간편결제로 낼 때만 — `삼성페이,네이버페이,카카오페이,PAYCO` |
| 〃 | `days_of_week` | 이 요일만 — `SAT,SUN` |
| 〃 | `time_start` · `time_end` (TIME) | 이 시각만 — `18:00` ~ `23:00` |
| 〃 | `max_eligible_amount` | 건당 이 금액까지만 계산 — 「5만 원까지 10%」 |
| 〃 | `per_payment_max_benefit` | 건당 최대 혜택 — 「건당 최대 2천 원」 |
| 〃 | `daily_limit_count` | 하루 횟수 — 「일 1회」 |
| 〃 | `value_type` 에 `PER_LITER` | 「리터당 60원」 |
| 〃 | `category_id` NULL 허용 | NULL = 모든 가맹점, 상위 업종이면 하위 업종 포함(교통 → 택시) |
| 🆕 `card_benefit_limit_groups` | `id`, `card_product_id`, `tier_id`, `name`, `monthly_limit_amount` | 「칼퇴 4개 업종 통합 월 4천 원」 |
| `card_performance_tiers` | `period` (`MONTH`/`QUARTER`), UNIQUE `(card_product_id, period, tier_level)` | 「분기 300만 원 이상」 |

**혜택 행은 실적 구간마다 하나다.** 실제 카드는 구간마다 한도가 다르다(30만 원 이상이면 월 4천, 60만이면 8천…). 그래서 같은 혜택을 구간 수만큼 행으로 두고 `tier_id` 가 「그 구간일 때의 규칙」을 가리킨다. 화면은 「지금 내 구간」의 행만 보여 준다.

## 3. 카드 정보 크롤링 — 어느 사이트에서 받아 어디에 넣었나

> 더미 카드 5종(`한빛 …`)은 CODEF 샌드박스의 **가상 카드**라 혜택 정보가 없다. 카드 이름과 두린은행 발급은 그대로 두고, 상품마다 비슷한 실제 카드의 혜택·실적 구간·연회비를 가져왔다.

### 3-1. 흐름 한 장
```
 카드고릴라 공개 API ──(scripts/crawl_card_benefits.py)──▶ data/cardgorilla/card_<번호>.json    원문 그대로 (참고 자료, 고치지 않음)
```

| 파일의 칸 | 뜻 |
|---|---|
| `categories` | 혜택에만 나오는 업종 7개 — 주점 `BAR` · 헬스·스포츠 `FITNESS` · 전자책 `EBOOK` · 백화점·아울렛 `DEPARTMENT_STORE`, 교통 아래 대중교통 `PUBLIC_TRANSIT` · 택시 `TAXI` · 카셰어링 `CAR_SHARING` |

- id 규칙: 구간 `cpt_<상품번호>_<M|Q><구간>` · 통합 한도 `cblg_<상품번호>_<key>_<M|Q><구간>` · 혜택 `cb_<상품번호>_<혜택번호>_<M|Q><구간>` (예: `cb_001_03_M2` = 한빛 라이프 체크 3번째 혜택의 2구간 규칙)
- 안전장치(틀리면 SQL 을 만들지 않고 멈춤): 모르는 칸 이름(오타) · 없는 업종 · 구간이 이어지지 않음(앞 구간 상한 ≠ 다음 구간 하한) · `…_by_tier` 개수 ≠ 구간 수 · 그 구간에 없는 통합 한도
- 결과: `categories 20 · card_performance_tiers 13 · card_benefit_limit_groups 15 · card_benefits 74`
  (혜택 74 = 라이프 체크 10×3 + 체크카드 1+5×2 + 쇼핑 8×3 + 신용 1+3 + 할인 5×1)
- `load_dummy.py` 는 이 상품 연회비로 `user_cards.annual_fee_amount` 를 채운다. 더미 카드 번호가 모두 4로 시작(VISA = 해외겸용)이라 해외겸용 금액.

### 4-2. API 별 설명

#### ① `GET /cards` — 내 카드 모아보기 (1-1-1)
- 조건: 로그인 회원 + `source = 'TOSS_ISSUED'` + **`status <> 'TERMINATED'`** (해지한 카드는 목록에서 빠짐)
- 카드마다 `period_spent`:
  ```python
  # 신용: 이번 기간 사용액(청구 전) / 체크: 이번 달 1일~오늘 쓴 돈 (체크는 낼 돈이 없어 card_money 가 0)
  if p.card_type == "CREDIT":
      spent = m.unbilled
  else:
      spent = spent_between(db, c.id, start, today + timedelta(days=1), counted_only=False)
  ```
- `unpaid_amount`(확정·연체 청구서 중 안 낸 돈)·`next_payment_date`·`product_summary`(한 줄 혜택 요약)
- 응답 예: `{"id":"card_002","product_name":"한빛신용카드","card_type":"CREDIT","period_spent":"0","unpaid_amount":"86900","next_payment_date":"2026-11-14","product_summary":"국내외 모든 가맹점 1.2% 할인, 분기 실적 추가 할인", …}`
- 금액은 **문자열**(`"86900"`) — 기획서 C-5 규칙.

#### ② `GET /cards/{cardId}` — 상세 + 혜택 + 실적 + 청구서 (1-1-2)
혜택 계산은 `backend/app/card_benefits.py`:
1. **실적 기간**: 지난달 `[지난달 1일, 이번 달 1일)`, 지난 분기 `[지난 분기 첫날, 이번 분기 첫날)`
2. **실적** = 그 기간 `amount − canceled_amount` 합, `is_performance_counted` 인 것만(세금·상품권 제외용 칸)
3. **구간 고르기**: 넘은 구간 중 가장 높은 것. 하나도 못 넘었으면 **첫 구간 행을 보여 주되 `achieved=false`**
   ```python
   reached = [t for t in mine if spent >= t.min_spend]
   tier = reached[-1] if reached else mine[0]
   ```
4. 그 구간의 혜택 행 + 실적 조건 없는 행(`tier_id IS NULL`)을 돌려준다. 혜택마다:
   - `title`: 「카페 55% 할인」·「주유 리터당 60원 할인」·「모든 가맹점 0.2% 적립」·「영화 5,500원 할인」
   - `conditions`: 칸을 사람 말로 — 「전월 30만 원 이상 썼을 때」·「스타벅스·폴바셋에서만」·「매장 결제만」·「토·일요일만」·「18시~23시 결제만」·「한 번에 1만 원 이상 결제」·「한 번에 최대 2,000원」·「하루 1회」 + `description`
   - `monthly_limit`(이 혜택만의 한도), `limit_group`(`{"name","monthly_limit"}` 통합 한도), `achieved`
5. `performance`: `[{"period":"MONTH","spent":"21300","tier_level":null,"tier_min_spend":"300000","next_min_spend":"300000"}]`
- 해지한 카드도 상세는 기록으로 볼 수 있다. 청구서의 잔액 부족은 **다른 카드 청구서까지 보고** 정하므로 ④ 의 `bills_of_user()` 를 같이 쓴다.

#### ③ `GET /cards/{cardId}/transactions` — 이용 내역 (1-1-3)
| 쿼리 | 뜻 | 잘못 넣으면 |
|---|---|---|
| `month=YYYYMM` | 그 달만 | `202613` → 422 `VALIDATION_ERROR` (정규식 `^\d{4}(0[1-9]|1[0-2])$`) |
| `category=CAFE` | 업종 code, **하위 업종 포함**(`TRANSPORT` → 택시·대중교통·카셰어링도) | 없는 code → 400 `INVALID_CATEGORY` |
| `installment=LUMP_SUM` / `INSTALLMENT` | 일시불만 / 할부만(2개월 이상) | 다른 값 → 422 |
- 먼저 `_owned()` 로 내 카드인지 확인 → 아니면 404. 최신순(같은 시각이면 id 큰 것 먼저).
- 응답 한 줄: `{"id":"ctx_00000018","transacted_at":"2026-10-28T00:01:00+09:00","merchant":"넷플릭스","category":"구독","category_code":"SUBSCRIPTION","amount":"17000","canceled_amount":"0","status":"APPROVED","installment_months":0,"is_overseas":false}`
- 화면은 달은 서버로 거르고, 업종 버튼은 받은 목록에서 바로 거른다. `category` 파라미터는 챗봇처럼 화면 없이 부를 때 쓴다.

#### ④ `GET /card-bills` · `GET /card-bills/{billId}` — 결제 캘린더 · 청구서 (1-1-4)
- 목록 = 내 모든 카드(해지한 카드 포함 — 낼 돈이 남을 수 있음)의 저장된 청구서 + **이번 기간 청구서**(쓰는 중 `SCHEDULED`, 아직 저장 전이라 `id: null`). 결제일 순.
- **잔액 부족(`low_balance`)** — 같은 결제 계좌에서 빠질 청구서를 결제일 순으로 **쌓아 더해** 잔액과 비교:
  ```python
  running[acc] = running.get(acc, 0) + b.total_amount - b.paid_amount
  b.low_balance = balance.get(acc, 0) < running[acc]
  ```
  예) card_002(86,900)·card_003(119,200)이 둘 다 acc_001 에서 11/14 에 빠지는데 잔액이 10만 원이면 → card_002 는 `false`, card_003 은 `true`.
- 상세 = 그 청구서 + `items[]`(`card_bill_items` 의 이용 내역·회차·원금). 남의 청구서·없는 청구서는 똑같이 404 `BILL_NOT_FOUND`.

#### ⑤ 결제일 알림 — `notify_card_payments(db, now)` (`backend/app/jobs.py`)
1. 확정(`CONFIRMED`) 청구서 중 결제일이 **3일 뒤 또는 오늘**인 것
2. 카드 설정에서 알림을 끈 카드(`payment_alert_enabled = false`)는 건너뜀, 탈퇴 회원도 건너뜀
3. `PAYMENT_DUE` 「11월 14일 카드 대금 결제 예정」 — 본문 「한빛신용카드(0002) 86,900원 · 결제 계좌 …」
4. 같은 계좌 청구서를 쌓아 더한 금액 > 잔액이면 `LOW_BALANCE` 「카드 대금 낼 잔액이 모자라요」 — 「결제 계좌에 106,100원을 더 채워 주세요」
5. **같은 알림은 한 번만**: `(event_id, user_id, type)` 이 이미 있으면 안 만든다. `event_id` 는 D-3 이면 청구서 id, 당일이면 `청구서 id + ':D-0'` (시나리오 시드의 「결제 예정」 알림이 청구서 id 를 쓰고 있어서 그 규칙에 맞춤)
- `python -m app.jobs` 에서는 **출금(`pay_due_card_bills`)보다 먼저** 돈다 — 당일 알림이 출금보다 먼저 가게.

## 5. 겪은 문제와 해결 (같은 일을 다시 할 때 참고)

### ① 모델을 다시 만들자 `ValueError: TIME`
- **원인**: `scripts/gen_models.py` 의 `type_code()` 가 아는 타입 목록에 `TIME` 이 없었다(그동안 시각 칸은 모두 `TIMESTAMP`).
- **해결**: `_base.py` 에 `TM = TIME(precision=0)` 을 두고, 생성기에 `if n == "TIME": return "TM", "time"` 와 import 후보(`time`, `TM`)를 더했다. `TS` 와 같은 방식.

### ② 스키마를 고쳤는데 개발 DB 를 `down -v` 로 다시 만들 수 없음
- **원인**: README 의 방법(`docker compose down -v` → `up`)은 볼륨을 통째로 지운다. 개발 DB 에는 챗봇 RAG 벡터 3,037개가 들어 있어 다시 만들려면 임베딩 API 를 또 불러야 한다.
- **해결**: 바뀐 두 표(`card_performance_tiers`·`card_benefits`)가 **비어 있었으므로** 그 둘만 지우고 `docs/sql/05` 의 새 정의로 다시 만들었다. `card_transactions` 가 `card_benefits` 를 가리키는 외래 키는 먼저 떼고 다시 붙인다(6-2 의 SQL). 테스트 DB 는 매번 `docs/sql` 로 새로 만들어서 상관없다.

### ③ 더미를 다시 넣었는데 연회비가 그대로 0원
- **원인**: `load_dummy.py` 의 INSERT 는 `ON CONFLICT DO NOTHING` — **이미 있는 행은 바꾸지 않는다**(약관 `content_url` 때와 같은 함정). 새 표의 행만 들어가고 `card_products`·`user_cards` 의 연회비는 그대로였다.
- **해결**: 이미 넣은 개발 DB 에는 UPDATE 로 직접 고쳤다(6-2).

### ④ 청구서 항목을 채우자 해지 전 확인의 「남은 할부」가 청구 금액과 같아짐
- **원인**: 원래 코드가 「안 낸 청구서의 항목 원금 합」을 남은 할부로 셌다. 전에는 항목이 0개라 드러나지 않았는데, 일시불까지 「할부」로 세고 있었다.
- **해결**: **할부 거래(2개월 이상)** 의 원금 − 이미 낸(`PAID`) 청구서에 들어간 회차 원금 으로 바꿨다. 더미는 전부 일시불이라 0원이 맞다(`test_termination_check_counts_only_installments_as_remaining`).

### ⑤ 카드 상세 화면이 열리다가 멈춤
- **원인**: 더미 카드는 유효기간(`resValidPeriod`)이 비어 `expires_at` 이 `null` 인데, 화면이 `expiry(c.expiresAt)` 로 바로 문자열을 잘랐다(`null.slice` 오류).
- **해결**: 타입을 `string | null` 로 바꾸고 「정보 없음」으로 보여 준다. `npx tsc -b` 가 통과하는지 확인.

### ⑥ 화면 테스트가 `Cannot find module '.../src/productRules'`
- **원인**: `node --test` 는 타입스크립트를 바로 읽지만 **확장자 없는 값 import**(`from './productRules'`)는 찾지 못한다(타입만 가져오는 `import type` 은 괜찮음).
- **해결**: `cardRules.ts` 안에 같은 모양의 금액 함수(`won`)를 두었다.

### ⑦ 새 API 가 화면에서 404 `NOT_FOUND`
- **원인**: 8010 에 떠 있던 서버가 `--reload` 없이 켜져 있어 **옛 코드**로 대답했다(회원가입 가이드북 4장 ③과 같은 문제).
- **해결**: 그 서버를 끄고 다시 켠다(6-3). 이 PC 에서는 `--reload` 가 오래된 작업 프로세스를 남기기도 해서 **`--reload` 없이** 켜고 코드를 고칠 때마다 다시 켰다.

### ⑧ 전체 테스트에서 탈퇴 테스트가 한 번 실패
- 카드 테스트를 빼고 돌리거나 탈퇴 테스트만 돌리면 통과했고, 전체를 다시 세 번 돌려 재현되지 않았다. 그 시각에 다른 작업(비밀번호 재설정)이 회원가입 파일을 고치던 중이었다.
- 카드 테스트는 바꾼 값(잔액·알림·임시 승인·카드 설정)을 **`finally` 에서 되돌린다** — 뒤에 도는 `test_withdrawal*.py` 가 더미 그대로를 가정하기 때문.

## 7. 남은 한계 (회고·README 에 쓸 거리)
- **혜택은 「보여 주기」만 한다.** 결제마다 어떤 혜택이 붙는지 계산해 `card_transactions.benefit_amount` 를 채우지 않아서, 기획서 1-1-2 의 「이번 달 받은 혜택 / 한도」는 아직 없다. 계산하려면 가맹점 이름 맞추기(더미 `스타벅스 강남역점` ↔ 혜택 `스타벅스`), 온/오프라인·간편결제 구분(더미 승인내역에 없음), 통합 한도 차감 순서가 필요하다(`docs/BACKLOG.md`).
- **혜택 표는 사람이 옮긴 것**이다. 원문이 줄글이라 숫자를 잘못 옮겼을 수 있다 → `data/cardgorilla/` 원문과 대조가 필요. 단순화한 것: 할인카드 커피 한도 「11~12월 22,000원」, 라이프 체크의 「음식점·주점 합산 일 1회·월 3회」, 분기 할인의 「매달 10만 원 이상」은 설명 글에만 있다.
- **한빛 카드는 가상 카드**라 혜택은 「비슷한 실제 카드를 참고한 것」이지 그 카드의 혜택이 아니다. 카드 이미지·유효기간·발급일은 더미에 없다.
- 더미 이용 내역이 9·10월뿐이라 지금(11월) 체크카드 「이번 달 쓴 돈」은 0원이고, 모든 카드가 「실적 미달」로 보인다.
- 결제일 알림은 **스케줄러가 없어** 손으로 `python -m app.jobs` 를 돌려야 한다. 청구 기간 마감(쓰는 중 → 확정 청구서) 작업도 아직 없다.
- 2·3차 미룸: 1-1-0 마이데이터 연동(모의 카드사 서버), 1-1-6 전월 실적 현황 화면·알림, 1-1-7 포인트 현금화, 1-1-8 연회비·안 쓰는 카드 알림, 모아보기의 예측 합계·추천 배너.
- **자연어 입력(챗봇)으로 카드 조회**는 아직 연결하지 않았다. 이용 내역 API 의 `category` 처럼 화면 없이 부를 수 있는 파라미터를 둔 것은 그때를 위해서다.
