## 0. 한눈에 보기

### 0-1. 챗봇 기능의 목적
- **말로 은행 앱을 쓴다.** 과제 필수 조건 「구현한 모든 기능을 요청으로 직접 처리하거나 해당 화면 링크 제공」 — 「내 계좌 잔액 알려줘」는 직접 답하고, 「송금하고 싶어」는 송금 화면 링크를 준다.
- **앞 대화를 이어 간다.** 「그 중 첫 번째 계좌의 10월 출금만」처럼 앞에서 말한 계좌를 기억한다. 정보가 모자라면 되묻는다.
- **문서에 근거해 답한다(RAG).** 약관·상품설명서·FAQ 질문은 `data/rag/` 문서에서 조항을 찾아 그 내용으로 답하고 출처를 붙인다. 근거가 없으면 「확인할 수 없어요」(기획서 5장 「중요」).
- **본인 것만 본다.** 회원 데이터는 로그인한 회원 것만 읽는다. 로그인하지 않은 손님은 문서 검색만 쓸 수 있다.
- **돈은 움직이지 않는다.** 송금·가입·해지는 챗봇이 하지 않고 화면으로 안내한다(1차 범위, 0-4).

### 0-2. 무엇을 만들었나
| 기능 | 하는 일 | 서버 주소 (API) / 실행 | 코드 위치 |
|---|---|---|---|
| 하이브리드 문서 검색 | 키워드(BM25) + 뜻(벡터) 검색 결과를 RRF 로 합쳐 조항을 찾음 | (챗봇 Tool 이 부름) · `scripts/rag_ingest.py --query … --mode` | `backend/app/rag.py` (**새 파일**) |
| 챗봇 서버 | 질문 → Gemini 가 Tool 을 골라 부르고 답함 · 화면 링크 · 대화 맥락 | `POST /agent/chat` | `backend/app/routers/agent.py` (**새 파일**) |
| 챗봇 그래프 | `llm → tools → llm …` 반복을 LangGraph 로 직접 그림 | — | `backend/app/agent.py` (**새 파일**) |
| 인증 게이트 | 손님은 문서 검색만, 회원은 내 정보 조회까지 | (같은 API) | `backend/app/agent.py` `TOOLS`·`GRAPHS` + `backend/app/deps.py` `OptionalUserId` |
| 챗봇 화면 — **원래 있던 것** | 오른쪽 아래 버튼 → 채팅창 · 추천 질문 · 링크 버튼 | — | `frontend/src/pages/ChatWidget.tsx` (`api.ts` 타입만 고침) |

### 0-3. 요청 한 번이 지나가는 길
```
 [채팅창 ChatWidget]  ──POST /agent/chat {message, context}──▶  [FastAPI routers/agent.py]
                                                                 ① 쿠키로 회원 확인 (없으면 손님)
                                                                 ② agent.answer() — 손님/회원 그래프 고르기
                                                                        │
           ┌────────────────────── LangGraph (agent.py) ──────────────────┘
           ▼
   START → [llm: Gemini 2.5 Flash] ──Tool 을 부르면──▶ [tools: ToolNode] ──결과──▶ [llm] … ──글로 답하면──▶ END
                                                        │
                                   search_documents ── rag.py ── PostgreSQL rag_chunks (pgvector) + BM25(메모리)
                                   my_accounts 등   ── 기존 API 함수 ── accounts · transactions …
           ▼
 ◀── {reply, links, suggestions, context}   ③ 답에서 [[#/경로]] 를 떼어 links 로, 최근 대화를 context 로
```
- **왜 서버인가**: Gemini 키와 DB 는 브라우저에 둘 수 없다. 그리고 「누구의 계좌인지」는 서버만 정할 수 있다(카드 가이드북 0-3 과 같은 이유).
- **왜 Tool 이 기존 API 함수를 부르나**: 챗봇이 계좌를 따로 SQL 로 읽으면 「본인 것만」·「해지 계좌 빼기」·「오류 코드」 규칙을 한 번 더 만들어야 한다. `list_accounts(db, user_id)` 를 그대로 부르면 화면과 **같은 규칙, 같은 숫자**가 나온다.

### 0-4. 이번에 정한 규칙 (사용자 결정 2026-11-10)
| 질문 | 결정 |
|---|---|

| 조회 Tool 대상 | **내 계좌·잔액, 내 예금·적금, 계좌 거래내역·이체 내역**. 카드는 넣지 않음(화면 링크 `#/cards` 로만) |

## 1. 문서 검색 — BM25 와 벡터 검색을 합쳐 retrieve

### 1-1. 원래 있던 것 (`scripts/rag_ingest.py`, `docs/sql/08_rag.sql`)
- `data/rag/` 의 md(약관·상품설명서·특약·동의서·카드 약관·안내·법령, 130개 문서)를 **parent-child 조각**으로 잘라 저장해 두었다.
  - parent = 조항 한 구간(2,394개, `rag_parents`, 글만) · child = parent 를 1,000자 안으로 자른 조각(3,037개, `rag_chunks`, 글 + 768차원 벡터)
  - **검색은 child 로, LLM 에는 parent 를 넘긴다** — 작은 조각이 잘 찾히고, 답할 때는 조항 전체가 필요해서.
- 검색은 **벡터 한 가지**뿐이었다: 질문을 Gemini 로 임베딩 → `embedding <=> 질문벡터`(코사인 거리) 가까운 순.

### 1-2. 왜 키워드 검색(BM25)을 더하나
같은 질문을 두 방식으로 찾으면 잘하는 게 다르다.
| 질문 | 벡터(뜻) | BM25(낱말) |
|---|---|---|
| 「예금거래기본약관 **제12조**」 | 「제12조」라는 **정확한 번호**를 못 맞춤 → 제17조·당좌약관 제12조가 1등 | 「예금·거래·기본·약관·12·조」가 다 든 **제12조가 1등** |
| 「정기예금 **깨면** 이자 얼마나 받아?」 | 「깨다 = 중도해지」를 알아서 **상품설명서**를 찾음 | 문서에 「깨다」가 없어 엉뚱한 법령 조항이 1등 |

→ 둘을 합치면(**하이브리드**) 정확한 번호·상품명과 일상 말투를 모두 잡는다(`docs/Doorin_해설집.md` 04-04-04 Hybrid Search).

### 1-3. BM25 를 어디서 계산하나 — 한국어는 형태소부터
- **PostgreSQL 기본 전문 검색(`tsvector`)은 쓰지 않았다.** 한국어 형태소 분석기가 없어 띄어쓰기로만 자르므로 「중도해지이율**은**」과 「중도해지이율」이 다른 낱말이 된다. 순위 함수 `ts_rank` 도 BM25 가 아니다.
- 그래서 **파이썬에서** 형태소로 자르고 BM25 를 계산한다. child 가 3천 개 정도라 메모리에 인덱스를 들고 있어도 충분하다.
```python
KEEP_TAGS = ("N", "VV", "VA", "XR", "SL", "SN", "SH")   # 명사·동사/형용사 어간·어근·영문·숫자·한자 (조사·어미·기호는 버림)

def tokens(text_: str) -> list[str]:
    return [t.form for t in kiwi().tokenize(text_) if t.tag.startswith(KEEP_TAGS)]

# rag.tokens("중도해지이율은 제12조") == ["중도", "해지", "이율", "12", "조"]
```
- 숫자(`SN`)·영문(`SL`)을 남겨야 「제12조」, 「PROD-001」 같은 정확한 키워드가 산다.
- BM25 는 처음에 15줄로 직접 짰다가, 사용자 결정으로 **`rank-bm25` 의 `BM25Okapi`** 로 바꿨다.
```python
def bm25_rank(query, ids, index, n=SEARCH_N):
    if index is None or not query:
        return []
    scores = index.get_scores(query)
    top = sorted(range(len(ids)), key=lambda i: scores[i], reverse=True)[:n]
    return [ids[i] for i in top if scores[i] > 0]      # 질문 낱말이 하나도 없는 child(점수 0)는 뺀다
```
- 인덱스는 **실험(`pc-1000`)마다 처음 검색할 때 한 번** 만들어(`bm25_index()`) 서버가 켜져 있는 동안 쓴다. 그래서 서버를 켠 뒤 첫 문서 검색만 느리다(5장 ③).

### 1-4. 두 결과를 합치기 — RRF (Reciprocal Rank Fusion)
BM25 점수(예: 12.7)와 코사인 거리(예: 0.31)는 **단위가 달라 더할 수 없다.** 그래서 점수는 버리고 **순위만** 쓴다.
```
RRF 점수 = Σ  1 / (60 + 그 검색에서의 순위)
```
```python
def rrf(rankings, k=RRF_K):            # RRF_K = 60
    fused = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            fused[doc_id] = fused.get(doc_id, 0) + 1 / (k + rank)
    return fused
```
- 양쪽에서 다 찾힌 것이 위로 온다: `rrf([["a","b"], ["b","c"]])` → b(1/62+1/61) > a(1/61) > c(1/62).
- 벡터·BM25 가 각각 child 를 **20개**(`SEARCH_N`)까지 후보로 낸다.

### 1-5. child → parent 로 묶어 돌려주기 (`rag.search()`)
1. 벡터: `ORDER BY embedding <=> CAST(:v AS vector) LIMIT 20` (SQLAlchemy `text()` 에서는 `::vector` 가 바인드 변수 문법과 겹쳐서 `CAST` 로 씀)
2. BM25: `bm25_rank(tokens(질문), …)`
3. RRF 로 합친 child 점수를 **parent 별 최고 점수**로 묶고 위에서 4개(`k=4`)
4. `rag_parents` 에서 그 parent 들의 글·메타데이터(출처 파일·문서 제목·장·조)를 꺼내 `(parent_id, 점수, 글, 메타데이터)` 로 돌려준다.
- `mode` 인자: `vector` · `bm25` · `hybrid`(기본). 챗봇은 항상 `hybrid`, 스크립트는 셋을 비교할 때 쓴다(6-3).

### 1-6. 세 방식 비교 결과 (실측 2026-11-10, 실험 `pc-1000`)
「예금거래기본약관 제12조」
| 순위 | vector | bm25 | **hybrid** |
|---|---|---|---|
| 1 | terms-004 **제17조** | terms-004 **제12조** ✅ | terms-004 **제12조** ✅ (RRF 0.0303 — 양쪽에서 점수를 받아 확실한 1등) |
| 2 | terms-003 제12조(당좌약관) | terms-004 제26조 | terms-004 제17조 |
| 3 | terms-004 제21조 | cards-010 제12조(대출약관) | terms-003 제12조 |
- 벡터만으로는 4위 안에 정답이 없었다. 하이브리드는 BM25 의 정답을 1등으로 올리면서 벡터 결과도 아래에 남긴다.
- 「정기예금 깨면 이자 얼마나 받아?」는 반대로 벡터가 상품설명서를 찾고 BM25 가 약했다. 하이브리드는 벡터 1등을 지켰지만 BM25 의 엉뚱한 법령 조항도 공동 2등으로 끼었다 → 평가 세트로 더 볼 것(7장).

## 2. 챗봇 서버 — `backend/app/agent.py` 와 `POST /agent/chat`

### 2-1. LangGraph 그래프 (노드를 직접 그림)
```
START ──▶ llm ──(마지막 메시지에 tool_calls 가 있음)──▶ tools ──▶ llm ──▶ … ──(없음 = 글로 답함)──▶ END
```
| 이름 | 종류 | 하는 일 |
|---|---|---|
| `MessagesState` | 상태 | 메시지 목록 하나(시스템·사람·AI·Tool 결과). 노드가 돌려준 메시지가 뒤에 붙는다 |
| `llm` | 노드 | `model(member).invoke(메시지들)` — Gemini 가 답하거나 Tool 을 부르는 AI 메시지 하나 |
| `tools` | 노드 (`ToolNode`) | AI 메시지의 `tool_calls` 를 실행해 결과를 `ToolMessage` 로 붙인다 |
| `route` | 조건 edge | `"tools" if state["messages"][-1].tool_calls else END` |
```python
def build_graph(member: bool):
    graph = StateGraph(MessagesState)
    graph.add_node("llm", lambda state: {"messages": [model(member).invoke(state["messages"])]})
    graph.add_node("tools", ToolNode(TOOLS[member], handle_tool_errors=_tool_error))
    graph.add_edge(START, "llm")
    graph.add_conditional_edges("llm", route, ["tools", END])
    graph.add_edge("tools", "llm")
    return graph.compile()

GRAPHS = {member: build_graph(member) for member in TOOLS}     # 손님용·회원용 두 개 (3장)
```
- 모델: `ChatGoogleGenerativeAI(model="gemini-2.5-flash", temperature=0, api_version="v1beta").bind_tools(도구 목록)` — `api_version` 은 5장 ①.
- `recursion_limit: 12` — Tool 을 끝없이 부르는 것을 막는다.

### 2-2. Tool 5개
`@tool` 함수의 **docstring 이 LLM 이 읽는 설명**이고, 인자 타입이 LLM 이 채울 칸이 된다.
| Tool | LLM 이 채우는 칸 | 실제로 부르는 것 | 손님 |
|---|---|---|---|
| `search_documents` | `query` | `rag.search(db, gemini(), query, "pc-1000")` → 출처·제목·조항 글 4개 | ✅ |
| `my_accounts` | (없음) | `routers/accounts.py` `list_accounts(db, user_id)` | ❌ |
| `my_subscriptions` | (없음) | `routers/subscriptions.py` `list_my_subscriptions(db, user_id)` | ❌ |
| `account_transactions` | `account_id`, `start_date`, `end_date`, `direction`(IN/OUT) | `routers/transactions.py` `list_transactions(…, limit=20)` | ❌ |
| `my_transfers` | (없음) | `routers/transfers.py` `list_transfers(db, user_id)` 최근 20건 | ❌ |
- API 함수는 FastAPI 가 아니어도 **보통 파이썬 함수처럼** 부를 수 있다(`Annotated[…, Query()] = None` 의 기본값이 그대로 기본값). 결과는 `jsonable_encoder` 로 JSON 모양으로.
- **남의 계좌**를 물으면 `list_transactions` 가 원래대로 `ApiError(404, "ACCOUNT_NOT_FOUND")` 를 던진다. `ToolNode(handle_tool_errors=_tool_error)` 가 이걸 받아 `"ACCOUNT_NOT_FOUND: 계좌를 찾을 수 없어요."` 를 **Tool 결과로** LLM 에 준다 → LLM 이 실패 사유를 지어내지 않고 그대로 전한다(기획서 7장 「실패 사유는 AI 가 지어내지 않고 백엔드 오류코드로」).
  ```python
  def _tool_error(e: ApiError) -> str:      # 인자 타입(ApiError)을 보고 ToolNode 가 「이 예외만 잡는다」를 정한다
      return f"{e.code}: {e.message}"
  ```

### 2-3. `user_id` 는 LLM 인자가 아니라 config 로
```python
@tool
def my_accounts(config: RunnableConfig) -> list[dict]:
    """내 계좌 목록과 잔액(해지 계좌 제외). 계좌 id 는 거래내역 조회와 화면 링크에 쓴다."""
    return jsonable_encoder(list_accounts(*_ctx(config)))

def _ctx(config):
    c = config["configurable"]
    return c["db"], c["user_id"]          # ← 세션에서 꺼낸 회원. LLM 이 바꿀 수 없다
```
- `config: RunnableConfig` 인자는 LangChain 이 **LLM 에게 보여 주는 칸에서 빼고** 실행할 때 채워 넣는다. 확인: `agent.my_accounts.args == {}` (LLM 이 채울 칸 0개).
- 그래프를 돌릴 때 넣는다:
  ```python
  config = {"configurable": {"db": db, "user_id": user_id}, "recursion_limit": 12, "max_concurrency": 1}
  out = GRAPHS[member].invoke({"messages": messages}, config)
  ```
- 만약 `my_accounts(user_id: str)` 처럼 인자로 두었다면, 사용자가 「user_002 계좌 보여줘」라고 하면 LLM 이 그 값을 넣을 수 있다. **LLM 은 믿을 수 없는 입력**으로 본다.
- `max_concurrency: 1` 은 5장 ④.

### 2-4. 시스템 프롬프트 (`PROMPT`)
요청마다 오늘 날짜(한국 시간)·손님/회원 한 줄(`WHO`, 3장)·쓸 수 있는 화면 경로를 채운다. 지키게 한 것:
- 계좌·잔액·거래는 **Tool 로 조회한 값만** 말하기, 지어내지 않기
- 약관·상품·금리 질문은 `search_documents` 근거로 답하고 `(출처: 문서 제목)`, 근거 없으면 「확인할 수 없어요」, 실제 적용 금리·가입 가능 여부는 상품 화면에서 확인하라고 안내
- 송금·가입·해지·카드 신청은 직접 하지 않고 화면 안내
- 필요한 정보가 모자라고 Tool 로도 알 수 없으면 되묻기, 이전 대화의 계좌·상품은 이어 쓰기

### 2-5. 화면 링크 — `[[#/경로]]` → `links`
- LLM 에게 「화면을 안내할 때는 답 끝에 `[[#/accounts]]` 처럼 적어라」라고 시키고, 서버가 떼어 낸다.
- **실제 있는 화면만** 남긴다: `SCREENS`(`frontend/src/App.tsx` 의 `PAGES`·`TITLES` 와 같은 고정 화면) + `DETAIL_SCREENS`(`/accounts/<id>`·`/my/savings/<id>`·`/products/<id>` … 정규식).
```python
def split_links(reply):
    links = []
    for path in ("/" + p for p in LINK.findall(reply)):
        label = SCREENS.get(path) or next((name for p, name in DETAIL_SCREENS if p.fullmatch(path)), None)
        if label and all(x["href"] != f"#{path}" for x in links):      # 없는 화면은 버리고, 같은 링크는 한 번만
            links.append({"label": label, "href": f"#{path}"})
    return LINK.sub("", reply).strip(), links

# split_links("잔액이에요. [[#/accounts]] [[#/hack]]") → ("잔액이에요.", [{"label": "내 계좌", "href": "#/accounts"}])
```
- 화면(`ChatWidget`)은 `links` 를 버튼으로 그리고 누르면 그 주소로 간다. 화면 링크는 이동만 할 뿐이라, 남의 계좌 id 링크여도 그 화면이 404 를 보여 줄 뿐이다.

### 2-6. 대화 맥락 — context 왕복 (`backend/app/routers/agent.py`)
```
1번째 요청  {message: "내 계좌 잔액 알려줘"}
1번째 응답  {reply: "...", context: {history: [{role:"user", text:"내 계좌 잔액 알려줘"}, {role:"assistant", text:"..."}]}}
2번째 요청  {message: "그 중 첫 번째 계좌의 10월 출금만", context: {history: [위 2개]}}      ← 화면이 그대로 돌려보냄
```
- 서버는 받은 `history` 를 `HumanMessage`/`AIMessage` 로 바꿔 시스템 프롬프트 뒤, 새 질문 앞에 넣는다. 응답에는 **최근 20개**(10번 주고받기)만 남긴다.
- Tool 호출·결과는 history 에 넣지 않는다(글만). 계좌 id 같은 건 답 글에 남아 있어 다음 질문에서 이어진다.
- 화면이 history 를 고쳐 보낼 수 있지만 **Tool 은 언제나 세션의 회원 데이터만** 읽으므로 남의 정보는 새지 않는다. 대신 들어오는 모양은 검사한다(신뢰 경계):
  | 칸 | 검사 | 어기면 |
  |---|---|---|
  | `message` | 500자 이하 (화면 입력칸 `maxLength` 와 같음) | 422 |
  | `context.history` | 20개 이하 | 422 |
  | `history[].role` | `user` / `assistant` 만 (`system` 을 끼워 넣어 규칙을 바꾸지 못하게) | 422 |
  | `history[].text` | 4,000자 이하 | 422 |


## 3. 인증 게이트 — 로그인 상태에 따라 도구 목록 자체를 바꾸기

### 3-1. 누가 손님이고 누가 회원인가 (`backend/app/deps.py` `get_optional_user_id`, **새 함수**)
챗봇은 로그인 없이도 쓰게 바꿨다(전에는 `CurrentUserId` 라 손님은 401). 다만 **쿠키가 있으면 다른 보호 API 와 똑같이** 검사한다.
| 상황 | 결과 | 이유 |
|---|---|---|
| 로그인 쿠키 없음 (개발용 `X-User-Id` 도 없음) | `None` → **손님** | |
| 살아 있는 세션 | 회원 id → **회원** | |
| 쿠키는 있는데 끊긴·없는 세션 | **401** (손님으로 내려 주지 않음) | 화면이 「세션 끝남 → 다시 로그인」을 다른 화면과 똑같이 처리하게 |
| 가입 마무리 중(`PENDING_VERIFICATION`) | **403 `SIGNUP_INCOMPLETE`** | 다른 보호 API 와 같은 규칙 |
```python
def get_optional_user_id(request, response, db, x_user_id=None) -> str | None:
    if not request.cookies.get(SESSION_COOKIE) and not (settings.auth_dev_header and x_user_id):
        return None
    return get_current_user_id(get_login(request, response, db, x_user_id))     # 원래 있던 검사를 그대로 다시 씀

OptionalUserId = Annotated[str | None, Depends(get_optional_user_id)]
```
라우터는 `def chat(body: ChatIn, db: DB, user_id: OptionalUserId)` 로 받고, `agent.answer()` 에 그대로 넘긴다.

### 3-2. 두 겹으로 막는다 (`backend/app/agent.py`)
```python
TOOLS = {  # 로그인했는가 → 쓸 수 있는 Tool
    False: [search_documents],
    True: [search_documents, my_accounts, my_subscriptions, account_transactions, my_transfers],
}

@cache
def model(member: bool):
    return ChatGoogleGenerativeAI(...).bind_tools(TOOLS[member])     # ① LLM 에게 보이는 도구 목록

def build_graph(member: bool):
    ...
    graph.add_node("tools", ToolNode(TOOLS[member], ...))            # ② 실제로 실행할 수 있는 도구 목록
```
| 겹 | 막는 것 |
|---|---|
| ① `bind_tools(TOOLS[member])` | 손님의 LLM 은 **회원 Tool 이 있는지도 모른다** — 고를 수 있는 도구가 문서 검색 하나뿐 |
| ② `ToolNode(TOOLS[member])` | 그래도 LLM 이 `my_accounts` 라는 이름을 **지어내 부르면** 손님 그래프의 ToolNode 에 없어서 실행되지 않고 `"Error: my_accounts is not a valid tool, try one of [search_documents]."` 만 돌아간다 |
- 프롬프트로 「손님에게는 계좌를 보여 주지 마」라고 시키는 것만으로는 막을 수 없다(LLM 은 지시를 어길 수 있다). **도구가 없으면 할 수 없다**가 확실하다.
- 회원 Tool 은 config 의 `user_id` 를 읽는데, 손님 config 에는 `user_id` 가 `None` 이다. 하지만 ② 때문에 손님 그래프에서는 회원 Tool 이 불릴 일이 없다.
- 시스템 프롬프트의 `WHO[member]` 한 줄: 손님이면 「개인 정보는 조회할 수 없으니 로그인을 안내한다(`[[#/login]]`)」 → 링크 목록에 `/login` 을 더했다.
- `answer()` 는 `member = user_id is not None` 으로 그래프를 고른다: `GRAPHS[member].invoke(...)`.

## 5. 겪은 문제와 해결 (같은 일을 다시 할 때 참고)

### ① 실제 Gemini 로 부르자 모든 질문이 503 — `Function calling is not enabled for api version v1`
- **원인**: 설치된 `google-genai 3.0` 이 기본으로 API **v1** 을 쓰는데, v1 은 Tool 호출(function calling)을 받지 않는다. 가짜 LLM 테스트는 Gemini 를 부르지 않아서 통과했다.
- **해결**: `ChatGoogleGenerativeAI(..., api_version="v1beta")`. 503 처리 덕분에 다른 API 는 멀쩡했고, 원인은 서버 로그의 traceback 에서 찾았다.

### ② 링크가 비어 있고 답 글에 `[[#accounts]]` 가 그대로 남음
- **원인**: 프롬프트 예시가 `[[#경로]]` 뿐이라 Gemini 가 `/` 를 빼고 `[[#accounts]]`·`[[#accounts/acc_001]]` 로 썼다. 정규식은 `/` 로 시작하는 것만 받았다.
- **해결**: 정규식을 `\[\[#?/?([\w/-]+)\]\]` 로 넓히고 앞에 `/` 를 붙여 비교, 프롬프트에 `(예: [[#/accounts]])` 를 더했다. 테스트에 `[[#accounts]]` 경우를 넣었다.

### ③ 서버를 켠 뒤 첫 약관 질문이 17초
- **원인**: 첫 문서 검색 때 child 3,037개를 형태소 분석해 BM25 인덱스를 만든다(그 뒤로는 메모리에서 바로).
- **해결(보류)**: 지금은 그대로 둔다(`rag.py` 의 `shortcut:` 주석). 줄이려면 서버 시작 때 미리 만들거나, 토큰을 DB 칸에 저장해 둔다. `rag_ingest.py --save` 로 벡터를 다시 채웠으면 **서버를 다시 켜야** 새 인덱스가 만들어진다.

### ④ Tool 을 여러 개 한꺼번에 부를 때 DB 세션이 꼬일 수 있음
- **원인**: LLM 이 Tool 을 한 번에 여러 개 부르면 `ToolNode` 가 **스레드로 나눠** 실행한다. 그런데 Tool 들은 요청 하나의 SQLAlchemy 세션(`db`)을 같이 쓰고, 세션은 여러 스레드가 동시에 쓰면 안 된다.
- **해결**: 그래프 config 에 `"max_concurrency": 1` — 하나씩 차례로 실행한다.

### ⑤ 테스트 DB 에서는 문서 검색 Tool 을 시험할 수 없음
- **원인**: 테스트 DB 는 매번 `docs/sql/0*.sql` 로 새로 만들어 `rag_*` 표가 **비어 있고**, 벡터 검색은 질문 임베딩에 Gemini 를 부른다.
- **해결**: 검색 부품(형태소·BM25·RRF)은 단위 테스트로, 실제 검색은 개발 DB 에서 `rag_ingest.py --query` 와 실제 대화로 확인했다(6-3·6-4).

### (참고) 원래 있던 함정 — 임베딩은 글마다 `Content` 로 감싼다
`gemini-embedding-2` 에 글 목록을 그대로 주면 한 콘텐츠로 합쳐 **벡터 1개만** 돌려준다(2026-11-09 실측). `rag.embed()` 는 글마다 `types.Content(parts=[types.Part(text=t)])` 로 감싸고, 개수가 맞는지 `assert` 한다. 코드를 `rag.py` 로 옮길 때 이 부분을 그대로 가져왔다.

## 7. 남은 한계 (회고·README 에 쓸 거리)
- **손님은 화면에서 챗봇을 열 수 없다.** API 는 손님을 받지만 챗봇 버튼(`ChatWidget`)이 로그인 뒤 화면 틀(`AppShell`)에만 있다. 로그인 화면에도 띄울지는 정하지 않았다.
- **호출 횟수 제한이 없다.** 손님도 문서를 검색할 때마다 Gemini 임베딩·답변을 부른다. 한도(예: 세션·IP 당 분당 N번)가 필요하다.
- **검색 평가 세트가 없다.** 1-6 은 질문 2개로 본 것뿐이다. 질문 20~30개와 정답 parent_id 로 vector·bm25·hybrid 의 recall@4·MRR 을 재야 「하이브리드가 낫다」를 숫자로 말할 수 있다. 「깨면」 같은 구어체에서 BM25 가 엉뚱한 조항을 끌어올리는 문제도 그때 본다(가중치·`SEARCH_N` 조정).
- **BM25 인덱스는 서버 메모리**라 첫 검색이 느리고(5장 ③), 벡터를 다시 채우면 서버를 다시 켜야 한다.
- **실행 Tool 이 없다.** 기획서 5장의 「그걸로 가입해줘」(확인 단계 → 가입)는 1차 범위 밖이라 화면 링크로만 안내한다. 만들려면 확인 단계·`Idempotency-Key`·본인 확인(step-up) 연결이 필요하다.
- **조회 Tool 범위**: 카드·청구서·상품 목록/금리 Tool 은 없다(카드는 0-4 결정, 상품 API `GET /products` 는 백엔드에 아직 없음). 상품 질문은 상품설명서 RAG 로만 답한다 — 금리 숫자는 DB 가 아니라 문서 근거다.
- **대화 맥락은 화면이 들고 있다.** 새로고침하면 대화가 사라지고, 사용자가 history 를 고쳐 보낼 수 있다(그래도 Tool 은 본인 데이터만 읽음). Tool 결과는 history 에 남지 않아, 같은 조회를 다음 질문에서 다시 부를 수 있다.
- **LLM 답은 매번 조금씩 다르다.** 링크를 붙일지·출처를 어떻게 적을지는 Gemini 가 정한다. 자동 테스트는 가짜 LLM 으로 「흐름과 권한」만 고정하고, 답 품질은 손으로 봤다.
- 실제 Gemini 대화는 **개발용 `X-User-Id` 헤더**로 돌려 봤다. 브라우저에서 쿠키 로그인으로 처음부터 끝까지 대화해 보는 것(6-5)은 이 문서를 쓰는 시점에 아직 하지 않았다.

## 8. 가입 실행 전 확인 — 상태 · 조건 분기 · interrupt

### 8-0. 목적과 이번에 정한 규칙 (사용자 결정 2026-11-10)
- **목적**: 「두린 적금 가입할래」 → 「20만 원씩 12개월」 → 「네」처럼 **여러 번에 나눠 말해도** 상품·금액·기간을 이어 붙이고, 돈이 움직이기 **전에 반드시 한 번 멈춰 확인**받는다. 확인을 받으면 본인 확인(step-up)이 들어 있는 **가입 화면 링크**를 준다.
- 먼저 기존 `agent.py` 를 확인했다: 상태는 `MessagesState`(메시지 목록)뿐, 분기는 `route` 하나(Tool 을 불렀나), `interrupt`·checkpointer 없음, 가입은 프롬프트로 「화면 안내」만. → **비슷한 기능이 없어 새로 만들었다.**

| 질문 | 결정 |
|---|---|
| 멈춘 대화를 다음 요청에서 어떻게 이어 가나 | **`InMemorySaver`**(LangGraph 내장 메모리 checkpointer) + 응답 `context` 에 `thread_id`. 서버를 다시 켜면 사라지지만 학습용으로 가장 단순하고 `interrupt` 를 그대로 쓸 수 있다. (다른 안: PostgreSQL checkpointer — 의존성·표가 늘어남 / interrupt 없이 context 에 대기 상태를 싣기) |
| 「step_up 화면」은 무엇인가 | 따로 없다. 가입 화면 `SubscribePage` 안에 본인 확인 칸(`StepUpField`)이 있다 → **가입 화면 + 금액·기간 채우기** `#/products/<id>/subscribe?amount=…&months=…` (화면이 이미 이 쿼리를 읽는다) |
| 「직전 상품」을 어떻게 아나 | **상품 목록·상세 Tool 추가** (LLM 이 이름으로 id 를 짐작하지 않게) |
| 어떤 작업에 확인 단계를 넣나 | **예금·적금 가입만**. 확인은 **글로 답**하고, 응답 `suggestions` 에 「네」「아니요」 버튼을 띄운다(화면 수정 없음) |
| 상품 API 가 없다 | 처음엔 「챗봇만 먼저」(모델을 직접 읽음) → 이어서 상품 API 를 만들어 챗봇이 그 함수를 부르게 바꿨다 (9장) |

### 8-1. 그래프 — 노드 3개, 분기 3개
```
START → llm ─(Tool 을 부르면)→ tools ─(가입 준비 끝: ready)→ confirm ─(interrupt: 확인 질문 → 화면에 보내고 멈춤)
         ↑                       │                              │  … 다음 요청의 말로 이어 감(resume) …
         └──────(그 밖)──────────┘                              ├─ 「네」    → 가입 화면 링크 → END
         ↑                                                      ├─ 「아니요」 → 취소 → END
         └──────────────────────────────────────────────────────┴─ 다른 말   → llm (새 요청으로, 상태는 유지)
        llm ─(글로 답하면)→ END
```
```python
def build_graph(member: bool):
    def llm(state: ChatState):
        system = SystemMessage(PROMPT.format(today=..., who=WHO[member], subscribe=SUBSCRIBE[member], screens=...))
        return {"messages": [model(member).invoke([system, *recent(state["messages"])])]}

    graph = StateGraph(ChatState)
    graph.add_node("llm", llm)
    graph.add_node("tools", ToolNode(TOOLS[member], handle_tool_errors=_tool_error))
    graph.add_node("confirm", confirm)
    graph.add_edge(START, "llm")
    graph.add_conditional_edges("llm", route, ["tools", END])                       # Tool 을 불렀나
    graph.add_conditional_edges("tools", route_after_tools, ["confirm", "llm"])     # 가입 준비가 끝났나
    graph.add_conditional_edges("confirm", route_after_confirm, ["llm", END])       # 확인 대신 다른 말을 했나
    return graph.compile(checkpointer=InMemorySaver() if member else None)          # 손님은 confirm 에 닿지 않아 저장 안 함
```
| 분기 | 조건 | 가는 곳 |
|---|---|---|
| `route` (1부와 같음) | 마지막 AI 메시지에 `tool_calls` 가 있나 | `tools` / END |
| `route_after_tools` | 상태 `ready` 가 참인가(가입 준비 Tool 이 READY 를 냄) | `confirm` / `llm` |
| `route_after_confirm` | 마지막 메시지가 사용자 말(`HumanMessage`)인가 = 「네/아니요」가 아닌 다른 말 | `llm` / END |

### 8-2. 상태 — `ChatState` (직전 상품 · 금액 · 기간)
```python
class ChatState(MessagesState):        # 메시지 목록 + 아래 칸들
    product_id: str | None
    amount: int | None     # 원. 예금은 넣을 금액, 적금은 월 납입액
    months: int | None
    days: int | None       # 일 단위 상품(표지어음·CD)의 기간
    ready: bool            # 가입 준비가 끝나 확인을 받아야 함
```
- 1부의 「이전 대화의 상품은 이어서 쓴다」는 **프롬프트 문장**(LLM 이 알아서)이었다. 이제는 **그래프 상태의 칸**이라 코드가 확실히 기억한다.
- 상태는 checkpointer 에 대화(thread)마다 저장되므로, 다음 요청에서 그대로 꺼내 쓴다(8-7).

### 8-3. 가입 준비 Tool — `prepare_subscription` (상태를 읽고, 상태를 바꾸는 Tool)
LLM 이 「가입하겠다」는 말을 들으면 부른다. **이번 말에서 새로 들은 값만** 넣으면 되고, 빠진 값은 상태에서 가져온다.
```python
@tool
def prepare_subscription(
    config: RunnableConfig,
    state: Annotated[dict, InjectedState],                   # ← 그래프 상태를 주입 (LLM 에게 안 보임)
    tool_call_id: Annotated[str, InjectedToolCallId],        # ← 이 호출의 id (ToolMessage 를 직접 만들려고)
    product_id: str | None = None, amount: int | None = None, months: int | None = None, days: int | None = None,
) -> Command:
    new = {"product_id": product_id, "amount": amount, "months": months, "days": days}
    slots = {k: v if v is not None else state.get(k) for k, v in new.items()}          # 새 값 + 이전 값 합치기
    if product_id and product_id != state.get("product_id") and (months is None and days is None):
        slots["months"] = slots["days"] = None          # 상품을 바꾸면 이전 상품의 기간은 안 맞을 수 있다 — 다시 묻는다
    plan = _check(db, user_id, slots)                   # 검사는 코드가 (8-4)
    if plan.error:
        slots |= dict.fromkeys(FORGET.get(plan.error.code, []))     # 틀린 값은 기억하지 않는다
        result = f"{plan.error.code}: {plan.error.message}"
    elif plan.missing:
        result = f"MISSING: {', '.join(plan.missing)}"             # 예: "MISSING: 월 납입액, 기간(개월)"
    else:
        result = "READY: 사용자에게 가입 내용을 확인받는 중"
    return Command(update={**slots, "ready": plan.error is None and not plan.missing,
                           "messages": [ToolMessage(result, tool_call_id=tool_call_id)]})
```
- **`InjectedState` · `InjectedToolCallId`**: `config` 처럼 LLM 이 채우는 칸에서 빠진다. 확인: `prepare_subscription.tool_call_schema` 의 칸은 `product_id · amount · months · days` 4개뿐.
- **`Command(update=…)`**: Tool 이 보통 값 대신 `Command` 를 돌려주면 `ToolNode` 가 그 내용으로 **상태를 바꾼다**. 그래서 Tool 결과 메시지(`ToolMessage`)도 직접 만들어 넣어야 한다(그 메시지가 LLM 의 Tool 호출에 대한 답이 된다).
- 결과 글 `MISSING`·오류 코드는 LLM 이 읽고 **빠진 값만 되묻거나 메시지를 그대로 전한다**(프롬프트 `SUBSCRIBE[True]`). `READY` 면 LLM 을 거치지 않고 바로 `confirm` 으로 간다(`route_after_tools`).
- `FORGET` 표 — 이 오류가 나면 그 칸을 비운다: `AMOUNT_OUT_OF_RANGE → amount`, `TERM_OUT_OF_RANGE·RATE_NOT_FOUND → months·days`, `PRODUCT_NOT_FOUND·PRODUCT_NOT_ON_SALE·NOT_SUBSCRIBABLE·TERM_UNIT_NOT_SUPPORTED·SUBSCRIPTION_LIMIT_EXCEEDED → product_id`.

### 8-4. 값 검사는 LLM 이 아니라 코드가 — `_check()`
| 순서 | 검사 | 실패하면 |
|---|---|---|
| 1 | 상품이 정해졌나 | `MISSING: 상품` |
| 2 | 상품이 있나 | `PRODUCT_NOT_FOUND` |
| 3 | 금액·기간이 다 있나 (일 단위 상품이면 일수, 아니면 개월) | `MISSING: 월 납입액 / 넣을 금액, 기간(개월) / 기간(일)` |
| 4 | 회원이 `ACTIVE` 인가 | `USER_NOT_ACTIVE` |
| 5 | 판매 중·가입 가능·금액 범위·기간 범위·금리 구간 — **상품 API 의 예상 이자 함수 `products.estimate()` 를 그대로 부른다** | `PRODUCT_NOT_ON_SALE` · `NOT_SUBSCRIBABLE` · `TERM_UNIT_NOT_SUPPORTED` · `AMOUNT_OUT_OF_RANGE` · `TERM_OUT_OF_RANGE` · `RATE_NOT_FOUND` |
| 6 | 정상(`ACTIVE`) 입출금(`CHECKING`) 계좌가 하나라도 있나 | `NO_SOURCE_ACCOUNT` (+ `[[#/accounts/new]]`) |
| 7 | 1인당 가입 개수 (`products.check_limit()`) | `SUBSCRIPTION_LIMIT_EXCEEDED` |
- 어느 계좌에서 낼지·그 계좌 잔액·본인 확인은 **가입 화면과 `POST /subscriptions`** 가 다시 본다(챗봇은 아직 계좌를 고르지 않았으니까).
- 규칙을 챗봇에 따로 두지 않고 상품 API 함수를 부르므로, 화면의 「예상 이자」와 챗봇의 판정이 **같은 규칙**이다(1부 0-3 「Tool 은 기존 API 함수를 부른다」와 같은 생각).

### 8-5. 확인 노드 — `confirm` 과 `interrupt`
```python
def confirm(state: ChatState, config: RunnableConfig):
    plan = _check(db, user_id, state)          # 멈춘 사이 바뀐 것(판매 중지·계좌 정지)도 다시 본다
    if plan.error or plan.missing:
        return {"ready": False, "messages": [AIMessage(f"가입 안내를 이어 갈 수 없어요. {…}")]}
    question = confirm_question(state, plan)
    reply = str(interrupt({"question": question}))      # ← 여기서 그래프가 멈춘다. 다음 요청의 말이 reply 가 된다
    asked = [AIMessage(question), HumanMessage(reply)]
    if YES.fullmatch(_short(reply)):
        done = AIMessage(f"가입 화면으로 안내할게요. … [[#{subscribe_path(state, plan)}]]", name=CONFIRMED)
        return {"ready": False, "messages": [*asked, done]}
    if NO.fullmatch(_short(reply)):
        return {"ready": False, "messages": [*asked, AIMessage("알겠어요, 가입 안내를 멈췄어요. …")]}
    return {"ready": False, "messages": asked}            # 다른 말 → llm 이 새 요청으로 (상품·기간은 상태에 남아 있음)
```
- **`interrupt(값)`** 은 그래프를 그 자리에서 멈추고 `값` 을 바깥(`invoke` 결과의 `__interrupt__`)으로 내보낸다. 나중에 `invoke(Command(resume=말), 같은 thread)` 로 부르면 **그 노드를 처음부터 다시 돌리고**, 이번에는 `interrupt()` 가 `말` 을 돌려준다.
  → 그래서 `interrupt` **앞에는 같은 값을 내는 읽기만** 둔다(`_check`·`confirm_question`). DB 에 쓰기를 두면 두 번 쓰인다.
- **확인 질문은 LLM 이 아니라 코드가 만든다** (`confirm_question`) — 금액·기간·금리를 LLM 이 지어낼 수 없게. 금리·만기일·이자는 `products.estimate()` 결과다:
  ```
  두린 적금(적금)에 매달 200,000원씩 12개월 동안 가입하려고 해요.
  기본 금리 연 3.20%로 만기일(2027.11.10)에 세전 이자 41,600원, 만기 금액 2,441,600원이 예상돼요(우대 금리 제외).
  출금 계좌 선택과 본인 확인(비밀번호)은 가입 화면에서 해요. 가입 화면으로 안내할까요?
  ```
- 확인 질문과 사용자의 답은 `asked` 로 대화 기록에도 남긴다 — 「다른 말」로 LLM 에 넘어갈 때 LLM 이 앞 질문을 보고 이어 받을 수 있게.

### 8-6. 「네 / 아니요」 판정 — 짧은 답만 본다
```python
YES = re.compile(r"(네|예|응|어|ㅇㅇ|ㅇ|좋아요?|그래요?|맞아요?|확인|진행(해(줘|주세요|요)?)?|가입(할게요?|해(줘|주세요|요)?)?|yes|ok|okay)")
NO  = re.compile(r"(아니(요|오)?|아뇨|ㄴㄴ|ㄴ|싫어요?|취소(해(줘|주세요|요)?)?|안\s?(할래요?|해요?)|그만(할래요?|둘래요?)?|no)")

def _short(text):   # 띄어쓰기·문장부호를 지우고 소문자로 — "네!" → "네", "OK" → "ok"
    return re.sub(r"[\s.!~,?]+", "", text).lower()
```
- **`fullmatch`**(말 전체가 딱 그 말)만 인정한다. 「네 근데 금액은 30만 원으로」·「아니 30만 원으로」는 둘 다 아니라서 **새 요청**으로 LLM 에 넘어가고, LLM 이 `prepare_subscription(amount=300000)` 을 다시 불러 바뀐 금액으로 다시 묻는다.
- 돈이 걸린 확인이라 **애매하면 승인으로 보지 않는다**. LLM 에게 「이게 승낙이냐」를 묻지 않은 것도 같은 이유(LLM 판단은 매번 다를 수 있다).

### 8-7. 멈춘 대화를 이어 가기 — checkpointer · `thread_id` · `answer()`
```python
def answer(db, user_id, message, history, thread_id=None) -> Answer:
    ...
    if not member:
        thread_id, run = None, {"messages": [*history 메시지, HumanMessage(message)]}      # 손님: 1부와 같음
    else:
        thread_id = thread_id or uuid.uuid4().hex
        config["configurable"]["thread_id"] = f"{user_id}:{thread_id}"     # 남의 thread_id 를 보내도 다른 칸
        saved = graph.get_state(config)
        if saved.next:                          # ① 확인 질문에서 멈춰 있다 → 이번 말이 그 답
            run = Command(resume=message)
        elif saved.values.get("messages"):     # ② 이어지는 대화 → 새 말만 더한다(상태는 서버에)
            run = {"messages": [HumanMessage(message)]}
        else:                                   # ③ 새 대화, 또는 서버를 다시 켜서 사라진 대화 → 화면이 보낸 history 로 시작
            run = {"messages": [*history 메시지, HumanMessage(message)]}
    out = graph.invoke(run, config)
    if out.get("__interrupt__"):                # 멈췄다 → 확인 질문을 답으로, 버튼 「네」「아니요」
        return Answer(out["__interrupt__"][0].value["question"], [], ["네", "아니요"], thread_id)
    last = out["messages"][-1]
    reply, links = split_links(last.text, confirmed=last.name == CONFIRMED)
    return Answer(reply, links, [], thread_id)
```
- **checkpointer** 는 그래프가 노드를 하나 지날 때마다 상태를 `thread_id` 칸에 저장한다. `get_state(config).next` 가 비어 있지 않으면 「아직 갈 노드가 남은 채 멈춤」 = interrupt 대기.
- **thread 키에 회원 id 를 붙인다** (`"<user_id>:<thread_id>"`). 화면이 남의 `thread_id` 를 보내도 내 id 가 앞에 붙어 다른 칸이 되므로 남의 확인 대기를 이어 가지 못한다(테스트 `test_thread_belongs_to_its_user`). `thread_id` 는 서버가 `uuid4().hex`(32자리)로 만들고, 들어올 때 `^[0-9a-f]{32}$` 가 아니면 422.
- **시스템 프롬프트는 상태에 저장하지 않고** `llm` 노드가 부를 때마다 앞에 붙인다(오늘 날짜가 바뀌어도 맞게).
- **대화가 서버에 쌓이므로 LLM 에 보낼 때 자른다** — `recent()`: 최근 사용자 말 10번(`MAX_TURNS`)부터. **사용자 말에서 끊어야** Tool 호출과 그 결과(`ToolMessage`)가 갈라지지 않는다(갈라지면 Gemini 가 거절한다).

### 8-8. 화면 링크 — 가입 화면은 「네」 답에서만
- 링크 정규식이 쿼리를 받게 넓혔다: `\[\[#?/?([\w/-]+)(\?[\w=&]+)?\]\]` → `#/products/prod_004/subscribe?amount=200000&months=12`. 쿼리는 영문·숫자·`=`·`&` 만 허용.
- `split_links(reply, confirmed)` — 가입 화면(`/products/<id>/subscribe`)은 **확인 노드가 만든 답**(`AIMessage(name="subscribe_confirmed")`)에서만 살린다. LLM 이 확인 없이 가입 화면 링크를 적어도 버린다(「확정 전 실행 금지」를 프롬프트가 아니라 코드로). 프롬프트의 쓸 수 있는 경로 목록에서도 `/subscribe` 를 뺐다.
- `AIMessage.name` 은 Gemini 로 보낼 때 쓰이지 않는 칸이라 표시용으로 써도 안전하다(`langchain_google_genai` 는 `ToolMessage` 의 name 만 읽는다).

### 8-9. API 모양에서 바뀐 것 (`backend/app/routers/agent.py`)
```
요청  {"message": "네", "context": {"history": [...], "thread_id": "3f2a…(32자리)"}}
응답  {"reply": "...", "links": [...], "suggestions": ["네", "아니요"] 또는 [], "context": {"history": [...], "thread_id": "3f2a…"}}
```
- `ChatContext` 에 `thread_id`(회원만, 손님은 `null`) 추가. 화면 `ChatWidget` 은 `context` 를 **통째로** 돌려보내므로(`saved.context = r.data.context`) 화면은 고치지 않았다(`api.ts` 의 `ChatContext` 타입에는 아직 `thread_id` 가 없다 — 실행에는 상관없음).
- `suggestions` 는 확인 질문일 때 `["네", "아니요"]` — 채팅창이 버튼으로 그린다.

### 8-10. 프롬프트에 더한 것
- 상품의 id·금리·가입 조건은 `search_products`·`product_detail` 로 조회한 값만 말한다(문서 RAG 는 설명용).
- 회원(`SUBSCRIBE[True]`): 가입하겠다고 하면 `prepare_subscription` 을 부르고 **새로 들은 값만** 넣는다. `MISSING` 이면 빠진 값만 묻는다. 가입은 직접 하지 않고 가입 화면 링크도 직접 적지 않는다(확인 단계가 준다).
- 손님(`SUBSCRIBE[False]`): 가입은 로그인한 뒤에 할 수 있다고 안내(`[[#/login]]`). 상품 조회·설명은 손님도 된다.

## 12. 겪은 문제와 해결 (2부)

### ⑥ 「step_up 화면 링크」로 넘기려는데 step_up 화면이 없다
- **확인**: 본인 확인은 화면마다 들어 있는 칸(`StepUpField` + `useStepUp`)이고, 가입 화면 `SubscribePage` 에도 있다. 그리고 `SubscribePage` 가 이미 `?amount=&months=&days=` 를 읽어 입력칸을 채운다.
- **해결**: 새 화면을 만들지 않고 가입 화면 링크에 금액·기간을 붙였다. 링크 정규식만 쿼리를 받게 넓혔다(8-8).

### ⑦ 서버가 대화를 기억하지 않는 구조에서 `interrupt` 를 쓰려면
- **원인**: `interrupt` 는 멈춘 그래프를 다음 요청에서 이어 가야 해서 checkpointer + `thread_id` 가 필요하다. 1부는 「화면이 history 를 들고 다니는」 구조였다.
- **해결**: 회원 그래프만 `InMemorySaver` 로 컴파일, `thread_id` 를 context 에 실어 왕복. 처음 요청·서버 재시작 뒤에는 화면이 보낸 history 로 시작(8-7 ③)해 1부 동작을 잃지 않게 했다. 손님 그래프는 1부 그대로.

### ⑧ 이 브랜치(Yellow) 백엔드에 상품 API 가 없었다
- **확인**: 화면은 `GET /products`·`/products/{id}`·`POST /subscriptions` 를 부르는데 Yellow 백엔드에 라우터가 없었다(Serin 브랜치에만 있음, 구조가 달라 그대로 못 가져옴). 챗봇이 가입 화면으로 보내도 그 화면이 상품을 못 불러오는 상태였다.
- **해결**: 먼저 챗봇만 만들고(그동안은 모델을 직접 읽음, BACKLOG 에 기록) → 9장의 상품 API 를 만든 뒤 챗봇이 그 함수를 부르게 바꿨다.

### ⑨ 금리표가 없는 상품을 고르면 챗봇이 기간을 끝없이 되물을 수 있었다
- **원인**: Serin 규칙에서는 금리표가 빈 상품이 기간 검사를 통과한 뒤 `RATE_NOT_FOUND` 로 실패한다. 챗봇은 `RATE_NOT_FOUND` 를 「기간이 틀렸다」로 보고 기간을 비우므로, 어떤 기간을 말해도 또 실패한다.
- **해결**: `estimate()` 맨 앞에서 금리표가 없으면 `NOT_SUBSCRIBABLE`(상세의 `subscribable=false` 와 같은 판정) — 챗봇은 이 코드면 **상품**을 비운다.

### ⑩ 셸 heredoc 으로 파이썬 파일을 고치다 `\n` 이 진짜 줄바꿈이 됨
- **원인**: Git Bash heredoc 안의 파이썬 문자열에 쓴 `\\n` 이 파일에 실제 줄바꿈으로 들어가 f-string 이 끊겼다(`SyntaxError: unterminated f-string`).
- **해결**: 그 줄만 편집기(Edit)로 `\n` 으로 고쳤다. 줄바꿈 글자가 들어가는 코드는 heredoc 으로 고치지 않는다.

### ⑪ 테스트가 전부 `psycopg.OperationalError` (DB 연결 실패)
- **원인**: Docker 의 `midproject-postgres` 컨테이너가 꺼져 있었다(`Exited (255)`) — 코드 문제가 아님.
- **해결**: `docker start midproject-postgres` → `pg_isready` 확인 뒤 다시 실행. 증상이 「모든 테스트가 시작도 못 하고 ERROR」면 먼저 `docker ps -a` 를 본다.

### ⑫ (참고) 가끔 실패하는 테스트 — `test_withdrawal.py::test_new_member_withdraws_end_to_end`
- 전체 실행에서 가끔 한 번 실패하고, 다시 돌리거나 그 파일만 돌리면 통과한다. **상품 API 를 만들기 전에도 같은 실패가 있었고** 2부에서 고친 파일과 겹치지 않아 이번 작업과는 관계없다고 봤다. 원인은 아직 보지 않았다(남은 한계).

## 14. 남은 한계 (2부)
- **확인 대기는 서버 메모리에만 있다.** 서버를 다시 켜면 사라지고, 쌓인 대화를 지우는 장치가 없어 서버가 켜져 있는 동안 계속 는다. 오래 쓰려면 PostgreSQL checkpointer(`langgraph-checkpoint-postgres`)와 오래된 thread 정리가 필요하다.
- **서버를 여러 개 띄우면 확인이 끊긴다.** 다음 요청이 다른 서버로 가면 그 서버 메모리에는 thread 가 없다(메모리 checkpointer 의 한계).
- **확인은 예금·적금 가입만.** 송금·카드 신청·중도 해지는 여전히 화면 링크만. 같은 틀(준비 Tool → `confirm` → 화면 링크)로 넓힐 수 있다.
- **「네」 판정은 정해 둔 말 목록이다.** 「ㄱㄱ」「그걸로 해」 같은 말은 승인으로 안 본다(새 요청으로 감). 일부러 보수적으로 둔 것.
- **챗봇은 출금 계좌·잔액을 고르지 않는다.** 확인 질문은 「정상 입출금 계좌가 하나라도 있다」까지만 보고, 어느 계좌·잔액은 가입 화면에서 정한다.
- **우대 금리는 계산하지 않는다**(기본 금리만, 3차). 확인 질문·예상 이자에 「우대 금리 제외」라고 적었다.
- **적금 추가 납입·만기 처리는 없다**(PROD-F11). 가입하면 첫 회차만 내고, 「내 가입 상품」의 추가 납입 버튼은 아직 `payable=false`.
- **N일 적금은 가입할 수 없다** — 매일 자동 납입(자동이체)이 생기면 연다.
- **상품설명서는 목록만** — 원문 파일을 열어 보는 기능은 없다(실제 은행 이름 문제, 9-0).
- `frontend/src/api.ts` 의 `ChatContext` 타입에 `thread_id`·상품 상세 `documents` 칸이 아직 없다(실행에는 상관없음, 화면에서 설명서 목록을 보여 주려면 더한다).
- **실제 Gemini 로 확인 흐름을 돌려 보지 않았다.** 자동 테스트는 가짜 LLM 이다. 실제 Gemini 가 「20만 원씩 12개월」에서 `prepare_subscription(amount=200000, months=12)` 를 잘 부르는지, 상품 이름으로 `search_products` 를 먼저 부르는지는 손으로 확인해야 한다.
- `test_withdrawal.py::test_new_member_withdraws_end_to_end` 가 가끔 실패한다(12장 ⑫) — 원인 미확인.

# 3부 — 질문의 의도는 누가 분석하나 (LLM 과 코드의 역할 나누기)

> 2026-11-10 정리. 새로 만든 코드는 없고, 1·2부에서 만든 `backend/app/agent.py` 가 **「무엇을 하려는 말인지」를 어디서 판단하는지** 질문(「의도 분석은 지금 LLM 이 하는 거지?」)에 답하며 정리한 장이다.
> 답: **그렇다.** 의도를 분류하는 단계를 따로 두지 않았고, Gemini 가 대화를 읽고 **어떤 Tool 을 부를지(또는 그냥 글로 답할지)를 직접 고른다.** 다만 틀리면 안 되는 부분은 코드가 정한다.

## 15. 의도 분석 = LLM 의 Tool 고르기 (function calling)

### 15-1. 따로 「의도 분류」 노드가 없다
흔히 떠올리는 챗봇 구조와 비교하면:
```
(흔한 구조)  질문 → [의도 분류기: 잔액조회/약관질문/가입…] → if 잔액조회: … elif 약관질문: … → 답
(두린 챗봇)  질문 → [llm: Gemini + Tool 목록] ─ Tool 을 골라 부름 ─▶ [tools] ─▶ [llm] … ─ 글로 답함 ─▶ END
```
- `llm` 노드가 Gemini 에 보내는 것: 시스템 프롬프트(`PROMPT`) + 최근 대화 10턴(`recent()`) + **묶어 둔 Tool 목록**(`bind_tools(TOOLS[member])`, 2-1·3-2).
- Gemini 가 돌려주는 AI 메시지는 둘 중 하나다:
  | Gemini 의 답 | 뜻 | 다음 |
  |---|---|---|
  | `tool_calls` 가 있음 (예: `my_accounts {}`) | 「이건 계좌 조회 의도구나」 → 그 Tool 을 이 인자로 불러 달라 | `route` → `tools` |
  | 글만 있음 | 바로 답하거나, 정보가 모자라 되묻기 | `route` → `END` |
- `route`(2-1)는 **Tool 을 불렀는지만** 본다 — 의도를 해석하지 않는다. 즉 「의도 분석」은 Gemini 가 Tool 하나를 고르는 순간에 일어난다.

### 15-2. Gemini 는 무엇을 보고 고르나
| 판단 재료 | 어디에 있나 | 예 |
|---|---|---|
| Tool 이름·**docstring**·인자 타입 | `@tool` 함수 (2-2) | `search_documents`: 「약관·상품설명서·…에서 질문과 관련된 조항을 찾는다」 → 약관 질문이면 이걸 고른다 |
| 시스템 프롬프트의 규칙 | `PROMPT`·`WHO`·`SUBSCRIBE` (2-4·8-10) | 「계좌·잔액은 Tool 로 조회한 값만」 「가입하겠다고 하면 `prepare_subscription`」 「부족하면 되묻는다」 |
| 앞 대화 | `recent(state["messages"])` | 「그 중 첫 번째 계좌의 10월 출금만」 → 앞 답의 계좌 id 로 `account_transactions` |
- 그래서 **docstring 을 고치면 Tool 고르는 방식이 바뀐다.** docstring 은 사람용 주석이 아니라 LLM 이 읽는 설명서다.
- 인자 칸(`query`, `account_id`, `start_date` …)을 채우는 것도 Gemini 다 — 「10월 출금」을 `start_date="2026-10-01", end_date="2026-10-31", direction="OUT"` 으로 바꾸는 일까지 LLM 이 한다.

### 15-3. 실제 Gemini 로 확인한 것 (2026-11-10, 회원 user_001, 15-6 의 스크립트)
| 질문 | Gemini 가 고른 것 | 답 (앞부분) |
|---|---|---|
| 내 계좌 잔액 알려줘 | `my_accounts {}` | 110-00-000001 계좌 1,250,000원 · 110-00-000002 계좌 874,890원 |
| 중도해지하면 이자 어떻게 돼? | `search_documents {'query': '중도해지 이자'}` | 약정 이율보다 낮은 중도해지이율이 적용돼요 … (출처: 적립식예금 약관, 「두린 청년미래적금」 상품설명서 등) |
| 적금 가입하고 싶어 | **Tool 없음** — 글로 되물음 | 어떤 적금 상품에 가입하시겠어요? … |
- 세 번째처럼 **「Tool 을 안 부른다」도 LLM 의 판단**이다. 상품이 정해지지 않아 되물었다(프롬프트 「부족하면 되묻는다」). 같은 질문에 `search_products` 를 먼저 부를 수도 있다 — LLM 답은 매번 조금씩 다르다(7장).

### 15-4. LLM 에게 맡기지 않고 코드가 정하는 것
「무슨 말인지」는 LLM 이 판단하지만, **틀리면 돈·개인정보가 걸리는 곳**은 코드가 막는다. LLM 은 믿을 수 없는 입력으로 본다(2-3).
| 무엇 | 누가 | 어떻게 | 자세히 |
|---|---|---|---|
| 고를 수 있는 Tool 의 **범위** | 코드 | 로그인 여부로 `TOOLS[member]` 를 바꿔 묶는다. 손님 LLM 은 회원 Tool 이 있는지도 모른다 | 3-2 |
| **누구의** 데이터인가 | 코드 | `user_id` 는 Tool 인자가 아니라 config(세션)에서 | 2-3 |
| 가입 확인 답 「네 / 아니요」 | 코드 | 정규식 `YES`·`NO` 를 `fullmatch` — 애매하면 승인 아님, LLM 에게 묻지 않음 | 8-6 |
| 가입 값이 맞나 (판매 중·금액·기간·출금 계좌) | 코드 | `_check()` → 상품 API 의 `products.estimate()` | 8-4 |
| 확인 질문의 금액·금리·이자 | 코드 | `confirm_question()` 이 DB 값으로 만든다 | 8-5 |
| 화면 링크 | 코드 | `split_links()` 가 실제 있는 화면만 남김. 가입 화면은 「네」 답에서만 | 2-5·8-8 |
| 실패 사유 | 코드 | Tool 이 `ApiError` 를 내면 `"오류 코드: 메시지"` 를 Tool 결과로 → LLM 은 그대로 전함 | 2-2 |
| 다음에 갈 노드 | 코드 | `route`·`route_after_tools`·`route_after_confirm` — 상태만 보고 정함 | 8-1 |

한 줄로: **LLM = 「무엇을 하려는 말인가」와 「Tool 인자 채우기」·「문장 만들기」, 코드 = 「해도 되나·누구 것인가·값이 맞나·실행해도 되나」.**

### 15-5. 왜 의도 분류기를 따로 두지 않았나
| 방법 | 장점 | 단점 |
|---|---|---|
| **LLM 이 Tool 을 고름 (지금)** | 의도 목록을 손으로 관리하지 않음. 「그 중 첫 번째 계좌의 10월 출금만」 같은 후속 질문·여러 Tool 조합(목록 → 상세)이 자연스럽다. Tool 을 하나 더하면 docstring 만 쓰면 됨 | 판단이 매번 조금 다를 수 있다. 왜 그 Tool 을 골랐는지 코드로 보이지 않는다 |
| 키워드·정규식 분류 | 결과가 항상 같고 빠르다 | 「잔액」「돈 얼마 있어」「통장에 남은 거」… 말투마다 규칙을 더해야 한다. 인자(날짜·계좌) 뽑기도 따로 짜야 한다 |
| LLM 분류 노드를 앞에 하나 더 (의도 → 분기) | 의도별로 다른 프롬프트·그래프를 쓸 수 있다 | LLM 호출이 한 번 더 들고, 결국 분류도 LLM 판단이라 흔들림은 같다 |
- 이 프로젝트는 과제 조건이 「구현한 **모든** 기능을 요청으로 처리 + 대화 맥락 유지 + 부족하면 추가 질문」이라, 의도를 미리 나열하기보다 LLM 에게 Tool 을 고르게 하는 쪽이 맞았다. 대신 **흔들려도 안전하게** 15-4 의 장치들을 코드로 두었다.
- 예외로 「네 / 아니요」만은 정규식이다(8-6) — 짧고 목록이 정해져 있으며, 돈이 걸린 승인이라 **같은 말에 항상 같은 판정**이어야 해서.

### 15-6. 직접 해 보기 — Gemini 가 어떤 Tool 을 골랐는지 보기
서버·화면 없이 그래프만 돌려 Tool 호출을 찍어 본다. 아래를 `backend/` 밖 아무 곳(예: 임시 폴더)에 `show_intent.py` 로 저장한다 — 저장소에 넣을 파일은 아니다. 준비는 6-1·6-2 와 같다(`backend/.env` 의 `GEMINI_API_KEY`, 개발 DB 켜 두기).
```python
import sys
from langchain_core.messages import AIMessage, HumanMessage
from app.agent import GRAPHS
from app.db import SessionLocal

db = SessionLocal()
config = {"configurable": {"db": db, "user_id": "user_001", "thread_id": "user_001:intent-demo"},
          "recursion_limit": 12, "max_concurrency": 1}
out = GRAPHS[True].invoke({"messages": [HumanMessage(sys.argv[1])]}, config)     # True = 회원 그래프
for m in out["messages"]:
    if isinstance(m, AIMessage) and m.tool_calls:
        for c in m.tool_calls:
            print("LLM 이 고른 Tool →", c["name"], c["args"])
print("답 →", out["messages"][-1].text[:200])
```
```bash
cd backend
# Git Bash 기준. PYTHONPATH=. 이 없으면 'No module named app', PYTHONIOENCODING 이 없으면 한글이 깨진다
PYTHONIOENCODING=utf-8 PYTHONPATH=. .venv/Scripts/python <저장한 경로>/show_intent.py "내 계좌 잔액 알려줘"
# LLM 이 고른 Tool → my_accounts {}
# 답 → … 1,250,000원 …
```
- 손님으로 보려면 `GRAPHS[False]` 와 `"user_id": None` 으로 바꾸고 `thread_id` 는 뺀다(손님 그래프는 checkpointer 가 없다, 2부 8-7). 「내 계좌 잔액 알려줘」에 Tool 없이 로그인 안내가 나오면 3장 인증 게이트가 보이는 것이다.
- 바꿔 볼 것: Tool 의 docstring 을 일부러 흐리게 고치고(예: `search_documents` 설명을 「문서 검색」 한 마디로) 같은 질문을 다시 넣어 보면, **docstring 이 의도 판단 재료**라는 것이 눈에 보인다. 해 본 뒤 원래대로 되돌린다.
- 실제 Gemini 를 부르므로 질문마다 API 호출이 1~3번 든다.

### 15-7. 남은 한계 (3부)

## 16. 구현한 기능

### 16-0. 목적
- 「엄마한테 월급통장에서 5만 원 보내줘」 같은 말을 받으면, 챗봇이 대화에서 **받는 사람 · 내 출금 계좌 · 금액** 세 값을 모아 한 문장으로 정리하고, 그 값이 미리 채워진 송금 화면으로 보내 준다.
- 전에는 송금 화면 링크만 주어서, 화면에서 처음부터 다시 골라야 했다.
- **챗봇은 여전히 송금을 실행하지 않는다.** 받는 계좌 확인(예금주 표시)·본인 확인·실제 이체는 송금 화면(`TransferPage`)과 이체 API 가 한다.

### 16-1. 이번에 정한 규칙 (사용자 결정 2026-11-11)
| 물어본 것 | 정한 것 |
|---|---|
| 「{별명}에게 {별명}계좌로 {얼마} 송금해줘」의 두 {별명}은? | 첫째 = **받는 사람 별칭**(자주 쓰는 계좌의 `nickname`), 둘째 = **내 출금 계좌 별명**(`resAccountNickName`) |
| 세 값을 다 모은 뒤 무엇을 하나? | **입력칸이 채워진 송금 화면 링크**를 준다 (문장만 보여 주기 · 가입처럼 네/아니요 확인은 고르지 않음) |
| 프롬프트의 어디를 고치나? | `{subscribe}` 자리에 들어가는 **`SUBSCRIBE` 사전**에 추가 — 회원(True)에는 송금 규칙, 손님(False)에는 「로그인한 뒤에」 안내 |
| 프롬프트 밖 수정(조회 Tool `my_favorites` 추가)을 해도 되나? | 진행. 그래프·상태·화면 코드는 건드리지 않는다 |
| 받는 사람 별명이 자주 쓰는 계좌에 없으면? | 없다고 알리고 **받는 사람만 비운 링크**(`from`·`amount` 만)를 준다. 계좌번호를 대화로 받지 않는다 |

### 16-2. 프롬프트 — `SUBSCRIBE` 사전에 더한 문구
`PROMPT` 의 `- {subscribe}` 자리에 `SUBSCRIBE[member]` 가 들어간다(8-10). 그 값 끝에 `\n- …` 로 줄을 이어 붙였다 — 프롬프트 틀(`PROMPT`)은 고치지 않았다.

회원(`SUBSCRIBE[True]`, [agent.py:97](../backend/app/agent.py#L97)):
```python
          "- 송금·이체를 요청하면 대화에서 값을 모아 「{받는 사람 별칭}에게 {내 출금 계좌 별명}계좌로 {금액} 송금해줘」 꼴을 채운다.\n"
          "  받는 사람은 my_favorites 의 별칭(nickname, 없으면 예금주 holder_name), 출금 계좌는 my_accounts 의 별명(resAccountNickName, 없으면 "
          "계좌 이름 resAccountName)에서 찾는다. 금액·출금 계좌가 빠졌거나 별명이 여러 곳에 맞으면 되묻는다. 이전 대화에서 말한 값은 이어서 쓴다.\n"
          "  다 모이면 그 문장으로 정리해 보여 주고 답 끝에 [[#/transfer?from=<출금 계좌 id>&bank=<은행>&to=<계좌번호 account_no>&amount=<원 단위 숫자>]] 를 "
          "적는다(은행 이름은 Tool 값 그대로, 값은 Tool 로 조회한 것만).\n"
          "  받는 사람이 my_favorites 에 없으면 자주 쓰는 계좌에 없다고 알리고 bank·to 를 뺀 링크를 준다(받는 계좌는 화면에서 입력). "
          "송금은 직접 하지 않는다 — 본인 확인과 실행은 송금 화면이 한다.",
```
손님(`SUBSCRIBE[False]`, [agent.py:105](../backend/app/agent.py#L105)):
```python
           "- 송금·이체도 로그인한 뒤에 할 수 있다고 안내한다([[#/login]]).",
```
- **`{받는 사람 별칭}` 의 중괄호는 안전한가?** `PROMPT.format(subscribe=SUBSCRIBE[member], …)` 는 `PROMPT` 안의 `{…}` 만 바꾼다. 끼워 넣는 **값** 안의 중괄호는 다시 풀지 않으므로 그대로 LLM 에게 간다. (반대로 `PROMPT` 본문에 `{받는 사람}` 을 직접 쓰면 `KeyError` 가 난다 — 그래서 사전 쪽에 넣는 편이 안전했다.)
- 「은행 이름은 Tool 값 그대로」를 적은 이유: 링크를 고르는 정규식이 `%` 나 `-` 가 든 값을 링크로 보지 않기 때문이다 (17-3).

### 16-4. 요청 한 번이 지나가는 길
```
「엄마한테 월급통장에서 5만원 보내줘」
  → llm: Gemini 가 SUBSCRIBE[True] 의 송금 규칙을 읽고 Tool 을 고른다
      → tools: my_favorites  → [{nickname: "엄마", bank: "…", account_no: "…", holder_name: "…"}, …]
      → tools: my_accounts   → [{id: "acc_001", resAccountNickName: "월급통장", …}, …]
  → llm: 세 값이 다 있으면
         「엄마에게 월급통장계좌로 50,000원 송금해줘」로 정리 + [[#/transfer?from=acc_001&bank=…&to=…&amount=50000]]
         빠진 값이 있으면 → 그것만 되묻고 END (다음 말에서 이어 감 — 대화는 thread 에 남아 있다, 8-7)
  → answer(): split_links() 가 [[…]] 를 떼어 links 로 → 화면이 「송금」 버튼으로 보여 줌
  → 사용자가 버튼을 누름 → TransferPage 가 주소의 from·bank·to·amount 로 입력칸을 채움
  → 받는 계좌 확인 · 본인 확인 · 이체 실행은 송금 화면과 이체 API
```
- 위 그림의 「엄마」「월급통장」은 설명용 이름이다(실제 더미 값이 아니다).
- 송금 화면이 읽는 주소 값: [TransferPage.tsx:68](../frontend/src/pages/TransferPage.tsx#L68) `from`(출금 계좌 id) · `bank` · `to`(계좌번호, 숫자만 남김) · `amount`. 이 화면 코드는 이번에 고치지 않았다 — 이체 결과 화면의 「다시 보내기」가 이미 같은 주소를 쓰고 있었다.
- `from` 이 내 정상 계좌가 아니면 송금 화면이 첫 번째 정상 계좌로 바꾼다. `bank`·`to` 가 없으면 받는 사람 칸은 빈 채로 열린다.

#### ② 자주 쓰는 계좌가 「엄마」 하나일 줄 알았는데 3개가 나와 단언이 실패
- 원인: 테스트 DB 의 `user_001` 에는 시드로 넣은 자주 쓰는 계좌가 이미 3개 있다. 테스트에서 하나를 새로 등록하고 「목록이 그것 하나」라고 단정했다.

### 16-7. 남은 한계 (4부)
- **실제 Gemini 가 규칙대로 하는지 모른다.** 자동 테스트는 가짜 LLM 이라 「세 값을 모으고 · 되묻고 · 링크를 맞게 적는지」는 시험하지 않는다(15-7 과 같은 한계).
- **송금 링크의 값은 LLM 이 적는다.** 가입 링크는 코드(`subscribe_path`)가 만들고 「네」 답에서만 살리는데(8-8), 송금 링크는 그런 장치가 없다. 계좌번호를 잘못 옮겨 적으면 다른 계좌가 채워진 채 화면이 열린다 — 막아 주는 것은 송금 화면의 예금주 표시와 본인 확인뿐이다. 더 안전하게 하려면 가입처럼 준비 Tool 을 두고 링크를 코드가 만들게 바꾼다.
- **자주 쓰는 계좌에 있는 사람만** 받는 사람 칸이 채워진다. 최근 보낸 계좌·내 다른 계좌·계좌번호 직접 말하기는 다루지 않는다.
- `backend/eval/eval_agent.py` 에 송금 평가 질문을 넣지 않았다.

### 17-3. 링크가 살아남는 조건 (고치지 않은 코드지만 이번 기능이 기대는 곳)
`LINK = re.compile(r"\[\[#?/?([\w/-]+)(\?[\w=&]+)?\]\]")` — 물음표 뒤에는 **글자·숫자·밑줄(`\w`, 한글 포함) · `=` · `&` 만** 올 수 있다. 2026-11-11 실제 확인:
| LLM 이 적은 것 | 결과 |
|---|---|
| `bank=두린은행&to=11000000000007` | 링크로 남음 |
| `to=110-00-000007` (하이픈) | 링크 아님 — `[[…]]` 가 답 글에 그대로 남음 |
| `bank=%EB%91%90…` (퍼센트 인코딩) | 링크 아님 — 위와 같음 |
| `from=…&amount=…` 만 | 링크로 남음 |
