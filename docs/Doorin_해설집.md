# 어려운 설계 목차를 하나씩 이해하는 해설집 🌸

**Serin’s Agent Lab · EASY EXPLANATION GUIDE** — 13 PARTS · 79개 세부 주제 · 499개 쉬운 해설

> ‘이게 대체 뭔데?’, ‘왜 이걸 고민해야 하지?’를 한 항목씩 설명했어. 기술을 다 쓸 필요는 없어. 이해한 뒤 우리 서비스에 필요한지만 판단하면 돼.

## 이 문서는 이렇게 읽으면 돼

- **무슨 뜻?** 낯선 단어를 쉽게 풀어 설명해.
- **왜 고민해?** 실제 설계할 때 결정해야 하는 이유를 설명해.
- **은행에서라면?** 지금 만드는 모의 금융 서비스의 예시로 연결해.
- 한 번에 499개를 읽지 말고, 원본 체크리스트에서 헷갈리는 번호만 찾아도 돼.

## ✦ 실제로는 이렇게 이어져

“A적금에 **매달 20만 원씩 12개월** 가입해줘.”

`LLM: 의도·조건 추출` → `DB: 상품 조건 조회` → `Tool: 이자 계산` → `State: 선택값 유지` → `사용자: 승인` → `서버: 재인증·가입 검증` → `API: 모의 계약 생성`

여기서 **상품 조건·계산·실행의 최종 판단은 서버**가 해. LLM 혼자 금리를 정하거나 계약을 만들지는 않아.

> **참고** · 이 해설집의 ‘은행 예시’는 이해를 돕는 설계 예시야. 기획서에서 확정된 규칙과 앞으로 팀이 결정할 사항을 구분해서 읽어줘. 실제 금융기관 운영 기준을 의미하지 않아.

## PART 01. 에이전트 요구사항 및 설계 범위

*무엇을 AI에 맡기고 어디서 멈출지 정의*

### 1.1 에이전트 역할 정의

#### 01-01-01 AI 에이전트의 핵심 목적 ★

- **01 · 무슨 뜻?** 은행 AI 도우미가 최종적으로 해줄 일을 한 문장으로 정하는 것.
- **02 · 왜 고민해?** 목적이 없으면 쓸데없는 기능과 Tool만 늘어나기 때문이야.
- **03 · 은행에서라면** “상품을 설명하고 조건을 확인해 모의 가입 화면까지 돕는다.”

#### 01-01-02 일반 챗봇과 AI 에이전트의 차이

- **01 · 무슨 뜻?** 질문에 답하는 챗봇과, 도구를 골라 실제 작업을 이어가는 에이전트를 비교하는 것.
- **02 · 왜 고민해?** 그냥 설명만 할지 실제 조회·신청까지 연결할지 구조가 달라져.
- **03 · 은행에서라면** “금리가 뭐야?”는 답변, “내 조건으로 계산해줘”는 조회·계산 Tool.

#### 01-01-03 AI가 처리할 작업과 백엔드가 처리할 작업 ★

- **01 · 무슨 뜻?** AI가 언어를 이해하는 일과 서버가 사실·권한·돈을 검증하는 일을 나누는 것.
- **02 · 왜 고민해?** AI가 만들어낸 숫자나 말로 잔액을 수정하면 안 돼.
- **03 · 은행에서라면** AI는 “10만 원 예치”를 추출하고, 계산·가입 가능 여부는 서버가 판단.

#### 01-01-04 AI의 자율성 및 실행 권한 범위 ★

- **01 · 무슨 뜻?** AI가 어디까지 혼자 선택·실행해도 되는지 경계선을 정하는 것.
- **02 · 왜 고민해?** 사용자 모르게 가입·해지 같은 상태 변경이 일어나지 않게 하려고.
- **03 · 은행에서라면** 상품 검색은 자동, 모의 가입은 사용자 승인+서버 인증 후 실행.

#### 01-01-05 단일 에이전트와 멀티 에이전트 비교

- **01 · 무슨 뜻?** 하나의 에이전트가 모두 처리할지 여러 전문 에이전트로 나눌지 비교하는 것.
- **02 · 왜 고민해?** 처음부터 여러 개로 나누면 운영과 디버깅이 어려워질 수 있어.
- **03 · 은행에서라면** 상품만 다루면 하나, 카드·거래까지 커지면 역할 분리를 검토.

### 1.2 은행 서비스 기능별 AI 적용 범위

#### 01-02-01 회원·인증 기능 (AUTH-F01~F13)

- **01 · 무슨 뜻?** 회원가입·로그인·PIN 등 회원 기능을 AI가 어느 정도 도울지 정하는 것.
- **02 · 왜 고민해?** 인증은 보안 핵심이라 AI가 비밀번호를 받거나 판정해선 안 돼.
- **03 · 은행에서라면** “비밀번호 바꾸는 곳 알려줘”는 안내, 실제 인증은 인증 서버.

#### 01-02-02 계좌 관리 기능 (ACCT-F01~F13)

- **01 · 무슨 뜻?** 계좌 개설·잔액·정지·해지 등 계좌 기능에서 AI 역할을 정하는 것.
- **02 · 왜 고민해?** 조회와 상태 변경의 위험 수준이 전혀 달라.
- **03 · 은행에서라면** “잔액 알려줘”는 권한 확인 후 조회, “해지해줘”는 엄격한 절차.

#### 01-02-03 예금·적금 상품 조회 (PROD-F01~F11)

- **01 · 무슨 뜻?** 정기예금·적금 검색부터 상품 가입 관련 기능을 AI가 어떻게 지원할지 범위를 정하는 것.
- **02 · 왜 고민해?** 기획서의 상품 기능이 챗봇의 핵심 후보이기 때문이야.
- **03 · 은행에서라면** “6개월 적금 찾아줘”를 DB 검색으로 연결.

#### 01-02-04 상품 조건 및 약관 설명

- **01 · 무슨 뜻?** 상품의 적용 조건과 약관 문구를 쉽게 설명하는 기능.
- **02 · 왜 고민해?** 공식 문서의 근거 없이 LLM이 조건을 지어낼 위험이 있어.
- **03 · 은행에서라면** “중도 해지하면?”에 해당 약관 조항을 찾아 설명.

#### 01-02-05 예상 이자 계산

- **01 · 무슨 뜻?** 원금·기간·금리에 따른 이자를 계산해 안내하는 기능.
- **02 · 왜 고민해?** 계산식과 금리를 AI에게 외워서 답하게 하면 오차가 생겨.
- **03 · 은행에서라면** “100만 원 1년 넣으면?” → 금리 조회 후 계산 Tool.

#### 01-02-06 상품 비교 및 추천

- **01 · 무슨 뜻?** 조건이 다른 상품을 나란히 비교하거나 적합한 후보를 알려주는 기능.
- **02 · 왜 고민해?** 추천 기준과 제공 정보의 객관성을 먼저 정해야 해.
- **03 · 은행에서라면** “월 20만 원씩 낼 때 두 적금 비교해줘.”

#### 01-02-07 상품 가입 조건 검증

- **01 · 무슨 뜻?** 신청 가능한 금액·기간·대상인지 확인하는 과정.
- **02 · 왜 고민해?** AI의 추측이 아니라 상품 정책을 반영한 서버 판단이어야 해.
- **03 · 은행에서라면** 최소 가입액을 넘는지 Rule/API로 검사.

#### 01-02-08 모의 상품 가입 및 중도 해지

- **01 · 무슨 뜻?** 모의 가입 또는 중도 해지를 자연어 요청에서 시작하게 하는 기능.
- **02 · 왜 고민해?** 돈이 움직이는 상태 변경이므로 승인·인증·중복방지가 필요해.
- **03 · 은행에서라면** “이 상품 가입” → 조건 확인 → 사용자 승인 → 서버 실행.

#### 01-02-09 카드 조회 및 분석 (CARD-F01~F16)

- **01 · 무슨 뜻?** 카드 발급·상태·예측·추천 등에서 AI 도우미의 범위를 정하는 것.
- **02 · 왜 고민해?** 추천 알고리즘 자체와 LLM 대화를 구분해야 해.
- **03 · 은행에서라면** 카드 사용액 예측은 분석 로직, AI는 결과를 설명.

#### 01-02-10 거래 조회 및 이체 (TRX-F01~F14)

- **01 · 무슨 뜻?** 거래 내역 조회와 이체 같은 기능에 AI를 연결할지 결정하는 것.
- **02 · 왜 고민해?** 이체는 오인식·중복 실행 시 피해가 커서 별도 통제가 필요해.
- **03 · 은행에서라면** “최근 이체 보여줘”와 “5만 원 보내줘”는 다른 권한.

#### 01-02-11 화면 이동·서비스 안내

- **01 · 무슨 뜻?** 챗봇이 앱의 적절한 화면으로 이동하도록 돕는 기능.
- **02 · 왜 고민해?** 모든 기능을 AI Tool로 직접 실행할 필요는 없기 때문이야.
- **03 · 은행에서라면** “PIN 변경하고 싶어” → PIN 변경 화면 안내.

### 1.3 에이전트 사용 시나리오

#### 01-03-01 단순 정보 질문

- **01 · 무슨 뜻?** 사용자가 한 가지 정보를 묻는 기본 사례.
- **02 · 왜 고민해?** 가장 단순한 기준선이 있어야 복잡한 설계가 필요한지 비교할 수 있어.
- **03 · 은행에서라면** “정기예금이 뭐야?”

#### 01-03-02 여러 조건을 포함한 복합 질문

- **01 · 무슨 뜻?** 한 문장에 여러 조건이나 질문을 넣는 상황.
- **02 · 왜 고민해?** 단일 Tool로 풀지, 질문을 나눠 처리할지 선택해야 해.
- **03 · 은행에서라면** “금리 높고 6개월 만기인 적금 두 개 비교해줘.”

#### 01-03-03 이전 대화에 대한 후속 질문

- **01 · 무슨 뜻?** 직전 대화를 기준으로 질문하는 상황.
- **02 · 왜 고민해?** 이전 상품이나 조건을 잘못 가져오면 엉뚱한 답이 나와.
- **03 · 은행에서라면** “그럼 이건 중도 해지 가능해?”의 ‘이건’ 찾기.

#### 01-03-04 정보가 부족한 요청

- **01 · 무슨 뜻?** 금액·기간처럼 필요한 값이 비어 있는 요청.
- **02 · 왜 고민해?** 추측해서 계산·실행하지 않고 사용자에게 물어야 해.
- **03 · 은행에서라면** “적금 계산해줘” → 월 납입액·기간 질문.

#### 01-03-05 복수 Tool을 순서대로 실행하는 요청

- **01 · 무슨 뜻?** 앞선 도구 결과를 써야 다음 도구를 실행할 수 있는 요청.
- **02 · 왜 고민해?** 실행 순서를 정하지 않으면 정보가 모자라거나 오류가 나.
- **03 · 은행에서라면** 상품 검색 → 금리 확인 → 이자 계산.

#### 01-03-06 사용자 확인이 필요한 요청

- **01 · 무슨 뜻?** 사용자의 명시적 확인 없이 실행해선 안 되는 요청.
- **02 · 왜 고민해?** 읽기와 쓰기의 안전 기준을 분리하기 위해서야.
- **03 · 은행에서라면** “가입 진행해” → 상품·금액 보여주고 승인받기.

#### 01-03-07 실행할 수 없는 요청

- **01 · 무슨 뜻?** 지원 대상이 아니거나 권한이 없는 요청.
- **02 · 왜 고민해?** 무리하게 수행하는 척하지 않고 명확히 선을 그어야 해.
- **03 · 은행에서라면** “다른 사람 계좌 보여줘” → 거부.

#### 01-03-08 오류·예외 상황

- **01 · 무슨 뜻?** Tool 실패·잘못된 입력·서버 장애가 발생하는 상황.
- **02 · 왜 고민해?** 실패해도 안전하게 종료하거나 복구하는 흐름을 정해야 해.
- **03 · 은행에서라면** 금리 API 장애 → 임의 금리를 쓰지 않고 재시도 안내.

### 1.4 기능 ID별 AI 지원 매트릭스

#### 01-04-01 기획서의 기능 ID별 지원 범위 목록화

- **01 · 무슨 뜻?** 기획서 기능 번호마다 AI가 무엇을 할지 표로 나열하는 것.
- **02 · 왜 고민해?** 기능이 많아 빠짐없이 범위를 통제하기 위해서야.
- **03 · 은행에서라면** `PROD-Fxx`별로 지원·미지원 표시.

#### 01-04-02 기능별 ‘직접 실행 / 설명 / 화면 링크 / 제외’ 분류 ★

- **01 · 무슨 뜻?** AI가 기능을 직접 실행할지, 설명·링크만 제공할지 구분하는 것.
- **02 · 왜 고민해?** 모든 기능을 Agent Tool로 만드는 건 비효율적이고 위험할 수 있어.
- **03 · 은행에서라면** PIN 재설정은 링크 안내, 예금 설명은 RAG.

#### 01-04-03 각 기능의 사용자 인텐트·입력값 정의

- **01 · 무슨 뜻?** 각 기능의 사용자 표현과 필요한 입력값을 정의하는 것.
- **02 · 왜 고민해?** 무슨 요청인지 알아도 입력값을 모르면 실행하지 못해.
- **03 · 은행에서라면** “예금 가입” 인텐트에는 상품·금액·기간이 필요.

#### 01-04-04 실제 상태 변경이 필요한 기능 별도 표시

- **01 · 무슨 뜻?** DB 상태를 바꾸는 기능을 따로 표시하는 것.
- **02 · 왜 고민해?** 조회보다 훨씬 강한 승인과 재검증이 필요해서야.
- **03 · 은행에서라면** 가입·해지·이체는 ‘쓰기’ 기능으로 표시.

#### 01-04-05 1차·2차·3차 단계별 AI 지원 범위 분리

- **01 · 무슨 뜻?** 개발 1·2·3차에 맞춰 AI가 지원할 기능을 나누는 것.
- **02 · 왜 고민해?** 아직 만들지 않은 API에 의존하면 에이전트가 실패해.
- **03 · 은행에서라면** 1차에는 상품 검색, 2차에는 해지 연동 추가 검토.

#### 01-04-06 AI/ML 분석 기능과 LLM Agent 기능 구분

- **01 · 무슨 뜻?** 데이터 분석·머신러닝과 LLM 에이전트 작업을 구별하는 것.
- **02 · 왜 고민해?** ‘AI’라는 이름이 같아도 필요한 기술과 검증이 달라.
- **03 · 은행에서라면** 카드 사용액 예측 모델과 그 결과를 설명하는 챗봇 분리.

### 1.5 책임 경계와 비목표

#### 01-05-01 LLM / RAG / DB / 서버 계산 책임 분리 ★

- **01 · 무슨 뜻?** 자연어 생성, 문서 검색, 데이터 조회, 정확한 계산의 책임을 나누는 것.
- **02 · 왜 고민해?** 각 도구가 잘하는 일에 맡겨야 정확하고 검증 가능해.
- **03 · 은행에서라면** LLM은 설명, RAG는 약관, DB는 현재 금리, 서버는 계산.

#### 01-05-02 인증·인가 및 개인정보 확인의 최종 책임 정의

- **01 · 무슨 뜻?** 본인 여부와 접근 권한을 최종적으로 누가 확인할지 정하는 것.
- **02 · 왜 고민해?** LLM 답변만으로 타인 정보 접근을 막을 수 없기 때문이야.
- **03 · 은행에서라면** 계좌 조회 API가 로그인 사용자와 계좌 소유자를 비교.

#### 01-05-03 잔액·금리·자격·해지 조건은 서버 결과 기준으로 검증 ★

- **01 · 무슨 뜻?** 잔액·금리·자격·해지 조건의 최종 판정자를 서버로 정하는 것.
- **02 · 왜 고민해?** 실시간·정책 데이터가 바뀌므로 생성된 문장보다 원본이 우선이야.
- **03 · 은행에서라면** “가입 가능”은 API의 검증 성공일 때만 표시.

#### 01-05-04 금융 작업을 LLM의 생성 텍스트만으로 확정하지 않기

- **01 · 무슨 뜻?** AI의 자연어 답변을 업무 확정 신호로 취급하지 않는 것.
- **02 · 왜 고민해?** ‘완료했어요’라는 텍스트만으로 실제 계약이 생기면 안 돼.
- **03 · 은행에서라면** 가입 완료는 서버 계약 ID와 성공 상태를 확인한 뒤 안내.

#### 01-05-05 운영용 금융 서비스가 아닌 교육용 모의 서비스 범위 명시

- **01 · 무슨 뜻?** 이 프로젝트가 교육용 가상 금융 서비스라는 경계를 문서화하는 것.
- **02 · 왜 고민해?** 실제 금융기관 보안·규제 충족으로 오해받지 않게 하려고.
- **03 · 은행에서라면** 화면·증명서·AI 답변에 ‘모의 서비스’ 표기.

## PART 02. LLM 및 LangChain 기초 설계

*프롬프트·출력·의도 추출의 기본 계약*

### 2.1 [00] Prompt Engineering

#### 02-01-01 System / Human / AI Message ★

- **01 · 무슨 뜻?** System은 AI의 규칙, Human은 사용자 말, AI는 모델 답변인 메시지 역할 구분.
- **02 · 왜 고민해?** 서로 다른 메시지의 우선순위를 혼동하지 않게 하려고.
- **03 · 은행에서라면** 시스템: “근거 없으면 모른다고 말해”; 사용자: “금리 알려줘.”

#### 02-01-02 PromptTemplate / ChatPromptTemplate

- **01 · 무슨 뜻?** 문장을 변수와 결합해 재사용하는 프롬프트 틀.
- **02 · 왜 고민해?** 기능마다 상품명·검색 결과만 바꿔 같은 형식으로 호출하려고.
- **03 · 은행에서라면** “{상품명}의 {조항}을 자료에 근거해 설명해.”

#### 02-01-03 역할 및 지시사항 설계

- **01 · 무슨 뜻?** 에이전트의 목적·금지사항·답변 방식을 명시하는 것.
- **02 · 왜 고민해?** 아무 지시가 없으면 역할과 답변 수준이 흔들려.
- **03 · 은행에서라면** “가입은 직접 확정하지 말고 승인 단계를 거친다.”

#### 02-01-04 Few-shot Prompting

- **01 · 무슨 뜻?** 입력과 바람직한 출력의 예시를 보여주는 프롬프트 방식.
- **02 · 왜 고민해?** 의도 분류나 정형 출력의 일관성을 높일지 판단하려고.
- **03 · 은행에서라면** “6개월 적금” → `product_search` 예시 제공.

#### 02-01-05 대화 컨텍스트 구성

- **01 · 무슨 뜻?** 현재 질문과 관련된 이전 대화·검색 결과를 넣는 방식.
- **02 · 왜 고민해?** 너무 많이 넣으면 비용이 늘고 오래된 정보를 끌어올 수 있어.
- **03 · 은행에서라면** 최근 선택 상품과 확정 슬롯만 첨부.

#### 02-01-06 프롬프트 인젝션 방어

- **01 · 무슨 뜻?** 검색 문서나 사용자 입력 속의 악의적 명령을 무시하도록 설계하는 것.
- **02 · 왜 고민해?** 약관 내용이 AI의 시스템 규칙을 덮어쓰지 못하게 하려고.
- **03 · 은행에서라면** 문서 속 “보안 검사를 건너뛰어”는 지시가 아닌 데이터.

### 2.2 [01] LangChain Basic

#### 02-02-01 Model / Prompt / Output Parser

- **01 · 무슨 뜻?** 모델 호출·프롬프트·출력 해석을 하나의 흐름으로 묶는 기본 부품들.
- **02 · 왜 고민해?** 입력부터 결과까지 어디서 변환되는지 알기 위해서야.
- **03 · 은행에서라면** 상품명 입력 → 프롬프트 → LLM → JSON 파싱.

#### 02-02-02 Chain 구성

- **01 · 무슨 뜻?** 여러 처리 단계를 연결해 하나의 작업으로 만드는 것.
- **02 · 왜 고민해?** 반복되는 답변 생성 흐름을 재사용하기 좋아.
- **03 · 은행에서라면** 검색된 문서를 넣고 요약까지 이어지는 체인.

#### 02-02-03 LCEL / Runnable

- **01 · 무슨 뜻?** LangChain의 호출 가능한 공통 인터페이스와 연결 표현 방식.
- **02 · 왜 고민해?** 구성요소를 표준 방식으로 이어 붙일지 판단하려고.
- **03 · 은행에서라면** `prompt → model → parser` 같은 형태.

#### 02-02-04 RunnableSequence

- **01 · 무슨 뜻?** Runnable을 앞뒤로 순서대로 이어 실행하는 방식.
- **02 · 왜 고민해?** 앞 결과를 다음 단계에서 써야 할 때 필요해.
- **03 · 은행에서라면** 질문 정리 → 답변 생성 → 출력 파싱.

#### 02-02-05 RunnableParallel

- **01 · 무슨 뜻?** 서로 독립적인 Runnable을 동시에 처리하는 방식.
- **02 · 왜 고민해?** 여러 조회를 빠르게 할 수 있는지 검토하려고.
- **03 · 은행에서라면** 상품 설명 요약과 FAQ 검색을 병렬 수행.

#### 02-02-06 LangChain과 LangGraph 역할 분리

- **01 · 무슨 뜻?** LangChain의 호출 부품과 LangGraph의 상태·분기 관리 역할 구분.
- **02 · 왜 고민해?** 같은 제어 흐름을 두 군데서 중복 구현하지 않기 위해서야.
- **03 · 은행에서라면** 개별 LLM 체인은 LangChain, 가입 승인 흐름은 Graph.

### 2.3 [04] Structured Output

#### 02-03-01 JSON 형태 출력

- **01 · 무슨 뜻?** 모델에게 자유 문장이 아닌 정해진 필드의 JSON을 받는 방식.
- **02 · 왜 고민해?** 서버가 결과를 안전하게 해석하고 다음 작업으로 연결하려고.
- **03 · 은행에서라면** `{"intent":"INTEREST_CALC","months":6}`.

#### 02-03-02 Pydantic 모델 정의 ★

- **01 · 무슨 뜻?** 필드의 자료형·필수 여부 등을 정의하는 Python 모델.
- **02 · 왜 고민해?** 잘못된 금액·기간이 다음 Tool로 넘어가지 않도록 검사해.
- **03 · 은행에서라면** `months`는 정수, `product_id`는 문자열로 정의.

#### 02-03-03 의도 분류 결과 구조화

- **01 · 무슨 뜻?** 사용자의 요청을 정해진 인텐트 값으로 반환하는 것.
- **02 · 왜 고민해?** 분기 노드가 애매한 문장 대신 일관된 값으로 이동해.
- **03 · 은행에서라면** “적금 찾아줘” → `SEARCH_PRODUCT`.

#### 02-03-04 상품명·금액·기간 등 파라미터 추출

- **01 · 무슨 뜻?** 문장에서 상품명·금액·기간을 정형 필드로 뽑는 것.
- **02 · 왜 고민해?** Tool 인자가 자연어 전체가 아니라 구체적 값이어야 해서야.
- **03 · 은행에서라면** “매달 10만 원, 12개월” → amount=100000, months=12.

#### 02-03-05 출력 유효성 검증

- **01 · 무슨 뜻?** 모델이 만든 데이터가 정해진 형식·범위에 맞는지 확인하는 것.
- **02 · 왜 고민해?** 모델 출력은 항상 올바르지 않기 때문이야.
- **03 · 은행에서라면** 금액이 음수거나 기간이 문자열이면 거부·수정 요청.

#### 02-03-06 구조화 출력 실패 시 재처리

- **01 · 무슨 뜻?** JSON이나 필드 검증이 실패했을 때 처리 방식을 정하는 것.
- **02 · 왜 고민해?** 한 번 잘못 출력됐다고 전체 대화를 망치지 않기 위해서야.
- **03 · 은행에서라면** 형식 재요청을 제한 횟수 시도 후 실패 안내.

### 2.4 LLM 모델 선택

#### 02-04-01 모델 제공자 및 종류

- **01 · 무슨 뜻?** 어떤 회사의 어떤 LLM을 쓸지 정하는 것.
- **02 · 왜 고민해?** API·가격·성능·보안 조건이 서로 다르기 때문이야.
- **03 · 은행에서라면** Gemini와 다른 지원 모델을 같은 테스트셋으로 비교.

#### 02-04-02 모델 성능과 응답 정확도

- **01 · 무슨 뜻?** 같은 질문에 얼마나 정확하게 답하는지 검증하는 것.
- **02 · 왜 고민해?** 한국어 약관·복합 질문 등 프로젝트 맞춤 성능이 중요해.
- **03 · 은행에서라면** 상품 두 개의 조건 비교에서 오류율 측정.

#### 02-04-03 Tool Calling 지원

- **01 · 무슨 뜻?** 모델이 도구 이름과 인자를 구조적으로 요청할 수 있는지 확인하는 것.
- **02 · 왜 고민해?** Tool Agent를 만들려면 호출 기능을 모델이 지원해야 해.
- **03 · 은행에서라면** `calculate_interest(amount=...,months=...)` 호출 테스트.

#### 02-04-04 Structured Output 지원

- **01 · 무슨 뜻?** 모델이 지정한 JSON/Pydantic 구조로 답할 수 있는지 확인하는 것.
- **02 · 왜 고민해?** 인텐트와 슬롯을 안전하게 추출하려고.
- **03 · 은행에서라면** 제품 검색 결과를 `product_ids` 배열로 받기.

#### 02-04-05 응답 속도 및 토큰 비용

- **01 · 무슨 뜻?** 한 번 답하는 시간과 비용을 비교하는 것.
- **02 · 왜 고민해?** Agent는 여러 번 LLM을 호출해 예상보다 느리고 비쌀 수 있어.
- **03 · 은행에서라면** 한 질문에 호출 3번일 때 총 지연·요금 비교.

#### 02-04-06 작업별 모델 분리 필요성

- **01 · 무슨 뜻?** 모든 노드에 같은 모델을 쓸지 가벼운 모델을 섞을지 검토하는 것.
- **02 · 왜 고민해?** 분류는 저렴하게, 복잡한 설명은 더 성능 좋은 모델로 나눌 수 있어.
- **03 · 은행에서라면** 인텐트 분류용 소형 모델 + 약관 설명용 모델.

### 2.5 Intent / Entity / Slot 설계

#### 02-05-01 의도 라벨 및 분류 기준 정의

- **01 · 무슨 뜻?** 사용자 요청 종류마다 이름과 판단 조건을 정하는 것.
- **02 · 왜 고민해?** ‘조회’와 ‘가입’이 뒤섞이면 잘못된 실행으로 이어질 수 있어.
- **03 · 은행에서라면** `SEARCH_PRODUCT`, `CALCULATE`, `SUBSCRIBE` 등 구분.

#### 02-05-02 상품명·상품 유형·금액·기간 Entity 정의

- **01 · 무슨 뜻?** 문장에서 찾아낼 구체적인 대상·속성을 정하는 것.
- **02 · 왜 고민해?** 개체를 정의해야 여러 방식의 말도 같은 값으로 처리할 수 있어.
- **03 · 은행에서라면** “1년”, “12개월”을 기간 Entity로 인식.

#### 02-05-03 필수 Slot / 선택 Slot / 기본값 구분 ★

- **01 · 무슨 뜻?** 꼭 받아야 할 값과 없어도 되는 값을 나누는 것.
- **02 · 왜 고민해?** 불필요한 질문을 줄이고 필수 정보 누락은 막으려고.
- **03 · 은행에서라면** 이자 계산에는 금액·기간 필수, 닉네임은 불필요.

#### 02-05-04 Slot 누락 시 명확한 추가 질문

- **01 · 무슨 뜻?** 필수 입력이 빠졌을 때 어떤 질문을 할지 설계하는 것.
- **02 · 왜 고민해?** AI가 임의로 기본값을 채워 가입하지 않도록 하기 위해서야.
- **03 · 은행에서라면** “얼마를 매달 납입할까요?”

#### 02-05-05 입력 단위·형식·범위 검증

- **01 · 무슨 뜻?** 추출한 값의 단위와 허용 범위를 확인하는 것.
- **02 · 왜 고민해?** ‘10’이 10원인지 10만 원인지 혼동하면 큰 오류야.
- **03 · 은행에서라면** “10만원” → 100000원, 기간은 상품 허용 범위로 검사.

#### 02-05-06 단일 발화의 복합 의도 해석

- **01 · 무슨 뜻?** 한 번에 두 가지 이상 부탁한 문장을 분리·처리하는 것.
- **02 · 왜 고민해?** 한 가지 인텐트만 인식하면 사용자의 일부 요청이 누락돼.
- **03 · 은행에서라면** “상품 찾아서 이자도 계산해줘” → 검색+계산.

### 2.6 대화 참조 해소

#### 02-06-01 ‘그 상품’ 같은 대명사 참조 해결 ★

- **01 · 무슨 뜻?** ‘그 상품’, ‘거기’ 등이 앞 대화의 무엇을 뜻하는지 찾는 것.
- **02 · 왜 고민해?** 지칭을 잘못 연결하면 다른 상품으로 가입할 수 있어.
- **03 · 은행에서라면** 직전 대화에서 사용자에게 보여준 상품을 참조.

#### 02-06-02 최근 상품과 현재 확정 상품 구분

- **01 · 무슨 뜻?** 화면에 보인 최근 후보와 사용자가 확정한 대상을 구분하는 것.
- **02 · 왜 고민해?** 추천한 상품이 곧 가입하기로 선택한 상품은 아니야.
- **03 · 은행에서라면** 3개를 추천했으면 ‘현재 확정 상품’은 아직 비어 있음.

#### 02-06-03 모호한 상품이 두 개 이상이면 재확인

- **01 · 무슨 뜻?** 둘 이상을 가리킬 수 있는 표현이면 다시 물어보는 것.
- **02 · 왜 고민해?** AI가 임의로 하나를 택하면 실수할 수 있어.
- **03 · 은행에서라면** “둘 중 어느 상품을 말씀하시는 건가요?”

#### 02-06-04 후속 질문에서 이전 금액·기간 재사용 기준

- **01 · 무슨 뜻?** 앞에서 말한 금액·기간을 새 질문에도 적용할지 정하는 것.
- **02 · 왜 고민해?** 관련 없는 새 요청에 옛 조건이 섞이지 않게 하려고.
- **03 · 은행에서라면** 같은 상품 비교 중엔 6개월 유지, 새 가입이면 확인.

#### 02-06-05 사용자가 의도를 바꿀 때 이전 Slot 초기화

- **01 · 무슨 뜻?** 상품·업무 목적이 바뀌면 이전 입력값을 폐기하는 것.
- **02 · 왜 고민해?** 오래된 금액으로 새 상품을 실행하지 않도록 하기 위해서야.
- **03 · 은행에서라면** 예금 계산에서 적금 가입으로 바뀌면 납입방식 초기화.

#### 02-06-06 추측 대신 사용자에게 질문할 조건

- **01 · 무슨 뜻?** 어느 정도 불확실할 때 추측을 멈추고 질문할지 정하는 것.
- **02 · 왜 고민해?** 사용자 부담과 안전성 사이 균형이 필요해.
- **03 · 은행에서라면** 상품 후보가 두 개면 확인, 단순 정의 질문이면 바로 답변.

## PART 03. Tool Calling 및 Agent 설계

*AI가 어떤 도구를 언제, 어디까지 호출하는가*

### 3.1 [05] Tool Agent

#### 03-01-01 Tool의 개념과 역할 ★

- **01 · 무슨 뜻?** AI가 직접 알 수 없는 값을 조회·계산·실행하도록 연결하는 함수.
- **02 · 왜 고민해?** AI의 언어 능력과 실제 시스템 기능을 이어 주기 위해서야.
- **03 · 은행에서라면** `get_product_rate(product_id)`.

#### 03-01-02 Function Calling / Tool Calling

- **01 · 무슨 뜻?** 모델이 정해진 형식으로 도구 실행을 요청하는 기능.
- **02 · 왜 고민해?** ‘이 Tool을 호출해줘’라는 일반 문장과 실제 호출은 달라.
- **03 · 은행에서라면** LLM이 계산 Tool 이름과 JSON 인자를 반환.

#### 03-01-03 Tool 정의 및 입력·출력 스키마 ★

- **01 · 무슨 뜻?** 각 도구가 어떤 값을 받고 어떤 결과를 돌려주는지 약속하는 것.
- **02 · 왜 고민해?** 잘못된 인자나 불분명한 결과가 연쇄 오류를 만들기 때문이야.
- **03 · 은행에서라면** `amount:int`, 결과 `interest:int`, `currency:str`.

#### 03-01-04 Tool 선택 방식

- **01 · 무슨 뜻?** 여러 Tool 중 어떤 것을 사용할지 판단하는 방식.
- **02 · 왜 고민해?** 모든 질문마다 모든 Tool을 실행할 필요는 없어서야.
- **03 · 은행에서라면** 약관 질문은 Retriever, 금리 질문은 상품 DB Tool.

#### 03-01-05 Tool 실행 결과 처리

- **01 · 무슨 뜻?** Tool이 돌려준 데이터를 검증하고 답변이나 다음 단계에 쓰는 것.
- **02 · 왜 고민해?** Tool 결과를 그대로 사용자에게 내보내도 되는지 확인해야 해.
- **03 · 은행에서라면** 금리 API 반환 날짜를 함께 표시.

#### 03-01-06 Tool 오류 처리

- **01 · 무슨 뜻?** 도구가 타임아웃·거절·오류를 낼 때 처리하는 것.
- **02 · 왜 고민해?** 실패를 성공처럼 포장하면 안 되고 재시도도 위험할 수 있어.
- **03 · 은행에서라면** 가입 Tool 실패 시 실제 계약 존재 여부부터 확인.

### 3.2 [12] ReAct Agent

#### 03-02-01 ReAct 패턴

- **01 · 무슨 뜻?** 모델이 필요한 Tool을 선택하고 결과를 읽어 다음 행동을 결정하는 반복 패턴.
- **02 · 왜 고민해?** 질문별로 검색·계산 순서가 달라질 때 유용해.
- **03 · 은행에서라면** 상품 검색 후 금리 Tool을 추가로 호출할지 결정.

#### 03-02-02 Tool 호출과 결과 확인 반복

- **01 · 무슨 뜻?** 도구 결과를 확인하고 부족하면 새 도구를 쓰는 흐름.
- **02 · 왜 고민해?** 한 번 조회로 답이 부족한 복합 질문을 풀려고.
- **03 · 은행에서라면** 상품 조회 뒤 약관 검색을 추가 실행.

#### 03-02-03 ReAct와 고정 Workflow 비교

- **01 · 무슨 뜻?** AI가 자유롭게 도구를 고르는 방식과 순서가 고정된 Graph 비교.
- **02 · 왜 고민해?** 금융 쓰기 작업은 고정 순서가 더 안전한 경우가 많아.
- **03 · 은행에서라면** 설명 검색은 ReAct, 가입 확정은 고정된 검증 노드.

#### 03-02-04 최대 반복 횟수 설정

- **01 · 무슨 뜻?** ReAct가 도구 호출을 몇 번까지 반복할지 제한하는 것.
- **02 · 왜 고민해?** 실수로 무한 반복해 비용이 늘거나 시스템에 부담을 주지 않게 해.
- **03 · 은행에서라면** 한 질문에서 Tool 호출 최대 횟수 설정.

#### 03-02-05 종료 조건 설계

- **01 · 무슨 뜻?** 언제 충분히 답했거나 더 진행하지 못했다고 판단할지 정하는 것.
- **02 · 왜 고민해?** 목적 없이 검색을 반복하지 않기 위해서야.
- **03 · 은행에서라면** 필요한 금리와 조건을 확보하면 종료, 근거 없으면 유보.

### 3.3 [28] Agent Tool Control

#### 03-03-01 Tool 호출 권한 제어

- **01 · 무슨 뜻?** 어떤 사용자·업무가 어느 Tool을 실행할 수 있는지 제한하는 것.
- **02 · 왜 고민해?** LLM의 선택이 곧 사용 권한이 되면 안 되기 때문이야.
- **03 · 은행에서라면** 미로그인 사용자의 `get_my_balance` 차단.

#### 03-03-02 읽기 전용 Tool / 실행 Tool 분리 ★

- **01 · 무슨 뜻?** 정보만 읽는 조회 Tool과 상태를 바꾸는 실행 Tool을 구분하는 것.
- **02 · 왜 고민해?** 쓰기는 승인·재인증·멱등성 등 훨씬 강한 보호가 필요해.
- **03 · 은행에서라면** `list_products`는 읽기, `subscribe_product`는 쓰기.

#### 03-03-03 사용자 인증 상태에 따른 Tool 제한

- **01 · 무슨 뜻?** 로그인·재인증 여부에 따라 사용 가능한 Tool을 제한하는 것.
- **02 · 왜 고민해?** 동일한 사용자 발화라도 인증 상태에 따라 허용 범위가 달라.
- **03 · 은행에서라면** 로그인 전에는 공개 상품만 조회 가능.

#### 03-03-04 Tool 호출 횟수 제한

- **01 · 무슨 뜻?** 한 요청에서 Tool을 몇 번까지 실행할 수 있을지 정하는 것.
- **02 · 왜 고민해?** 오류 루프와 과도한 비용·서버 호출을 막기 위해서야.
- **03 · 은행에서라면** 재시도 2번, 전체 도구 실행 상한 적용.

#### 03-03-05 Tool 실행 조건 및 차단 규칙

- **01 · 무슨 뜻?** 도구 실행 전에 통과해야 할 정책을 정의하는 것.
- **02 · 왜 고민해?** 잘못된 작업을 실행 뒤에 발견하면 늦을 수 있어.
- **03 · 은행에서라면** 가입 Tool 앞에서 상품 상태·금액·승인 검사.

#### 03-03-06 위험 작업 승인 및 실행 제한

- **01 · 무슨 뜻?** 고위험 기능의 승인 없이 도구 실행을 막는 것.
- **02 · 왜 고민해?** “가입해줘”라는 발화만으로 계약을 만들지 않게 해.
- **03 · 은행에서라면** 사용자 확정 버튼과 인증 결과 확인 후 실행.

#### 03-03-07 Runtime Context로 신뢰 가능한 사용자 식별 전달 ★

- **01 · 무슨 뜻?** LLM이 쓴 user_id 대신 서버에서 검증한 식별자를 전달하는 것.
- **02 · 왜 고민해?** 모델이 임의의 타인 ID를 만들어 전달하지 못하게 해야 해.
- **03 · 은행에서라면** 서버가 로그인 세션으로 `user_id`를 주입.

사용자의 요청, 대화 이력, 도구 실행 결과, 현재 작업 상태 등을 어떻게 관리하고 전달할 것인지
#### 03-03-08 Middleware / wrap_tool_call 도입 검토

- **01 · 무슨 뜻?** Tool 호출 중간에 권한 검사·로깅 등을 끼워 넣는 공통 장치 검토.
- **02 · 왜 고민해?** Tool마다 보안 로직을 복사하지 않고 중앙에서 통제할 수 있어.
- **03 · 은행에서라면** 모든 Tool 호출을 감싸 실행 전 인증 확인.

`wrap_tool_call`은 Middleware에서 사용하는 도구 호출 래퍼(Wrapper) 개념.
Tool이 실제로 실행되기 전과 실행된 후에 추가 로직을 끼워 넣을 수 있는 기능
#### 03-03-09 Tool 입력·출력 사전/사후 검증

- **01 · 무슨 뜻?** 도구 실행 전 인자, 실행 후 반환 데이터를 검증하는 것.
- **02 · 왜 고민해?** 잘못된 값이나 노출하면 안 되는 정보가 사용자에게 넘어갈 수 있어.
- **03 · 은행에서라면** 금액 타입·계좌 소유권 검사, 응답에서 내부 토큰 제거.

#### 03-03-10 ToolCallLimitMiddleware 등 제한 장치 비교

- **01 · 무슨 뜻?** Tool 호출 제한 기능을 자체 구현할지 제공 Middleware를 사용할지 비교.
- **02 · 왜 고민해?** 이미 있는 검증 기능으로 단순하게 구현할 수 있는지 확인하려고.
- **03 · 은행에서라면** ToolCallLimitMiddleware 적용 가능 여부 테스트.

### 3.4 은행 서비스 전용 Tool

#### 03-04-01 상품 목록 조회 Tool

- **01 · 무슨 뜻?** 현재 판매 가능한 상품 목록을 읽는 도구.
- **02 · 왜 고민해?** LLM이 상품 목록을 외워서 만들어내지 않게 하려고.
- **03 · 은행에서라면** “6개월 예금 찾아줘” → 상품 조회 API.

#### 03-04-02 상품 상세 및 금리 조회 Tool

- **01 · 무슨 뜻?** 상품별 금리·기간·상태를 가져오는 도구.
- **02 · 왜 고민해?** 상품마다 다르고 수시로 바뀌는 값을 원본에서 받아야 해.
- **03 · 은행에서라면** `product_id`로 우대금리·기본금리 확인.

#### 03-04-03 예상 이자 계산 Tool ★

- **01 · 무슨 뜻?** 입력된 원금·금리·기간을 정해진 규칙으로 계산하는 도구.
- **02 · 왜 고민해?** 숫자 연산을 LLM 자유 생성에 맡기면 오류가 날 수 있어.
- **03 · 은행에서라면** 100만 원·12개월·연 3% 계산.

#### 03-04-04 가입 조건 검증 Tool

- **01 · 무슨 뜻?** 가입 조건을 서버 정책에 따라 검사하는 도구.
- **02 · 왜 고민해?** 설명에는 충분해도 실제 가입 가능성을 AI가 단정할 수 없어.
- **03 · 은행에서라면** 최소 금액·가입 기간·계좌 유형 검사.

#### 03-04-05 모의 가입 실행 Tool

- **01 · 무슨 뜻?** 실제 모의 가입 계약 생성을 서버에 요청하는 도구.
- **02 · 왜 고민해?** 읽기와 다른 위험을 갖는 쓰기 작업이기 때문이야.
- **03 · 은행에서라면** 승인·step-up 후 계약 생성 요청.

#### 03-04-06 내 가입 상품 조회 Tool

- **01 · 무슨 뜻?** 사용자가 이미 가입한 상품을 조회하는 도구.
- **02 · 왜 고민해?** 본인 계약을 확인해야 중복 신청이나 해지 요청을 처리할 수 있어.
- **03 · 은행에서라면** “내가 가입한 적금 보여줘.”

#### 03-04-07 상품 중도 해지 Tool

- **01 · 무슨 뜻?** 모의 가입 계약의 중도 해지를 요청하는 도구.
- **02 · 왜 고민해?** 손익·상태 변화가 있으므로 별도 승인·검증이 필요해.
- **03 · 은행에서라면** 계약 선택 → 예상 해지 금액 확인 → 해지 실행.

#### 03-04-08 계좌·거래 조회 Tool 적용 범위

- **01 · 무슨 뜻?** 잔액이나 거래 조회를 어떤 조건까지 AI에 제공할지 정하는 것.
- **02 · 왜 고민해?** 개인 데이터는 인증·소유권 보호가 우선이야.
- **03 · 은행에서라면** 로그인한 사용자의 계좌만 읽기 전용 조회.

#### 03-04-09 화면 이동 링크 생성 Tool

- **01 · 무슨 뜻?** AI가 사용자를 특정 서비스 화면으로 보내는 링크를 반환하는 것.
- **02 · 왜 고민해?** 모든 일을 대화창에서 직접 처리하지 않아도 되기 때문이야.
- **03 · 은행에서라면** “카드 해지는 여기서” → 허용된 앱 내부 경로 반환.

#### 03-04-10 Tool별 인증·권한·실행 조건

- **01 · 무슨 뜻?** 도구마다 호출 권한과 선행 조건을 문서화하는 것.
- **02 · 왜 고민해?** 같은 Tool 집합이라도 모두가 언제나 사용할 수 있지는 않아.
- **03 · 은행에서라면** 가입 Tool = 로그인+승인+인증+서버 검증 필요.

### 3.5 Tool 계약·권한·신뢰 경계

#### 03-05-01 Tool별 입력 스키마·출력 스키마 표준화

- **01 · 무슨 뜻?** Tool의 요청과 응답 필드를 일정한 규칙으로 맞추는 것.
- **02 · 왜 고민해?** 서로 다른 API를 노드들이 안정적으로 연결하기 위해서야.
- **03 · 은행에서라면** 모든 오류 결과에 `code`, `message`, `retryable` 제공.

#### 03-05-02 읽기 Tool과 쓰기 Tool의 별도 실행 정책

- **01 · 무슨 뜻?** 조회와 변경을 실행하는 통로·조건을 분리하는 것.
- **02 · 왜 고민해?** 쓰기 Tool을 조회 Tool처럼 쉽게 호출하지 못하게 하려고.
- **03 · 은행에서라면** 조회 전용 DB 연결과 가입 전용 API 분리.

#### 03-05-03 LLM이 전달한 user_id를 신뢰하지 않기

- **01 · 무슨 뜻?** 모델이 출력한 사용자 식별값을 권한 판단에 사용하지 않는 것.
- **02 · 왜 고민해?** 악의적 프롬프트로 다른 사람의 정보에 접근할 수 있어.
- **03 · 은행에서라면** LLM의 `user_id="user_2"`는 무시.

#### 03-05-04 서버 세션에서 확인한 사용자로 Tool 실행 제한

- **01 · 무슨 뜻?** 신뢰 가능한 세션의 로그인 사용자로 도구 실행 범위를 제한하는 것.
- **02 · 왜 고민해?** 개인별 데이터 격리의 최종 책임이 서버에 있어.
- **03 · 은행에서라면** 서버 인증 컨텍스트의 사용자로 잔액 API 호출.

#### 03-05-05 Tool 결과의 에러 코드와 재시도 가능 여부 정의

- **01 · 무슨 뜻?** Tool 오류가 재시도 가능한지 종류별로 정의하는 것.
- **02 · 왜 고민해?** 네트워크 오류와 권한 거절을 같은 방식으로 재시도하면 안 돼.
- **03 · 은행에서라면** `TIMEOUT`은 상태 조회, `FORBIDDEN`은 즉시 중단.

#### 03-05-06 Tool이 반환한 화면 링크의 대상과 권한 검증

- **01 · 무슨 뜻?** AI가 만든 링크가 실제 허용 경로·대상인지 확인하는 것.
- **02 · 왜 고민해?** 잘못된 링크나 타인 리소스로 이동시키면 위험해.
- **03 · 은행에서라면** 허용한 `/products/{id}` 패턴만 반환.

#### 03-05-07 Tool 응답 내 악의적 텍스트를 지시로 해석하지 않기

- **01 · 무슨 뜻?** 도구 응답에 들어 있는 문장을 AI의 상위 지시로 취급하지 않는 것.
- **02 · 왜 고민해?** 외부 데이터가 에이전트 동작을 조작하는 것을 막아야 해.
- **03 · 은행에서라면** API 설명에 “인증 생략” 문구가 있어도 무시.

### 3.6 실행 안전장치

#### 03-06-01 멱등 키(idempotency key) 사용 기준 ★

- **01 · 무슨 뜻?** 같은 요청을 여러 번 보내도 업무 결과가 한 번만 생기게 하는 키.
- **02 · 왜 고민해?** 네트워크 재시도로 모의 계약이 두 개 생성되지 않게 하려고.
- **03 · 은행에서라면** 가입 요청마다 고유 멱등 키 전달.

#### 03-06-02 중복 Tool 호출과 중복 업무 실행 분리

- **01 · 무슨 뜻?** LLM이 도구를 두 번 부른 사실과 실제 업무 두 번 실행을 구분하는 것.
- **02 · 왜 고민해?** 호출 횟수만 줄여도 DB 중복을 완전히 막을 수는 없어.
- **03 · 은행에서라면** 서버도 같은 가입 키의 중복 요청을 차단.

#### 03-06-03 타임아웃 시 먼저 실행 결과 조회

- **01 · 무슨 뜻?** 응답이 늦어서 끊겼을 때 실행 여부를 먼저 확인하는 것.
- **02 · 왜 고민해?** 서버가 성공했는데 AI만 실패로 본 상황이 있을 수 있어.
- **03 · 은행에서라면** 계약 상태 조회 후 미실행일 때만 재요청.

#### 03-06-04 승인받은 파라미터와 실행 요청 일치 검증

- **01 · 무슨 뜻?** 사용자가 확인한 상품·금액·계좌와 실제 실행 인자를 비교하는 것.
- **02 · 왜 고민해?** 승인 뒤 조건이 달라지면 사용자 의사와 다른 실행이 돼.
- **03 · 은행에서라면** 승인한 100만 원과 실행 요청 150만 원이면 차단.

#### 03-06-05 실행 전 서버 재검증 시점 결정

- **01 · 무슨 뜻?** 조건 검사를 언제 다시 할지 정하는 것.
- **02 · 왜 고민해?** 승인 사이에 계좌 잔액·상품 상태가 바뀔 수 있어.
- **03 · 은행에서라면** 가입 직전 서버가 금액·잔액을 재검증.

#### 03-06-06 작업별 감사 식별자와 요청 추적 ID 설계

- **01 · 무슨 뜻?** 여러 노드·API 로그를 같은 작업으로 묶는 식별자를 두는 것.
- **02 · 왜 고민해?** 문제 발생 시 어느 요청에서 무슨 일이 있었는지 추적해야 해.
- **03 · 은행에서라면** `request_id`로 Tool·DB·감사 이벤트 연결.

## PART 04. RAG 아키텍처 설계

*정확한 상품·약관 문서만 찾아 설명*

### 4.1 [06] RAG Basic

#### 04-01-01 RAG 도입 목적 ★

- **01 · 무슨 뜻?** 외부 자료를 검색한 뒤 그 내용을 근거로 답변하는 방식을 왜 쓰는지 정하는 것.
- **02 · 왜 고민해?** 모델 기억만으로는 상품 약관을 정확히 설명하기 어려워.
- **03 · 은행에서라면** “이 적금 중도 해지 조건은?” → 문서를 찾아 답변.

#### 04-01-02 RAG와 일반 LLM 답변 비교

- **01 · 무슨 뜻?** 모델이 알고 있는 지식으로 답하는 것과 검색 문서를 읽고 답하는 것의 차이.
- **02 · 왜 고민해?** 바뀔 수 있는 규정에는 근거 확인이 필요하기 때문이야.
- **03 · 은행에서라면** 일반 금융 용어는 설명 가능, 특정 약관은 RAG 확인.

#### 04-01-03 RAG와 DB Tool 조회의 차이 ★

- **01 · 무슨 뜻?** 문서 문장을 찾는 RAG와 정형 데이터를 읽는 DB 조회를 구분하는 것.
- **02 · 왜 고민해?** 이 둘을 혼동하면 검색으로 실시간 잔액을 알아내려 할 수 있어.
- **03 · 은행에서라면** 약관 문장은 RAG, 현재 기본금리는 DB API.

#### 04-01-04 검색 대상 문서 및 데이터 범위

- **01 · 무슨 뜻?** 어떤 파일을 검색 대상으로 넣을지 목록을 정하는 것.
- **02 · 왜 고민해?** 자료가 부정확하거나 범위 밖이면 답변도 틀려.
- **03 · 은행에서라면** 상품 약관·FAQ·설명서만 인덱싱할지 결정.

### 4.2 [07] Vector DB

#### 04-02-01 Embedding 모델

- **01 · 무슨 뜻?** 문장을 숫자 벡터로 바꾸는 모델.
- **02 · 왜 고민해?** 비슷한 의미의 문서를 찾는 데 사용해.
- **03 · 은행에서라면** “미리 깨면 어떻게 돼?”와 ‘중도해지’를 연결.

#### 04-02-02 벡터 저장소 선택

- **01 · 무슨 뜻?** 벡터를 저장하고 검색할 시스템을 고르는 것.
- **02 · 왜 고민해?** 규모·관리 편의·비용에 따라 선택이 달라져.
- **03 · 은행에서라면** 학습용 Chroma 또는 기존 DB의 벡터 확장 검토.

#### 04-02-03 Vector Store 구조

- **01 · 무슨 뜻?** 문서 벡터와 관련 정보를 어떤 구조로 보관할지 설계하는 것.
- **02 · 왜 고민해?** 저장 방식이 엉키면 재색인·필터가 어려워.
- **03 · 은행에서라면** 청크 텍스트+embedding+상품 ID 저장.

#### 04-02-04 문서 메타데이터

- **01 · 무슨 뜻?** 문서 본문 외의 상품·버전·페이지 같은 부가 정보.
- **02 · 왜 고민해?** 비슷한 내용 중 정확한 문서만 골라내기 위해서야.
- **03 · 은행에서라면** `product_id`, `effective_at`, `page`.

#### 04-02-05 상품 ID 및 문서 버전 연결

- **01 · 무슨 뜻?** 벡터로 검색한 문서가 어느 상품·버전 소속인지 연결하는 것.
- **02 · 왜 고민해?** 다른 상품의 약관을 가져오면 금융 설명이 틀려.
- **03 · 은행에서라면** `prod_12`의 2026년 약관만 필터.

### 4.3 [08] RAG Pipeline

#### 04-03-01 Document Loader

- **01 · 무슨 뜻?** PDF·Markdown 등 원본 파일을 읽어 문서 객체로 바꾸는 도구.
- **02 · 왜 고민해?** 검색 전에 내용이 제대로 읽혔는지 확인해야 해.
- **03 · 은행에서라면** 상품 약관 Markdown을 Document로 로딩.

#### 04-03-02 Document Splitting / Chunking

- **01 · 무슨 뜻?** 긴 문서를 검색하기 좋게 작은 조각으로 나누는 것.
- **02 · 왜 고민해?** 너무 크면 검색이 둔하고, 너무 작으면 맥락이 끊겨.
- **03 · 은행에서라면** 약관을 조항 단위로 Chunking.

#### 04-03-03 Embedding

- **01 · 무슨 뜻?** 문서 조각을 검색용 숫자 표현으로 변환하는 과정.
- **02 · 왜 고민해?** 질문과 문서의 의미 유사도를 비교하기 위해서야.
- **03 · 은행에서라면** ‘이자 지급’ 조항을 벡터로 인코딩.

#### 04-03-04 Indexing

- **01 · 무슨 뜻?** 문서와 벡터·메타데이터를 검색 가능한 형태로 저장하는 과정.
- **02 · 왜 고민해?** 새 문서가 추가됐을 때 어디까지 갱신할지 정해야 해.
- **03 · 은행에서라면** 약관을 청크로 나눠 DB에 색인 생성.

#### 04-03-05 Retriever ★

- **01 · 무슨 뜻?** 질문과 관련 있는 문서를 찾아오는 구성요소.
- **02 · 왜 고민해?** 검색 범위·개수를 조절해야 답변이 정확해.
- **03 · 은행에서라면** 질문마다 관련 조항 4개 반환.

#### 04-03-06 Retrieval Chain

- **01 · 무슨 뜻?** 검색 결과를 LLM 입력과 연결해 답변을 만드는 체인.
- **02 · 왜 고민해?** 검색까지만 해서는 사용자가 읽기 쉬운 답이 되지 않아.
- **03 · 은행에서라면** Retriever → 관련 조항 → 답변 생성.

#### 04-03-07 검색 결과 기반 답변 생성

- **01 · 무슨 뜻?** 찾은 문서에 한정해서 자연어 답을 만드는 단계.
- **02 · 왜 고민해?** 모델이 문서에 없는 조건을 덧붙이지 않도록 통제해야 해.
- **03 · 은행에서라면** “가입 기간 6~12개월”을 출처와 함께 설명.

### 4.4 [09] Advanced RAG Search

#### 04-04-01 Similarity Search

- **01 · 무슨 뜻?** 질문과 가장 비슷한 벡터의 문서를 찾는 방법.
- **02 · 왜 고민해?** 기본 검색으로 충분한지 먼저 판단하기 위해서야.
- **03 · 은행에서라면** ‘중도 해지’와 유사한 약관 청크 검색.

#### 04-04-02 MMR 검색

- **01 · 무슨 뜻?** 비슷한 문서만 중복해서 뽑지 않고 다양한 결과를 고르는 검색.
- **02 · 왜 고민해?** 같은 문구만 여러 개 나오면 핵심 정보가 빠질 수 있어.
- **03 · 은행에서라면** 해지 조항·이자 조항을 골고루 가져오기.

#### 04-04-03 Metadata Filtering

- **01 · 무슨 뜻?** 상품 ID·문서 종류 같은 조건으로 검색 대상을 제한하는 것.
- **02 · 왜 고민해?** 의미가 비슷해도 다른 상품 문서는 답이 될 수 없어.
- **03 · 은행에서라면** 현재 선택한 적금의 약관만 검색.

#### 04-04-04 Hybrid Search

- **01 · 무슨 뜻?** 키워드 검색과 의미 기반 벡터 검색을 함께 사용하는 방식.
- **02 · 왜 고민해?** 정확한 상품명·코드와 자연스러운 질문을 모두 처리하려고.
- **03 · 은행에서라면** `PROD-001` 같은 코드는 키워드로, 질문은 벡터로.

#### 04-04-05 Multi-Query Retrieval

- **01 · 무슨 뜻?** 한 질문을 여러 검색 표현으로 바꾸는 방식.
- **02 · 왜 고민해?** 사용자의 말과 문서의 용어가 달라 검색이 실패할 수 있어.
- **03 · 은행에서라면** “깨면 손해?” → ‘중도 해지’, ‘중도해지이율’ 검색.

#### 04-04-06 Query Rewriting

- **01 · 무슨 뜻?** 질문을 검색하기 쉬운 문장으로 재작성하는 방법.
- **02 · 왜 고민해?** ‘그거’ 같은 표현을 문서 검색에 그대로 넣으면 안 좋아.
- **03 · 은행에서라면** “그 상품 이율” → “A적금 기본금리”.

#### 04-04-07 Reranking

- **01 · 무슨 뜻?** 1차 검색 결과를 추가 모델·규칙으로 다시 정렬하는 방법.
- **02 · 왜 고민해?** 가장 관련 높은 조항을 앞에 배치하려고.
- **03 · 은행에서라면** 검색 10개 중 상품명과 조항이 정확한 3개 선정.

#### 04-04-08 검색 결과 품질 개선

- **01 · 무슨 뜻?** 검색 결과가 잘못 나오는 원인을 찾아 개선하는 작업.
- **02 · 왜 고민해?** 검색법을 더 복잡하게 하기 전에 문제를 측정해야 해.
- **03 · 은행에서라면** 오답 질문 목록으로 청크·필터·검색법 조정.

- **02 · 왜 고민해?** 한 질문에 설명과 정확한 수치가 함께 필요할 수 있어.
- **03 · 은행에서라면** 금리 DB 조회 + 중도 해지 약관 RAG.

#### 04-05-03 검색 필요 여부 판단

- **01 · 무슨 뜻?** 검색이 꼭 필요한 질문과 아닌 질문을 구별하는 것.
- **02 · 왜 고민해?** 모든 발화마다 RAG를 돌리면 느리고 불필요해.
- **03 · 은행에서라면** “안녕”에는 검색 없이 응답.

#### 04-05-04 DB 조회와 RAG 검색 사이 선택 ★

- **01 · 무슨 뜻?** 현재 사실을 읽을지 조항을 찾을지 결정하는 것.
- **02 · 왜 고민해?** 정형 데이터는 DB가, 설명 근거는 RAG가 더 적합해.
- **03 · 은행에서라면** 잔액은 DB, 약관의 해지 제한은 RAG.

#### 04-05-05 검색 결과의 출처 표시

- **01 · 무슨 뜻?** 답변을 뒷받침하는 자료의 문서·조항을 사용자에게 보여주는 것.
- **02 · 왜 고민해?** 사용자가 왜 그런 답을 받았는지 확인할 수 있어.
- **03 · 은행에서라면** “약관 제3조 기준”과 문서 링크 표시.

### 4.6 [23] Agentic RAG

#### 04-06-01 검색 필요성 판단

- **01 · 무슨 뜻?** LLM이 답변 전에 문서 검색이 필요한지 선택하는 것.
- **02 · 왜 고민해?** 모든 요청을 하나의 고정 검색 방식으로 처리할 필요는 없어.
- **03 · 은행에서라면** 가입 절차 질문은 약관 검색, 단순 메뉴 질문은 안내.

- **02 · 왜 고민해?** 한 번의 검색으로 서로 다른 조항을 놓칠 수 있어.
- **03 · 은행에서라면** “해지 이율과 가입 기간”을 두 질의로 분리.

#### 04-06-03 복수 검색어 생성

- **01 · 무슨 뜻?** 같은 뜻을 여러 검색어로 바꿔 찾는 것.
- **02 · 왜 고민해?** 사용자 표현이 문서 제목과 다를 수 있어서야.
- **03 · 은행에서라면** ‘깨기’, ‘중도해지’, ‘계약 종료’ 검색.

#### 04-06-04 검색 결과 평가

- **01 · 무슨 뜻?** 찾은 문서가 질문을 해결할 만큼 충분한지 평가하는 것.
- **02 · 왜 고민해?** 관련 없는 청크로 억지 답을 만들지 않도록 하려고.
- **03 · 은행에서라면** 검색 조항에 실제 중도해지이율이 있는지 확인.

#### 04-06-05 추가 검색 및 재검색

- **01 · 무슨 뜻?** 검색 자료가 부족하면 다른 질문·범위로 다시 검색하는 것.
- **02 · 왜 고민해?** 한 번 검색에 실패해도 찾을 수 있는 정보를 놓치지 않게 해.
- **03 · 은행에서라면** 상품 ID를 고정한 채 다른 용어로 재검색.

#### 04-06-06 Agentic RAG와 일반 RAG 비교

- **01 · 무슨 뜻?** Agent가 검색을 조절하는 방식과 고정 RAG 파이프라인 비교.
- **02 · 왜 고민해?** 동적 방식이 정확도는 높여도 비용·오류가 늘 수 있어.
- **03 · 은행에서라면** 약관 질문이 단순하면 고정 RAG부터 사용.

#### 04-11-02 검색 근거와 답변 각 주장 연결

- **01 · 무슨 뜻?** 답변의 각 핵심 내용이 어떤 문서에 근거하는지 연결하는 것.
- **02 · 왜 고민해?** 출처 링크 하나만 있어도 답변 전체가 맞는 건 아니야.
- **03 · 은행에서라면** ‘가입기간’은 제2조, ‘해지율’은 제5조로 연결.

#### 04-11-03 근거 부족 시 답변 유보 및 안내 ★

- **01 · 무슨 뜻?** 근거가 충분하지 않으면 단정하지 않고 답을 보류하는 것.
- **02 · 왜 고민해?** 정확성을 위해 모른다고 말해야 하는 상황이 있어.
- **03 · 은행에서라면** 추출 못 한 우대조건은 “문서에서 확인되지 않음”.

#### 04-11-04 검색 실패와 원문에 답이 없는 상태 구분

- **01 · 무슨 뜻?** 검색기가 실패한 것과 원문 자체에 답이 없는 경우를 구별하는 것.
- **02 · 왜 고민해?** 다시 검색할지 자료 담당자에게 확인할지 대응이 달라.
- **03 · 은행에서라면** DB 장애는 ‘조회 실패’, 문서 누락은 ‘근거 없음’.

#### 04-11-05 문서 내 Prompt Injection 방어

- **01 · 무슨 뜻?** 검색 문서 속 악의적인 명령을 실행하지 않게 방어하는 것.
- **02 · 왜 고민해?** RAG 자료도 외부 입력이므로 신뢰할 수 없는 명령이 포함될 수 있어.
- **03 · 은행에서라면** 약관 속 ‘이체 실행’ 같은 문장은 Tool 명령이 아님.

#### 04-11-06 개인별 비공개 문서가 검색 범위에 섞이지 않도록 필터

- **01 · 무슨 뜻?** 사용자마다 읽을 수 있는 비공개 문서를 분리하는 것.
- **02 · 왜 고민해?** RAG 검색에서도 계좌 조회와 같은 접근 통제가 필요해.
- **03 · 은행에서라면** 다른 사용자의 개인 계약 문서를 검색 대상에서 배제.

## PART 05. LangGraph 기본 아키텍처

*상태·노드·라우팅을 명확하게 설계*

### 5.1 [11] LangGraph Basic

#### 05-01-01 StateGraph ★

- **01 · 무슨 뜻?** 노드와 연결선, 상태를 가진 LangGraph 작업 흐름의 기본 틀.
- **02 · 왜 고민해?** 대화와 Tool을 단계별로 관리하려고.
- **03 · 은행에서라면** 질문 분류 → 조회 → 답변 Graph.

#### 05-01-02 State 스키마

- **01 · 무슨 뜻?** Graph 전체가 공유할 데이터 필드의 구조.
- **02 · 왜 고민해?** 노드마다 무엇을 읽고 바꾸는지 정해 혼란을 줄여.
- **03 · 은행에서라면** `intent`, `product_id`, `messages`, `status`.

#### 05-01-03 Node ★

- **01 · 무슨 뜻?** Graph 안에서 한 가지 처리를 맡는 함수 단위.
- **02 · 왜 고민해?** 기능을 작게 나누면 테스트·수정하기 쉬워.
- **03 · 은행에서라면** `classify_intent` 노드.

#### 05-01-04 Edge

- **01 · 무슨 뜻?** 한 노드 다음에 어느 노드가 실행될지 연결하는 선.
- **02 · 왜 고민해?** 정해진 처리 순서를 코드로 표현하려고.
- **03 · 은행에서라면** 분류 노드 → Tool 실행 노드.

#### 05-01-05 Conditional Edge ★

- **01 · 무슨 뜻?** 상태에 따라 다음 노드를 다르게 고르는 조건부 연결.
- **02 · 왜 고민해?** 사용자 요청마다 필요한 처리가 다르기 때문이야.
- **03 · 은행에서라면** `intent=CALC`면 계산 노드, `RAG`면 검색 노드.

#### 05-01-06 START / END

- **01 · 무슨 뜻?** Graph 시작점과 종료점을 지정하는 표시.
- **02 · 왜 고민해?** 대화 한 턴의 실행 범위와 종료 조건을 명확히 하려고.
- **03 · 은행에서라면** `START → router → answer → END`.

#### 05-01-07 Graph Compile / Invoke

- **01 · 무슨 뜻?** Graph를 실행 가능한 객체로 만들고 호출하는 절차.
- **02 · 왜 고민해?** 설계한 노드를 실제 동작으로 검증하기 위해서야.
- **03 · 은행에서라면** `compile()` 후 사용자 메시지로 `invoke()`.

#### 05-01-08 노드 간 데이터 전달

- **01 · 무슨 뜻?** 이전 노드의 결과가 다음 노드에 어떻게 전달되는지 정하는 것.
- **02 · 왜 고민해?** 빠진 State나 타입 불일치로 흐름이 끊기지 않게 하려고.
- **03 · 은행에서라면** 검색 노드가 `docs`를 저장하고 답변 노드가 읽음.

### 5.2 [13] Memory & State

#### 05-02-01 MessagesState

#### 05-02-02 사용자 정의 State

- **02 · 왜 고민해?** 승인 대기 중 화면을 닫아도 이어갈지 결정하려고.

#### 05-02-05 Store

- **01 · 무슨 뜻?** 대화 한 스레드를 넘어 재사용할 정보를 저장하는 공간.
- **02 · 왜 고민해?** 장기 선호도 등 어떤 정보가 지속될지 구분해야 해.
- **03 · 은행에서라면** 즐겨 찾는 상품 유형을 별도 저장할지 검토.

- **03 · 은행에서라면** 사용자별 채팅방마다 다른 `thread_id` 사용.

- **02 · 왜 고민해?** 체크포인터의 값이 실제 잔액·계약 원본이 되면 안 돼.
- **03 · 은행에서라면** `selected_product`는 State, 실제 가입 계약은 DB.

#### 05-04-05 Tool 실행 전 검증

- **01 · 무슨 뜻?** 위험한 Tool을 부르기 직전에 조건을 검사하는 것.

### 5.5 Graph 입출력 계약

#### 05-05-01 Graph 입력값 명세

- **02 · 왜 고민해?** 프런트엔드와 에이전트 서버가 같은 형식을 써야 해.
- **03 · 은행에서라면** `message`, `thread_id` 등 입력 계약 정의.

- **02 · 왜 고민해?** 프런트엔드가 결과를 안정적으로 화면에 표시하려고.

- **01 · 무슨 뜻?** 사용자에게 필요한 정보만 결과로 전달하는 것.
- **02 · 왜 고민해?** 내부 상태 노출은 보안과 유지보수에 불리해.
- **03 · 은행에서라면** Tool 원문·내부 DB 키 전부를 표시하지 않기.

#### 05-05-06 스트리밍 중간 상태와 최종 응답 구분

- **01 · 무슨 뜻?** 중간 진행 알림과 최종 확정 결과를 구별하는 것.
- **02 · 왜 고민해?** 진행 중인 ‘조회 중’을 완료로 오인하지 않게 하려고.
- **03 · 은행에서라면** “금리 확인 중…”과 “계산 완료”를 다른 이벤트로.

- **01 · 무슨 뜻?** 추가 인증·실행·완료·취소 등의 상태를 정의하는 것.
- **02 · 왜 고민해?** 실행 허용과 재개·종료 조건을 명확히 하려고.
- **03 · 은행에서라면** `AWAITING_AUTH` → `EXECUTING` → `DONE`.

#### 05-06-03 상태 전이 허용/거부 규칙

- **01 · 무슨 뜻?** 어떤 상태에서 다음 상태로 갈 수 있는지 규칙을 만드는 것.
- **02 · 왜 고민해?** 승인 없이 실행 상태로 점프하지 못하게 하려고.
- **03 · 은행에서라면** `AWAITING_APPROVAL`에서 ‘승인’일 때만 다음 단계.

#### 05-06-04 상품·금액·계좌 변경 시 확인 상태 무효화 ★

- **01 · 무슨 뜻?** 사용자가 금액이나 계좌를 바꾸면 이전 확인을 취소하는 것.
- **02 · 왜 고민해?** 승인받은 내용과 실제 실행 내용이 달라질 위험이 있어.
- **03 · 은행에서라면** 승인 후 계좌 변경 → 승인 초기화.

#### 05-06-05 상태별 Tool 실행 허용 범위

- **01 · 무슨 뜻?** 각 작업 상태에서 호출할 수 있는 Tool을 제한하는 것.
- **02 · 왜 고민해?** 순서가 어긋난 실행을 막으려고.
- **03 · 은행에서라면** `COLLECTING_INPUT` 중엔 가입 실행 Tool 사용 금지.

#### 05-06-06 장기 중단·재접속·새 채팅 처리

- **01 · 무슨 뜻?** 오래 멈췄다 돌아오거나 새 채팅을 열었을 때 처리하는 것.
- **02 · 왜 고민해?** 예전 금리·승인·로그인 상태를 계속 믿으면 안 돼.
- **03 · 은행에서라면** 하루 지난 가입 대기는 재검증·재승인.

## PART 06. LangGraph Agentic Workflow 패턴

*반복·병렬·계획·승인을 비교*

### 6.1 [17] Reflection / Evaluator-Optimizer

#### 06-01-01 초안 생성

- **01 · 무슨 뜻?** LLM이 최초 답안을 만드는 단계.
- **02 · 왜 고민해?** 평가·개선할 초안이 있어야 다음 단계가 의미 있어.
- **03 · 은행에서라면** 상품 약관 초안 설명 생성.

#### 06-01-02 결과 평가

- **01 · 무슨 뜻?** 초안이 요구사항과 근거에 맞는지 검사하는 단계.
- **02 · 왜 고민해?** 잘못된 답을 그대로 사용자에게 내보내지 않으려고.
- **03 · 은행에서라면** 약관 문구·출처·금리 숫자 일치 여부 검사.

#### 06-01-03 피드백 및 수정

- **01 · 무슨 뜻?** 평가 결과를 바탕으로 답변을 고치는 단계.
- **02 · 왜 고민해?** 고칠 수 있는 오류에만 추가 비용을 쓰기 위해서야.
- **03 · 은행에서라면** “근거 없음” 피드백 후 답변 문장 수정.

#### 06-01-04 반복 개선 종료 기준

- **01 · 무슨 뜻?** 수정 시도를 몇 번까지 할지 결정하는 것.
- **02 · 왜 고민해?** 무한 반복과 비용 증가를 막으려고.
- **03 · 은행에서라면** 2회 수정 후에도 불확실하면 답변 유보.

#### 06-01-05 금융 답변 검증에 적용 가능성

- **01 · 무슨 뜻?** Reflection을 금리·약관 설명 검증에 적용할지 검토하는 것.
- **02 · 왜 고민해?** 설명에는 유용해도 거래를 다시 실행하는 데 쓰면 위험해.
- **03 · 은행에서라면** 답변만 재생성하고 가입 Tool은 재실행하지 않기.

### 6.2 [18] Parallelization

#### 06-02-01 병렬 노드 실행

- **01 · 무슨 뜻?** 독립적인 Graph 노드를 동시에 처리하는 방식.
- **02 · 왜 고민해?** 순차 실행보다 빠르게 응답할 수 있는지 검토하려고.
- **03 · 은행에서라면** 두 상품의 정보 조회를 동시 실행.

#### 06-02-02 병렬 Tool 호출

- **01 · 무슨 뜻?** 여러 도구를 동시에 호출하는 것.
- **02 · 왜 고민해?** 서로 의존하지 않는 조회를 빠르게 모으려고.
- **03 · 은행에서라면** A상품과 B상품의 금리를 각각 조회.

#### 06-02-03 병렬 검색

- **01 · 무슨 뜻?** 서로 다른 문서 검색을 동시에 진행하는 것.
- **02 · 왜 고민해?** 복합 질문에서 검색 시간을 줄일 수 있어.
- **03 · 은행에서라면** 가입 조건과 중도 해지 조항 검색을 동시에 수행.

#### 06-02-04 병렬 결과 병합

- **01 · 무슨 뜻?** 병렬 결과를 하나의 답으로 정리하는 과정.
- **02 · 왜 고민해?** 결과의 상품 ID·기준 시점이 섞이지 않게 해야 해.
- **03 · 은행에서라면** 상품별 검색 결과를 구분해 비교표 생성.

#### 06-02-05 순차 처리 대비 효과

- **01 · 무슨 뜻?** 병렬화로 얻는 시간 단축과 복잡도 증가를 비교하는 것.
- **02 · 왜 고민해?** 호출 수가 늘고 결과 병합 오류도 생길 수 있어.
- **03 · 은행에서라면** 병렬 2개와 순차 2개의 속도·정확도 측정.

### 6.3 [19] Orchestrator-Worker

#### 06-03-01 작업 분해

- **01 · 무슨 뜻?** 복잡한 요청을 여러 작은 작업으로 쪼개는 것.
- **02 · 왜 고민해?** 한 에이전트가 모든 과정을 한 번에 풀기 어렵기 때문이야.
- **03 · 은행에서라면** 금리 확인·약관 설명·이자 계산으로 분해.

#### 06-03-02 Orchestrator 역할

- **01 · 무슨 뜻?** 어떤 하위 작업을 만들고 배분할지 결정하는 관리자 역할.
- **02 · 왜 고민해?** 작업들 사이의 목표와 순서를 통제하려고.
- **03 · 은행에서라면** ‘비교 요청’을 분석해 A/B 상품 조회 작업 생성.

#### 06-03-03 Worker 역할

- **01 · 무슨 뜻?** 실제로 개별 하위 작업을 처리하는 구성요소.
- **02 · 왜 고민해?** 각 작업을 독립적으로 만들면 재사용·테스트가 쉬워.
- **03 · 은행에서라면** 각 상품의 금리를 읽는 Worker.

#### 06-03-04 작업별 결과 통합

- **01 · 무슨 뜻?** 여러 Worker 결과를 종합하는 것.
- **02 · 왜 고민해?** 각각 답만 내면 사용자는 전체 결론을 얻기 어려워.
- **03 · 은행에서라면** 두 상품의 금리·조건을 한 표로 비교.

#### 06-03-05 복합 금융 요청 적용 가능성

- **01 · 무슨 뜻?** 은행 복합 요청에 이 패턴이 필요한지 검토하는 것.
- **02 · 왜 고민해?** 작은 서비스에는 작업 분해가 과한 구조일 수 있어.
- **03 · 은행에서라면** 두 상품 조회만 필요하면 단순 병렬 Tool로 충분할 수도.

### 6.4 [20] Plan-and-Execute

#### 06-04-01 작업 계획 생성 (Planner)

- **01 · 무슨 뜻?** 목표 달성을 위한 순서를 모델이 먼저 계획하는 역할.
- **02 · 왜 고민해?** 단계가 다양하고 예측하기 어려운 요청에 적합한지 살펴봐.
- **03 · 은행에서라면** ‘상품 비교 후 계산’의 단계 목록 작성.

#### 06-04-02 계획에 따른 단계별 실행 (Executor)

- **01 · 무슨 뜻?** 계획의 단계들을 실제로 수행하는 역할.
- **02 · 왜 고민해?** 계획과 실행을 분리하면 검증 지점을 만들 수 있어.
- **03 · 은행에서라면** 계획된 상품 조회 Tool을 순서대로 호출.

#### 06-04-03 실행 결과에 따른 재계획 (Replanner)

- **01 · 무슨 뜻?** 실행 결과가 달라지면 계획을 수정하는 역할.
- **02 · 왜 고민해?** 없는 상품·누락 데이터가 나왔을 때 경로를 바꾸려고.
- **03 · 은행에서라면** A상품 없음 → 다른 후보 제시로 계획 수정.

#### 06-04-04 고정 Workflow와 비교 ★

- **01 · 무슨 뜻?** AI가 만드는 계획과 개발자가 미리 정한 고정 흐름 비교.
- **02 · 왜 고민해?** 가입 같은 쓰기 작업에는 고정 절차가 더 적합할 수 있어.
- **03 · 은행에서라면** 검색은 유연하게, 가입은 정해진 검증 순서로.

#### 06-04-05 실행 비용 및 복잡도 검토

- **01 · 무슨 뜻?** 계획 단계마다 모델을 호출하는 비용과 관리 부담 평가.
- **02 · 왜 고민해?** 단순 요청에 Planner까지 붙이면 느려질 수 있어.
- **03 · 은행에서라면** 한 번의 상품 조회에 계획 노드가 필요한지 비교.

#### 06-04-06 위험한 실행 계획을 검증하는 기준

- **01 · 무슨 뜻?** 모델이 제안한 작업 계획 자체를 실행 전에 검증하는 것.
- **02 · 왜 고민해?** 금지된 쓰기 Tool이나 인증 생략 경로가 포함될 수 있어.
- **03 · 은행에서라면** “승인 없이 가입” 계획은 실행 전에 거부.

#### 06-04-07 완료·중단·계획 반복 종료 조건

- **01 · 무슨 뜻?** 작업이 언제 끝나고 언제 포기해야 하는지 정하는 것.
- **02 · 왜 고민해?** 계획 수정이 계속 반복되는 루프를 막으려고.
- **03 · 은행에서라면** 최대 3단계 재계획 후 근거 없으면 중단.

### 6.5 [21] Human-in-the-Loop

#### 06-05-01 사용자 승인 요청

- **01 · 무슨 뜻?** 사용자에게 실행해도 되는지 분명히 묻는 단계.
- **02 · 왜 고민해?** AI가 임의로 모의 가입을 확정하지 않게 하기 위해서야.
- **03 · 은행에서라면** “이 조건으로 가입할까요?” 승인 버튼.

#### 06-05-02 실행 전 정보 확인 ★

- **01 · 무슨 뜻?** 승인 전 정확한 상품·금액·기간·계좌를 보여주는 것.
- **02 · 왜 고민해?** 사용자가 무엇을 허락하는지 알 수 있어야 해.
- **03 · 은행에서라면** 상품 A, 100만 원, 6개월을 요약.

#### 06-05-03 interrupt / resume ★

- **01 · 무슨 뜻?** Graph 실행을 멈춰 확인을 받고 같은 지점에서 이어가는 기능.
- **02 · 왜 고민해?** 승인 대기를 작업 흐름 안에서 표현하려고.
- **03 · 은행에서라면** `interrupt()` 후 사용자 승인 시 `resume`.

#### 06-05-04 승인·거절·수정 분기

- **01 · 무슨 뜻?** 승인·거절·조건 수정의 경우를 분리하는 것.
- **02 · 왜 고민해?** 모든 입력을 ‘진행’으로 취급하면 위험하기 때문이야.
- **03 · 은행에서라면** 거절은 종료, 수정은 다시 검증 단계로 이동.

#### 06-05-05 가입·해지·이체 전 최종 확인

- **01 · 무슨 뜻?** 중요 업무를 시작하기 직전에 마지막 확인을 두는 것.
- **02 · 왜 고민해?** 조회와 달리 실제 업무 상태가 바뀌기 때문이야.
- **03 · 은행에서라면** 가입·해지·이체 전에 확인 화면.

#### 06-05-06 사용자 승인과 서버 인증 분리 ★

- **01 · 무슨 뜻?** 동의 버튼과 비밀번호/PIN 등 재인증을 다른 것으로 취급하는 것.
- **02 · 왜 고민해?** ‘하고 싶다’는 의사와 ‘본인이다’는 증명이 달라.
- **03 · 은행에서라면** 승인 후 별도 `step-up` 인증 검증.

#### 06-05-07 승인 내용 변경 시 재확인

- **01 · 무슨 뜻?** 확인한 조건이 바뀌면 기존 승인을 무효화하는 것.
- **02 · 왜 고민해?** 사용자 뜻과 다른 내용으로 실행하지 않게 하려고.
- **03 · 은행에서라면** 100만 원 승인 후 200만 원으로 바꾸면 재승인.

#### 06-05-08 승인 만료 / 중복 승인 방지

- **01 · 무슨 뜻?** 한 번 준 승인에 유효시간과 1회 사용 제한을 둘지 정하는 것.
- **02 · 왜 고민해?** 오래된 승인이나 반복 클릭으로 중복 실행을 막으려고.
- **03 · 은행에서라면** 승인 토큰 소진 후 두 번째 가입 시도 거부.

### 6.6 [22] Time Travel

#### 06-06-01 State Snapshot

- **01 · 무슨 뜻?** 특정 순간에 저장된 Graph 상태의 복사본.
- **02 · 왜 고민해?** 어떤 단계에서 값이 바뀌었는지 조사할 수 있어.
- **03 · 은행에서라면** 상품 선택 직후의 State 확인.

#### 06-06-02 이전 Checkpoint 복원

- **01 · 무슨 뜻?** 예전 체크포인트 상태를 불러오는 것.
- **02 · 왜 고민해?** 버그가 난 흐름을 다시 분석하기 좋아.
- **03 · 은행에서라면** 승인 직전 State를 테스트 환경에서 복원.

#### 06-06-03 특정 지점에서 재실행

- **01 · 무슨 뜻?** 이전 시점부터 Graph를 다시 돌리는 기능.
- **02 · 왜 고민해?** 노드 동작을 비교하거나 수정 사항을 재검증하려고.
- **03 · 은행에서라면** 검색 노드를 새 버전으로 재실행해 답변 비교.

#### 06-06-04 디버깅 및 시뮬레이션 활용

- **01 · 무슨 뜻?** 저장된 상태를 활용해 문제를 재현하는 것.
- **02 · 왜 고민해?** 실패 원인을 추측하지 않고 확인할 수 있어.
- **03 · 은행에서라면** ‘잘못된 상품 선택’ 당시의 상태 재현.

#### 06-06-05 금융 작업 재실행 위험 검토

- **01 · 무슨 뜻?** 되감기 이후 쓰기 Tool이 다시 실행될 위험을 확인하는 것.
- **02 · 왜 고민해?** 금융 업무는 재생 시 중복 계약·출금이 생길 수 있어.
- **03 · 은행에서라면** 실거래 대신 모의 환경과 읽기 Tool만 재실행.

### 6.7 패턴 선택 원칙

#### 06-07-01 정해진 처리 흐름과 자율 계획 실행 분리

- **01 · 무슨 뜻?** 미리 정한 절차와 모델이 자유롭게 만든 계획을 구별하는 것.
- **02 · 왜 고민해?** 안전한 확정 작업까지 모델 자율 판단에 맡기지 않으려고.
- **03 · 은행에서라면** 가입 승인 순서는 고정, 상품 탐색은 동적.

#### 06-07-02 Reflection 재시도에서 쓰기 Tool 제외 기준

- **01 · 무슨 뜻?** 답변 개선을 위해 반복할 때 실제 쓰기 Tool은 빼는 것.
- **02 · 왜 고민해?** 답변 재작성 중 계약이 중복 생성되면 안 돼.
- **03 · 은행에서라면** Reflection 반복에서는 설명 노드만 재실행.

#### 06-07-03 병렬 실행 가능한 조회 작업만 병렬화할지 판단

- **01 · 무슨 뜻?** 독립적인 조회만 병렬로 실행할지 결정하는 것.
- **02 · 왜 고민해?** 동시에 같은 잔액을 변경하는 작업은 충돌할 수 있어.
- **03 · 은행에서라면** A/B 상품 금리 조회는 병렬, 같은 계좌 출금은 통제.

#### 06-07-04 중복 실행이 가능한 노드와 불가능한 노드 구분

- **01 · 무슨 뜻?** 다시 실행해도 안전한 노드와 위험한 노드를 나누는 것.
- **02 · 왜 고민해?** 장애 복구·타임트래블 설계의 기준이 돼.
- **03 · 은행에서라면** 문서 검색은 재실행 가능, 가입 Tool은 결과 확인 우선.

#### 06-07-05 실행 완료 기록과 Graph 재시작 시점 연결

- **01 · 무슨 뜻?** 서버의 실제 업무 완료 기록과 Graph 재시작을 연결하는 것.
- **02 · 왜 고민해?** Graph만 멈췄다고 업무가 취소된 것은 아닐 수 있어.
- **03 · 은행에서라면** 가입 결과가 저장됐으면 ‘완료’ State로 복구.

## PART 07. Multi-Agent 아키텍처

*하나의 Agent면 충분한지 먼저 검토*

### 7.1 [24] Subgraph

#### 07-01-01 기능별 Subgraph 분리

- **01 · 무슨 뜻?** 큰 Graph 안에서 특정 업무 흐름을 별도 작은 Graph로 나누는 것.
- **02 · 왜 고민해?** 커진 Graph를 읽고 테스트하기 쉽게 만들 수 있어.
- **03 · 은행에서라면** 상품 설명 Subgraph와 가입 Subgraph 분리.

#### 07-01-02 상위 Graph와 연결

- **01 · 무슨 뜻?** 작은 Graph를 전체 Agent의 처리 흐름에 연결하는 것.
- **02 · 왜 고민해?** 각 기능을 하나의 서비스처럼 통합하려고.
- **03 · 은행에서라면** Router → 상품 검색 Subgraph → 답변.

#### 07-01-03 State 전달 및 공유

- **01 · 무슨 뜻?** 상위 Graph와 하위 Graph가 어떤 State를 주고받을지 정하는 것.
- **02 · 왜 고민해?** 공유할 필요 없는 내부 정보를 밖으로 노출하지 않으려고.
- **03 · 은행에서라면** 상품 ID만 전달하고 내부 검색 결과는 하위에서 관리.

#### 07-01-04 RAG 전용 Subgraph

- **01 · 무슨 뜻?** 문서 검색·근거 생성만 담당하는 Subgraph를 만들지 검토하는 것.
- **02 · 왜 고민해?** RAG 검색 단계가 복잡해졌을 때 별도 관리가 편해.
- **03 · 은행에서라면** 질문 재작성 → 검색 → 근거 검증을 묶기.

#### 07-01-05 상품 조회·가입 Subgraph

- **01 · 무슨 뜻?** 상품 조회와 가입 절차를 별도 Subgraph로 나눌지 정하는 것.
- **02 · 왜 고민해?** 읽기·쓰기는 권한과 테스트 기준이 다르기 때문이야.
- **03 · 은행에서라면** 조회 Subgraph는 자유 검색, 가입은 고정 승인 절차.

#### 07-01-06 Subgraph 입력·출력 State 변환

- **01 · 무슨 뜻?** 상위·하위 Graph의 필드 이름과 자료형을 서로 맞추는 것.
- **02 · 왜 고민해?** 서로 다른 State Schema를 바로 합치면 오류가 나.
- **03 · 은행에서라면** 상위 `item_id`를 하위 `product_id`로 매핑.

#### 07-01-07 Subgraph Streaming 및 이벤트 전달

- **01 · 무슨 뜻?** 하위 Graph 진행 상황을 화면이나 상위 Graph에 전달하는 것.
- **02 · 왜 고민해?** 긴 작업이 어디까지 진행됐는지 알려주기 위해서야.
- **03 · 은행에서라면** “약관 검색 중”, “조건 확인 중” 이벤트 전달.

### 7.2 [25] Supervisor

#### 07-02-01 Supervisor Agent 역할

- **01 · 무슨 뜻?** 여러 전문 에이전트 중 누가 일을 맡을지 정하는 관리자 에이전트.
- **02 · 왜 고민해?** 업무 영역이 늘 때 통합 창구를 만들 수 있어.
- **03 · 은행에서라면** 질문을 상품 담당 또는 카드 담당에 위임.

#### 07-02-02 전문 Agent 선택

- **01 · 무슨 뜻?** 질문에 맞는 전문 에이전트를 선택하는 것.
- **02 · 왜 고민해?** 잘못 맡기면 불필요한 도구를 쓰거나 답이 틀려.
- **03 · 은행에서라면** “적금 이자”는 상품 Agent, “카드 상태”는 카드 Agent.

#### 07-02-03 작업 위임

- **01 · 무슨 뜻?** 관리자가 하위 Agent에 구체적인 작업을 전달하는 것.
- **02 · 왜 고민해?** 누가 어떤 데이터와 권한으로 일할지 명확히 하려고.
- **03 · 은행에서라면** 상품 Agent에 “A적금 조건 조회”만 위임.

#### 07-02-04 결과 취합

- **01 · 무슨 뜻?** 전문 Agent의 답변을 취합해 최종 응답하는 것.
- **02 · 왜 고민해?** 각 Agent가 답했을 때 중복·모순을 정리해야 해.
- **03 · 은행에서라면** 상품 조건과 연결 계좌 정보를 함께 안내.

#### 07-02-05 Supervisor 패턴의 필요성

- **01 · 무슨 뜻?** Supervisor가 단일 Router보다 나은지 판단하는 것.
- **02 · 왜 고민해?** 에이전트가 많아질수록 비용과 오류 지점도 늘어.
- **03 · 은행에서라면** 상품 기능만 있다면 단순 Router가 더 쉬울 수 있어.

#### 07-02-06 전문 Agent 위임 Tool 구성 및 한계

- **01 · 무슨 뜻?** 전문 Agent를 호출하는 Tool과 권한 범위를 정하는 것.
- **02 · 왜 고민해?** 위임 과정에서 원래 요청의 권한을 넘지 않게 하려고.
- **03 · 은행에서라면** 상품 Agent에 이체 실행 Tool은 제공하지 않기.

### 7.3 [26] Handoff

#### 07-03-01 Agent 간 작업 이관

- **01 · 무슨 뜻?** 한 에이전트가 진행하던 일을 다른 에이전트에게 넘기는 것.
- **02 · 왜 고민해?** 대화 중 담당 업무가 바뀔 수 있어서야.
- **03 · 은행에서라면** 상품 상담 도중 카드 관련 질문을 카드 Agent에 이관.

#### 07-03-02 Handoff 조건

- **01 · 무슨 뜻?** 어떤 상황에서 다른 Agent로 넘길지 조건을 정하는 것.
- **02 · 왜 고민해?** 필요 없이 왕복 위임하면 대화가 길어져.
- **03 · 은행에서라면** 상품 담당이 카드 청구 문의를 받으면 이관.

#### 07-03-03 컨텍스트 전달

- **01 · 무슨 뜻?** 다음 에이전트에게 필요한 정보만 함께 보내는 것.
- **02 · 왜 고민해?** 맥락이 끊기면 사용자가 다시 설명해야 할 수 있어.
- **03 · 은행에서라면** 현재 질문·선택 카드만 전달, 불필요한 PIN은 제외.

#### 07-03-04 작업 소유권 및 책임

- **01 · 무슨 뜻?** 이관 전후 누구에게 처리 책임이 있는지 정하는 것.
- **02 · 왜 고민해?** 실패·승인·실행 상태가 모호해지지 않게 하려고.
- **03 · 은행에서라면** 카드 Agent가 받은 뒤 카드 API 책임을 가짐.

#### 07-03-05 Handoff 이후 결과 처리

- **01 · 무슨 뜻?** 이관된 작업 결과를 다시 어디로 돌려줄지 정하는 것.
- **02 · 왜 고민해?** 대화가 중간에 끝나거나 중복 답변하지 않게 하려고.
- **03 · 은행에서라면** 카드 Agent 결과를 원래 대화에 요약해 반환.

### 7.4 전체 Multi-Agent 구조 비교

#### 07-04-01 Single Agent ★

- **01 · 무슨 뜻?** 한 개의 Agent가 Tool을 모두 선택해서 처리하는 구조.
- **02 · 왜 고민해?** 초기 개발에서 가장 단순한 비교 기준이야.
- **03 · 은행에서라면** 상품 DB·RAG·계산 Tool을 한 Agent에 연결.

#### 07-04-02 Router + 단일 Agent

- **01 · 무슨 뜻?** 먼저 요청을 분류하고 필요한 단일 Agent를 호출하는 구조.
- **02 · 왜 고민해?** 단순 Router만으로 복잡한 감독자가 필요한지 비교하려고.
- **03 · 은행에서라면** 상품 문의만 상품 Agent로 전달.

#### 07-04-03 Supervisor + 전문 Agent

- **01 · 무슨 뜻?** Supervisor가 여러 전문 에이전트를 제어하는 구조.
- **02 · 왜 고민해?** 업무 영역이 많아질 때 관리 이점을 얻을 수 있는지 보려고.
- **03 · 은행에서라면** 상품·카드·거래 에이전트를 감독.

#### 07-04-04 Orchestrator-Worker

- **01 · 무슨 뜻?** 작업을 분해해 여러 Worker에게 시키는 구조.
- **02 · 왜 고민해?** ‘여러 영역 담당자’와 ‘작업 병렬 분해’를 구분하려고.
- **03 · 은행에서라면** 상품 두 개 비교를 개별 Worker에 나눔.

#### 07-04-05 Subgraph 기반 모듈형 Agent

- **01 · 무슨 뜻?** 업무별 작은 Graph를 조립한 구조.
- **02 · 왜 고민해?** Agent 개수를 늘리지 않고도 코드 모듈화를 할 수 있어.
- **03 · 은행에서라면** 하나의 Graph 안에 RAG·가입 Subgraph 구성.

#### 07-04-06 복잡도 대비 성능 및 유지보수 비교 ★

- **01 · 무슨 뜻?** 구현·지연·오류·수정 난이도를 비교하는 것.
- **02 · 왜 고민해?** 멋있어 보이는 복잡한 구조가 항상 좋은 건 아니야.
- **03 · 은행에서라면** 단일 Agent와 Supervisor의 실행 시간·유지보수 비교.

#### 07-04-07 Agent 간 반복 위임·무한 루프 방지

- **01 · 무슨 뜻?** 서로에게 작업을 넘기며 끝없이 반복하지 않게 하는 것.
- **02 · 왜 고민해?** 멀티 에이전트는 위임 루프가 생길 수 있어.
- **03 · 은행에서라면** 최대 Handoff 횟수와 담당자 결정 규칙 설정.

## PART 08. Memory 및 대화 관리

*챗봇 기억과 금융 업무 상태를 분리*

### 8.1 [03] Conversation Memory

#### 08-01-01 대화 이력 저장

- **01 · 무슨 뜻?** 이전 사용자·AI 메시지를 저장하는 것.
- **02 · 왜 고민해?** 후속 질문의 대화 맥락을 유지하려고.
- **03 · 은행에서라면** “그 예금”을 알기 위해 이전 메시지 확인.

#### 08-01-02 Short-term Memory

- **01 · 무슨 뜻?** 현재 대화에서 잠시 유지할 정보.
- **02 · 왜 고민해?** 채팅 턴 사이의 선택 상품·진행 상황을 이어주려고.
- **03 · 은행에서라면** 이번 대화의 선택 상품과 6개월 기간.

#### 08-01-03 Long-term Memory

- **01 · 무슨 뜻?** 대화가 끝난 뒤에도 쓸 정보를 따로 관리하는 것.
- **02 · 왜 고민해?** 지속할 가치가 있는 정보와 지우지 말아야 할 정보를 구분해야 해.
- **03 · 은행에서라면** 사용자가 명시적으로 저장한 선호 상품 유형만 검토.

#### 08-01-04 대화 요약 및 컨텍스트 압축

- **01 · 무슨 뜻?** 긴 대화를 요약하거나 오래된 문맥을 줄이는 것.
- **02 · 왜 고민해?** 토큰을 낭비하지 않고 중요한 상태만 유지하려고.
- **03 · 은행에서라면** 20턴 대화를 선택 상품·현재 금액·남은 질문으로 정리.

### 8.2 [31] PostgreSQL Checkpointer

#### 08-02-01 In-memory Checkpointer와 비교 ★

- **01 · 무슨 뜻?** 프로세스 메모리에만 저장하는 방식과 DB 저장 방식 비교.
- **02 · 왜 고민해?** 서버가 재시작되면 메모리 상태가 사라질 수 있어.
- **03 · 은행에서라면** MemorySaver는 개발용, DB 저장은 복구용으로 비교.

#### 08-02-02 PostgreSQL 기반 State 저장

- **01 · 무슨 뜻?** Graph Checkpoint를 PostgreSQL 같은 DB에 보존하는 것.
- **02 · 왜 고민해?** 승인 대기 등 장시간 작업을 이어갈 수 있게 하려고.
- **03 · 은행에서라면** 중단한 상품 가입 흐름을 DB에서 복원.

#### 08-02-03 대화 세션 복구

- **01 · 무슨 뜻?** 사용자가 다시 접속했을 때 이전 Graph 상태를 읽는 것.
- **02 · 왜 고민해?** 모든 작업을 처음부터 반복하지 않게 할 수 있어.
- **03 · 은행에서라면** 가입 확인 전 화면으로 안전하게 복귀.

#### 08-02-04 사용자별 대화 격리

- **01 · 무슨 뜻?** 서로 다른 사용자의 저장된 대화가 섞이지 않도록 하는 것.
- **02 · 왜 고민해?** 금융 대화는 개인 정보가 포함될 수 있기 때문이야.
- **03 · 은행에서라면** `user_id`와 `thread_id`의 권한 검증.

#### 08-02-05 저장된 대화의 보존·삭제

- **01 · 무슨 뜻?** 대화 기록을 언제 삭제하고 무엇을 보존할지 정하는 것.
- **02 · 왜 고민해?** 체크포인트에 민감 정보가 남아 있으면 개인정보 문제가 생겨.
- **03 · 은행에서라면** 탈퇴 시 대화 State 삭제 정책 따로 정하기.

### 8.3 은행 서비스 대화 State

#### 08-03-01 현재 선택한 상품

- **01 · 무슨 뜻?** 현재 대화에서 설명·가입 대상으로 선택한 상품.
- **02 · 왜 고민해?** 다음 질문이 어느 상품에 관한 것인지 알아야 해.
- **03 · 은행에서라면** `selected_product_id = prod_01`.

#### 08-03-02 예치금 / 월 납입액

- **01 · 무슨 뜻?** 예금 원금 또는 적금 월 납입액.
- **02 · 왜 고민해?** 금액이 없으면 이자 계산·가입 검증을 진행할 수 없어.
- **03 · 은행에서라면** `amount=100000`과 납입 유형 저장.

#### 08-03-03 가입 기간

- **01 · 무슨 뜻?** 상품에 가입하려는 개월 수.
- **02 · 왜 고민해?** 상품별 허용 기간과 예상 이자 계산에 필요해.
- **03 · 은행에서라면** `duration_months=12`.

#### 08-03-04 선택한 출금 계좌

- **01 · 무슨 뜻?** 사용자가 가입금 출금에 사용할 계좌.
- **02 · 왜 고민해?** 서버는 본인 소유·상태·잔액을 확인해야 해.
- **03 · 은행에서라면** `source_account_id=acc_03`.

#### 08-03-05 부족한 입력값

- **01 · 무슨 뜻?** 아직 사용자에게 받아야 하는 필수 정보 목록.
- **02 · 왜 고민해?** 한 번에 모든 정보를 묻지 않고 필요한 것만 물을 수 있어.
- **03 · 은행에서라면** `missing_slots=["duration_months"]`.

#### 08-03-06 진행 중인 작업 ★

- **01 · 무슨 뜻?** 현재 상품을 찾는 중인지 가입을 진행 중인지 등 업무 단계.
- **02 · 왜 고민해?** 다른 요청이 들어왔을 때 기존 작업을 이어갈지 판단하려고.
- **03 · 은행에서라면** `workflow=SUBSCRIPTION`, `step=VERIFY`.

#### 08-03-07 사용자 승인 상태

- **01 · 무슨 뜻?** 사용자가 무엇을 확인하고 승인했는지 상태.
- **02 · 왜 고민해?** 실행 단계에 넘어가도 되는지 판단하려고.
- **03 · 은행에서라면** 상품·금액 조건에 대한 승인 기록 참조.

#### 08-03-08 로그인 및 세션 변경 시 상태 처리

- **01 · 무슨 뜻?** 로그인 상태나 세션이 변경됐을 때 현재 작업 처리.
- **02 · 왜 고민해?** 인증이 끝났는데 오래된 승인으로 실행하면 위험해.
- **03 · 은행에서라면** 로그아웃 시 가입 실행 대기 상태 폐기.

#### 08-03-09 작업 완료 후 State 초기화

- **01 · 무슨 뜻?** 업무 종료 뒤 임시 선택값을 어떻게 비울지 정하는 것.
- **02 · 왜 고민해?** 완료된 가입 금액이 다음 요청에 잘못 쓰이지 않게 하려고.
- **03 · 은행에서라면** 가입 성공 뒤 임시 승인·금액 Slot 초기화.

### 8.4 State 수명주기·재개 정책

#### 08-04-01 사용자 ID와 thread_id 연결 정책

- **01 · 무슨 뜻?** 로그인 사용자와 하나의 채팅 흐름을 어떻게 연결할지 정하는 것.
- **02 · 왜 고민해?** 사용자 데이터 격리와 여러 채팅 구분이 필요해.
- **03 · 은행에서라면** 한 사용자에 여러 thread를 허용할지 결정.

#### 08-04-02 다중 탭·기기에서 동일 작업 충돌 처리

- **01 · 무슨 뜻?** 동일한 작업을 두 탭이나 기기에서 동시에 진행할 때 처리하는 것.
- **02 · 왜 고민해?** 같은 가입이 중복 실행될 수 있기 때문이야.
- **03 · 은행에서라면** 탭 A와 B가 모두 승인해도 계약은 한 번만 생성.

#### 08-04-03 로그아웃·세션 만료·계정 탈퇴 시 처리

- **01 · 무슨 뜻?** 로그아웃·인증 만료·탈퇴 때 저장된 대화 상태를 어떻게 처리하는 것.
- **02 · 왜 고민해?** 예전 상태로 보호된 Tool을 실행하지 못하도록 해야 해.
- **03 · 은행에서라면** 세션 만료 후 개인 잔액 조회는 다시 로그인 요구.

#### 08-04-04 작업 중 장기 중단 후 재개 시 조건 재검증

- **01 · 무슨 뜻?** 오래 중단한 작업의 예전 검증 결과를 다시 확인하는 것.
- **02 · 왜 고민해?** 금리·잔액·가입 자격이 달라졌을 수 있어.
- **03 · 은행에서라면** 일주일 지난 가입 준비 State는 조건 재조회.

#### 08-04-05 영속 저장할 State와 일회성 State 분리

- **01 · 무슨 뜻?** 오래 남길 값과 한 번만 쓸 임시 값을 구분하는 것.
- **02 · 왜 고민해?** 불필요한 개인정보 저장과 잘못된 재사용을 막아.
- **03 · 은행에서라면** 상품 후보는 잠시 보관, 일회용 인증 값은 보관 금지.

#### 08-04-06 Memory에 저장하지 않아야 할 자격 증명 구분

- **01 · 무슨 뜻?** 비밀번호·PIN·토큰 등 저장하면 위험한 값을 정의하는 것.
- **02 · 왜 고민해?** LLM 메모리가 인증정보의 보관소가 되면 안 돼.
- **03 · 은행에서라면** PIN 원문·비밀번호·세션 토큰을 State에 저장하지 않기.

#### 08-04-07 오래된 승인/인증 결과 무효화

- **01 · 무슨 뜻?** 승인·인증 결과를 오래 재사용하지 않도록 무효화하는 것.
- **02 · 왜 고민해?** 한 번의 작업에만 허용된 권한을 다른 작업에 쓰면 위험해.
- **03 · 은행에서라면** `step_up_challenge_id` 사용·만료 후 재인증.

### 9.2 [36] MCP

#### 09-02-01 MCP 도입 목적

- **01 · 무슨 뜻?** AI가 외부 도구·데이터에 연결하는 표준 방식인 MCP가 필요한지 결정하는 것.
- **02 · 왜 고민해?** 단순 REST Tool만 있어도 되는 경우가 있기 때문이야.
- **03 · 은행에서라면** 상품 API를 MCP Server로 감쌀 실익 비교.

#### 09-02-02 MCP Server / Client

- **01 · 무슨 뜻?** 도구를 제공하는 서버와 호출하는 클라이언트의 역할.
- **02 · 왜 고민해?** MCP를 쓰려면 양쪽의 연결·인증 흐름을 이해해야 해.
- **03 · 은행에서라면** MCP Server가 상품 조회 Tool 제공, Agent가 Client.

#### 09-02-03 MCP Tool 구성

- **01 · 무슨 뜻?** MCP를 통해 노출할 Tool과 입력 스키마를 정의하는 것.
- **02 · 왜 고민해?** 불필요한 관리자 작업까지 공개하지 않도록 하기 위해서야.
- **03 · 은행에서라면** 상품 검색만 공개, 계좌 수정은 별도 보호.

#### 09-02-04 기존 API Tool과 MCP 비교

- **01 · 무슨 뜻?** MCP를 쓰는 방법과 기존 API Tool을 직접 호출하는 방법 비교.
- **02 · 왜 고민해?** 기술을 추가할수록 인증·운영할 컴포넌트가 늘어.
- **03 · 은행에서라면** 현재 FastAPI 상품 조회를 직접 Tool로 쓰는 방식과 비교.

#### 09-02-05 서비스 내부 연동에 MCP가 필요한지

- **01 · 무슨 뜻?** 은행 프로젝트 내부 서비스 연결에 MCP가 꼭 필요한지 검토.
- **02 · 왜 고민해?** 새 기술 연습과 제품에 필요한 기술은 별도 문제야.
- **03 · 은행에서라면** 팀원 API가 REST라면 기존 방식이 더 간단할 수 있어.

#### 09-03-03 DB 조회 Tool

- **01 · 무슨 뜻?** DB를 직접 조회하는 도구.
- **02 · 왜 고민해?** 어떤 데이터는 서버 API보다 직접 조회가 편한지 검토하려고.

#### 09-03-04 MCP 기반 Tool

- **01 · 무슨 뜻?** MCP 프로토콜을 통해 제공된 도구.
- **02 · 왜 고민해?** 표준 도구 서버를 공유할 필요가 있는지 확인하려고.

#### 09-03-05 Tool 입출력 표준화

- **01 · 무슨 뜻?** 여러 연동 방식의 인자·결과 형식을 맞추는 것.
- **02 · 왜 고민해?** Graph가 Tool 종류마다 다르게 처리하지 않도록 하려고.
- **03 · 은행에서라면** 성공/실패를 공통 `status`로 반환.

#### 09-03-06 실행 결과와 오류 코드 전달

- **01 · 무슨 뜻?** 서버 오류 정보를 Agent와 화면에 어떻게 전달할지 정하는 것.
- **02 · 왜 고민해?** 사용자가 다음에 무엇을 해야 하는지 설명하려고.
- **03 · 은행에서라면** `ACCOUNT_SUSPENDED` → “정지 해제가 필요해요.”

#### 09-03-07 외부 시스템 장애 시 처리

- **01 · 무슨 뜻?** 외부 서버가 응답하지 않을 때 어떤 경로로 갈지 정하는 것.
- **02 · 왜 고민해?** 장애를 숨기거나 위험한 재시도를 하지 않기 위해서야.
- **03 · 은행에서라면** 원장 서버 장애 시 잔액을 추측하지 않기.

### 9.4 금융 서비스 데이터 소유권

#### 09-04-01 인증 파트: user_id 및 step-up 검증

- **01 · 무슨 뜻?** 회원 식별자·재인증 결과를 인증 파트가 소유한다는 기준.
- **02 · 왜 고민해?** 에이전트가 로그인 여부를 직접 만들어내지 않기 위해서야.
- **03 · 은행에서라면** `user_id`, `step_up_challenge_id`는 인증 서버 확인.

#### 09-04-02 계좌 파트: 계좌 상태 및 소유권

- **01 · 무슨 뜻?** 계좌가 누구 것이고 현재 어떤 상태인지 계좌 파트가 판단.
- **02 · 왜 고민해?** Agent가 계좌 상태를 임의로 변경·가정하면 안 돼.
- **03 · 은행에서라면** 일시정지 계좌는 거래 전 서버가 차단.

#### 09-04-03 거래 파트: 확정 잔액·원장·입출금

- **01 · 무슨 뜻?** 실제 잔액과 거래 기록의 원본을 거래 파트가 관리.
- **02 · 왜 고민해?** 여러 파트가 각자 잔액을 계산하면 불일치가 생길 수 있어.
- **03 · 은행에서라면** 이체 성공 뒤 원장 기준 잔액 조회.

#### 09-04-04 상품 파트: 상품·가입 계약

- **01 · 무슨 뜻?** 상품 정보와 가입 계약의 기준 데이터를 상품 파트가 관리.
- **02 · 왜 고민해?** Agent State를 계약 DB와 혼동하지 않게 하려고.
- **03 · 은행에서라면** 상품 가입 Tool은 상품 서버의 계약 생성 API 호출.

#### 09-04-05 카드 파트: 카드 상태 및 결제 계좌

- **01 · 무슨 뜻?** 카드 발급·정지·연결 계좌 등의 원본을 카드 파트가 관리.
- **02 · 왜 고민해?** 카드 조회가 계좌나 AI에서 임의로 바뀌면 안 돼.
- **03 · 은행에서라면** 카드 해지는 카드 API가 최종 상태 변경.

#### 09-04-06 에이전트가 각 파트 데이터를 직접 수정하지 않는 경계 ★

- **01 · 무슨 뜻?** AI가 각 도메인 테이블을 직접 수정하지 않도록 경계를 정하는 것.
- **02 · 왜 고민해?** 업무 규칙과 감사 처리를 우회할 위험이 있기 때문이야.
- **03 · 은행에서라면** Agent는 계좌 SQL UPDATE 대신 담당 API 호출.

### 9.5 내부 API·작업 실행 계약

#### 09-05-01 서버가 신뢰하는 사용자 인증 컨텍스트 정의

- **01 · 무슨 뜻?** 서버가 믿을 수 있는 로그인 사용자·세션 정보를 정의하는 것.
- **02 · 왜 고민해?** LLM 인자만으로 타인을 가장하지 못하게 하려고.
- **03 · 은행에서라면** 검증한 세션으로 Tool 실행 Context 구성.

#### 09-05-02 Tool 호출과 내부 API 요청 매핑 ★

- **01 · 무슨 뜻?** Agent Tool이 실제 어느 백엔드 API를 호출할지 표로 연결하는 것.
- **02 · 왜 고민해?** 팀원 기능과 AI 기능의 책임을 명확히 나누려고.
- **03 · 은행에서라면** `subscribe_product` → 상품 파트 POST 가입 API.

#### 09-05-03 업무 오류 코드→사용자 안내 매핑

### 10.1 [27] Fault Tolerance

#### 10-01-01 Timeout

- **01 · 무슨 뜻?** 도구나 모델 응답을 얼마 동안 기다릴지 제한하는 것.
- **02 · 왜 고민해?** 응답이 멈춘 채 영원히 기다리지 않도록 하려고.

#### 10-01-02 Retry

- **01 · 무슨 뜻?** 일시 오류가 났을 때 다시 시도하는 것.
- **02 · 왜 고민해?** 네트워크 오류로 실패한 조회를 복구할 수 있어.
- **03 · 은행에서라면** 문서 검색 1회 재시도.

#### 10-01-03 Fallback

- **01 · 무슨 뜻?** 주 기능을 사용할 수 없을 때 안전한 대체 경로로 가는 것.
- **02 · 왜 고민해?** 서비스 전체가 멈추는 일을 줄이기 위해서야.
- **03 · 은행에서라면** LLM 실패 시 상품 상세 화면 링크 제공.

#### 10-01-04 복구 가능한 오류와 불가능한 오류

- **01 · 무슨 뜻?** 다시 하면 회복될 오류와 즉시 중단해야 할 오류를 구분하는 것.
- **02 · 왜 고민해?** 권한 오류를 무한 재시도하지 않도록 하려고.
- **03 · 은행에서라면** 일시 네트워크 장애와 권한 없음은 다르게 처리.

#### 10-01-05 Tool 실패 시 안전한 종료

- **01 · 무슨 뜻?** Tool을 사용할 수 없을 때 안전하게 실행을 끝내는 것.
- **02 · 왜 고민해?** AI가 결과를 지어내거나 부분 작업을 계속하지 않도록 하려고.
- **03 · 은행에서라면** 금리 조회 실패면 계산·가입을 중단.

#### 10-01-06 중복 실행 방지

- **01 · 무슨 뜻?** 같은 요청으로 계약이 여러 번 생기지 않게 하는 것.
- **02 · 왜 고민해?** Agent 재시도만으로 쓰기 중복이 발생할 수 있어.
- **03 · 은행에서라면** 서버 멱등 키로 가입 한 번 보장.

- **02 · 왜 고민해?** 첫 분기부터 틀리면 모든 뒤 작업이 달라져.
- **03 · 은행에서라면** “이자 계산”을 가입 실행으로 오인하지 않았는지 평가.

#### 11-02-02 올바른 노드 분기

- **01 · 무슨 뜻?** Graph가 예상한 경로로 이동했는지 검사하는 것.
- **02 · 왜 고민해?** 최종 답만 맞아도 금지된 경로를 거쳤을 수 있어.
- **03 · 은행에서라면** 약관 질문은 RAG 노드로 갔는지 확인.

#### 11-02-03 Tool 선택 정확도

- **01 · 무슨 뜻?** 여러 Tool 중 맞는 것을 골랐는지 측정하는 것.
- **02 · 왜 고민해?** 필요 없는 도구를 사용하면 비용·위험이 늘어.
- **03 · 은행에서라면** 금리 조회에 가입 Tool을 호출하지 않는지 확인.

#### 11-02-04 Tool 실행 성공률

- **01 · 무슨 뜻?** 실제 Tool 실행이 정상 종료됐는지 확인하는 것.
- **02 · 왜 고민해?** 모델이 호출을 결정한 것과 서버 실행 성공은 달라.
- **03 · 은행에서라면** 계산 Tool 결과가 성공 코드인지 검사.

#### 11-02-05 최종 답변 품질

- **01 · 무슨 뜻?** 사용자에게 보여준 문장이 정확하고 이해하기 쉬운지 평가.
- **02 · 왜 고민해?** 내부 경로가 맞아도 잘못 설명하면 사용자에게 문제가 돼.
- **03 · 은행에서라면** 이자 계산 결과·가정이 함께 안내됐는지 평가.

#### 11-02-06 시나리오별 실행 경로 평가

- **01 · 무슨 뜻?** 전체 노드·도구 순서가 기대한 시나리오와 일치하는지 검사.
- **02 · 왜 고민해?** 최종 문장만 평가하면 승인 누락을 발견하기 어려워.
- **03 · 은행에서라면** 가입은 조건 검증→승인→인증→실행 순서 확인.

#### 11-02-07 Trajectory 평가: 필수·금지·허용 Tool

- **01 · 무슨 뜻?** 실제로 호출된 Tool들의 목록과 순서를 평가하는 방식.
- **02 · 왜 고민해?** 필수 Tool이 빠지거나 금지 Tool이 실행됐는지 확인하려고.
- **03 · 은행에서라면** 승인 테스트에 가입 Tool 호출이 없어야 하는 경우 검사.

#### 11-02-08 승인 없이 쓰기 Tool이 호출되지 않았는지 채점 ★

- **01 · 무슨 뜻?** 승인 이전에 쓰기 Tool을 실행하지 않았는지 채점하는 것.
- **02 · 왜 고민해?** 금융 Agent의 가장 중요한 안전 기준 중 하나야.
- **03 · 은행에서라면** ‘거절’한 테스트에서 가입 API 호출 0건 확인.

### 11.3 [35] RAG Golden Set

#### 11-03-01 평가용 질문·정답 데이터셋

- **01 · 무슨 뜻?** 질문과 모범답·근거를 묶어 놓은 평가용 데이터 모음.
- **02 · 왜 고민해?** 모델 변경 전후를 공정하게 비교하기 위해서야.
- **03 · 은행에서라면** “중도해지 가능?”에 정답 조항을 붙여 저장.

#### 11-03-02 상품별 정답 기준

- **01 · 무슨 뜻?** 상품별로 무엇을 정답으로 인정할지 기준을 세우는 것.
- **02 · 왜 고민해?** 유사 상품의 조건을 섞은 답을 정답 처리하면 안 돼.
- **03 · 은행에서라면** A상품 최저 가입액은 A상품 기준으로만 채점.

#### 11-03-03 근거 문서 연결

- **01 · 무슨 뜻?** 정답이 어느 문서·조항에 있는지 연결하는 것.
- **02 · 왜 고민해?** 답변이 우연히 맞았는지 실제 근거를 찾았는지 확인할 수 있어.
- **03 · 은행에서라면** Golden Set에 약관 제5조 링크 첨부.

#### 11-03-04 정상·실패 사례

- **01 · 무슨 뜻?** 정상 질문과 일부러 실패를 유도하는 질문을 함께 준비하는 것.
- **02 · 왜 고민해?** 쉬운 질문만 잘해도 실제 서비스는 오류가 날 수 있어.
- **03 · 은행에서라면** 존재하지 않는 상품·해지 불가 요청 포함.

#### 11-03-05 변경 전후 회귀 평가

- **01 · 무슨 뜻?** 코드·프롬프트 변경 후 같은 테스트를 다시 실행하는 것.
- **02 · 왜 고민해?** 새 기능 추가가 옛 기능을 망치지 않았는지 확인하려고.
- **03 · 은행에서라면** Retriever 수정 전후 정답률 비교.

#### 11-03-06 정답 불가·정보 부족 질문 포함 ★

- **01 · 무슨 뜻?** 정답이 없거나 정보가 부족한 질문을 평가셋에 넣는 것.
- **02 · 왜 고민해?** 억지로 답을 만들어내는 환각을 검출하려고.
- **03 · 은행에서라면** 문서에 없는 특별 우대금리를 물으면 ‘확인 불가’가 정답.

#### 11-03-07 개발셋 / 독립 테스트셋 분리

- **01 · 무슨 뜻?** 개발 중 자주 보는 문제와 처음 보는 최종 테스트 문제를 나누는 것.
- **02 · 왜 고민해?** 평가 문항에만 맞춘 과적합을 줄이기 위해서야.
- **03 · 은행에서라면** 연습 80문항, 검증용 별도 20문항 보관.

#### 11-03-08 평가셋 원문 검수·버전 관리

- **01 · 무슨 뜻?** 정답셋 자체가 원문과 일치하는지 검수하고 버전 기록하는 것.
- **02 · 왜 고민해?** 틀린 정답으로 평가하면 좋은 Agent도 나쁘게 채점돼.
- **03 · 은행에서라면** 약관 개정 시 정답 근거와 평가셋 버전 갱신.

### 11.4 통합 Agent 평가

#### 11-04-01 대화 맥락 유지 정확도

- **01 · 무슨 뜻?** Agent가 앞에서 정한 조건을 정확히 기억하는지 평가.
- **02 · 왜 고민해?** 오래된 상품·금액을 재사용하면 실수하기 때문이야.
- **03 · 은행에서라면** 3턴 뒤에도 현재 선택 상품을 올바르게 사용.

#### 11-04-02 후속 질문 처리 정확도

- **01 · 무슨 뜻?** “그럼 1년이면?” 같은 질문을 자연스럽게 이어 처리하는지 검사.
- **02 · 왜 고민해?** 실제 사용자는 매번 상품명을 반복하지 않아.
- **03 · 은행에서라면** 기간만 바꿔 이자를 다시 계산하는지 확인.

#### 11-04-03 필수 입력값 누락 탐지

- **01 · 무슨 뜻?** 필수 입력이 없을 때 질문을 제대로 하는지 평가.
- **02 · 왜 고민해?** 없는 값을 AI가 추정하는 위험을 잡아내려고.
- **03 · 은행에서라면** 금액 없이 가입 요청 시 금액 질문을 하는지 확인.

#### 11-04-04 잘못된 상품 선택 방지

- **01 · 무슨 뜻?** 비슷한 상품 중 다른 상품을 실수로 선택하지 않는지 검사.
- **02 · 왜 고민해?** 잘못된 상품 ID로 가입하면 거래가 잘못될 수 있어.
- **03 · 은행에서라면** A적금 선택 후 B적금 가입 Tool 호출 금지.

#### 11-04-05 승인 없는 작업 실행 방지

- **01 · 무슨 뜻?** 승인하지 않은 작업을 실제 실행하지 않는지 검증하는 것.
- **02 · 왜 고민해?** 정확한 문장보다 실행 안전이 우선인 상황이 있어.
- **03 · 은행에서라면** “취소”라고 답한 경우 서버 계약 생성 0건.

#### 11-04-06 환각 및 근거 없는 답변 발생률

- **01 · 무슨 뜻?** 근거 없는 사실이나 조작된 수치를 얼마나 자주 내는지 측정.
- **02 · 왜 고민해?** 금리·조건에 대한 환각을 수치로 관리하려고.
- **03 · 은행에서라면** 원문에 없는 혜택을 만들어낸 비율 측정.

#### 11-04-07 평균 응답 시간

- **01 · 무슨 뜻?** 요청부터 최종 결과까지 걸린 평균 시간을 측정.
- **02 · 왜 고민해?** 사용자 경험과 병목 개선 우선순위를 정하려고.
- **03 · 은행에서라면** 상품 검색 질문의 평균 3초 여부 검토.

#### 11-04-08 토큰 사용량 및 비용

- **01 · 무슨 뜻?** 한 요청에서 쓴 토큰과 호출 비용을 측정.
- **02 · 왜 고민해?** Agent 단계가 늘면 운영비가 증가할 수 있어.
- **03 · 은행에서라면** RAG 재검색 3회 시 비용 상승 확인.

#### 11-04-09 전체 E2E 성공률

- **01 · 무슨 뜻?** 처음 요청부터 올바른 결과까지 전체 흐름의 성공률.
- **02 · 왜 고민해?** 개별 Tool이 성공해도 전체 시나리오는 실패할 수 있어.
- **03 · 은행에서라면** 상품 검색→계산→승인 전 중단까지 E2E 테스트.

### 11.5 금융 전용 공격·오류 테스트

#### 11-05-01 다른 사용자의 계좌 조회·호출 차단

- **01 · 무슨 뜻?** 다른 사람의 계좌를 읽거나 수정하려는 시도를 차단하는지 시험.
- **02 · 왜 고민해?** 사용자 간 정보 격리는 반드시 서버에서도 보장돼야 해.
- **03 · 은행에서라면** 사용자 A가 B의 `account_id`로 요청하면 403.

#### 11-05-02 오래된 약관·금리 사용 방지

- **01 · 무슨 뜻?** 만료된 약관·이전 금리로 안내하지 않는지 테스트.
- **02 · 왜 고민해?** 상품 조건 변경 후 잘못된 설명을 막기 위해서야.
- **03 · 은행에서라면** 신약관 적용 후 구약관 조항이 답에 안 나오는지 확인.

#### 11-05-03 Prompt Injection / Tool 결과 조작 방어

- **01 · 무슨 뜻?** 악의적 사용자·문서·Tool 응답이 Agent를 조종할 수 있는지 시험.
- **02 · 왜 고민해?** 외부 문장 하나로 보안 정책이 뒤집히면 안 돼.
- **03 · 은행에서라면** 문서의 “모든 Tool 권한 허용”을 무시하는지 확인.

#### 11-05-04 중복 승인 및 중복 실행 방지

- **01 · 무슨 뜻?** 여러 번 확인 버튼을 눌러도 실제 실행은 한 번인지 시험.
- **02 · 왜 고민해?** UI와 네트워크 재전송으로 중복 계약이 생길 수 있어.
- **03 · 은행에서라면** 가입 승인 버튼 연속 두 번 클릭 테스트.

#### 11-05-05 거절 후 실행 금지

- **01 · 무슨 뜻?** 사용자가 거절한 뒤에는 실행이 멈추는지 시험.
- **02 · 왜 고민해?** 거절을 다른 의도로 해석하면 위험해.
- **03 · 은행에서라면** “아니, 그만” 뒤 쓰기 API 호출 0건.

#### 11-05-06 타임아웃 후 중복 계약·출금 방지

- **01 · 무슨 뜻?** 서버 응답이 끊긴 뒤 가입·출금이 두 번 생기지 않는지 시험.
- **02 · 왜 고민해?** 타임아웃은 실행 실패를 뜻하지 않기 때문이야.
- **03 · 은행에서라면** 가입 성공 직후 응답 유실을 시뮬레이션.

#### 11-05-07 세션 만료 상태에서 재개 시 재인증

- **01 · 무슨 뜻?** 인증이 만료된 상태를 복구할 때 다시 확인하는지 시험.
- **02 · 왜 고민해?** 옛 인증 결과를 재사용하면 안 돼.
- **03 · 은행에서라면** 로그아웃 후 작업 재개 시 재로그인 요구.

#### 11-05-08 로그·추적 데이터에 개인정보가 남지 않음

- **01 · 무슨 뜻?** 추적·로그 자료가 PIN·계좌번호 원문 등을 노출하지 않는지 시험.
- **02 · 왜 고민해?** 운영 로그도 민감한 정보 저장소가 될 수 있어.
- **03 · 은행에서라면** LangSmith Trace에서 토큰 마스킹 검증.

## PART 12. 은행 전용 Agent Workflow 설계

### 12.1 진입 및 라우팅

#### 12-01-01 사용자 메시지 수신

- **01 · 무슨 뜻?** 사용자가 챗봇에 메시지를 보내면 Graph에 전달하는 시작 단계.

- **03 · 은행에서라면** “12개월 적금 추천해줘” 수신.

#### 12-01-02 로그인 상태 확인

- **01 · 무슨 뜻?** 개인 조회·가입이 필요한 요청에 로그인 여부를 확인하는 것.
- **02 · 왜 고민해?** 공개 상담과 개인 금융 작업의 권한이 달라.
- **03 · 은행에서라면** 상품 설명은 공개, 내 잔액은 로그인 필수.

#### 12-01-03 대화 State 로딩

- **01 · 무슨 뜻?** 저장된 현재 대화 정보를 읽어 시작하는 것.
- **02 · 왜 고민해?** 후속 질문에 필요한 상품·기간을 기억하려고.
- **03 · 은행에서라면** 이전 `selected_product` 불러오기.

#### 12-01-04 의도 분류

- **01 · 무슨 뜻?** 현재 요청의 목적을 분류하는 것.
- **02 · 왜 고민해?** 어느 업무 흐름으로 이동할지 결정하려고.
- **03 · 은행에서라면** `PRODUCT_SEARCH` 또는 `SUBSCRIBE` 선택.

#### 12-01-05 Tool / RAG / 일반 응답 분기

- **01 · 무슨 뜻?** 일반 설명·문서 검색·데이터 Tool을 어느 경로로 보낼지 정하는 것.
- **02 · 왜 고민해?** 모든 질문을 같은 방식으로 처리하면 느리고 부정확해.
- **03 · 은행에서라면** 약관 → RAG, 금리 → DB, 인사 → 일반 답변.

### 12.2 상품 조회 Workflow

#### 12-02-01 상품명·유형·조건 추출

- **01 · 무슨 뜻?** 질문에서 찾을 상품 종류와 조건을 뽑아내는 것.
- **02 · 왜 고민해?** 검색 API에 넘길 명확한 조건을 만들어야 해.
- **03 · 은행에서라면** “6개월 고금리 예금” → type=deposit, months=6.

#### 12-02-02 DB 조회

- **01 · 무슨 뜻?** 구조화된 조건으로 상품 데이터베이스를 조회하는 것.
- **02 · 왜 고민해?** 실제 상품 목록을 기준으로 답해야 하니까.
- **03 · 은행에서라면** `GET /products?type=...` 호출.

#### 12-02-03 검색 조건 보완

- **01 · 무슨 뜻?** 검색 결과가 없거나 조건이 모호하면 사용자에게 보완을 요청하는 것.
- **02 · 왜 고민해?** 없는 상품을 지어내거나 아무거나 추천하면 안 돼.
- **03 · 은행에서라면** “기간 조건을 넓혀볼까요?”

#### 12-02-04 결과 정리 및 응답

- **01 · 무슨 뜻?** 찾은 상품을 사용자에게 읽기 좋은 형식으로 보여주는 것.
- **02 · 왜 고민해?** 내부 ID 목록만으로는 선택하기 어렵기 때문이야.
- **03 · 은행에서라면** 금리·기간·가입 조건을 상품 카드로 표시.

### 12.3 상품 상세 설명 Workflow

#### 12-03-01 상품 식별

- **01 · 무슨 뜻?** 사용자가 묻는 상품의 ID를 정확히 확정하는 것.
- **02 · 왜 고민해?** 비슷한 상품명끼리 정보를 섞지 않으려고.
- **03 · 은행에서라면** “청년 적금 A”를 `prod_a`로 확인.

#### 12-03-02 DB 정보 조회

- **01 · 무슨 뜻?** 상품의 현재 금리·기간 등 구조화된 속성을 읽는 것.
- **02 · 왜 고민해?** 최신 수치는 약관 추측이 아니라 DB가 기준이야.
- **03 · 은행에서라면** 상세 API에서 기본금리·만기 조회.

#### 12-03-03 RAG 필요성 판단

- **01 · 무슨 뜻?** 문서 검색이 필요한 질문인지 판단하는 것.
- **02 · 왜 고민해?** 모든 상품 정보를 RAG로 찾을 필요는 없어.
- **03 · 은행에서라면** 해지 조항은 RAG, 현재 금리는 DB.

#### 12-03-04 근거 문서 검색

- **01 · 무슨 뜻?** 해당 상품의 공식 설명서·약관 조항을 찾아오는 것.
- **02 · 왜 고민해?** 답변의 근거를 확보하려고.
- **03 · 은행에서라면** `product_id` 필터로 중도해지 조건 검색.

#### 12-03-05 답변 및 출처 표시

- **01 · 무슨 뜻?** 근거를 표시하며 읽기 쉬운 설명을 제공하는 것.
- **02 · 왜 고민해?** 사용자가 결과를 검증할 수 있게 하려고.
- **03 · 은행에서라면** “약관 4조에 따르면…” 링크 제공.

### 12.4 이자 계산 Workflow

#### 12-04-01 금액·기간 추출

- **01 · 무슨 뜻?** 사용자 말에서 예치액과 기간을 뽑는 것.
- **02 · 왜 고민해?** 계산 Tool의 필수 인자를 준비하기 위해서야.
- **03 · 은행에서라면** “100만 원, 12개월” 추출.

#### 12-04-02 누락값 확인

- **01 · 무슨 뜻?** 계산에 필요한 값이 비어 있으면 추가로 묻는 것.
- **02 · 왜 고민해?** 임의 금액·기간으로 결과를 만들지 않으려고.
- **03 · 은행에서라면** “얼마를 넣을 예정인가요?”

#### 12-04-03 금리 조회

- **01 · 무슨 뜻?** 상품의 적용 금리를 서버에서 조회하는 것.
- **02 · 왜 고민해?** 변경 가능한 숫자를 LLM 기억에 맡기지 않으려고.
- **03 · 은행에서라면** A예금 기본금리 조회.

#### 12-04-04 계산 Tool 실행

- **01 · 무슨 뜻?** 정해진 계산식과 반올림 규칙으로 실제 계산하는 것.
- **02 · 왜 고민해?** 언어 모델이 숫자를 추정하지 않도록 하려고.
- **03 · 은행에서라면** 계산 API가 세전 예상 이자 반환.

#### 12-04-05 계산 결과 및 가정 표시

- **01 · 무슨 뜻?** 결과와 계산 전제·제외 항목을 함께 안내하는 것.
- **02 · 왜 고민해?** 예상 이자를 확정 지급액으로 오해하지 않게 하려고.
- **03 · 은행에서라면** “세전 예상·우대조건 미적용” 표시.

### 12.5 모의 가입 Workflow

#### 12-05-01 가입 의도 확인

- **01 · 무슨 뜻?** ‘설명해줘’와 ‘실제로 가입 진행해줘’를 구별하는 것.
- **02 · 왜 고민해?** 단순 관심만으로 계약이 생기면 안 돼.
- **03 · 은행에서라면** “가입할래”를 가입 의도로 인식.

#### 12-05-02 상품·금액·기간 확정

- **01 · 무슨 뜻?** 가입할 상품·금액·기간을 확정하는 것.
- **02 · 왜 고민해?** 실제 서버 검증에 필요한 입력값들이야.
- **03 · 은행에서라면** A상품, 100만 원, 6개월 확정.

#### 12-05-03 출금 계좌 선택

- **01 · 무슨 뜻?** 돈이 빠져나갈 본인 계좌를 사용자에게 고르게 하는 것.
- **02 · 왜 고민해?** 임의의 계좌에서 출금하면 안 되기 때문이야.
- **03 · 은행에서라면** 활성 출금 가능 계좌 목록 보여주기.

#### 12-05-04 가입 조건 검증 ★

- **01 · 무슨 뜻?** 상품 정책과 계좌 조건으로 신청 가능 여부를 검사하는 것.
- **02 · 왜 고민해?** AI의 자연어 판단보다 서버 업무 규칙이 우선이야.
- **03 · 은행에서라면** 최소 가입금·계좌 상태·잔액 점검.

#### 12-05-05 가입 정보 요약

- **01 · 무슨 뜻?** 승인 전에 최종 거래 내용을 한눈에 보여주는 것.
- **02 · 왜 고민해?** 사용자가 무엇에 동의하는지 분명해야 해.
- **03 · 은행에서라면** 금액·기간·출금 계좌·상품명 요약.

#### 12-05-06 사용자 명시적 승인 ★

- **01 · 무슨 뜻?** 사용자가 실제 가입에 명확히 동의하도록 받는 것.
- **02 · 왜 고민해?** 조회나 설명과 달리 상태 변경이 발생하기 때문이야.
- **03 · 은행에서라면** “이 내용으로 가입” 버튼.

#### 12-05-07 본인 확인(step-up)

- **01 · 무슨 뜻?** 중요 작업을 실행할 권한이 있는 본인인지 재확인하는 것.
- **02 · 왜 고민해?** ‘동의했다’와 ‘본인이다’는 다른 검증이야.
- **03 · 은행에서라면** `POST /auth/step-up`으로 유효한 인증 결과 획득.

#### 12-05-08 가입 실행 Tool 호출

- **01 · 무슨 뜻?** 안전한 검증을 거쳐 상품 서버에 가입 실행 요청을 보내는 것.
- **02 · 왜 고민해?** LLM은 계약을 직접 만들지 않고 전용 API를 호출해야 해.
- **03 · 은행에서라면** 승인값·인증값을 검증한 후 가입 Tool.

#### 12-05-09 결과 확인 및 State 정리 ★

- **01 · 무슨 뜻?** 서버 계약 결과를 확인하고 임시 상태를 정리하는 것.
- **02 · 왜 고민해?** 성공 메시지의 근거를 확보하고 다음 대화 오염을 막으려고.
- **03 · 은행에서라면** 계약 ID 확인 후 `approved=false` 등 초기화.

### 12.6 모의 중도 해지 Workflow

#### 12-06-01 대상 계약 식별

- **01 · 무슨 뜻?** 사용자가 중도 해지하려는 가입 계약을 특정하는 것.
- **02 · 왜 고민해?** 계약이 여러 개인데 아무거나 해지하면 안 돼.
- **03 · 은행에서라면** “지난달 가입한 적금”의 계약 ID 확인.

#### 12-06-02 해지 가능 여부 검증

- **01 · 무슨 뜻?** 지금 해당 상품·계약을 해지할 수 있는지 검사하는 것.
- **02 · 왜 고민해?** 만기·상태·정책 등 제한이 있을 수 있어.
- **03 · 은행에서라면** 상품 서버의 중도 해지 가능 여부 조회.

#### 12-06-03 사용자 승인 및 본인 확인

- **01 · 무슨 뜻?** 해지 결과를 안내하고 사용자 승인·본인 확인을 받는 것.
- **02 · 왜 고민해?** 원금·예상 이자 등 영향을 이해한 후 진행해야 해.
- **03 · 은행에서라면** 예상 환급액 제시 → 승인 → step-up.

#### 12-06-04 해지 Tool 실행

- **01 · 무슨 뜻?** 조건이 모두 충족될 때 해지 API를 호출하는 것.
- **02 · 왜 고민해?** 상태 변경은 검증된 상품 서버가 담당해야 해.
- **03 · 은행에서라면** `terminate_subscription(contract_id)`.

#### 12-06-05 결과 확인 및 안내

- **01 · 무슨 뜻?** 해지가 실제로 완료됐는지 확인해 사용자에게 알리는 것.
- **02 · 왜 고민해?** 응답 유실을 완료로 오인하지 않으려고.
- **03 · 은행에서라면** 계약 상태 `TERMINATED` 확인 후 안내.

### 12.7 복합 요청 Workflow

#### 12-07-01 단일 요청에서 여러 의도 분리

- **01 · 무슨 뜻?** 사용자 한 문장에 포함된 여러 요청을 분리하는 것.
- **02 · 왜 고민해?** 일부 요구를 놓치지 않고 처리하려고.
- **03 · 은행에서라면** “상품 비교하고 두 개의 이자 계산해줘.”

#### 12-07-02 작업 간 의존성 판단

- **01 · 무슨 뜻?** 어떤 작업 결과가 다음 작업에 필요한지 판단하는 것.
- **02 · 왜 고민해?** 의존 작업을 무조건 병렬로 하면 실패해.
- **03 · 은행에서라면** 상품 선택 후에만 해당 상품의 이자 계산 가능.

#### 12-07-03 순차 실행 / 병렬 실행 선택

- **01 · 무슨 뜻?** 독립 작업을 동시에 할지 순서대로 할지 결정하는 것.
- **02 · 왜 고민해?** 속도와 데이터 일관성 사이 균형이 있어.
- **03 · 은행에서라면** A/B 상품 조회는 병렬, 가입은 순차.

#### 12-07-04 중간 결과 공유

- **01 · 무슨 뜻?** 한 단계에서 얻은 결과를 다음 단계에 올바르게 넘기는 것.
- **02 · 왜 고민해?** 중간 금리·상품 ID가 섞이면 최종 답이 틀려.
- **03 · 은행에서라면** A상품 금리는 A상품 계산에만 사용.

#### 12-07-05 최종 결과 통합

- **01 · 무슨 뜻?** 여러 결과를 하나의 이해하기 쉬운 답으로 합치는 것.
- **02 · 왜 고민해?** 사용자에게 Tool 결과를 나열만 하면 불편해.
- **03 · 은행에서라면** 상품별 금리·예상 이자를 비교표로 표시.

### 12.8 예외 및 복구 Workflow

#### 12-08-01 상품을 찾지 못한 경우

- **01 · 무슨 뜻?** 검색에 맞는 상품이 하나도 없는 상황에 대응하는 것.
- **02 · 왜 고민해?** 존재하지 않는 상품을 만들어 안내하지 않으려고.
- **03 · 은행에서라면** 조건을 완화할지 사용자에게 제안.

#### 12-08-02 RAG 근거가 없는 경우

- **01 · 무슨 뜻?** 약관 검색에 근거가 없을 때 답변을 보류하는 것.
- **02 · 왜 고민해?** 없는 혜택·조건을 생성하지 않게 하려고.
- **03 · 은행에서라면** “해당 문서에서 확인되지 않아요.”

#### 12-08-03 금리 데이터가 없는 경우

- **01 · 무슨 뜻?** 현재 적용 금리를 가져오지 못하는 경우를 처리하는 것.
- **02 · 왜 고민해?** 계산에 임의 금리를 쓸 수 없어서야.
- **03 · 은행에서라면** 금리 조회 실패 시 계산 중단.

#### 12-08-04 가입 조건이 충족되지 않은 경우

- **01 · 무슨 뜻?** 최소금액·계좌 상태 등의 규칙을 만족하지 못할 때 안내.
- **02 · 왜 고민해?** 서버 거절 사유를 정확히 알려줘야 해.
- **03 · 은행에서라면** “이 상품은 가입 가능 기간이 아닙니다.”

#### 12-08-05 사용자가 승인을 거절한 경우

- **01 · 무슨 뜻?** 사용자가 가입·해지 승인을 거절할 때 처리하는 것.
- **02 · 왜 고민해?** 거절 후 실행이 이루어지면 안 되기 때문이야.
- **03 · 은행에서라면** Graph 종료, 승인 상태 폐기.

#### 12-08-06 대화 중 상품을 변경한 경우

- **01 · 무슨 뜻?** 대화 도중 선택 상품을 바꾸는 경우를 처리하는 것.
- **02 · 왜 고민해?** 이전 상품의 금리·승인을 새 상품에 쓰지 않으려고.
- **03 · 은행에서라면** 상품 변경 → 슬롯 일부 초기화 → 재검증.

#### 12-08-07 Tool 및 DB 장애가 발생한 경우

- **01 · 무슨 뜻?** DB나 Tool이 멈췄을 때 안전하게 중단·복구하는 것.
- **02 · 왜 고민해?** 실패를 숨기거나 같은 계약을 다시 실행하지 않으려고.
- **03 · 은행에서라면** 쓰기 요청 타임아웃 → 상태 확인.

### 12.9 가입·해지의 인증·승인 체인

#### 12-09-01 서버 측 가입·해지 가능 여부 재검증

- **01 · 무슨 뜻?** 가입·해지 실행 직전에 모든 업무 조건을 서버에서 다시 검사하는 것.
- **02 · 왜 고민해?** 승인 사이에 금리·잔액·계약 상태가 바뀔 수 있어.
- **03 · 은행에서라면** 가입 실행 바로 전 계좌 상태 재조회.

#### 12-09-02 상품·금액·기간·계좌의 승인 시점 고정

- **01 · 무슨 뜻?** 사용자가 승인한 조건을 바뀌지 않는 묶음으로 고정하는 것.
- **02 · 왜 고민해?** 승인 후 인자가 몰래 달라지는 것을 막으려고.
- **03 · 은행에서라면** 상품 A·100만원·6개월·계좌 1을 승인 데이터에 묶기.

#### 12-09-03 사용자 승인과 step_up_challenge_id 별도 확인

- **01 · 무슨 뜻?** 사용자의 의사 확인과 별도 본인 확인 결과를 모두 검증하는 것.
- **02 · 왜 고민해?** ‘내가 원한다’와 ‘내 계정의 소유자다’가 구분돼.
- **03 · 은행에서라면** 승인 플래그와 `step_up_challenge_id` 동시 검사.

#### 12-09-04 인증 action·세션·사용자·유효시간·일회용 조건 검증

- **03 · 은행에서라면** 인증 방식 확정 / LLM 모델 선택은 검토 중.

#### 13-04-03 미해결 위험 및 팀 협의 항목 정리

- **01 · 무슨 뜻?** 아직 해결되지 않은 문제와 팀원 협의가 필요한 지점을 기록.
- **02 · 왜 고민해?** 구현 중 책임 공백이나 충돌이 생기지 않게 하려고.
- **03 · 은행에서라면** 가입 API의 멱등 키 처리 주체 확인 요청.

#### 13-04-04 수용 테스트와 설계 결정의 연결

- **01 · 무슨 뜻?** 설계의 각 결정에 어떤 테스트가 필요한지 연결하는 것.
- **02 · 왜 고민해?** 설계가 실제로 지켜지는지 검증할 수 있어.
- **03 · 은행에서라면** ‘무승인 가입 금지’ → 승인 누락 테스트.

#### 13-04-05 변경 시 영향받는 Graph·Tool·State 확인

- **01 · 무슨 뜻?** 기능 변경 시 영향받는 Graph·Tool·State를 찾는 것.
- **02 · 왜 고민해?** 한 곳 수정으로 다른 작업이 깨지지 않도록 하려고.
- **03 · 은행에서라면** 상품 기간 필드 변경 시 계산·가입 노드 점검.

#### 13-04-06 최종 배포 이전 시뮬레이션/모의 데이터 검증

- **01 · 무슨 뜻?** 실제 공개 전에 가상 데이터로 전체 실행을 확인하는 것.
- **02 · 왜 고민해?** 금융 업무를 실수로 변경하지 않고 안전하게 검증하려고.
- **03 · 은행에서라면** 더미 계좌·상품으로 모의 가입 E2E 테스트.
