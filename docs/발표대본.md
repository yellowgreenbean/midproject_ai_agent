- 실제 Gmail 로 인증번호 메일 받기 (가이드북 회원가입 15-8: 「해 보지 않음」)

  → 하나라도 안 되면 그 부분은 Swagger 로 보여 주거나 「남은 한계」에서 말한다.

**서버가 켜져 있으면 예약 작업이 저절로 돈다** — `app/main.py` 의 스케줄러가 1분마다 `jobs.run_minutely()` 를 부른다(`SCHEDULER_ENABLED` 기본 켬). 예약 송금·자동이체 실행, 타행 처리중 확정, 카드 결제일 알림·대금 출금, 만기 지급, 탈퇴 회원 가명 처리가 모두 여기서 돈다.

- 더미 청구서 결제일이 11월 14일이라 11/11(D-3)·11/14(당일)에는 결제일 알림이 저절로 생기고, **11/14 이후에는 카드 대금이 이미 출금돼** 결제 캘린더가 달라진다.

**시연 뒤 되돌리기** — 시연 중 가입·납입·송금을 하면 개발 DB 가 바뀐다. 처음 상태로 돌리는 법은 `docs/가이드북_회원가입로그인.md` 10-12. 손으로 `python -m app.jobs` 를 돌릴 필요는 없다(서버가 이미 돌린다).

## 2. 기획 (약 8분)

### 2-1. 무엇을 만드는가

**[화면]** `docs/기획서.md` 맨 위 목차 표

우리 과제는 「자주 쓰는 은행 앱을 참고한 은행 모바일 웹서비스 클론」이고, 참고 대상은 **토스**입니다.
그래서 동작이 애매할 때는 「토스는 어떻게 하나」를 먼저 찾고, 조사한 내용은 출처와 함께 `docs/domain-rules.md` 에 남겼습니다.

은행 이름은 **두린은행**입니다. 예금·적금 상품은 실제 우리은행 상품 30개를 이름만 바꿔 옮겼고, 금융 데이터는 전부 CODEF 샌드박스 응답 모양을 따라 직접 만든 **더미 데이터**입니다. 실제 돈·실제 은행 API 는 쓰지 않습니다.

### 2-2. 기획서 한 파일, 여섯 파트

기획서는 `docs/기획서.md` **한 파일**로 합쳤습니다.

| 파트 | 내용 | 기능 번호 |
|---|---|---|
| Part 1 | 회원가입 · 로그인 · 간편 인증(PIN) | `AUTH-F01` ~ `F13` |
| Part 2 | 계좌 관리 (개설·조회·잔액·상태·알림) | `ACCT-F01` ~ `F13` |
| Part 3 | 예금·적금 상품 | `PROD-F01` ~ `F12` |
| Part 4 | 카드 | `CARD-F01` ~ `F16` |
| Part 5 | 거래 (이체·송금·예약·내역) | `TRX-F01` ~ `F14` |
| Part 6 | 카드·거래 연결과 공통 규칙 (이름·형식 규칙 C-5) | — |

원래 파트마다 기능 번호가 F01 부터 겹쳐서, 합칠 때 앞에 파트 이름을 붙였습니다. 앞으로 대화할 때 「AUTH-F09」, 「PROD-F12」처럼 부르면 서로 헷갈리지 않습니다.
그리고 각 파트는 **1차(필수) · 2차(편의) · 3차(확장)** 로 단계를 나눠 두었습니다.

### 2-3. 파트를 하나로 묶는 공통 규칙 다섯 가지

여러 파트가 한 DB 를 쓰기 때문에, 파트가 달라도 꼭 같이 지켜야 하는 규칙을 정했습니다. 이게 기획에서 가장 중요한 부분이라고 생각합니다.

1. **잔액은 거래 원장으로만 바뀐다.**
   카드 대금, 적금 납입, 중도 해지 지급도 각 파트가 잔액을 직접 고치지 않고 거래 파트의 원장에 한 줄을 남깁니다. 거래 유형은 `TRANSFER_OUT/IN` · `CARD_PAYMENT` · `SUBSCRIPTION_PAYMENT` · `SUBSCRIPTION_PAYOUT` 등으로 정했습니다(Part 5 3장).
2. **중요한 작업 직전에는 본인 확인(step-up)을 다시 받는다.**
   로그인해 있어도 이체·가입·카드 해지·탈퇴 직전에는 비밀번호나 PIN 을 한 번 더 받습니다. 받은 확인 번호는 **5분 · 한 번 · 그 작업 · 그 세션**에서만 쓸 수 있습니다.
3. **본인 것만 보인다.**
   남의 계좌·카드·가입 상품 id 를 넣으면 「없는 것」과 **똑같은 404** 를 돌려줍니다. 있는지조차 알려 주지 않습니다.
4. **같은 요청이 두 번 와도 한 번만 처리한다.**
   가입·이체는 `Idempotency-Key` 헤더를 받습니다. 버튼을 두 번 눌러도 돈은 한 번만 빠집니다.
5. **이름·형식 통일 (Part 6 C-5).**
   기본 키는 `id`, 참조는 `<테이블>_id`, API 는 snake_case, 금액은 문자열, 시각은 `+09:00`.

### 2-4. 파트 사이의 연결 — 회원 탈퇴가 좋은 예

**[화면]** 기획서 Part 1 「3.3 회원 탈퇴」 흐름도

탈퇴는 회원 파트 기능이지만, 실제로는 모든 파트가 엮여 있습니다. 토스 방식대로 탈퇴 전에 세 단계를 확인합니다.
① 남은 돈 옮기기 — 모든 계좌 잔액 0원, 처리 중 이체 없음, 진행 중 예금·적금 없음
② 삭제될 데이터 확인
③ 연결된 서비스 정리 — 예약 송금·자동이체, 해지 안 된 카드, **해지했어도 낼 대금이 남은 카드**

그런데 구현해 보니 문제가 있었습니다. 개발 DB 의 기존 회원 29명 중 **17명이 탈퇴를 할 수 없었습니다.** 잔액을 옮길 이체도, 적금 중도 해지도, 카드 해지도 아직 없었기 때문입니다. 게다가 1차 이체는 두린은행 계좌끼리만인데, 탈퇴는 「본인 명의 계좌로 옮기기」를 요구해서 돈을 내보낼 곳이 없었습니다.

그래서 탈퇴에 필요한 정리 기능을 차수보다 앞당겨 만들었습니다(기획서 변경 이력 18).
- 타행 이체 + 회원마다 **본인 명의 타행 계좌** 시드
- 계좌 정지 해제, 적금 중도 해지, 카드 해지
- 신용카드 「지금 결제하기」(선결제)

이렇게 기획서끼리 어긋난 곳은 구현하다가 발견되는 경우가 많아서, 고친 내용은 전부 **기획서 변경 이력**에 날짜와 함께 남겼습니다.

### 2-6. 시스템 구조

```
 [브라우저 frontend :5173]  ──HTTP(쿠키 sid)──▶  [FastAPI backend :8010]  ──SQL──▶  [PostgreSQL 17 (Docker) :5433]
     React + TypeScript                          검사 · 해시 · 계산 · 저장                 스키마: docs/sql/0*.sql
                                                  │
                                                  └─▶ Gemini 2.5 Flash (챗봇) · RAG 문서 벡터(pgvector)
```

화면이 DB 에 직접 붙지 않고 꼭 서버를 거칩니다. 이유는 두 가지입니다.
하나, 브라우저 코드는 누구나 열어 볼 수 있어서 DB 비밀번호를 둘 수 없습니다.
둘, **「누구의 데이터인가」는 서버만 정할 수 있습니다.** 화면이 「user_001 카드 줘」라고 보내면 아무나 남의 id 를 넣을 수 있으니까, 서버는 로그인 쿠키 → 세션 → 회원 순서로 주인을 정합니다.

금액 판정(낼 돈·잔액 부족·실적 구간·예상 이자)도 서버 한 곳에서 계산하고 화면은 받은 숫자를 보여 주기만 합니다. 그래서 챗봇이 같은 API 함수를 부르면 **화면과 같은 숫자**가 나옵니다.

## 3. Swagger 소개 (약 6분)

### 3-1. Swagger 가 무엇이고 왜 쓰나

**[화면]** http://localhost:8010/docs

FastAPI 는 코드를 읽어서 이 API 문서 화면을 자동으로 만들어 줍니다. 기능별로 묶여 있고, 각 API 의 요청 칸·응답 모양이 다 보입니다.
「Try it out」 → 「Execute」를 누르면 **실제 서버에 요청**이 갑니다. 화면을 만들기 전에 서버가 맞게 동작하는지 여기서 먼저 확인했습니다.

한 가지 포인트는, Swagger 도 브라우저라서 **로그인하면 쿠키가 저장되고 다음 요청에 같이 갑니다.** 그래서 로그인 한 번이면 그 회원으로 다른 API 를 다 눌러 볼 수 있습니다.

### 3-2. 오류 모양은 하나로 통일

모든 오류는 같은 모양입니다.
```json
{"success": false, "error": {"code": "PAYMENT_TYPE_REQUIRED", "message": "정액적립식과 자유적립식 중 납입 방식을 골라 주세요."}}
```
`code` 는 화면과 챗봇이 분기할 때 쓰고, `message` 는 사용자에게 그대로 보여 줄 문장입니다. 챗봇도 실패 이유를 지어내지 않고 이 `code` 와 `message` 를 그대로 전합니다.

### 3-3. 직접 눌러 보기 (아래 순서대로)

**[동작 1] 로그인**
`POST /auth/login` → `{"username": "minjun_kim", "password": "…"}` → 200
> 이제 쿠키가 생겨서 이 브라우저는 김민준 님으로 로그인된 상태입니다.

**[동작 2] 본인 것만 보이는지**
`GET /cards` → 카드 3장 (`card_001` · `card_002` · `card_003`)
`GET /cards/{cardId}` 에 `card_006`(다른 회원 카드) → **404 `CARD_NOT_FOUND`**, 없는 카드 `card_999` 와 응답이 똑같습니다.
> 남의 카드를 「권한 없음」이 아니라 「없음」으로 답하는 이유는, 그 id 가 존재한다는 사실조차 알려 주지 않기 위해서입니다.

**[동작 3] 상품 조회와 예상 이자 (로그인 없이도 됨)**
`GET /products?sort=rate` → 30개, 금리 높은 순
`POST /products/prod_004/estimate` `{"amount": "100000", "months": 12}` → `interest: "20800"`
같은 곳에 `{"amount": "600000", "months": 12}` → 422 `AMOUNT_OUT_OF_RANGE` (월 한도 50만 원)

**[동작 4] 본인 확인 → 가입 → 같은 키로 한 번 더**
1. `POST /auth/step-up` `{"action": "SUBSCRIPTION", "password": "…"}` → `step_up_challenge_id`
2. `POST /subscriptions` 헤더 `Idempotency-Key: demo-001`, 본문 `{"product_id": "prod_004", "account_id": "acc_001", "amount": "100000", "months": 12, "payment_type": "FIXED", "step_up_challenge_id": "…"}` → 201
3. **같은 키로 한 번 더 Execute** → 같은 계약이 돌아오고, `GET /accounts` 를 보면 잔액은 한 번만 줄었습니다.

> (본인 확인 번호 없이 보내면 403 `STEP_UP_REQUIRED`, 잔액은 그대로입니다.)

**[동작 5] 받는 계좌 확인 + 금액 오입력 경고**
`GET /transfer-targets/verify` 에 `bank=두린은행`, `account_no=<처음 보내는 계좌>`, `amount=1000000`
→ 예금주 이름 · `is_mine` · `warnings: ["FIRST_LARGE"]`
> 송금 재확인 화면의 「금액을 한 번 더 확인해 주세요」가 이 `warnings` 로 나옵니다. 경고 판정도 화면이 아니라 서버가 합니다.

**[동작 6] 다른 은행 예적금 내역 — CODEF 샌드박스 실제 호출**
`GET /external-deposit-accounts/{accountNo}/transactions` 에 `accountNo=54780300000000`, `organization=0004`, `startDate=20190101`, `endDate=<오늘 YYYYMMDD>`
→ CODEF 응답의 `data` 가 그대로 옵니다.
> 이건 더미가 아니라 서버가 그 자리에서 CODEF 샌드박스를 부른 결과입니다. 토큰은 SDK 로 받고, 요청 본문은 URL 인코딩, 응답은 디코딩해야 해서 `app/codef.py` 에 감쌌습니다. CODEF 가 응답하지 않으면 503 `EXTERNAL_UNAVAILABLE` 로 답합니다.

**[동작 7] 챗봇 API**
`POST /agent/chat` `{"message": "내 계좌 잔액 알려줘"}`
→ `reply`(답 글) · `links`(화면 링크 버튼) · `suggestions`(추천 버튼) · `context`(다음 요청에 돌려보낼 대화 맥락) 네 칸이 옵니다.

> 「이번 회차」 줄을 보시면 정액적립식은 「넣었어요 · 다음 회차는 ○월 ○일부터」라고 나옵니다. 회차는 달력의 1일~말일이 아니라 **가입일부터 한 달씩** 자른 기간입니다. 달력 기준이면 30일 가입 12개월 적금이 13번 낼 수 있게 되거든요.
> 자유적립식이면 회차 한도 안에서 [돈 넣기]로 여러 번 넣을 수 있고, 한도를 넘으면 「이번 회차에는 350,000원까지 더 넣을 수 있어요」처럼 남은 한도를 알려 줍니다.
> 만기일이 되면 서버가 1분마다 도는 작업에서 원금 + 이자를 출금 계좌로 보내고 알림을 남깁니다. 이자는 **실제 납입 기록마다** 계산해서, 놓친 회차만큼 이자가 줄어듭니다.

### 4-5. 카드 (4분)

**[화면]** 내 카드 `#/cards`
> 체크·신용 카드를 한 화면에 모았습니다. 카드마다 이번 달 쓴 돈, 낼 돈, 한 줄 혜택 요약이 보입니다.
> 아래 **결제 캘린더**에는 모든 카드의 청구서가 결제일별로 묶여 있습니다 — 11월 14일 206,100원. (11/14 이후에 발표하면 스케줄러가 이미 출금했으므로 숫자가 다르다 — 0장)
> 같은 결제 계좌에서 빠질 청구서를 결제일 순으로 **쌓아 더해서** 잔액과 비교하기 때문에, 잔액이 모자라면 「결제 계좌 잔액이 모자라요」 경고가 뜹니다.

**[화면]** 할인카드 `#/cards/card_003`
> 카드 상세입니다. 커피 55%, 대중교통·택시 33% 같은 혜택과 「18시~23시 결제만」, 「한 번에 최대 2,000원」 같은 조건이 보입니다.

> 「저녁 6~11시만」 같은 조건은 설명 글로만 두지 않고 스키마에 칸을 추가했습니다. 나중에 실제 할인 계산까지 가려고요.

**[화면]** 한빛체크카드 `#/cards/card_001`
> 혜택 위의 실적 안내 줄을 보시면 「지난달 ○원 썼어요. 300,000원 이상 쓰면 혜택을 받아요」, 못 받는 혜택에는 「실적 미달」 표시가 붙습니다.

> 업종을 「교통」으로 고르면 아래 업종인 택시·대중교통·카셰어링도 함께 나옵니다.

**[동작]** 주소창에 `#/cards/card_006` (다른 회원 카드)
> 「카드를 찾을 수 없어요」 — 아까 Swagger 에서 본 404 가 화면에서는 이렇게 보입니다.

### 4-6. 챗봇 (4분)

**[동작]** 오른쪽 아래 챗봇 버튼
> 처음 열면 LLM 을 부르지 않고 인사와 추천 질문 3개를 바로 보여 줍니다.

**① 내 정보 조회** — 「내 계좌 잔액 알려줘」
> 생활비 통장 1,250,000원, 비상금 통장 874,890원. Gemini 가 `my_accounts` 라는 Tool 을 골라 부른 결과입니다.
> 중요한 건 이 Tool 이 **계좌 화면과 같은 서버 함수**를 부른다는 점입니다. 그래서 「본인 것만」, 「해지 계좌 빼기」 규칙이 화면과 똑같이 적용됩니다.
> 그리고 회원 id 는 LLM 이 채우는 칸이 아니라 **세션에서** 넣습니다. 사용자가 「user_002 계좌 보여줘」라고 해도 LLM 이 그 값을 넣을 방법이 없습니다.

**② 대화 이어 가기** — 「그 중 첫 번째 계좌의 10월 출금 내역만 보여줘」
> 앞 대화에서 말한 계좌를 기억해서 10월 출금만 보여 줍니다. 「10월 출금」을 날짜 범위와 출금 방향으로 바꾸는 것도 LLM 이 합니다.

**③ 문서 근거 답 (RAG)** — 「예금거래기본약관 제12조 내용이 뭐야?」
**[화면]** 답과 출처가 나오면 PPT 「RAG — 문서에 근거해 답한다」 → 「왜 하이브리드인가」 슬라이드로 잠깐 넘겼다가 다시 챗봇으로 (약 1분)
> RAG 는 LLM 이 외운 지식으로 답하지 않고, **먼저 우리 문서에서 근거를 찾아 그걸 보고 답하게** 하는 방식입니다. 약관·금리 같은 내용은 LLM 이 지어내면 안 되니까요.
> **준비** — 우리은행 약관·상품설명서·FAQ 등 문서 130개를 조항 단위로 잘랐습니다. 조항 하나(parent, 2,394개)를 다시 1,000자 안의 조각(child, 3,037개)으로 자르고, 조각마다 Gemini 임베딩 벡터(768차원)를 PostgreSQL pgvector 에 넣었습니다. **찾을 때는 작은 조각으로, 답할 때는 조항 전체를** 넘깁니다. 작은 조각이 더 잘 찾히고, 답할 때는 조항 앞뒤가 다 필요하기 때문입니다.
> **찾기** — 두 가지 검색을 같이 씁니다. 뜻으로 찾는 **벡터 검색**은 「정기예금 깨면」을 「중도해지」로 알아듣지만, 「제12조」 같은 정확한 번호에 약합니다. 낱말로 찾는 **BM25** 는 그 반대입니다. 한국어는 「중도해지이율은」의 「은」 같은 조사가 붙어서 띄어쓰기로 자르면 다른 낱말이 되기 때문에, 형태소 분석기 Kiwi 로 잘라서 계산합니다.
> **합치기** — 두 검색의 점수는 단위가 달라 더할 수 없어서, 점수는 버리고 **순위만** 합칩니다(RRF, 각 검색의 1/(60+순위) 를 더함). 양쪽에서 다 찾힌 조항이 위로 올라옵니다. 그래서 이 질문에서는 벡터만 썼을 때 4위 안에도 없던 제12조가 1등입니다.
> **답하기** — 위에서 4개 조항을 Gemini 에 넘기고, 답 끝에 출처(문서 이름·조항)를 붙입니다. 근거가 없으면 「확인할 수 없어요」라고 답하게 했습니다.
> 아직 질문 2개로만 비교했고, 검색 품질을 숫자로 잴 평가 세트는 남은 과제입니다.

**④ 가입까지 이어지는 대화** — 「두린 적금 가입하고 싶어」 → 「20만 원씩 12개월」
> 여러 번에 나눠 말해도 상품·금액·기간을 **그래프 상태**에 이어 붙입니다. 그리고 돈이 움직이기 전에 **반드시 한 번 멈춰서** 확인을 받습니다.
> 지금 나온 확인 질문의 금리·만기일·이자는 LLM 이 쓴 게 아니라 **코드가 DB 값으로** 만든 문장입니다. 숫자를 LLM 이 지어낼 수 없게요.

**[동작]** 「네」 버튼
> 「네」를 누르면 금액·기간이 미리 채워진 **가입 화면 링크**가 나옵니다. 챗봇이 직접 가입하지 않고, 본인 확인이 있는 가입 화면으로 넘깁니다.
> 「네」 판정은 LLM 에게 묻지 않고 정해 둔 짧은 말만 인정합니다. 「네 근데 30만 원으로」처럼 애매하면 승인으로 보지 않고 새 요청으로 처리해서 30만 원으로 다시 묻습니다. 돈이 걸린 확인이라 일부러 보수적으로 했습니다.
> LangGraph 로 노드를 직접 그렸습니다 — `llm` → `tools` → `confirm`, 확인 노드에서 `interrupt` 로 멈췄다가 다음 말로 이어 갑니다.

**⑤ 남의 계좌는 「없음」** — 「acc_007 계좌 거래내역 보여줘」 (다른 회원 계좌)
> 「계좌를 찾을 수 없어요」 — Swagger 에서 본 404 `ACCOUNT_NOT_FOUND` 를 Tool 이 그대로 LLM 에 돌려주고, LLM 은 실패 이유를 지어내지 않고 그대로 전합니다. 「user_002 계좌 보여줘」라고 해도 회원 id 를 LLM 이 넣을 칸이 없어서 내 계좌만 나옵니다.

**⑥ 손님은 문서 검색만** (말로만, 또는 Swagger 에서 로그아웃 후 — 지금 로그인 화면에는 챗봇 버튼이 없다)
> 로그인하지 않은 손님에게는 LLM 에 **보이는 도구 목록 자체**가 문서·상품 검색뿐입니다. 프롬프트로 「손님에게는 계좌를 보여 주지 마」라고 시키는 건 LLM 이 어길 수 있지만, 도구가 없으면 할 수가 없습니다. 혹시 LLM 이 계좌 Tool 이름을 지어내 불러도 실행할 도구 목록에 없어서 실행되지 않습니다.

### 4-7. (시간이 남으면) 보안·정리 기능 (1분)

> PIN 은 바꾸기·만들기·다시 정하기가 있습니다. 111111 · 123456 · 생년월일은 금지이고, 5번 틀리면 10분 잠금입니다.

## 5. 정리 (약 2분)

### 5-1. 어떻게 확인했나

- 자동 테스트: 백엔드 전체 **371개 통과**, 화면 테스트 28개 통과 (2026-11-10, `docs/가이드북_예적금상품가입.md` 4-5. 2026-11-11 에 다시 세어도 371개). 시험 파일 19개 — 회원가입·인증·PIN·비밀번호·약관·탈퇴, 계좌 개설·상태, 이체 기능(`test_transfer_features.py`), 상품·적금, 카드·카드 신청, 챗봇, CORS
- 더미 데이터 정합성 게이트 `scripts/check_dummy.py` **오류 0** — 거래 중간 잔액이 음수가 없는지, 카드 청구 합계 = 승인내역 합계인지, 적금 납입 = 같은 날 같은 금액 출금인지 등
- 테스트는 실제 쿠키 로그인으로 돌리고, 챗봇은 API 키 없이 **가짜 LLM + 진짜 Tool·DB** 로 「흐름과 권한」을 고정했습니다.
- 가이드북마다 「실패 상황 직접 확인해 보기」 표에 기대 결과와 실제 결과를 적어 두어서, README 의 실패 상황 항목에 그대로 쓸 수 있습니다.

### 5-2. 남은 한계

- **챗봇** — 확인 대기 상태를 서버 메모리에 둬서 서버를 다시 켜면 사라집니다. 호출 횟수 제한이 없고, 검색 품질을 숫자로 잴 평가 세트도 아직 없습니다(질문 2개로만 비교). 카드 조회 Tool 은 아직 연결하지 않았습니다.
- **카드** — 혜택은 「보여 주기」까지만 하고, 결제마다 실제 할인 금액을 계산하지는 않습니다. 혜택 표는 원문 줄글을 사람이 옮긴 것이라 대조가 필요합니다. 신용카드 발급(모의 심사·한도), 마이데이터 연동·포인트·추천·예측은 2·3차입니다. 청구 기간 마감(쓰는 중 → 확정 청구서) 작업도 아직 없습니다.
- **예금·적금** — 자동 납입이 없고, 우대금리·중도해지 이율·세금은 계산하지 않습니다(세전 [모의 규칙]).
- **예약 작업** — 스케줄러가 서버 프로세스 안의 스레드라 서버가 꺼져 있으면 멈추고, 다시 켰을 때 밀린 것부터 실행합니다. 서버를 여러 대 띄우는 구조는 생각하지 않았습니다.
- **다른 은행 내역** — 회원과 다른 은행 계좌를 잇는 표가 없어 코드에 user_001 만 적어 두었습니다. 마이데이터 연결 기능을 만들면 표로 옮겨야 합니다.

### 5-3. 팀원과 맞출 것

- 거래·카드는 여러분 기획을 따라 제 서버에 먼저 만들어 둔 것입니다. **여러분이 정한 API 모양·상태 값과 다르면 알려 주세요**, 그쪽에 맞추겠습니다.
- 구현하면서 바꾼 공통 규칙(본인 확인 `action` 값 추가, 알림 종류 `SECURITY` 추가, 카드 관리 기록 `LINKED_ACCOUNT_CHANGE` 등)은 기획서 변경 이력과 `docs/sql/` 에 반영했습니다. 한 번 훑어봐 주시면 좋겠습니다.

## 6. 예상 질문과 답 (참고용)

| 질문 | 답 |
|---|---|
| 의도 분류는 어떻게 해요? | 따로 분류 단계가 없습니다. Gemini 가 대화를 읽고 어떤 Tool 을 부를지 직접 고릅니다(function calling). Tool 의 docstring 이 판단 재료예요. 대신 「누구 것인가 · 값이 맞나 · 실행해도 되나」는 코드가 정합니다. |
| 왜 PostgreSQL 기본 전문 검색 대신 BM25 를 따로 돌려요? | 한국어 형태소 분석기가 없어 띄어쓰기로만 잘라서 「중도해지이율은」과 「중도해지이율」이 다른 낱말이 됩니다. 그래서 파이썬에서 Kiwi 로 형태소를 자르고 `rank-bm25` 로 계산합니다. 조각이 3천 개 정도라 메모리로 충분합니다. |
| 남의 계좌를 403 이 아니라 404 로 주는 이유는? | 403 이면 「그 id 는 있다」는 사실이 새어 나갑니다. 없는 것과 글자 하나까지 같은 응답을 줍니다. |
| 본인 확인 번호를 가입 실패 때도 써 버리나요? | 아니요. 「사용함」 표시를 작업과 같은 트랜잭션에서 커밋해서, 작업이 실패해 롤백되면 번호도 다시 쓸 수 있습니다. |
| 이체할 때 동시에 A→B, B→A 가 오면? | 잔액 행을 계좌 id 가 작은 것부터 잠가서 데드락을 막습니다(`backend/app/ledger.py`). 원장 기록이 잔액을 음수로 만들면 예외로 트랜잭션 전체를 실패시킵니다. |
| 예약 송금은 누가 언제 실행해요? | 서버가 켜질 때 스레드 하나가 1분마다 `jobs.run_minutely()` 를 부릅니다. 한 건씩 따로 커밋해서 한 건이 실패해도 다른 예약은 돌고, 1회 예약은 상태를 먼저 「처리 중」으로 바꾼 쪽만 실행해 두 번 나가지 않습니다. |
| 다른 파트가 막는 이유를 어떻게 물어요? | 기획서의 `/internal/...` API 대신 같은 서버 안의 파트별 함수(`backend/app/internal.py`, 이름은 기획서 경로와 1:1)로 묻습니다. 팀원 서버가 생기면 함수 안만 HTTP 호출로 바꾸면 됩니다. |
| 서버를 왜 `--reload` 없이 켜요? | 이 PC 에서는 `--reload` 가 새 코드를 못 읽을 때가 있었습니다. 새 API 가 404 면 대개 예전 서버가 아직 떠 있는 것입니다. |
| 카드 혜택 크롤링, 문제 없어요? | robots.txt 에서 허용된 주소만, 공개 JSON API 로 받았고, 카드마다 1초씩 쉬었습니다. 학습용 모의 서비스 안에서만 쓰고 원문·출처·받은 날을 남겼습니다. 카드 이미지는 가져오지 않았습니다. |
