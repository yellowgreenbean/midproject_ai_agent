### 0-2. 왜 「py 파일 하나 실행」이 아니라 「서버 API」인가
```
 [브라우저 화면 frontend :5173]  ──HTTP 요청──▶  [FastAPI 서버 backend :8010]  ──SQL──▶  [PostgreSQL (Docker) :5433]
        버튼을 누른다                         검사·해시·저장을 한다                     데이터를 보관한다
```
- 브라우저 코드는 누구나 열어 볼 수 있다. 그래서 화면이 DB 에 직접 붙으면 DB 비밀번호가 그대로 드러난다 → **반드시 서버를 거친다.**
- 사용자가 버튼을 누를 때마다 실행돼야 하므로, 한 번 실행하고 끝나는 스크립트가 아니라 **계속 켜져 있는 서버의 API** 여야 한다.
- `scripts/*.py`(예: `seed_scenarios.py`)는 「처음에 데이터를 채워 넣는」 일회용 도구다. 이번에도 약관 4개를 넣는 데만 썼다.

### 0-3. 이번에 정한 규칙 (사용자 결정 2026-11-09)
| 질문 | 결정 |
|---|---|
| 가입 약관 | 토스식 4개: 서비스 이용약관(필수) · 전자금융거래 이용약관(필수) · 개인정보 수집·이용 동의(필수) · 마케팅 정보 수신 동의(선택) |
| 같은 이메일로 여러 계정? | **막는다** (1 이메일 = 1 계정, 탈퇴한 회원의 이메일은 다시 쓸 수 있음) |

## 1. Docker 는 무슨 일을 했나

### 1-1. 역할
Docker 는 **PostgreSQL 데이터베이스를 내 PC 에 설치하지 않고 「상자(컨테이너)」 안에서 돌리는 도구**다.
- 설정 파일: `backend/docker-compose.yml`
- 이미지: `pgvector/pgvector:pg17` (PostgreSQL 17 + 챗봇 RAG 용 벡터 확장)
- 컨테이너 이름: `midproject-postgres`
- 포트: 내 PC 의 **5433** → 상자 안 5432 (이 PC 에는 이미 다른 PostgreSQL 이 5432 를 써서 5433 으로 열었다)
- 접속 정보: 사용자 `app` / 비밀번호 `app` / DB `midproject` (개발용), `midproject_test` (테스트용)
- 데이터는 **볼륨** `postgres-data` 에 저장된다 → 컨테이너를 껐다 켜도, 이미지를 바꿔 다시 만들어도 데이터는 남는다.
  (`docker compose down -v` 처럼 `-v` 를 붙이면 볼륨까지 지워진다 — 조심)

### 1-2. 이번 작업에서 Docker 로 한 일
| 순서 | 명령 | 하는 일 |
|---|---|---|
| ① | `cd backend` → `docker compose up -d --wait` | DB 상자를 켠다. `--wait` 는 DB 가 접속을 받을 준비(healthy)가 될 때까지 기다린다 |
| ② | `docker exec -i midproject-postgres psql -U app -d midproject -v ON_ERROR_STOP=1 < seed.sql` | 약관 4개가 들어간 시드 SQL 을 DB 에 넣는다 (`docker exec` = 상자 안에서 명령 실행) |
| ③ | `docker exec midproject-postgres psql -U app -d midproject -c "SELECT ..."` | 가입 결과가 DB 에 들어갔는지 직접 본다 |
| ④ | (테스트) `pytest` | 테스트가 같은 상자 안의 `midproject_test` DB 를 매번 지우고 새로 만들어 쓴다 → 개발 DB 는 건드리지 않음 |

> 서버(FastAPI)와 화면(Vite)은 Docker 가 아니라 **내 PC 에서 바로** 돌린다. Docker 는 DB 만 맡는다.

### 1-3. 처음 켰을 때 본 경고 (정렬 규칙 버전)
이미지를 `postgres:17` → `pgvector/pgvector:pg17` 로 바꾸자 이런 경고가 나왔다.
```
WARNING:  database "midproject" has a collation version mismatch
```
두 이미지의 운영체제 문자 정렬 라이브러리 버전이 달라서다. 문자열 인덱스를 다시 만들고 버전을 맞추면 사라진다(데이터는 그대로).
```bash
docker exec midproject-postgres psql -U app -d midproject -c "REINDEX DATABASE midproject" -c "ALTER DATABASE midproject REFRESH COLLATION VERSION"
docker exec midproject-postgres psql -U app -d midproject_test -c "REINDEX DATABASE midproject_test" -c "ALTER DATABASE midproject_test REFRESH COLLATION VERSION"
```

## 2. DB 의 어떤 표를 쓰나 (`docs/sql/01_users.sql`, `docs/sql/05_card_products.sql`)

표는 **이미 만들어져 있었다**(docs/sql 이 원본, Docker 첫 기동 때 자동 생성). 이번에 표 구조는 바꾸지 않았다.

| 표 | 가입 때 들어가는 것 | 중요한 제약 |
|---|---|---|
| `users` | 회원 1행: `id`(예: `user_6d7b…`), `username`, `name`, `email`, `email_verified_at`, `birth_date`, `gender`, `payday`, `status='ACTIVE'` | `uk_users_username UNIQUE(username)` → **같은 아이디는 DB 가 최종으로 막는다** |
| `auth_identities` | 로그인 수단 1행: `provider='LOCAL'`, `provider_subject=아이디` | 로그인(`/auth/login`)이 이 표로 아이디를 찾는다 |
| `local_credentials` | 비밀번호 **해시** 1행 (`$argon2id$...`) | 원문 비밀번호는 어디에도 저장하지 않는다 |
| `user_consents` | 약관마다 1행 (동의 `true` / 선택 약관을 안 고르면 `false`) | 「어떤 버전에 언제 동의했는지」 기록 |
| `email_verifications` | 인증번호를 보낼 때 1행 → 가입이 끝나면 지움 | 인증번호는 해시(`challenge_digest`)로만 저장 |
| `terms` | (시드) 공통 약관 4행 `trm_001`~`trm_004` | `card_product_id IS NULL` = 카드 약관이 아닌 공통 약관 |
| `sessions` | 가입 직후 자동 로그인 세션 1행 | 쿠키 원문이 아니라 해시만 저장(원래 로그인과 같음) |
| `auth_audit_logs` | `event_type='SIGNUP'` 기록 1행 | 감사 기록(기획서 8.1-7) |

### 로그인은 DB 를 어떻게 확인하나 (원래 있던 코드, `backend/app/routers/auth.py`)
```python
row = db.execute(
    select(User, LocalCredential)
    .join(AuthIdentity, AuthIdentity.user_id == User.id)
    .join(LocalCredential, LocalCredential.user_id == User.id)
    .where(AuthIdentity.provider == "LOCAL", AuthIdentity.provider_subject == body.username)
).first()
```
- 아이디로 `auth_identities` → `users` → `local_credentials` 를 이어 찾는다.
- 없는 아이디·틀린 비밀번호·탈퇴 회원은 **모두 같은** `401 INVALID_CREDENTIALS` — 「그 아이디가 있는지」를 남에게 알려 주지 않으려고.
- 그래서 가입 때 `auth_identities` 와 `local_credentials` 를 꼭 같이 만들어야, 가입한 아이디로 바로 로그인된다.

### 3-2. FastAPI 의 기본 모양 (이번 코드에 반복해서 나옴)
```python
router = APIRouter(tags=["signup"])            # API 묶음. main.py 에서 app.include_router(...) 로 등록

class EmailSendIn(BaseModel):                   # 요청 본문(JSON)의 모양 — Pydantic 이 타입·길이를 먼저 검사(틀리면 422)
    email: str = Field(max_length=254)
    purpose: Purpose = "SIGNUP"

@router.post("/auth/email-verifications", response_model=EmailSendOut, status_code=201)
def send_email_code(body: EmailSendIn, db: DB):  # db: 요청마다 DB 연결 하나 (app/deps.py 의 DB)
    ...
    raise ApiError(409, "EMAIL_TAKEN", "이미 가입된 이메일이에요.")   # 오류는 이렇게 → {"success":false,"error":{...}}
    ...
    db.add(row); db.commit()                    # SQLAlchemy: 행 추가 → 커밋해야 DB 에 실제로 저장
    return EmailSendOut(...)                    # 성공 응답(JSON)
```
- `ApiError` (`app/errors.py`): 기획서 7.1 오류 모양 `{"success": false, "error": {"code", "message"}}` 으로 바꿔 준다. 화면은 `message` 를 그대로 보여 준다.
- `select(...)`, `db.scalar(...)`: SQLAlchemy 로 SQL 을 만든다. 예) `select(User.id).where(User.username == "abc")` ≒ `SELECT id FROM users WHERE username='abc'`
- 모델(`app/models/`)은 `scripts/gen_models.py` 가 DB 를 읽어 만든 것 — **손으로 고치지 않는다**.

### 3-3. API 별 설명 (`backend/app/routers/signup.py`)

#### ① `GET /terms` — 약관 목록
```python
select(Terms).where(Terms.card_product_id.is_(None)).order_by(Terms.required.desc(), Terms.id)
```
공통 약관만, 필수 먼저. 응답 `[{"id":"trm_001","title":"서비스 이용약관","required":true,"version":"1.0",...}, ...]`

#### ② `GET /auth/usernames/availability?username=...` — 아이디 중복 확인
1. 형식 검사 `^[a-z][a-z0-9_]{3,19}$` (영문 소문자로 시작, 4~20자) → 틀리면 `400 INVALID_USERNAME`
2. `users` 에 같은 `username` 이 있는지 → `{"available": true}` 또는 `{"available": false}`
- 「사용 가능」은 **예약이 아니다**. 확인 뒤 다른 사람이 먼저 가입할 수 있으므로 ⑤ 가입 때 다시 검사한다(기획서 AUTH-F02).

#### ③ `POST /auth/email-verifications` — 인증번호 발송
1. 이메일 정리(앞뒤 공백 제거, 소문자로) + 형식 검사 → `400 INVALID_EMAIL`
2. 가입 용도인데 이미 가입된 이메일이면 → `409 EMAIL_TAKEN` (1 이메일 = 1 계정)
3. 같은 이메일로 60초 안에 또 요청 → `429 EMAIL_RESEND_TOO_SOON`
4. 24시간 안에 10번 넘게 → `429 EMAIL_SEND_LIMIT`
5. 6자리 번호를 만들고 `email_verifications` 에 **해시만** 저장: `SHA-256("행id:번호")`, 만료 = 지금 + 5분
6. 응답 `{"expires_at", "resend_at", "dev_code"}`
- **`dev_code` = 모의 메일.** 실제 메일 서버가 없으니 번호를 응답에 담아 주고, 화면이 「(모의 메일 — 인증번호 123456)」로 보여 준다.
  실제 서비스라면 이 칸을 지우고 메일을 보내야 한다(코드에 `shortcut:` 주석으로 표시).
- 표에 「보낸 시각」 칸이 없어서 `만료 시각 − 5분` 으로 계산한다.

#### ④ `POST /auth/email-verifications/confirm` — 인증번호 확인
1. 그 이메일·용도의 **가장 최근** 행만 본다 → 새 번호를 받으면 예전 번호는 자동으로 무효
2. 없거나 이미 씀 → `400 EMAIL_VERIFICATION_NOT_FOUND` / 5분 지남 → `400 EMAIL_VERIFICATION_EXPIRED` / 5번 틀림 → `429 EMAIL_VERIFICATION_LOCKED`
3. 틀리면 `attempt_count + 1` 후 `400 EMAIL_CODE_MISMATCH` ("4번 더 시도할 수 있어요")
4. 맞으면 무작위 **인증 토큰**을 만들어 돌려준다. 행에는 `used_at = 지금`, `challenge_digest = SHA-256(토큰)` 으로 바꿔 저장
   → 이 행은 이제 「이 이메일은 인증됨」 증표. 토큰 원문은 DB 에 없다.
- `with_for_update()` (행 잠금): 같은 번호로 동시에 두 번 확인해도 하나만 통과.
- `secrets.compare_digest`: 비교 시간이 일정해서 시간 차로 정답을 추측할 수 없다.

#### ⑤ `POST /auth/register` — 회원가입 (DB 에 아이디 저장)
코드 안 번호 주석(1~6)과 같은 순서다.
1. **모든 값을 서버가 다시 검사** (화면 검사는 편의일 뿐 — 화면을 거치지 않고 요청을 보낼 수도 있으니까)
   아이디 형식 · 비밀번호(8~64자, 영문+숫자, 아이디 포함 금지) · 비밀번호 확인 일치 · 이메일 · 이름(한글/영문 2~20자) · 생년월일(1900-01-01 ~ 오늘) · 성별 `M/F` · 월급일 1~31 또는 빈 값
2. **인증 토큰 확인**: 그 이메일 + 가입 용도 + `SHA-256(토큰)` 이 맞고, 인증한 지 30분 안 → 아니면 `400 EMAIL_NOT_VERIFIED`
3. **약관**: 모르는 약관 id → `400 INVALID_TERMS`, 필수 약관 하나라도 빠짐 → `400 REQUIRED_TERMS_NOT_AGREED`
4. **중복 재검사**: 아이디 → `409 USERNAME_TAKEN`, 이메일 → `409 EMAIL_TAKEN`
5. **만들기** (한 트랜잭션 — 중간에 실패하면 전부 취소)
   ```python
   db.add(user)
   db.flush()      # ← 회원을 먼저 DB 에 보낸다 (이유는 4장 「겪은 문제 ①」). 동시에 같은 아이디면 여기서 IntegrityError → 409
   db.add(AuthIdentity(... provider="LOCAL", provider_subject=아이디))
   db.add(LocalCredential(... password_hash=hash_password(비밀번호)))   # Argon2id 해시
   for t in terms: db.add(UserConsent(... agreed=t.id in agreed))      # 약관마다 1행, 안 고른 선택 약관은 false
   db.delete(proof)   # 인증 토큰은 1회용 → 증표 행 삭제
   ```
6. **바로 로그인**: `start_session()` (로그인과 같은 함수) → 쿠키 `sid` 발급 + `auth_audit_logs` 에 `SIGNUP` 기록 → `db.commit()`
   응답 `201 {"user_id","username","name","status":"ACTIVE"}`

### 3-4. 보안에서 지킨 것 (기획서 8.1)
| 항목 | 어떻게 |
|---|---|
| 비밀번호 원문 저장 금지 | Argon2id 해시만 `local_credentials` 에. 요청 모델에 `repr=False` 로 로그 출력에도 안 남게 |
| 인증번호 원문 저장 금지 | SHA-256 해시만. 행 id 를 섞어 같은 번호라도 해시가 다름 |
| 중복 아이디 동시 가입 | 가입 직전 재검사 + DB `UNIQUE` 제약이 최종 방어 |
| 인증 토큰 재사용 | 가입 성공 시 증표 행 삭제, 행 잠금으로 동시 사용 차단 |
| 다른 사이트에서 가입 요청 | 원래 있던 `check_origin` 미들웨어(`app/main.py`)가 허용 주소가 아닌 POST 를 403 |

## 4. 겪은 문제와 해결 (같은 일을 다시 할 때 참고)

### ① 가입하면 「이미 사용 중인 아이디예요」가 뜸 (새 아이디인데도)
- **원인**: 모델(`app/models/`)에 `relationship()` 이 없어서 SQLAlchemy 가 표 사이 순서를 모른다.
  그래서 `user_consents` 를 `users` 보다 **먼저** INSERT → 외래 키 위반(IntegrityError) → 그걸 「아이디 중복」으로 잡고 있었다.
- **찾은 방법**: SQL 로그를 켜고 한 번 호출해 봤다.
  ```python
  import logging; logging.basicConfig(); logging.getLogger("sqlalchemy.engine").setLevel(logging.INFO)
  ```
  → `INSERT INTO user_consents ...` 다음 바로 `ROLLBACK` 이 보였다.
- **해결**: `db.add(user)` 직후 `db.flush()` 로 회원을 먼저 보내고, **그 단계의 IntegrityError 만** 아이디 중복으로 본다.

### ② curl 로 가입하면 `There was an error parsing the body`
- **원인**: Windows 명령줄이 한글("가이드")을 깨뜨려 JSON 이 망가짐. 서버 문제가 아니다.
- **해결**: 본문을 UTF-8 파일로 만들어 `--data-binary @body.json` 으로 보내거나, 아래 5-3 의 Swagger 화면을 쓴다.

### ③ 서버를 켰는데 `[WinError 10013]` 로 바로 꺼짐 / 새 API 가 404
- **원인**: 예전에 켠 서버가 아직 8010 을 쓰고 있었다(옛 코드로 대답 → 새 주소는 404 `NOT_FOUND`).
- **해결**: 예전 서버 창에서 `Ctrl + C`. 창을 못 찾으면 PowerShell 로:
  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where-Object CommandLine -like "*uvicorn*" | Select ProcessId, CommandLine
  Stop-Process -Id <위에서 나온 번호>
  ```
- 개발할 때는 `--reload` 를 붙여 켜면 코드를 저장할 때마다 서버가 저절로 다시 뜬다.

## 6. 약관 본문 크롤링 — 서비스 이용약관 (`trm_001`)

> 2026-11-09 추가. 토스 「서비스 이용약관」 웹페이지를 받아 `data/rag/terms/service_terms.md` 로 저장한 과정이다.
> 이 파일은 **가입 약관 본문**(`terms.content_url`)이면서 **챗봇 RAG 자료**(`scripts/rag_ingest.py` 가 `data/rag/*/*.md` 를 모두 읽음)로도 쓰인다.

### 6-1. 왜 필요한가
- DB 의 `terms` 표에는 약관 **본문 위치**를 적는 `content_url` 칸이 있다. 시드에서 `trm_001` 은 본문 파일 경로를 가리키지만, **파일이 없었다**.
- 토스 클론이므로 토스의 실제 약관을 원본으로 쓴다. 다른 원본 자료(`data/rag/` 의 우리은행 PDF)처럼 **내용은 고치지 않고 출처를 적는다**.

### 6-2. 크롤링 전에 확인할 3가지
| 확인 | 방법 | 결과 (2026-11-09) |
|---|---|---|
| ① 가져가도 되는 주소인가 | `https://toss.im/robots.txt` 를 열어 `Disallow:` 목록에 `/docs` 가 있는지 본다 | `/docs/` 는 막혀 있지 않음 |
| ② 본문이 HTML 에 바로 들어 있나 | 아래 명령으로 받아서 본문 글자(`제1조`)가 보이는지 확인. 안 보이면 자바스크립트가 나중에 그리는 페이지라 브라우저 자동화가 필요하다 | 들어 있음 → `requests` 로 충분 |
| ③ 어떻게 쓸 것인가 | 학습용 모의 서비스 안에서만, 원문 그대로, 출처·시행일·받은 날을 파일 맨 위에 적는다 | `docs/domain-rules.md` 5-4 에도 기록 |

### 6-4. 스크립트 — `scripts/crawl_toss_terms.py`
이미 설치된 `requests`(페이지 받기) + `beautifulsoup4`(HTML 읽기)만 쓴다. `qna_crawler/` 의 우리은행 FAQ 크롤러와 같은 도구다.
```bash
pip install requests beautifulsoup4     # (처음만, 이미 있으면 건너뜀)
```
| 부분 | 하는 일 |
|---|---|
| `fetch(url)` | `requests.get(..., timeout=20)` 으로 받는다. `User-Agent` 에 공부용 크롤러라고 적고, `raise_for_status()` 로 404·500 이면 바로 멈추며, 한글이 깨지지 않게 `encoding = "utf-8"` |
| `to_markdown(html, …)` | `<h1>` 을 찾고 그 부모 `<div>` 를 본문으로 본다. 드롭다운에서 시행일·현재판 주소를 꺼내 파일 맨 위 **앞머리**(`---` 사이 `source:`·`effective:`·`fetched:`)에 넣는다. `pdf_to_md.py` 가 만든 `.md` 와 같은 모양이라 `rag_ingest.py` 가 `source:` 를 출처로 읽고, 앞머리는 본문 조각에 넣지 않는다 |
| 줄 규칙 (정규식) | `^제\s*\d+\s*장` → `## 제목` · `^제\s*\d+\s*조(의\s*\d+)?\s*\(` → `### 제목` · `- 부칙 -` / `- 부속약관 -` → `## 부칙` / `## 부속약관` (부속약관 다음 줄 = 그 약관 이름 → `###`) · 그 밖의 `<p>` 는 문단 그대로 · 빈 `<p>` 는 버림 |
| 안전장치 | 제목이나 조항을 하나도 못 찾으면 **파일을 만들지 않고 멈춘다** — 토스가 페이지 구조를 바꾸면 빈 약관 파일이 생기는 대신 오류로 알 수 있게 |

## 8. 본인 확인 — `POST /auth/step-up`

### 8-1. 왜 필요한가
이체·카드 해지·탈퇴처럼 되돌리기 어려운 작업은, 로그인해 있어도 **바로 직전에 비밀번호를 한 번 더** 받는다(기획서 Part 1 7장, 9.3).
간편 비밀번호(PIN)는 3차라서 지금은 로그인 비밀번호로 확인한다.

### 8-2. 정한 규칙 (사용자 결정 2026-11-09)
| 항목 | 값 | 어디에 |
|---|---|---|
| 본인 확인 번호 유효 시간 | **5분** | `app/rules.py` `STEP_UP_TTL` |
| 쓸 수 있는 범위 | **한 번만 · 받은 작업(action)에만 · 받은 로그인 세션에서만** | `consume_step_up()` |
| 비밀번호 연속 실패 | **5번이면 영구 잠금** (`423 STEP_UP_LOCKED`, 「영업점 방문」 안내). 시드 `user_027` 이 이 상태 | `STEP_UP_MAX_FAILURES` |
| 실패를 세는 곳 | `local_credentials.failed_attempts` (로그인 실패는 세지 않음, 기획서 6.3) | |

작업 이름(`action`)은 DB 의 허용 값과 같다: `TRANSFER`(이체) · `SCHEDULED_TRANSFER`(예약 취소·자동이체 해지) · `CARD_TERMINATION`(카드 해지) ·
`CARD_MANAGEMENT`(카드 대금 결제) · `SUBSCRIPTION`(예금·적금 중도 해지) · `ACCOUNT_STATUS_CHANGE`(계좌 정지 해제) · `WITHDRAWAL`(탈퇴) · `PROFILE_CHANGE`.

### 8-3. 코드 (`backend/app/routers/auth.py`)
```python
@router.post("/step-up", status_code=201)
def step_up(body: StepUpIn, login: ..., db: DB):
    cred = db.get(LocalCredential, user.id, with_for_update=True)   # 동시에 여러 번 틀려도 횟수가 정확하게
    if cred.failed_attempts >= 5: raise step_up_locked()            # 423
    if not verify_password(cred.password_hash, body.password):
        cred.failed_attempts += 1; db.commit()                        # 실패도 저장하고
        raise ApiError(400, "STEP_UP_FAILED", "… N번 더 틀리면 잠겨요.")
    cred.failed_attempts = 0
    db.add(StepUpChallenge(id=new_id("stu"), action=body.action, session_id=..., expires_at=now + 5분))

def consume_step_up(db, challenge_id, login, action):   # 이체·해지 같은 작업 API 가 부른다
    ch = db.get(StepUpChallenge, challenge_id, with_for_update=True)
    if (없음 or 남의 것 or 다른 세션 or 다른 작업 or 이미 씀 or 5분 지남): raise 403 STEP_UP_REQUIRED
    ch.consumed_at = now     # 커밋은 작업과 같이 → 작업이 실패해 롤백되면 번호도 다시 쓸 수 있다
```
- `step_up_challenges.session_id` 가 필수 칸이라, 개발용 `X-User-Id` 헤더(세션 없음)로는 받을 수 없다(401).
- 쓰기 API 는 공통 의존성 `CurrentLogin`(`app/deps.py`)으로 「세션 있는 로그인 + 가입 마무리 중이 아님」을 받는다.

### 8-4. 직접 해 보기 (Swagger `http://localhost:8010/docs`)
1. `POST /auth/login` 으로 로그인 (브라우저에 쿠키가 생김)
2. `POST /auth/step-up` 에 `{"action": "WITHDRAWAL", "password": "<비밀번호>"}` → `step_up_challenge_id`
3. 틀린 비밀번호로 5번 → 다섯 번째에 `423 STEP_UP_LOCKED`. 잠금을 풀려면(개발 DB):
   ```bash
   docker exec midproject-postgres psql -U app -d midproject -c "UPDATE local_credentials SET failed_attempts = 0 WHERE user_id = '<회원 id>'"
   ```

### 9-3. 최종 탈퇴의 순서 — 한 트랜잭션 (하나라도 실패하면 아무것도 안 바뀜)
```
1. 회원 행 잠금 → 본인 확인 번호 사용(WITHDRAWAL)
2. 잔액 행을 먼저 잠그고 ①②③ 다시 검사   ← 검사~해지 사이에 입금이 끼어들지 못하게
3. 남은 계좌 모두 해지(CLOSED) + account_activity_logs 에 CLOSE {"reason": "회원 탈퇴"}
   (잔액 0원 정지 계좌도 정지 해제 없이 해지 — 기획서 확정 예외, 이 경로에서만)
4. users.status = WITHDRAWN, withdrawn_at · 모든 기기 로그아웃(sessions.revoked_at) · 점검 행 COMPLETED
5. 모든 약관 동의 철회 — 동의 중인 약관마다 agreed=false 행을 더한다(이력은 남김)
6. 즉시 삭제 (자식 표부터) · 감사 기록 WITHDRAWAL
```
**왜 세션은 지우지 않고 「끊기」만?** `step_up_challenges.session_id` 가 세션을 가리키고, 그 본인 확인 기록은 5년 보존하는 이체·카드 기록이 가리킨다.
세션 행을 지우면 DB 가 외래 키 위반으로 거부한다. 그래서 `revoked_at` 만 채운다.

### 9-5. 화면 안내문을 고친 이유
탈퇴 화면 ② 문구가 「아이디 1개월 뒤 삭제」, 「로그인 기록 바로 삭제」였는데 실제 동작은 반대(아이디 영구 보존, 로그인 기록 5년 보존)였다.

### 9-6. 겪은 문제
- **PostgreSQL 은 LEFT JOIN 의 빈칸 쪽을 잠글 수 없다** (`FOR UPDATE cannot be applied to the nullable side of an outer join`).
  계좌 + 잔액을 LEFT JOIN 하며 잔액 행을 잠그려다 실패 → 잔액 행만 잠그는 문장을 따로 먼저 실행했다(`internal.account_readiness`).
- **응답 시각에 마이크로초가 붙었다** — DB 칸이 `TIMESTAMP(0)`(초 단위)인데 파이썬 값을 그대로 돌려줘서. `now.replace(microsecond=0)`.

**잔액을 바꾸는 순서 — `backend/app/ledger.py`** (기획서 Part 5 14장)
```python
bals = ledger.lock_balances(db, [계좌들])      # 잔액 행을 계좌 id 가 작은 것부터 FOR UPDATE (A→B, B→A 동시 이체의 데드락 방지)
# … 잠근 채로 잔액·상태 확인 …
ledger.post(db, bals[acc], "TRANSFER_OUT", 금액, now, display_name=…)   # 원장 한 줄 + 잔액 변경
```
이체(`TRANSFER_OUT/IN`) · 중도 해지(`SUBSCRIPTION_PAYOUT`) · 카드 대금(`CARD_PAYMENT`)이 모두 이 두 함수를 쓴다.
`post()` 는 잔액이 음수가 되면 예외를 던져 트랜잭션째 실패시킨다(확인이 빠진 버그를 돈 손실 대신 오류로).

**같은 모양의 쓰기 API** — 모두 `{"step_up_challenge_id": …}` 를 받고, ① 내 것인지 확인(남의 것은 404) ② `consume_step_up()` ③ 상태 확인 ④ 잠그고 바꾸기 ⑤ `db.commit()`.

### 10-6. 이체 실행의 흐름 (`create_transfer`)
```
1. 같은 Idempotency-Key 로 이미 처리했나? → 그 결과를 그대로 (버튼 두 번 = 한 번만 나감)
2. 입력: 금액 1원 이상 정수 · 은행이 목록에 있나 · 자릿수 · 받는 계좌 찾기 · 같은 계좌 금지   → 400/404 (이체 행 안 만듦)
     두린은행 → accounts."resAccount" / 다른 은행 → external_accounts(가상 타행)
3. 본인 확인(TRANSFER) · RESTRICTED 회원은 본인 명의 계좌로만 → 403 RESTRICTED_TRANSFER
4. 잔액 행 잠금 → 상태·한도(1회·1일)·잔액 확인
     걸리면 FAILED + 사유(ACCOUNT_NOT_ACTIVE / LIMIT_EXCEEDED / INSUFFICIENT_BALANCE / INVALID_ACCOUNT) — 원장 없음, 201 로 결과를 돌려줌
     통과하면 SUCCESS + 원장(두린은행: 출금·입금 / 다른 은행: 출금만, 받는 쪽은 서비스 밖)
   다른 은행 시험 계좌: 예금주 「임처리」 → PENDING(원장 없음, 10분 뒤 jobs 가 확정) / 「오실패」 → FAILED
```
- **본인 명의 판단:** 가상 타행 표에는 회원 id 가 없어 **예금주 이름 = 회원 이름**이면 본인 명의로 본다(받는 계좌 확인 API 의 `is_mine` 도 같은 규칙).
- 수수료는 0원(기획서 4장 기본안, 타행도 0원).

### 10-11. 쓸모 있는 SQL — 회원별 탈퇴를 막는 항목 세기
```sql
SELECT u.id, u.status,
  (SELECT count(*) FROM accounts a JOIN account_balances b ON b.account_id = a.id
    WHERE a.user_id = u.id AND a.lifecycle_status <> 'CLOSED' AND b.balance > 0)                       AS 잔액,
  (SELECT count(*) FROM transfers t WHERE t.user_id = u.id AND t.status = 'PENDING')                    AS 처리중,
  (SELECT count(*) FROM subscriptions s WHERE s.user_id = u.id AND s.status = 'ACTIVE')                AS 예적금,
  (SELECT count(*) FROM scheduled_transfers s WHERE s.user_id = u.id
    AND s.status IN ('SCHEDULED','PROCESSING','ACTIVE','PAUSED'))                                      AS 예약자동,
  (SELECT count(*) FROM user_cards c WHERE c.user_id = u.id AND c.source = 'TOSS_ISSUED'
    AND c.status <> 'TERMINATED')                                                                     AS 카드
FROM users u WHERE u.status <> 'WITHDRAWN' ORDER BY u.id;
```
`docker exec -it midproject-postgres psql -U app -d midproject` 로 들어가서 붙여 넣는다.

### 10-13. 겪은 문제
- **셸 명령 하나에 긴 파이썬 코드를 넣었다가 따옴표 해석 오류로 통째로 실행이 안 됐다.** 긴 코드는 파일로 쓴 뒤 붙이거나 편집 도구로 나눠 넣는다.
- **카드 상세 응답 모양이 크다(혜택·한도·청구서).** 화면 코드를 읽어 실제로 쓰는 칸만 정확히 채우고, 혜택은 빈 목록으로 두었다(탈퇴 정리에 필요 없음).
- **「지금 탈퇴할 수 있는 회원은 새로 가입한 회원뿐」이라고 처음에 잘못 말했다** — 짐작 대신 10-11 의 SQL 로 세어 보니 12명은 이미 가능했다. 데이터에 대한 말은 세어 보고 한다.

### 11-2. 서버가 새 코드를 못 읽을 때 (2026-11-09 두 번 겪음)
- `--reload` 는 파일이 바뀌면 서버를 다시 켜는 기능이다. `backend` 전체를 지켜보면 패키지 설치(`.venv` 안 파일 수천 개)에도 반응하다가 꼬였고,
  옛 코드를 실행하던 **작업자 프로세스가 남아** 같은 포트로 응답했다 → 새 API 가 404.
- `--reload-dir app` 으로 코드 폴더만 지켜보게 했지만, 이 PC(한글 경로·Windows)에서는 「Reloading…」 뒤 새 서버가 안 뜨는 일이 또 생겼다.
- **지금은 `--reload` 없이 켠다.** 코드를 고치면 서버 창에서 `Ctrl + C` 후 다시 켠다.
  ```bash
  cd backend
  .venv\Scripts\python -m uvicorn app.main:app --port 8010
  ```
- 새 API 가 404 면, 남은 서버를 찾아 번호로 끈다:
  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Select ProcessId, ParentProcessId, CreationDate, CommandLine
  Stop-Process -Id <uvicorn 이나 spawn_main 이 들어간 줄의 번호>
  ```
  `CreationDate` 가 코드를 고치기 전이면 옛 서버다.

### 11-3. 개발 DB 가 `docs/sql` 정의대로인지 확인하는 법

```bash
for f in docs/sql/0*.sql; do docker exec -i midproject-postgres psql -U app -d schema_check -q -v ON_ERROR_STOP=1 < "$f"; done

docker exec midproject-postgres pg_dump -U app -d schema_check --schema-only --no-owner --no-privileges > b.sql
diff a.sql b.sql                  # 다른 줄이 \restrict … (pg_dump 가 매번 바꾸는 토큰) 뿐이면 같다

```

- **예약 실행 배치가 없다** — 예약 송금·자동이체가 실행 시각이 와도 나가지 않는다. 그래서 실행 시각이 지난 예약은 취소를 허용했다(만들면 이 예외를 없앤다).
- **청구서 확정 배치가 없다** — 이번 기간 사용액이 결제일 전에 `CONFIRMED` 청구서로 저장되지 않는다(화면에는 계산해서 「쓰는 중」으로 보임). 결제일 일괄 출금은 저장된 확정 청구서만 낸다.
- **연회비 환급은 0원으로 기록**한다 — 원장에 환급 입금 유형이 없다. 할부는 해지한 카드의 이번 기간 선결제 때 1회차로 묶어 처리한다.
- **본인 명의 판단이 예금주 이름 비교**다 — 이름이 같은 다른 사람의 타행 계좌도 본인 명의로 보인다(가상 타행에 회원 id 가 없어서).
- 같은 `Idempotency-Key` 이체가 **정확히 동시에** 오면 둘째는 DB 고유 제약에 걸려 500 이 난다(돈은 한 번만 나감).
- 최근 보낸 계좌는 두린은행만 보여 준다(화면의 간편 송금 목록에 은행 칸이 없어서).
- 카드 이용 내역(`GET /cards/{id}/transactions`)·혜택·카드 신청은 아직 없다 — 카드 상세에서 그 구역만 비거나 오류 문구가 보인다.
- 서버 `--reload` 가 이 PC 에서 불안정하다(11-2).

### 13-1. 시작할 때 있던 것 / 없던 것

### 13-3. API 정의

모두 `backend/app/routers/password.py`. 오류 모양은 다른 API 와 같다: `{"success": false, "error": {"code": "...", "message": "..."}}`.
이메일 인증 토큰은 앞의 3-3 ③④(`POST /auth/email-verifications` → `/confirm`)로 받는다 — `purpose` 만 다르게.

#### ① `POST /auth/username-recovery` — 아이디 찾기 (로그인 필요 없음)
```jsonc
// 요청 — purpose: USERNAME_RECOVERY 로 받은 이메일 인증 토큰
{ "email": "findme.one@example.com", "email_verification_token": "<token>" }
// 200 응답 — 가입한 아이디가 없으면 []
[ { "username": "fin*******", "created_at": "2026-11-10T14:03:21+09:00" } ]
```
| 오류 | 언제 |
|---|---|
| `400 INVALID_EMAIL` | 이메일 형식이 틀림 |
| `400 EMAIL_NOT_VERIFIED` | 토큰이 없음 · 다른 용도(예: 가입용) · 인증 후 30분 지남 · 이미 씀(토큰은 한 번만) |

#### ② `POST /auth/password-resets` — 재설정 ① 아이디·이메일 확인 (로그인 필요 없음)
```jsonc
// 요청 — purpose: PASSWORD_RESET 로 받은 이메일 인증 토큰
{ "username": "findme_one", "email": "findme.one@example.com", "email_verification_token": "<token>" }
// 201 응답 — reset_token 원문은 이 응답에만 있고 DB 에는 해시만
{ "reset_token": "<43자 무작위>", "expires_at": "2026-11-10T14:10:00+09:00" }
```
| 오류 | 언제 |
|---|---|
| `400 EMAIL_NOT_VERIFIED` | ①과 같음 |
| `400 IDENTITY_MISMATCH` | 아이디와 이메일이 같은 회원 것이 아님(없는 아이디 · 남의 아이디 · 비밀번호 없는 계정 · 탈퇴 회원). **이메일 인증 토큰은 쓰지 않은 채로 남는다** |

#### ③ `POST /auth/password-resets/confirm` — 재설정 ② 새 비밀번호 (로그인 필요 없음)
```jsonc
{ "reset_token": "<②의 토큰>", "new_password": "secondpass456", "new_password_confirm": "secondpass456" }
// 204 응답 (본문 없음) — 이 회원의 모든 세션이 끊긴다
```
| 오류 | 언제 |
|---|---|
| `400 RESET_TOKEN_INVALID` | 토큰이 없음 · 5분 지남 · 이미 씀 · 더 새 토큰을 받음 · 그사이 탈퇴 |
| `400 INVALID_PASSWORD` | 가입 규칙 위반 |
| `400 PASSWORD_MISMATCH` | 새 비밀번호 두 칸이 다름 |
| `400 SAME_AS_OLD_PASSWORD` | 지금 비밀번호와 같음 |

새 비밀번호 오류 3가지는 **토큰을 쓰지 않는다** — 5분 안에 고쳐서 다시 보내면 된다.

#### ④ `POST /users/me/password/change` — 비밀번호 변경 (로그인 필요)
```jsonc
{ "current_password": "firstpass123", "new_password": "secondpass456", "new_password_confirm": "secondpass456" }
// 204 응답 — 지금 브라우저의 세션만 남고 다른 기기는 로그아웃
```
| 오류 | 언제 |
|---|---|
| `401 UNAUTHORIZED` / `SESSION_EXPIRED` | 로그인 안 함 / 세션 끝남 |
| `400 PASSWORD_NOT_SET` | 비밀번호가 없는(Google 전용) 계정 |
| `400 INVALID_PASSWORD` · `PASSWORD_MISMATCH` | 새 비밀번호 규칙 위반 — **실패로 세지 않음** |
| `400 WRONG_PASSWORD` | 지금 비밀번호가 틀림 — 「N번 더 틀리면 잠겨요」, `failed_attempts` +1 |
| `423 STEP_UP_LOCKED` | 5번째로 틀렸거나 이미 잠김 — 본인 확인(`/auth/step-up`)과 같은 잠금 |
| `400 SAME_AS_OLD_PASSWORD` | 지금 비밀번호와 같음 |

#### 화면 ↔ API
| 화면 | 순서 |
|---|---|
| 아이디 찾기 `#/find-id` | 이메일 → 「번호 받기」 → 번호 「확인」 → ① → 가린 아이디 |
| 비밀번호 재설정 `#/reset-password` | 아이디 + 이메일 번호 확인 → 「다음」(②) → 새 비밀번호 두 칸 → 「새 비밀번호로 정하기」(③) |
| 비밀번호 변경 `#/settings/password` | 지금 · 새 · 확인 → ④ |

```python
잠김? → 423  /  새 비밀번호 형식 → 400 (세지 않음)  /  지금 비밀번호 틀림 → failed_attempts +1, commit, 400·423
```

**왜 「지금 비밀번호와 같은지」를 두 방법으로 보나?** ③ 재설정은 지금 비밀번호를 모르므로 `verify_password(저장된 해시, 새 비밀번호)` 로 비교한다.
④ 변경은 방금 지금 비밀번호를 맞혔으니 문자열끼리 `new == current` 로 충분하다(해시 계산을 한 번 아낌).

**왜 형식 검사를 지금 비밀번호 확인보다 먼저?** 새 비밀번호를 잘못 적은 것만으로 잠금 횟수가 늘지 않게.

### 13-11. 겪은 것
- **`git stash` 로 「원래부터 있던 경고인지」 확인하다 아찔했다.** `git stash` 는 작업 중인 **모든** 수정 파일을 치운다 — 이번에는 다른 작업(카드 실적 구간 `docs/sql/05_card_products.sql`)의 수정도 같이 치워졌다가 `pop` 으로 돌아왔다.
  여러 작업이 한 폴더에서 동시에 진행 중이면 `git stash` 대신 바뀐 파일 하나만 `git diff <파일> > 백업.patch` 로 떠 두자.
- 첫 확인 때 보인 `git status` 목록(수정 파일 수십 개)이 이미 커밋된 뒤의 옛 목록이었다 — 지금 상태는 언제나 `git status` 를 새로 돌려 확인한다.
- pytest 의 `repr=False … has no effect` 경고(`UnsupportedFieldAttributeWarning`)는 이번 코드 이전부터 나던 것이다(`test_auth.py` 만 돌려도 나옴). 동작에는 영향 없음.
- **「5분 지난 토큰」 테스트가 가끔만 실패했다.** DB 칸이 `TIMESTAMP(0)` 이라 PostgreSQL 이 초 아래를 **반올림**해 저장한다(12:00:00.6 → 12:00:01).
  그래서 만료 시각에서 딱 5분만 빼면 1초 안쪽으로 아직 유효할 때가 있었다 → 테스트에서는 **6분**을 뺀다. 시간 경계를 시험할 때는 여유를 1초 이상 둔다.

### 14-1. 시작할 때 있던 것 / 없던 것
| 구분 | 내용 |
|---|---|
| 있던 것 (화면) | `PinPage`(`#/settings/pin`) — 만들기·바꾸기·다시 정하기 셋 다 「① 본인 확인 → ② 새 번호 → ③ 한 번 더」, 섞인 키패드 `PinPad`, 금지 번호 검사 `pinRules.ts`. 중요 작업의 본인 확인 칸 `useStepUp` 은 PIN 을 만든 회원에게 키패드를 보여 준다 |

그래서 「바꾸기」만 만들어도 `/auth/step-up` 이 PIN 을 받는 일(AUTH-F12)은 같이 해야 했다.

### 14-3. API 정의

#### ① `POST /auth/step-up` — `password` 또는 `pin` 중 하나 (로그인 필요)
```jsonc
{ "action": "PIN_CHANGE", "pin": "135790" }        // 바꾸기 — 지금 PIN
{ "action": "PIN_RESET",  "password": "…" }         // 만들기(PIN_ENROLL) · 다시 정하기 — 로그인 비밀번호
{ "action": "TRANSFER",   "pin": "135790" }         // 그 밖의 작업 — 둘 중 아무거나
// 201 응답 — 전과 같음
{ "step_up_challenge_id": "stu_…", "expires_at": "2026-11-10T15:05:00+09:00" }
```
| 오류 | 언제 |
|---|---|
| `400 STEP_UP_CREDENTIAL_REQUIRED` | `password` 와 `pin` 을 둘 다 보내거나 둘 다 안 보냄 |
| `400 PIN_REQUIRED` / `PASSWORD_REQUIRED` | `PIN_CHANGE` 에 비밀번호 / `PIN_ENROLL`·`PIN_RESET` 에 PIN |
| `400 PIN_NOT_SET` | PIN 을 안 만든 회원이 `pin` 으로 확인 |
| `400 STEP_UP_FAILED` | PIN 이 틀림 — 「N번 더 틀리면 10분 동안 쓸 수 없어요」 |
| `423 PIN_LOCKED` | 5번째로 틀렸거나 잠긴 동안 — 「HH:MM까지 쓸 수 없어요」 |

#### ② `GET /auth/pin` — PIN 상태
```jsonc
{ "enabled": true, "locked_until": null, "changed_at": "2026-11-10T15:00:00+09:00" }
// locked_until: 지금 잠겨 있을 때만 시각, 잠금이 끝났으면 null
// changed_at:   마지막으로 정한 때 (한 번도 안 바꿨으면 만든 때)
```

#### ③ `POST /auth/pin/enroll` · `/change` · `/reset` — 요청 모양이 같다
```jsonc
{ "step_up_challenge_id": "stu_…", "pin": "246802", "pin_confirm": "246802" }
// 200 (만들기는 201) 응답 — ②와 같은 모양
```
| 오류 | 언제 |
|---|---|
| `403 STEP_UP_REQUIRED` | 번호가 없음 · 5분 지남 · 이미 씀 · **다른 작업용**(예: `PIN_CHANGE` 번호로 `/reset`) — 화면은 ① 본인 확인으로 돌아간다 |
| `400 INVALID_PIN` | 6자리 숫자가 아님 · 금지 번호 |
| `400 PIN_MISMATCH` | 두 칸이 다름 |
| `409 PIN_ALREADY_SET` | 이미 PIN 이 있는데 만들기 |
| `400 PIN_NOT_SET` | PIN 이 없는데 바꾸기 · 다시 정하기 |
| `400 SAME_AS_OLD_PIN` | 바꾸기에서 지금 PIN 과 같음 |

`403` 말고는 모두 **본인 확인 번호를 쓰지 않는다**(커밋 전에 오류) — 5분 안에 새 PIN 만 다시 보내면 된다. 화면도 그렇게 ② 새 번호로 돌아간다.

#### 화면 ↔ API (`#/settings/pin`, 마이페이지 → 간편 비밀번호(PIN))
| 버튼 | ① 본인 확인 | ②③ 새 번호 두 번 |
|---|---|---|
| 간편 비밀번호 바꾸기 | 키패드로 지금 PIN → `step-up(PIN_CHANGE, pin)` | `/auth/pin/change` |
| 간편 비밀번호를 잊으셨나요? | 로그인 비밀번호 → `step-up(PIN_RESET, password)` | `/auth/pin/reset` |
| 간편 비밀번호 만들기 (PIN 없을 때) | 로그인 비밀번호 → `step-up(PIN_ENROLL, password)` | `/auth/pin/enroll` |

화면 코드는 고치지 않았다 — 요청·응답 모양과 오류 코드(`STEP_UP_REQUIRED` 면 처음부터)가 이미 이렇게 맞춰져 있었다.

### 14-4. DB 의 어떤 표를 쓰나
| 표 | 본인 확인(PIN) | 만들기 | 바꾸기 · 다시 정하기 |
|---|---|---|---|
| `pin_credentials` | `failed_attempts` +1 / 0, 5번이면 `locked_until = 지금 + 10분` | 1행 추가 (`pin_hash` = Argon2id) | `pin_hash` · `changed_at` 교체, `failed_attempts = 0` · `locked_until = NULL` |
| `step_up_challenges` | 1행 추가 | 그 번호 `consumed_at` | 그 번호 + **안 쓴 번호 전부** `consumed_at` |
| `notifications` | — | — | `SECURITY` 1행 |
| `auth_audit_logs` | `STEP_UP_PIN` (성공·실패) | `PIN_ENROLL` | `PIN_CHANGE` · `PIN_RESET` |

### 14-5. 코드
```python
# app/routers/auth.py — PIN 확인 (step-up 안에서)
cred = SELECT pin_credentials WHERE user_id  FOR UPDATE      # 동시에 여러 번 틀려도 횟수가 정확하게
if cred is None: raise 400 PIN_NOT_SET
if cred.locked_until:
    if 지금 < locked_until: raise 423 PIN_LOCKED
    locked_until, failed_attempts = None, 0                   # 잠금 시간이 지났으면 다시 5번
if not verify_password(cred.pin_hash, pin):                  # 비밀번호와 같은 Argon2id — 회원마다 솔트
    failed_attempts += 1;  5번이면 locked_until = 지금 + 10분
    commit → 400 STEP_UP_FAILED 또는 423 PIN_LOCKED
failed_attempts = 0

# app/routers/pin.py — 셋이 같은 함수 _set_pin(op, …)
consume_step_up(db, 번호, login, ACTION[op])                 # 「사용함」 표시 — 아래에서 오류면 롤백되어 다시 쓸 수 있다
pin_error(새 PIN, 생년월일) → 400 INVALID_PIN  /  두 칸 다름 → 400 PIN_MISMATCH
만들기인데 이미 있음 → 409  /  바꾸기·다시 정하기인데 없음 → 400 PIN_NOT_SET
바꾸기이고 verify_password(지금 해시, 새 PIN) → 400 SAME_AS_OLD_PIN
해시 교체 · 잠금 풀기 · UPDATE step_up_challenges SET consumed_at = 지금 WHERE 안 쓴 것 · 알림 · 감사 → commit
```
**왜 다시 정하기에서는 「지금 것과 같아요」를 안 알려 주나?** 알려 주면 PIN 이 잠긴 사람도 다시 정하기 화면에서 번호를 하나씩 넣어 보며
「같아요」가 나올 때까지 지금 PIN 을 맞혀 볼 수 있다 — 5번 잠금을 우회하는 통로가 된다. 바꾸기는 방금 지금 PIN 을 맞혔으니 알려 줘도 새는 것이 없다.

**왜 잠금이 끝나면 `failed_attempts` 를 0 으로?** 잠글 때 5 를 그대로 남겨 두어(왜 잠겼는지 보이게) 시드 `user_019`(5번, 잠김)와 모양이 같다.
그대로 두면 잠금이 끝난 뒤 한 번만 틀려도 6 ≥ 5 로 바로 다시 잠긴다.

만들기·바꾸기는 상태를 바꾸므로 테스트마다 `/auth/register` 로 새 회원(PIN 없음)을 만든다. 시드 회원은 PIN 으로 확인만 해 본다.
`conftest.py` 에 `seed_pin()` 을 추가했다(`seed_password()` 와 같이 `backend/.env` 의 `SEED_PIN`). 전체 333개 통과.

### 14-9. 겪은 것
- **「10분 잠금」 테스트가 `10.0017분 <= 10` 으로 실패했다.** `locked_until` 은 앱(파이썬) 시계로, 비교한 `now()` 는 DB(Docker) 시계로 잰 값이라 둘이 0.1초쯤 달랐다.
  시간 경계를 볼 때는 양쪽에 여유를 둔다(9.9 ~ 10.1분).
- 기존 테스트가 시드 회원으로 **비밀번호** 본인 확인을 하고, 테스트 DB 에는 시드 PIN 도 들어 있다. 「PIN 을 만든 회원은 PIN 만」으로 정했으면 기존 테스트가 줄줄이 깨졌을 것 — 그래서 일반 작업은 둘 다 받게 했다.

### 14-10. 남은 한계
- **6자리 PIN 자체가 약하다**(기획서 8.2) — 10분 잠금이라 하루에 최대 720번 넣어 볼 수 있다. 실제 은행은 기기 등록·누적 잠금을 함께 쓴다. 여기서는 PIN 이 뚫려도 계좌 파트의 소유권·한도 검사가 따로 있다.
- 비밀번호 본인 확인을 계속 받으므로 PIN 이 잠겨도 비밀번호로 이체할 수 있다(일부러 그렇게 둠).
- 만들기에는 알림을 남기지 않는다(바꾸기·다시 정하기만).
- 화면은 고치지 않았고 브라우저로 눌러 보지는 않았다 — API 테스트로만 확인.

# 2부 — 인증번호를 진짜 메일로 보내기 (AUTH-F03 보완)

> 만든 날: 2026-11-10 · 기획서 근거: Part 1 AUTH-F03(이메일 인증), 7장 API
> 리뷰 기준: 커밋 `f807ea4` 위의 커밋 안 된 작업 트리 (2026-11-10) 중 메일 발송에 관한 줄

## 1부와 달라진 점
| 1부에서 | 2부부터 |
|---|---|
| 인증번호를 **응답의 `dev_code`** 로 돌려주고 화면이 「(모의 메일 — 인증번호 123456)」로 보여 줬다 (3장 ③ · 7장 · 13-12) | 번호는 **메일로만** 간다. 응답의 `dev_code` 는 테스트에서만(`EMAIL_DEV_CODE=true`) 채워지고 평소에는 `null` |
| 메일 서버 설정이 없었다 | `backend/.env` 의 `SMTP_HOST` · `SMTP_PORT` · `SMTP_USER` · `SMTP_PASSWORD` · `MAIL_FROM` |
| 발송은 항상 성공 | 메일 서버에 못 붙으면 `503 EMAIL_SEND_FAILED`, 인증 행을 저장하지 않음 |
| 화면 안내: 「인증번호를 보냈어요. (모의 메일 — 인증번호 …)」 | 「OOO로 인증번호를 보냈어요. 메일함(스팸함 포함)을 확인해 주세요.」 |

**정정** (1부의 줄은 고치지 않는다): 3장 ③의 6번 줄과 그 아래 「`dev_code` = 모의 메일」, 5장 3·4번 줄, 7장 첫 줄, 13장 아이디 찾기 예시 1번 줄,
13-12 첫 줄은 이제 **테스트에서만** 맞다. 개발 서버에서 직접 해 볼 때는 `dev_code` 가 `null` 이므로 메일함(또는 SMTP 를 비워 둔 경우 서버 콘솔, 15-5)에서 번호를 본다.
13-12 의 「재설정 사실 알림도 메일 대신 앱 알림」은 그대로다 — 이번에 메일로 바꾼 것은 **인증번호**뿐이다.

## 15. 구현한 기능 — 인증번호 메일

### 15-4. 요청 한 번이 지나가는 길
```
가입 화면 「인증번호 받기」 (SignupPage.tsx onSendCode)
  → sendEmailCode (api.ts)  POST /auth/email-verifications {email, purpose}
      → send_email_code (signup.py)
          이메일 형식 · 가입 여부 · 60초 · 24시간 10번 검사        ← 1부와 같음
          번호 6자리 → email_verifications 에 해시만 add (아직 commit 전)
          send_code_mail (mailer.py)
             SMTP_HOST 없음 → 서버 콘솔에 번호
             있음 → SMTP 접속 → STARTTLS(465 면 처음부터 SSL) → 로그인 → 보내기
             실패 → MailError → rollback → 503 EMAIL_SEND_FAILED
          commit → 201 {expires_at, resend_at, dev_code: null}
  사용자: 메일함에서 번호 확인 → 「확인」
  → confirmEmailCode  POST /auth/email-verifications/confirm → {token}   ← 1부와 같음
  → register          POST /auth/register {…, email_verification_token} ← 토큰 없으면 400 EMAIL_NOT_VERIFIED
```

### 15-5. 메일 설정 — `backend/.env`
`.env` 맨 아래에 빈 칸을 만들어 두었다(이 파일은 `.gitignore` 라 커밋되지 않는다).
```bash
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=내주소@gmail.com
SMTP_PASSWORD=앱비밀번호16자리      # Google 계정 → 보안 → 2단계 인증 → 앱 비밀번호. 계정 비밀번호가 아님. 띄어쓰기 없이
MAIL_FROM=                          # 비우면 SMTP_USER 로 보낸다
```
- `SMTP_HOST` 를 비워 두면 서버를 켠 터미널에 이렇게 찍힌다:
  `SMTP_HOST 가 없어 메일 대신 콘솔에 찍습니다: [SIGNUP] me@example.com 인증번호 123456`
- 설정을 바꾸면 서버를 **다시 켜야** 한다(`--reload` 를 쓰지 않으므로).

### 15-6. 겪은 문제와 해결
#### ① 기존 테스트가 모두 응답의 `dev_code` 로 번호를 받고 있었다
- 원인: `test_signup.py` · `test_password.py` 의 `verified_token` · `mail_token` 이 `r.json()["dev_code"]` 를 쓴다. 메일로만 보내면 테스트가 번호를 알 길이 없다.
- 해결: 설정 `email_dev_code`(기본 `false`)를 두고 `conftest.py` 가 `EMAIL_DEV_CODE=true` 로 켠다. 기존 테스트는 한 줄도 안 고쳤다.

#### ② `.env` 에 SMTP 를 넣으면 테스트가 `…@example.com` 으로 진짜 메일을 보낼 뻔했다
- 원인: 설정은 `backend/.env` 를 읽고, 테스트도 같은 설정을 쓴다.
- 해결: `conftest.py` 에서 `os.environ["SMTP_HOST"] = ""`. pydantic-settings 는 **환경변수가 `.env` 보다 우선**이라 테스트에서는 항상 콘솔로 간다.

#### ③ 콘솔 로그의 `—` 가 `—` 로 깨져 나왔다
- 원인: Windows 콘솔 글자표(cp949)에 em dash 가 없다.
- 해결: 로그 문구의 `—` 를 `:` 로 바꿨다. 한글은 터미널 설정에 따라 깨져 보일 수 있지만 번호(숫자)는 늘 보인다.

#### ④ `npx vitest run` 이 「no tests」
- 원인: 이 프로젝트 화면 테스트는 vitest 가 아니라 Node 내장 테스트(`node --test`)다.
- 해결: `cd frontend && npm test`.

### 15-10. 남은 한계
- **실제 SMTP 로 보내는 길은 자동 테스트가 없다.** 테스트는 `send_code_mail` 을 가로채거나 콘솔로 보낸다. STARTTLS · 로그인 · 465(SSL) 갈래는 직접 보내 봐야 안다.
- **메일 서버가 받아 준 뒤의 실패(주소 없음 · 스팸 차단)는 모른다.** 그때는 201 이 나가고 사용자는 메일을 못 받는다 → 60초 뒤 다시 받기.
- **발송을 기다리는 동안 요청이 멈춘다**(최대 10초 timeout). 실제 서비스는 메일을 큐에 넣고 따로 보낸다.
- **아무 주소로나 보낼 수 있다** — 아래 16-4 「발견한 문제」.
- Gmail 은 하루 보낼 수 있는 양이 정해져 있다. 학습용으로는 충분하다.

- **왜**: 부르는 쪽(`signup.py`)이 smtplib 의 여러 예외를 몰라도 되게. 실패 로그에는 받는 주소 · 번호를 남기지 않고 **예외 종류만** 남긴다(개인정보).
```python
def send_code_mail(to: str, code: str, purpose: str, ttl_minutes: int) -> None:
    if not settings.smtp_host:
        log.warning("SMTP_HOST 가 없어 메일 대신 콘솔에 찍습니다: [%s] %s 인증번호 %s", purpose, to, code)
        return
    msg = build_code_mail(to, code, purpose, ttl_minutes)
    ctx = ssl.create_default_context()
    try:
        if settings.smtp_port == 465:
            server = smtplib.SMTP_SSL(settings.smtp_host, settings.smtp_port, timeout=10, context=ctx)
        else:
            server = smtplib.SMTP(settings.smtp_host, settings.smtp_port, timeout=10)
        with server:
            if settings.smtp_port != 465:
                server.starttls(context=ctx)
            if settings.smtp_user:
                server.login(settings.smtp_user, settings.smtp_password)
            server.send_message(msg)
    except (smtplib.SMTPException, OSError) as e:
        log.error("인증 메일 발송 실패: %s", type(e).__name__)
        raise MailError from e
```

### 18-5. API 정의
#### `GET /users/me/consents` — 내 동의 내역
- 인증: 로그인(쿠키). `PENDING_VERIFICATION` 은 403 `SIGNUP_INCOMPLETE`
- 응답 200 (필수 먼저, 그다음 id 순)
```json
[
  {"terms_id": "trm_001", "title": "서비스 이용약관", "required": true, "version": "1.0", "agreed": true, "recorded_at": "2026-11-11T10:20:30+09:00"},
  {"terms_id": "trm_004", "title": "마케팅 정보 수신 동의", "required": false, "version": "1.0", "agreed": false, "recorded_at": null}
]
```

#### `PATCH /users/me/consents` — 선택 동의 바꾸기
- 요청 `{"terms_id": "trm_004", "agreed": true}` → 응답 200: 위와 같은 목록(바뀐 뒤)

| HTTP | code | 언제 |
|---|---|---|
| 400 | `REQUIRED_TERMS_LOCKED` | 필수 약관(`trm_001`~`003`)을 바꾸려 함 |
| 404 | `TERMS_NOT_FOUND` | 공통 약관이 아닌 id (카드 약관 포함) |
| 401 | `UNAUTHENTICATED` | 로그인 안 함 |

#### `GET /terms/{terms_id}` — 약관 본문
- 인증: 없음
- 응답 200
```json
{"id": "trm_003", "title": "개인정보 수집·이용 동의", "required": true, "version": "1.0",
 "effective_at": "2026-11-01T00:00:00+09:00",
 "source": "두린은행 직접 작성 (개인정보 보호법 제15조 제2항 형식, docs/domain-rules.md 5-5)",
 "content": "두린은행(이하 \"은행\"이라 합니다)은 …\n\n## 1. 수집·이용 목적\n…"}
```
- `content`: 파일이 없거나, `.md` 가 아니거나, `data/` · `docs/` 밖이면 `null` → 화면 「약관 본문을 준비하고 있어요.」
- `source` 가 `http` 로 시작하면(토스 원문) 화면 맨 아래에 「원문: toss.im」 링크
- 오류: 404 `TERMS_NOT_FOUND`

### 18-6. 약관 본문 파일과 DB
| id | 약관 | `content_url` | 본문 |
|---|---|---|---|
| `trm_001` | 서비스 이용약관 (필수) | `data/rag/terms/service_terms.md` | 토스 원문 (6장, 「토스」→「두린 은행」은 `scripts/rename_bank.py`) |
| `trm_002` | 전자금융거래 이용약관 (필수) | `data/rag/terms/electronic_financial_transactions_terms.md` (**`.pdf` 에서 바꿈**) | 우리은행 PDF 변환본 |
| `trm_003` | 개인정보 수집·이용 동의 (필수) | `data/rag/terms/privacy_consent.md` (**새 파일**) | 직접 작성 — 출처 · 근거는 `docs/domain-rules.md` 5-5 |
| `trm_004` | 마케팅 정보 수신 동의 (선택) | `data/rag/terms/marketing_consent.md` (**새 파일**) | 〃 |

시드(`scripts/seed_scenarios.py`)도 고쳤지만, 시드는 `ON CONFLICT DO NOTHING` 이라 **이미 넣은 DB 의 `terms` 행은 안 바뀐다.** 그래서 켜 둔 DB 는 직접 바꿨다:
```bash
docker exec midproject-postgres psql -U app -d midproject -c "UPDATE terms SET content_url = 'data/rag/terms/electronic_financial_transactions_terms.md' WHERE id = 'trm_002'"
docker exec midproject-postgres psql -U app -d midproject -c "UPDATE terms SET content_url = 'data/rag/terms/' || CASE id WHEN 'trm_003' THEN 'privacy_consent.md' ELSE 'marketing_consent.md' END WHERE id IN ('trm_003','trm_004')"
docker exec midproject-postgres psql -U app -d midproject -c "SELECT id, content_url FROM terms WHERE card_product_id IS NULL ORDER BY id"   # 4줄 모두 data/rag/terms/…md
```
- 직접 쓴 동의서는 법이 「동의 받을 때 알려라」고 한 4가지를 장으로 나눴다: ① 목적 ② 항목 ③ 보유·이용 기간 ④ 거부할 권리와 불이익 (개인정보 보호법 제15조 제2항 — `data/rag/laws/personal_information_protection_act.md` 에서 원문 확인).
  항목은 이 앱이 실제로 받는 값(`users` 표)만, 보유 기간은 기획서의 탈퇴 규칙(탈퇴 후 1개월 유예 · 금융거래·접속 기록 5년)과 같게 썼다.
- 새 파일에는 「우리」라는 낱말을 쓰지 않았다 — `rename_bank.py` 가 `data/rag` 의 모든 `.md` 에서 「우리」를 「두린」으로 바꾸기 때문이다.
- 굵게(`**`) · 목록 기호(`- `)도 쓰지 않았다 — 화면의 변환기가 그리지 않아 별표 · 줄표가 그대로 보인다(18-10 ⑧).

### 18-10. 겪은 문제와 해결
#### ① 「약관 및 동의 내역」이 비어 있었다
- 원인: 화면은 `GET /users/me/consents` 를 부르는데 서버에 그 경로가 없었다(기획서 7장 표에만 있음) → 404.
- 해결: `routers/consents.py` 를 만들고 `main.py` 에 등록. **서버를 다시 켜야** 새 경로가 생긴다.

#### ② 1초 안에 두 번 바꾸면 무엇이 최신인지 모른다
- 원인: `user_consents.recorded_at` 이 `TIMESTAMP(0)`(초 단위)이고 `id` 는 무작위라, 같은 초의 두 행은 순서가 없다. 테스트에서 `[False, False, True]` 처럼 뒤섞였다.
- 해결: 새 행의 시각이 앞 행보다 늦지 않으면 **앞 행 + 1초**로 남긴다(shortcut — 실제 서비스면 칸을 `TIMESTAMP(6)` 으로 늘리거나 순번 칸을 둔다).

#### ③ 가입 화면에서 약관을 보려고 화면을 옮기면 입력이 사라진다
- 원인: 가입 정보는 `SignupPage` 의 상태(state)에만 있다. 주소가 바뀌면 화면이 새로 그려진다.
- 해결: 주소를 바꾸지 않는 전체 화면 창(`TermsDialog`)으로 띄운다. 마이페이지는 주소가 있는 새 화면이다(뒤로 가기 · 링크가 되게).

#### ④ `trm_002` 가 PDF 를 가리켰다 · 시드를 다시 넣어도 안 바뀐다
- 원인: 화면은 Markdown 만 그린다. 시드는 `ON CONFLICT DO NOTHING` 이라 있는 행을 고치지 않는다.
- 해결: 시드를 `.md` 로 고치고, 켜 둔 DB 는 18-6 의 `UPDATE`.

#### ⑤ 토스 동의서 원문이 웹에 없었다
- 찾아본 곳: `toss.im/terms`(약관 목록에 가입 동의서 없음) · 토스뱅크 사이트맵과 약관 자료실(스크립트로 채우는 화면이라 HTML 에 본문 없음) · `toss.im/privacy-policies`(역시 스크립트) · 웹 검색. 자세한 표는 `docs/domain-rules.md` 5-5.
- 해결: 사용자 결정으로 법 형식에 맞춰 직접 썼다(18-6). 실제 서비스의 처리방침을 적용하는 일은 18-12 ①로 남겼다.

#### ⑥ lint 경고 「React Compiler has skipped optimizing this component」
- 원인: 가입 화면에서 창 닫기 함수를 `useCallback(…, [])` 로 감쌌는데, React Compiler 가 추론한 의존성(`setViewing`)과 달랐다.
- 해결: `useCallback` 을 빼고, 창(`TermsDialog`)이 `onClose` 를 ref 에 담아 쓰게 했다 → 부모가 다시 그려져도 초점 · 스크롤 잠금 준비를 다시 하지 않는다.

#### ⑦ 마이페이지 첫 화면의 마케팅 스위치가 움직이지 않았다
- 원인: [SettingsPage.tsx](../frontend/src/pages/SettingsPage.tsx) 가 약관 id 를 `'marketing'` 으로 찾았다. 실제 id 는 `trm_004` 다.
- 해결: `MARKETING_TERMS_ID = 'trm_004'` 상수로 바꿨다.

#### ⑧ 직접 쓴 동의서의 굵게 · 목록 기호가 화면에 그대로 보일 뻔했다
- 원인: 변환기는 약관 파일에 있던 것(제목 · 문단 · 표)만 그린다. 처음 쓴 동의서에 `**필수**` · `- ` 줄이 있었다.
- 해결: 동의서에서 `**` 와 `- ` 를 뺐다. 변환기를 늘리는 일은 18-12 ① 의 6번.

### 18-11. 남은 한계
- **직접 쓴 동의서 2개는 법률 검토를 받지 않았다.** 개인정보 보호법 조문(제15조 · 제22조)은 원문으로 확인했지만, 마케팅의 「야간 발송 안 함」 · 「수신 거부 방법 표시」가 기대는 정보통신망법 제50조는 원문을 받지 않았다.
- **시드 회원(`user_001` 등)은 가입 동의 기록이 없다** → 필수 약관도 「동의 안 함 · 기록 없음」으로 보인다. 직접 가입한 회원은 정상이다.
- **약관이 개정되면(버전이 바뀌면) 다시 동의받는 흐름이 없다** — 기획서 AUTH-F10 「[협의 필요] 약관 개정 시 재동의」. 지금 화면은 동의한 버전만 보여 준다.
- **마케팅에 동의해도 실제로 보내는 기능이 없다** (동의서에도 「학습용이라 발송 안 함」이라고 적었다).
- **1초 보정**(18-10 ②)은 shortcut 이다.
- **챗봇은 새 동의서 2개를 아직 모른다** — `data/rag/terms/` 에 넣기만 했다. RAG 에 넣으려면 `backend/.venv/Scripts/python scripts/rag_ingest.py --save` 를 다시 돌린다(`GEMINI_API_KEY` 필요).
- Markdown 변환기는 굵게 · 링크 · 목록 기호를 글자 그대로 보여 준다.
- 가입 화면 창 · 목차 이동은 **브라우저로 직접 눌러 보지 않았다**(타입 검사 · 빌드 · 단위 테스트만).

### 18-12. 이 밖에 더 구현할 일
#### ① 토스나 실제 금융 서비스의 개인정보 처리방침 적용해 보기
- **왜**: 지금 동의서 2개는 법 형식만 맞춘 직접 작성본이다. 실제 금융사가 무엇을 · 왜 · 얼마나 오래 보관하는지 적은 **개인정보 처리방침**을 들여오면 ① 마이페이지에 「개인정보 처리방침」 메뉴를 붙일 수 있고(개인정보 보호법 제30조: 처리방침을 정해 공개해야 함) ② 직접 쓴 동의서의 항목 · 보유 기간이 실제 서비스와 얼마나 다른지 비교할 수 있다.
- **처리방침 ≠ 동의서**: 처리방침은 「공개」하는 문서이고 동의를 받지 않는다. 그래서 `user_consents` 대상이 아니라 **보기 전용**이다.
- **어디서 받나 (후보)**

  | 후보 | 주소 | 받는 방법 | 메모 |
  |---|---|---|---|
  | 토스 | https://toss.im/privacy-policies | 화면을 스크립트로 채운다 → 브라우저 개발자 도구 「네트워크」 탭에서 본문을 주는 JSON 주소를 찾거나, Playwright 같은 브라우저 자동화(새 패키지 — 먼저 정할 것) | 2026-11-11 `requests` 로는 제목만 받혔다 |
  | 토스뱅크 | https://www.tossbank.com/customer/information/privacy/privacy-policy | 위와 같음 | 은행이라 두린은행과 더 비슷하다 |
  | 우리은행 등 PDF 를 주는 은행 | 각 은행 「개인정보처리방침」 페이지 | PDF 를 받아 `scripts/pdf_to_md.py` | 지금 RAG 문서 대부분이 우리은행 것이라 이어 쓰기 쉽다 |
- **할 일 순서**
  1. 받을 곳을 정하고 `robots.txt` 를 확인한 뒤 `docs/domain-rules.md` 5장에 출처 · 받은 날을 적는다.
  2. `.md` 로 저장(예: `data/rag/terms/privacy_policy.md`) → 회사 이름 바꾸기(`scripts/rename_bank.py` 에 파일 추가).
  3. `terms` 에 새 행(예: `trm_005` 「개인정보 처리방침」)을 넣는다. **가입 체크박스에 섞이지 않게** 해야 한다 — 지금 `GET /terms` · `common_terms()` 는 `card_product_id IS NULL` 이면 다 가져온다. 「동의 대상이 아닌 문서」를 가르는 칸(예: `kind`)을 두거나 별도 경로로 읽는다. DB 칸을 늘리면 `docs/sql` · 모델 · 시드를 같이 고친다.
  4. 화면: 마이페이지 「약관」 묶음에 「개인정보 처리방침」 줄을 더하고, 기존 `TermsDetailPage` · `TermsViewer` 를 그대로 쓴다(본문 API `GET /terms/{id}` 재사용).
  5. 처리방침과 `privacy_consent.md` 의 항목 · 보유 기간을 표로 비교해 동의서를 고친다(버전 `1.1` — 이때 ③ 재동의 흐름이 필요해진다).
  6. 처리방침은 길고 굵게 · 목록이 많다 → `termsMarkdown.ts` 에 굵게 · 목록을 더하고 테스트도 더한다.

#### ② 시드 회원에게 가입 동의 기록 넣기
`seed_scenarios.py` 에서 회원마다 가입일(`created_at`) 기준으로 필수 3개는 `true`, 마케팅은 몇 명만 `true` 인 `user_consents` 행을 만든다. 시드를 다시 넣을 때 지우고 넣을 수 있게 `reset_sql` 에도 더한다.

#### ③ 약관 개정 때 다시 동의받기
`terms.version` 이 내 마지막 동의 버전보다 높으면 로그인 직후 「바뀐 약관」 화면을 띄운다 → 필수는 동의해야 계속, 선택은 그대로 둔다. 기획서 AUTH-F10 [협의 필요]라 규칙부터 정한다.

#### ④ 카드 신청 화면의 카드 약관에도 「보기」
`CardApplyPage.tsx` 의 약관 줄도 같은 `TermsDialog` 를 쓸 수 있다(카드 약관도 `terms` 행이라 `GET /terms/{id}` 가 그대로 읽는다 — 본문 파일만 있으면).
