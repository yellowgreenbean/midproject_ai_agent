# 1부 — 구현한 기능

## 0. 한눈에 보기

### 0-1. 목적
- **새 통장을 앱에서 바로 만든다.** 과제 필수 기능 「은행 앱 기본 기능: 계좌」 — 토스처럼 유형을 고르고 약관에 동의하면 그 자리에서 계좌번호가 나온다(ACCT-F01).
- **만들기 직전에 본인인지 한 번 더 확인한다.** 로그인 쿠키만 훔친 사람이 내 이름으로 계좌를 늘리지 못하게, 간편 비밀번호(PIN) 6자리 — PIN 이 없으면 로그인 비밀번호 — 를 다시 받는다(변경 이력 23).
- **계좌를 잠시 막거나 없앤다.** 잃어버린 카드 · 의심 거래 때 계좌를 **일시정지**하고, 필요 없어진 계좌는 **해지**한다(ACCT-F05). 해지는 돈이나 연결된 상품이 남아 있으면 막고 **왜 막혔는지**를 알려 준다.
- **본인 계좌만 바꾼다.** 과제 필수 「인증된 사용자가 본인에게 허용된 정보 · 기능만 이용」 — 남의 계좌는 없는 계좌와 똑같이 404.

### 0-3. 이번에 정한 규칙 (사용자 결정 2026-11-10)
| 물어본 것 · 사용자가 한 말 | 정한 것 |
|---|---|
| 「일시정지 하나만 만들까요, 아니면 … 계좌 해지(ACCT-F05)도 같이 만들어. 해지는 잔액, 처리 중인 이체, 진행 중인 예금·적금, 연결된 카드를 확인해.」 | 일시정지 · 정지 해제 · 해지를 같이 만든다. 해지 점검 4가지: `BALANCE_REMAINING` · `PENDING_TRANSFER` · `LINKED_SUBSCRIPTION` · `LINKED_CARD` |
| 「고쳐줘. 점검 결과가 막히도록. '이 계좌에 연결된 카드가 있다'는 답이 나오도록.」 | **다른 파트 점검이 실패(예외)하면 그 점검의 사유로 막는다** — 카드 점검이 터지면 `LINKED_CARD`. 「확인 못 함」을 「문제없음」으로 넘기지 않는다(변경 이력 20) |
| 데드락을 없앨까 (같은 질문의 답 안에서) | 해지의 잠금 순서를 **잔액 행 → 계좌 행**으로 — 탈퇴 일괄 해지 · 이체 · 적금 중도 해지와 같은 순서 |
| 계좌 개설 본인 확인 번호의 작업 종류 | **`ACCOUNT_OPEN` 을 새로 추가** (`docs/sql/01_users.sql` CHECK 제약 · 모델 · 개발 DB ALTER) — 정지 · 해지용 `ACCOUNT_STATUS_CHANGE` 와 섞지 않는다 |
| PIN 을 아직 안 만든 회원 | **로그인 비밀번호로 대신** — 이체 · 상품 가입 화면과 같은 방식(PIN 이 있으면 키패드, 없으면 비밀번호 칸 + 「만들기」 링크) |

기획서에서 그대로 가져온 규칙(사용자에게 따로 묻지 않음):
- 유형은 `CHECKING`(입출금통장) · `SAVINGS`(저축예금) 2종. 예금 · 적금은 계좌가 아니라 상품 가입(Part 3).
- 회원 상태 `ACTIVE` 만 개설. `RESTRICTED` 는 정리 · 보호 동작(정지 · 정지 해제 · 해지)만 된다(Part 1 7.3).
- 1인당 계좌 수 제한 없음(Part 2 14장 「초기에는 별도 제한 없이」).
- 정지된 계좌는 입금 · 출금을 모두 막는다(10.3). 사용자가 해지하려면 정지 해제가 먼저(탈퇴 일괄 해지만 예외).
- 해지 ≠ 삭제: 행 · 별명 · 거래 기록은 남기고 `closed_at` 만 채운다. 즐겨찾기는 푼다.

### 0-4. 요청 한 번이 지나가는 길

**계좌 개설**
```
[AccountOpenPage]  유형·약관 → [다음] → step='verify'
     │  PIN 6자리(또는 비밀번호)
     ├─▶ POST /auth/step-up {action: ACCOUNT_OPEN, pin}          routers/auth.py step_up
     │        └ pin_credentials 확인 → step_up_challenges INSERT (5분, 이 세션, 이 action, 1회)
     └─▶ POST /accounts {account_type, consents, step_up_challenge_id}   헤더 Idempotency-Key
              routers/accounts.py open_account
              ① 유형 · 약관 검사 (422)
              ② users 행 FOR UPDATE  ← 같은 회원의 개설 요청을 한 줄로 세운다
              ③ 같은 키로 만든 계좌가 있나? (account_activity_logs.metadata.idempotency_key) → 있으면 그 계좌를 그대로
              ④ 회원 ACTIVE? (403)
              ⑤ consume_step_up(..., "ACCOUNT_OPEN")  (403 STEP_UP_REQUIRED)
              ⑥ 계좌번호 110 + 무작위 11자리 (겹치면 다시, 5번)
              ⑦ 한 트랜잭션: accounts + account_balances(0원, ledger.open_balance)
                              + notification_preferences(기본값) + account_activity_logs(OPEN)
              ⑧ commit → GET /accounts/{id} 와 같은 모양으로 201
```

**계좌 해지**
```
[AccountDetailPage] [계좌 해지] → close_blockers 가 있으면 사유 + 링크만 (본인 확인 안 받음)
                                  없으면 PIN → POST /auth/step-up {action: ACCOUNT_STATUS_CHANGE}
     └─▶ POST /accounts/{id}/close {step_up_challenge_id}        routers/accounts.py close_account
              ① 내 계좌인가 (404)            ② consume_step_up
              ③ account_balances 행 FOR UPDATE → ④ accounts 행 FOR UPDATE   ← 이 순서가 데드락을 막는다
              ⑤ CLOSED / SUSPENDED 면 409     ⑥ 잔액 행 없으면 503
              ⑦ close_blockers: 잔액 ≠ 0 · 거래 · 상품 · 카드 점검 (점검마다 저장점, 실패 = 막힘)
                 → 하나라도 있으면 409 ACCOUNT_CLOSE_NOT_ALLOWED + reasons
              ⑧ account_activity_logs(CLOSE) · lifecycle_status=CLOSED · closed_at · is_favorite=False → commit
```

## 1. 계좌 개설 — 표 네 개를 한 번에

### 1-1. 무엇이 생기나
| 표 | 칸 | 값 | 누가 만드나 |
|---|---|---|---|
| `accounts` | `id` | `acc_` + 무작위 20자 (`new_id`) | 계좌 파트 |
| | `resAccount` | `110` + 무작위 11자리 = 14자리 (`BANK_ACCOUNT_DIGITS["두린은행"]`) | |
| | `resAccountDisplay` | `110-XXXXX-XXXXXX` — 숫자를 하나도 빼지 않는다 | |
| | `resAccountName` | `CHECKING` 입출금통장 · `SAVINGS` 저축예금 (`rules.ACCOUNT_PRODUCT_NAMES`) | |
| | `lifecycle_status` · `resAccountStartDate` · `closed_at` | `ACTIVE` · 오늘 `YYYYMMDD` · `null` | |
| `account_balances` | `balance` · `currency` | `0` · `KRW` | **거래 파트** 함수 `ledger.open_balance` (기획서 ACCT-F01 정상 흐름 8 「잔액 초기화는 원장 책임 시스템과 연계」) |
| `notification_preferences` | (전부 기본값) | 입출금 알림 켬 | 계좌 파트 (ACCT-F06) |
| `account_activity_logs` | `action` · `metadata` | `OPEN` · `{account_type, idempotency_key, consents}` | 계좌 파트 (ACCT-F10) |

- 넷이 **한 트랜잭션**이다. 하나라도 실패하면 아무것도 남지 않는다.
- 더미 계좌의 화면 번호(`110-00-000001`)는 14자리 중 일부를 빼고 보여 주는 원래 모양 그대로 두었다. 새 계좌만 14자리 전부를 보여 준다.

### 1-2. 같은 요청이 두 번 오면 (`Idempotency-Key`)
- 화면은 페이지를 열 때 `crypto.randomUUID()` 로 번호 하나를 만들고, 그 화면에서 몇 번을 눌러도 같은 번호를 보낸다([AccountOpenPage.tsx:36](../frontend/src/pages/AccountOpenPage.tsx#L36)).
- `accounts` 표에는 요청 번호 칸이 없다. **DB 를 바꾸지 않으려고** 개설 기록(`account_activity_logs`)의 `metadata.idempotency_key` 에 둔다. 예금 · 적금 가입(`subscriptions.idempotency_key`)과 이체(`transfers.idempotency_key`)는 전용 칸이 있다.
- 찾을 때는 **회원별로** 찾는다(`actor_id = 로그인 회원`) — 다른 사람이 우연히 같은 번호를 써도 섞이지 않는다.
- 같은 번호 + 같은 유형 → 처음 만든 계좌를 그대로 201. 같은 번호 + 다른 유형 → 409 `IDEMPOTENCY_KEY_REUSED`.

### 1-3. 동시에 여러 번 오면 — 회원 행 잠금
- 「같은 키로 만든 계좌가 있나」를 확인하고 만들기까지 사이에 두 번째 요청이 끼면, 둘 다 「처음」이라고 보고 계좌가 2개 생긴다.
- 그래서 확인하기 전에 `users` 행을 `FOR UPDATE` 로 잠근다. 같은 회원의 개설 요청은 한 줄로 서고, 두 번째 요청은 첫 번째가 커밋한 뒤에 확인하므로 「이미 있음」을 본다.
- 실제로 이 잠금을 빼고 테스트(`test_concurrent_same_key_makes_one_account`, 8개 동시)를 돌리면 한 요청 번호로 계좌가 2개 생겼다.

### 1-4. 본인 확인 단계 (2026-11-10 추가)
- 순서가 중요하다: **유형 · 약관 검사 → 회원 잠금 → 같은 키 재요청 확인 → 회원 상태 → 본인 확인 번호 사용**.
  - 같은 키 재요청을 본인 확인보다 **먼저** 본다. 응답을 못 받고 다시 누른 사람은 이미 쓴 번호를 다시 보내는데, 그때도 처음 계좌를 돌려줘야 하기 때문이다.
  - 회원 상태도 본인 확인보다 먼저 본다. 어차피 못 만드는 회원(`RESTRICTED`)에게 PIN 을 받지 않는다.
- 번호는 `consume_step_up` 이 확인한다: 이 회원 · 이 로그인 세션 · `ACCOUNT_OPEN` · 5분 안 · 처음 쓰는 번호. 하나라도 아니면 403 `STEP_UP_REQUIRED`.
- 번호를 「사용함」으로 표시하는 것도 개설과 **같은 커밋**이다. 개설이 실패해 롤백되면 번호도 다시 쓸 수 있다.
- 개발용 `X-User-Id` 헤더에는 로그인 세션이 없어서 본인 확인 번호를 받을 수 없다 → 그 헤더로는 계좌를 만들 수 없다.

## 2. 계좌 상태 관리 — 일시정지 · 정지 해제 · 해지

### 2-1. 상태가 바뀌는 길
```
         suspend               close
 ACTIVE ─────────▶ SUSPENDED    ACTIVE ─────────▶ CLOSED   (되돌릴 수 없음)
        ◀─────────
          resume
 SUSPENDED ─close─▶ ✗ 409 「정지를 해제한 뒤에 해지할 수 있어요」 (탈퇴 일괄 해지만 예외 — internal.close_for_withdrawal)
```
- 셋 다 본인 확인 `ACCOUNT_STATUS_CHANGE` 가 필요하고, 성공하면 `account_activity_logs` 에 `SUSPEND` · `RESUME` · `CLOSE` 를 `from_status` 와 함께 남긴다. 실패한 요청은 기록하지 않는다(롤백).
- 셋 다 `RESTRICTED` 회원도 된다(정리 · 보호 동작, Part 1 7.3). 정지 해제는 회원 탈퇴 ①(정지 계좌의 남은 돈 옮기기)의 첫 단계이기도 하다.
- 정지된 계좌로는 돈이 들어오지도 나가지도 않는다. 거래 파트(`run_transfer`)가 이체 때 두 계좌의 `lifecycle_status` 를 보고 `ACCOUNT_NOT_ACTIVE` 로 실패시킨다.

### 2-2. 해지 점검 4가지와 담당 파트
| 사유 코드 | 무엇을 보나 | 담당 파트 · 함수 |
|---|---|---|
| `BALANCE_REMAINING` | 잔액 ≠ 0 (잠근 잔액 행으로) | 거래 — `ledger.lock_balances` |
| `PENDING_TRANSFER` | 이 계좌에서 나가는 처리중(`PENDING`) 이체, 실행 대기 예약 송금 · 활성/일시정지 자동이체 | 거래 — `internal.transfer_blockers(db, user_id, account_id)` |
| `LINKED_SUBSCRIPTION` | 이 계좌가 출금 계좌인 진행 중(`ACTIVE`) 예금 · 적금 | 상품 — `internal.subscription_blockers` |
| `LINKED_CARD` | 이 계좌에 연결된 우리 발급 카드 중 해지 안 된 것 + **해지했어도 낼 대금이 남은 것** | 카드 — `internal.card_blockers` (대금은 카드 파트 `card_money`) |

- 점검 함수는 **회원 탈퇴 점검과 같은 함수**에 `account_id` 를 넘겨 「이 계좌만」 본다 — 두 곳의 기준이 서로 달라지지 않는다.
- 기획서는 이것들을 계좌 단위 내부 API(`GET /internal/accounts/{accountId}/transfer-blockers` 등)로 적었다. 지금은 서버가 하나라 같은 서버의 함수로 부른다(사용자 결정 2026-11-09). 팀원 서버가 생기면 그 함수 안만 HTTP 호출로 바꾸면 된다.
- 카드 기준은 기획서(「해지 안 된 카드」)보다 하나 넓다: 해지한 카드라도 낼 대금이 남으면 막는다. 탈퇴용으로 정한 규칙(2026-11-09 Q5 — 결제 계좌가 없어지면 청구할 곳이 없어짐)을 같은 함수로 그대로 쓴 결과다.

### 2-3. 점검이 실패하면 — 「막힘」으로 본다
- 「막힘」은 두 가지다.
  - **점검 결과 막힘**: 「연결된 카드가 있다」는 답을 받았다. 사용자가 할 일이 정해진다.
  - **점검 실패**: 답을 못 받았다(예외 · 쿼리 오류). 카드가 있는지 없는지 모른다.
- 점검 실패를 「문제없음」으로 넘기면 카드가 연결된 계좌가 해지되는 사고가 난다. 그래서 실패하면 **그 점검의 사유로 막는다**(사용자 결정). 서버 로그에 `계좌 해지 점검 실패 — LINKED_CARD 로 막음 (account_id=…)` 을 남겨, 개발 쪽에서는 진짜 카드인지 점검 실패인지 구별한다.
- **점검마다 저장점(savepoint)을 둔다.** PostgreSQL 은 트랜잭션 안에서 쿼리 하나가 오류를 내면 그 뒤의 쿼리를 모두 거부한다. 저장점이 없으면 첫 점검의 쿼리 오류 하나로 뒤의 점검까지 모두 실패해, 없는 사유까지 막힘으로 나온다. 실제로 `begin_nested` 를 빼고 돌리면 `test_failed_db_query_in_one_check_does_not_break_the_others` 가 실패한다.
- 잔액을 못 읽는 경우만 예외다: 사유가 아니라 503 `BALANCE_UNAVAILABLE`. 기획서 ACCT-F03 「잔액 오류를 0원 같은 값으로 둔갑시키지 않는다」.

### 2-4. 잠금 순서 — 잔액 행 먼저
- 해지는 잔액 행과 계좌 행을 **둘 다 잠근 채로** 검사하고 해지한다. 그 사이에 이체가 돈을 넣거나 빼지 못하게(7.3 「시점/동시성 보장」).
- 잔액을 바꾸거나 계좌를 해지하는 다른 곳(이체 · 탈퇴 일괄 해지 · 적금 중도 해지)은 모두 **잔액 행을 먼저** 잠근다. 해지가 계좌 행을 먼저 잠그면, 둘이 서로 상대 잠금을 기다리다 PostgreSQL 이 한쪽을 끊는다(데드락 → 500).
- 그래서 해지도 잔액 행 → 계좌 행. 남의 계좌는 잠그기 전에 404 로 거른다.
- 같은 이유로 이체(`run_transfer`)가 잔액 행을 잠근 **뒤에** 두 계좌의 상태를 다시 읽게 고쳤다(`db.refresh`). 전에는 잠그기 전에 읽은 상태를 써서, 해지 · 정지와 거의 동시에 온 이체가 이미 해지된 계좌에 돈을 넣을 수 있었다.

## 3. 겪은 문제와 해결 (같은 일을 다시 할 때 참고)

### ① 화면에서 계좌를 만들면 405 — 「백엔드 서버는 이미 켜져있는거 아니야?」
- 원인: 8010 서버가 코드를 고치기 전(오전 10:45)에 `--reload` 없이 켜져 있었다. 그 서버의 API 목록에는 `/accounts` 가 `GET` 만 있었다. 이 PC 에서는 `--reload` 도 새 경로를 잘 못 잡는다.
- 해결: 서버를 끄고 같은 명령으로 **다시** 켠다. 새 경로가 404 · 405 면 먼저 예전 서버를 의심한다.

### ② 동시 요청 테스트가 잠금 없이도 통과했다
- 원인: 스레드마다 `TestClient` 를 만드는 시간이 길어 요청이 사실상 하나씩 들어갔다.
- 해결: 클라이언트를 **먼저 다 만들고** `threading.Barrier` 로 한꺼번에 출발시킨다(`test_concurrent_same_key_makes_one_account`). 그 뒤로는 잠금을 빼면 3번 중 1번꼴로 계좌가 2개 생겼다.

### ③ 활동 기록 순서를 비교하는 테스트가 가끔 실패
- 원인: `occurred_at` 이 초 단위(`TIMESTAMP(0)`)라, 한 테스트 안의 SUSPEND · RESUME · CLOSE 가 같은 초에 찍힌다.
- 해결: 순서가 아니라 **무엇이 몇 번 남았는지**만 본다(정렬한 목록으로 비교, `test_account_status.py` `actions`).

### ④ 점검 하나가 실패하면 계좌 상세가 500 으로 통째로 깨졌다
- 원인: 점검이 예외를 그대로 올렸다. 해지 요청은 롤백돼 결과적으로 막히긴 했지만 오류 코드가 없었고, 상세 화면은 열리지도 않았다.
- 해결: `_blocked` 로 감싸 「실패 = 그 사유로 막힘」 + 저장점(2-3).

### ⑤ 같은 회원의 해지와 탈퇴가 겹치면 데드락
- 원인: 해지는 계좌 행 → 잔액 행, 탈퇴 일괄 해지는 잔액 행 → 계좌 행 순서로 잠갔다.
- 해결: 해지를 잔액 행 → 계좌 행으로(2-4). **동시 실행을 재현하는 테스트는 없다** — 코드의 잠금 순서만 맞췄다.

### ⑥ 본인 확인을 넣자 기존 개설 테스트가 전부 403
- 원인: 기존 테스트는 개발용 `X-User-Id` 헤더로 시드 회원(user_020~023)에게 계좌를 열었다. 헤더에는 로그인 세션이 없어 본인 확인 번호를 받을 수 없다.
- 해결: 정상 흐름은 테스트마다 `/auth/register` 로 새 회원(가입 = 로그인)을 만들어 시험한다. 계좌를 여는 다른 테스트(`test_account_status.py` · `test_transfer_features.py` 의 `open_account` · `open_funded`)도 `ACCOUNT_OPEN` 번호를 받게 고쳤다. 상태로 막히는 경우(`user_024` RESTRICTED · `user_028` 가입 마무리 중)는 본인 확인보다 앞에서 걸리므로 헤더로 그대로 본다.

### ⑦ (참고) 원래 있던 불안정한 테스트
- `test_withdrawal.py::test_new_member_withdraws_end_to_end` 는 이번 변경 전부터 혼자 돌려도 8번 중 1번꼴로 실패한다. 추정 원인은 ③과 같은 초 단위 반올림(탈퇴의 동의 철회 기록이 가입 때 동의 기록보다 앞선 것처럼 보임). 손대지 않았다.

## 5. 남은 한계 (회고 · README 에 쓸 거리)
- **본인 확인 문구가 실제와 다를 수 있다**: 점검이 실패했을 뿐인데 「연결된 카드가 있어요」로 보인다. 그 안내를 보고 카드 화면에 가면 정리할 카드가 없다. (안전한 쪽을 고른 대가)
- **요청 번호를 개설 기록 `metadata` 에 둔다**: 전용 칸 · 고유 제약이 없어 「회원 행 잠금」에만 기대어 중복을 막는다. 같은 방식을 쓰는 다른 곳과 맞추려면 `accounts` 에 칸을 추가해야 한다.
- **개설 약관 동의는 개설 기록에만 남는다**: `terms` 에 예금거래기본약관을 넣으면 회원가입 약관 목록에 같이 나와서 넣지 않았다. 그래서 「약관 및 동의 내역」 화면에는 이 동의가 보이지 않는다.
- **1인당 계좌 수 제한이 없다**: 실제 은행은 단기간 여러 계좌 개설을 막는다(대포통장 방지).
- **배송 중인 카드 신청은 해지를 막지 않는다**: 아래 7-N 「발견한 문제」 참고.
- **데드락 수정 · 이체 상태 재확인은 동시 실행 테스트가 없다**: 잠금 순서와 `refresh` 를 코드로만 맞췄다.
- 브라우저로 화면을 직접 눌러 본 확인은 아직 없다(자동 테스트 · 타입 검사 · 빌드만).

## 10. API 별

### A1. `POST /accounts` — 계좌 개설
- **바뀐 점 (2026-11-10)**: 본문에 `step_up_challenge_id` 추가 — 없거나 맞지 않으면 403 `STEP_UP_REQUIRED`. 같은 `Idempotency-Key` 재요청은 이미 쓴 번호여도 처음 계좌를 돌려준다.
- 인증: 로그인 세션 + 본인 확인 `ACCOUNT_OPEN` (먼저 `POST /auth/step-up {"action": "ACCOUNT_OPEN", "pin" | "password"}`)
- 요청

| 이름 | 위치 | 타입 | 필수 | 제약 · 설명 |
|---|---|---|---|---|
| `Idempotency-Key` | 헤더 | string | ✅ | 8~80자. 같은 회원 · 같은 키면 처음 계좌를 돌려준다 |
| `account_type` | 본문 | string | ✅ | `CHECKING` · `SAVINGS` (그 밖은 422 `INVALID_ACCOUNT_TYPE`), 최대 30자 |
| `consents` | 본문 | string[] | ✅ (값으로) | `"required_terms"` 가 들어 있어야 함, 최대 10개 |
| `step_up_challenge_id` | 본문 | string \| null | ✅ (값으로) | `ACCOUNT_OPEN` 본인 확인 번호, 최대 40자. 빠지면 403 |

- 응답 `201` — 계좌 상세

| 이름 | 타입 | 설명 |
|---|---|---|
| `id` | string | `acc_` + 무작위 20자 |
| `resAccount` | string | 14자리 숫자, `110` 으로 시작 |
| `resAccountDisplay` | string | `110-XXXXX-XXXXXX` |
| `resAccountName` | string | 입출금통장 · 저축예금 |
| `resAccountNickName` | string | 새 계좌는 `""` |
| `account_type` · `lifecycle_status` | string | 요청한 유형 · `ACTIVE` |
| `is_favorite` | boolean | `false` |
| `resAccountStartDate` · `closed_at` | string · null | 오늘 `YYYYMMDD` · `null` |
| `version` | integer | 계좌 행 버전 (상태가 바뀔 때마다 1씩) |
| `resAccountCurrency` · `resAccountBalance` · `balance_as_of` | string | `KRW` · `"0"` · `YYYYMMDDHHmmss` |
| `close_blockers` | string[] | 지금 해지를 막는 사유 (새 계좌는 `[]`) |
| `notifications_enabled` | boolean | 입출금 알림 (새 계좌는 `true`) |

```json
{
  "id": "acc_f69aefe08128c10a900c",
  "resAccount": "11073252947503",
  "resAccountDisplay": "110-73252-947503",
  "resAccountName": "입출금통장",
  "resAccountNickName": "",
  "account_type": "CHECKING",
  "lifecycle_status": "ACTIVE",
  "is_favorite": false,
  "resAccountStartDate": "20261111",
  "closed_at": null,
  "version": 1,
  "resAccountCurrency": "KRW",
  "resAccountBalance": "0",
  "balance_as_of": "20261111001818",
  "close_blockers": [],
  "notifications_enabled": true
}
```

- 오류 (코드가 검사하는 순서)

| HTTP | code | message | 언제 |
|---|---|---|---|
| 401 | `UNAUTHORIZED` | 로그인이 필요합니다. | 로그인 안 함 |
| 403 | `SIGNUP_INCOMPLETE` | 가입을 마무리해 주세요. | 가입 마무리 중(`PENDING_VERIFICATION`) — 로그인 확인 단계에서 |
| 422 | `VALIDATION_ERROR` | 요청 값을 확인해 주세요. | `Idempotency-Key` 없음 · 길이 초과 |
| 422 | `INVALID_ACCOUNT_TYPE` | 계좌 유형을 다시 선택해 주세요. | 유형이 `CHECKING` · `SAVINGS` 가 아님 |
| 422 | `REQUIRED_TERMS_NOT_AGREED` | 필수 약관에 동의해 주세요. | `consents` 에 `required_terms` 없음 |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 이미 다른 내용으로 보낸 요청 번호예요. 처음부터 다시 만들어 주세요. | 같은 키로 이미 다른 유형의 계좌를 만듦 |
| 403 | `USER_NOT_ACTIVE` | 지금 계정 상태에서는 계좌를 만들 수 없어요. | 회원이 `ACTIVE` 가 아님(`RESTRICTED` 등) |
| 403 | `STEP_UP_REQUIRED` | 본인 확인을 다시 해 주세요. | 번호 없음 · 다른 회원/세션/action · 이미 씀 · 5분 지남 · 헤더 로그인 |
| 503 | `ACCOUNT_NUMBER_UNAVAILABLE` | 계좌번호를 만들지 못했어요. 잠시 후 다시 시도해 주세요. | 무작위 번호가 5번 연속 겹침 |
| 409 | `CONFLICT_RETRY` | 다른 요청과 겹쳤어요. 잠시 후 다시 시도해 주세요. | 커밋 때 다른 요청이 같은 번호를 막 가져감 (아무것도 안 남음) |

```json
{ "success": false, "error": { "code": "STEP_UP_REQUIRED", "message": "본인 확인을 다시 해 주세요." } }
```

본인 확인 번호 받기 (`POST /auth/step-up`, 기존 API — `action` 값만 늘었다):
```json
{ "step_up_challenge_id": "stu_33d2e96cb9b66657d446", "expires_at": "2026-11-11T00:23:18.297140+09:00" }
```

### A2. `POST /accounts/{accountId}/suspend` — 일시정지
- 인증: 로그인 세션 + 본인 확인 `ACCOUNT_STATUS_CHANGE`. `RESTRICTED` 회원도 된다.
- 요청

| 이름 | 위치 | 타입 | 필수 | 제약 · 설명 |
|---|---|---|---|---|
| `accountId` | 경로 | string | ✅ | 내 계좌 id |
| `step_up_challenge_id` | 본문 | string | ✅ | 최대 40자 |

- 응답 `200` — 계좌 상세, `lifecycle_status: "SUSPENDED"`, `version` 이 1 오른다. 활동 기록 `SUSPEND {from_status: ACTIVE}`.

```json
{ "id": "acc_f69aefe08128c10a900c", "lifecycle_status": "SUSPENDED", "version": 2, "closed_at": null, "resAccountBalance": "0", "close_blockers": [], "…": "(나머지 칸은 A1 과 같음)" }
```

- 오류 (코드가 검사하는 순서)

| HTTP | code | message | 언제 |
|---|---|---|---|
| 422 | `VALIDATION_ERROR` | 요청 값을 확인해 주세요. | 본문에 `step_up_challenge_id` 없음 |
| 404 | `ACCOUNT_NOT_FOUND` | 계좌를 찾을 수 없어요. | 없는 계좌 · 남의 계좌 |
| 403 | `STEP_UP_REQUIRED` | 본인 확인을 다시 해 주세요. | 번호가 맞지 않음 (예: `TRANSFER` 용 번호) |
| 409 | `ACCOUNT_ALREADY_SUSPENDED` | 이미 일시정지된 계좌예요. | 이미 `SUSPENDED` |
| 409 | `INVALID_STATUS_TRANSITION` | 해지한 계좌는 일시정지할 수 없어요. | `CLOSED` |

### A3. `POST /accounts/{accountId}/resume` — 정지 해제
- 인증 · 요청: A2 와 같다.
- 응답 `200` — `lifecycle_status: "ACTIVE"`. 활동 기록 `RESUME {from_status: SUSPENDED}`.
- 오류: `VALIDATION_ERROR`(422) → `ACCOUNT_NOT_FOUND`(404) → `STEP_UP_REQUIRED`(403) → 409 `ACCOUNT_NOT_SUSPENDED` 「정지된 계좌가 아니에요.」(정지 상태가 아닐 때).

### A4. `POST /accounts/{accountId}/close` — 해지
- 인증 · 요청: A2 와 같다.
- 응답 `200` — `lifecycle_status: "CLOSED"`, `closed_at` = 오늘 `YYYYMMDD`, `is_favorite: false`. 활동 기록 `CLOSE {from_status: ACTIVE, reason: "사용자 해지"}`. 해지한 계좌는 `GET /accounts` 기본 목록에서 빠지고 `?status=CLOSED` 로만 보인다.

```json
{ "id": "acc_f69aefe08128c10a900c", "lifecycle_status": "CLOSED", "closed_at": "20261111", "is_favorite": false, "version": 4, "close_blockers": [], "…": "(나머지 칸은 A1 과 같음)" }
```

- 오류 (코드가 검사하는 순서)

| HTTP | code | message | 언제 |
|---|---|---|---|
| 422 | `VALIDATION_ERROR` | 요청 값을 확인해 주세요. | 본문에 `step_up_challenge_id` 없음 |
| 404 | `ACCOUNT_NOT_FOUND` | 계좌를 찾을 수 없어요. | 없는 계좌 · 남의 계좌 (잠그기 전에) |
| 403 | `STEP_UP_REQUIRED` | 본인 확인을 다시 해 주세요. | 번호가 맞지 않음 |
| 409 | `INVALID_STATUS_TRANSITION` | 이미 해지한 계좌예요. | `CLOSED` |
| 409 | `INVALID_STATUS_TRANSITION` | 일시정지된 계좌는 정지를 해제한 뒤에 해지할 수 있어요. | `SUSPENDED` |
| 503 | `BALANCE_UNAVAILABLE` | 잔액을 불러오지 못했어요. 잠시 후 다시 시도해 주세요. | 잔액 행 없음 |
| 409 | `ACCOUNT_CLOSE_NOT_ALLOWED` | 걸린 사유 문장을 이어 붙인 것 | 사유가 하나라도 있음 — `error.reasons` 에 코드 목록 |

`reasons` 의 순서는 늘 `BALANCE_REMAINING` → `PENDING_TRANSFER` → `LINKED_SUBSCRIPTION` → `LINKED_CARD` 이고, 걸린 것만 들어간다. 시드 `user_001` 의 `acc_001`:
```json
{
  "success": false,
  "error": {
    "code": "ACCOUNT_CLOSE_NOT_ALLOWED",

    "reasons": ["BALANCE_REMAINING", "PENDING_TRANSFER", "LINKED_SUBSCRIPTION", "LINKED_CARD"]
```
