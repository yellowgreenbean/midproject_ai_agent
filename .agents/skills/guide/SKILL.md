# /guide — 구현한 기능의 가이드북 쓰기

사용자가 **혼자 코드를 리뷰하고, 같은 기능을 다시 만들 수 있게** 하는 문서를 쓴다.
인자: `$ARGUMENTS` (예: `/guide 상품`, `/guide 카드 f807ea4`, 빈 값도 된다)

## 절대 규칙
- **커밋·푸시하지 않는다.** `git add` 도 하지 않는다. 사용자가 직접 한다(사용자 결정 2026-11-10).
- **이미 있는 가이드북은 덧붙이기만 한다.** 기존 줄은 오타·경로 오류까지 고치지 않는다. 고칠 게 보이면 새 장에 「정정」으로 적는다.
- **기억으로 쓰지 않는다.** 함수 이름·줄 번호·응답 값·테스트 수는 모두 지금 파일과 실제 실행 결과에서 옮긴다.
- **개발 DB 에 쓰는 일**(더미 다시 넣기, 실제 가입·이체 요청 등)은 하기 전에 사용자에게 묻는다. 읽기 요청과 테스트 DB(`midproject_test`)는 묻지 않아도 된다.
- 문서는 한국어, 처음 배우는 사람이 읽는 말투로 쓴다. 기존 `docs/가이드북_*.md` 의 말투와 형식을 따른다.

## 1. 무엇을 쓸지 정하기
1. **기능 이름**: `$ARGUMENTS` 의 첫 낱말. 없으면 이 대화에서 구현한 기능으로 정한다.
2. **파일**: `docs/가이드북_<기능이름>.md` — 이름은 띄어쓰기 없는 한국어(예: `회원가입로그인`, `카드`, `챗봇랭그래프`).
   - `ls docs/가이드북_*.md` 로 같은 기능의 가이드북이 있는지 먼저 본다. 있으면 그 파일에 덧붙인다.
3. **범위(어떤 변경이 이 기능인가)**:
   - 기준 커밋이 주어지면 `git diff <기준>` (커밋된 것 + 작업 트리)과 `git log <기준>..HEAD`.
   - 없으면 `git status` · `git diff HEAD` · 새 파일(`??`). 작업 트리에 여러 기능이 섞여 있으므로 **이 기능 파일만** 고른다. 이 대화에서 고친 파일 목록을 우선 쓴다.
   - 문서에 범위의 기준을 적는다: 「기준: 커밋 `abc1234` 이후」 또는 「기준: 커밋 안 된 작업 트리 (2026-11-10)」.
4. 다음 중 하나라도 확실하지 않으면 시작하기 전에 **AskUserQuestion 으로 한 번에 묻는다**: 기능 이름 · 새 파일인지 기존 파일에 덧붙일지 · 어떤 파일이 범위에 드는지 · API 예시를 받으려고 서버를 켜도 되는지.

## 2. 재료 모으기
- 범위 안의 파일은 **diff 와 함께 지금 내용 전체를** 읽는다. 바뀐 함수는 줄 번호를 적어 둔다.
- 이 대화에서 사용자가 정한 것(AskUserQuestion 답 · 직접 한 말)을 날짜와 함께 모은다 → 「정한 규칙」 표.
- 이 대화에서 겪은 오류와 해결 방법을 모은다 → 「겪은 문제와 해결」.
- 관련 테스트를 실제로 돌려 숫자를 받는다.
  - 서버: `cd backend && .venv\Scripts\python -m pytest -q tests/<관련 파일>` (Docker 의 `midproject-postgres` 가 꺼져 있으면 `docker start midproject-postgres` 를 한 뒤)
  - 화면: `cd frontend && npx vitest run <관련 파일>`
  - 더미 데이터를 바꿨으면 `python3 scripts/check_dummy.py` → `오류 0`.
- API 응답 예시: 개발 서버(`http://localhost:8010`)에 **읽기 요청만** 보내 받는다. 서버는 `--reload` 없이 켠다. 새 경로가 404 이면 예전 서버가 떠 있는 것이므로 끄고 다시 켠다. 받을 수 없는 예시(돈이 움직이는 요청 등)는 응답 모양에 맞춰 쓰고 「(예시 — 실제 호출 아님)」이라고 표시한다.

## 3. 쓰기 — 형식은 [template.md](template.md)
세 부분을 이 순서로 쓴다.

**① 구현한 기능**: 목적 · 만든 것 표(기능 / 화면 / API / 코드 위치) · 정한 규칙(사용자 결정 날짜) · 동작 흐름 · 겪은 문제와 해결 · 직접 해 보기(명령을 그대로 복사해 쓸 수 있게) · 실패 상황 확인 · 자동 테스트 결과 · 남은 한계.

**② 코드 리뷰**
- **바뀐 파일 링크 표**: 파일 · 새로 만듦/바꿈 · 줄 수(+/−) · 한 줄 설명 · 먼저 볼 곳 링크. 링크는 `docs/` 에서 본 상대 경로다: `[agent.py:120](../backend/app/agent.py#L120)`. 줄 번호는 이 문서를 쓴 시점 기준이라고 표 위에 적는다.
- **사람 말로 쓴 diff**: 핵심 함수마다 「전에는 → 이제는 → 왜」 세 줄과 짧은 코드 발췌(10~25줄). 새 파일은 「전에는: 없었음」. 사소한 변경(이름 바꾸기·import)은 표 한 줄로 묶는다.
- **리뷰 체크리스트**: `- [ ]` 항목으로, 사용자가 직접 확인할 것. 항목마다 **어디를 보나(링크)** · **무엇이 맞아야 하나** · **어떻게 확인하나(테스트 이름이나 명령)** 를 적는다. 이 프로젝트에서 빠뜨리지 않을 것:
  - 권한: 다른 사용자(`user_id`)의 계좌·카드·가입에 닿지 못하는가
  - 돈: 금액 계산(원 미만 처리), 잔액 잠금, 원장 기록과 잔액이 같이 움직이는가, 실패하면 전부 되돌아가는가
  - 중복 요청: `Idempotency-Key`, 같은 요청 두 번
  - 본인 확인: step-up 번호의 action · 1회 사용 · 만료
  - 입력 검사와 오류 코드·HTTP 상태가 정의서와 같은가
  - 화면 규칙(`frontend/src/*Rules.ts`)과 서버 규칙이 어긋나지 않는가
  - 테스트가 다루지 않는 경우 — 찾았으면 「테스트 없음」이라고 적는다
- 리뷰하다 실제 문제를 찾으면 **고치지 말고** 「발견한 문제」로 적고 끝날 때 사용자에게 알린다.

**③ API 정의서**: 이 범위에서 HTTP API 를 새로 만들거나 바꿨을 때만. 없으면 「이번 변경에는 API 가 없다 — (이유)」 한 줄.
- 한눈에 보기 표: # · 메서드·경로 · 하는 일 · 로그인 · 화면 함수(`frontend/src/api.ts`)
- 공통 규칙(인증·CSRF·값 모양·오류 형식)은 다시 쓰지 말고 [docs/API정의서_상품_챗봇.md](../../../docs/API정의서_상품_챗봇.md) 1장을 링크한다. 이 기능에만 있는 규칙만 쓴다.
- API 마다: 인증 · 요청 표(이름·타입·필수·제약) · 응답 표 · JSON 예시 · 오류 표(**코드가 검사하는 순서대로**: HTTP 상태 · code · message · 언제).
- 바꾼 API 는 무엇이 바뀌었는지 먼저 적는다.

## 4. 기존 파일에 덧붙일 때
1. 덧붙이기 전 줄 수와 해시를 잰다: `N=$(wc -l < 파일); head -n $N 파일 | md5sum`
2. 마지막 장 번호 다음부터 새 「N부」로 쓴다(예: 기존이 14장까지면 `# N부 — <제목>` 아래 15장부터). 맨 위에 「1부와 달라진 점」 표를 둔다.
3. 덧붙인 뒤 `head -n $N 파일 | md5sum` 이 처음과 같은지 확인한다. 다르면 되돌리고 다시 쓴다.

## 5. 마무리
- 문서의 링크가 가리키는 파일이 모두 있는지 확인한다(`../` 경로를 하나씩 `ls`).
- 사용자에게 짧게 알린다: 파일 경로(링크) · 새로 쓴 장 · 테스트 결과 숫자 · 리뷰 중 발견한 문제(있으면) · 실제 호출이 아닌 예시 · **「커밋·푸시는 하지 않았다」**.
