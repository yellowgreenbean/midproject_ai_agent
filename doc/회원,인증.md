## 1. 목표

> 과제 조건: "회원가입과 로그인·로그아웃 기능을 구현하고, 인증된 사용자가 본인에게 허용된 정보와 기능을 이용할 수 있도록 한다."

- 이 파트가 책임지는 것:
  - 회원가입: 실제 은행 앱의 가입 흐름을 참고해 필요한 정보를 입력받고, 중복·형식 검증을 거쳐 사용자를 생성한다.
  - 로그인·로그아웃: 아이디와 비밀번호로 인증하고, 로그인 상태를 세션으로 유지하며, 로그아웃 시 세션을 종료한다.
  - 본인 정보 보호: 로그인한 사용자가 자신의 계좌·카드·거래·대화 내역만 보고 조작할 수 있게 한다. 타인의 데이터는 URL을 직접 입력해도 접근되지 않아야 한다.
  - 인증 관련 자연어 요청 처리: "로그아웃 해줘", "비밀번호 바꿔줘" 같은 요청을 직접 처리하거나 해당 화면으로 안내한다.
  - 인증 실패 상황의 동작 정의: 중복 가입, 비밀번호 오류, 세션 만료, 미인증 접근 등에서 사용자에게 무엇을 보여줄지 정한다.
- 이 파트가 다른 파트에 제공하는 것(공통 규칙):
  - users 테이블과 user_id: 계좌, 카드, 거래, 대화 기록 등 모든 테이블이 user_id로 사용자와 연결된다. (DB 담당)
  - 접근 제어 규칙(6장): 모든 조회·변경은 세션의 user_id 기준으로 필터링한다. 네 명이 각자 구현할 때 동일하게 적용한다. (전원)
  - 로그인 필요 화면 보호 방식: 데코레이터 또는 미들웨어 한 가지로 통일해 모든 화면에서 같은 방식으로 쓴다. (전원)
  - 미인증 상태의 자연어 요청 처리 기준: 로그인하지 않은 사용자의 요청에 어떻게 답할지 정한다. (자연어 담당)
  - 2차 인증 제공 여부: 이체 등 중요 동작 전 간편비밀번호 확인 기능을 둘지와 그 호출 방식을 정한다. (계좌 담당)

- 완료 기준:
  - 가입 → 로그인 → 보호된 화면 이용 → 로그아웃 흐름이 끊김 없이 동작한다.
  - 로그인하지 않으면 보호된 화면과 데이터에 접근할 수 없다.
  - 로그인한 사용자가 다른 사용자의 데이터를 어떤 경로로도 볼 수 없다.
  - 10장의 실패 시나리오가 모두 기대한 대로 동작하고, 그 결과가 README에 기록된다.

## 2. 참고한 실제 은행 앱

| 앱 | 가입 단계 수 | 받는 정보 | 로그인 방식 | 참고할 점 |
|---|---|---|---|---|
| 토스 | 약 5단계 (휴대폰 번호 → 이름·생년월일·통신사 → 문자 본인인증 → 약관 동의 → 간편비밀번호·생체 설정) | 휴대폰 번호, 이름, 주민번호 앞자리(생년월일·성별), 통신사 | 간편비밀번호(숫자 PIN), 생체인증. 기기 등록 기반이라 아이디·비밀번호 입력이 없음 | 한 화면에 입력 하나씩만 받는 단계형 UI. 가입 즉시 홈으로 진입. 아이디 개념이 없어 우리 프로젝트와 구조가 다름 |
| 카카오뱅크 | 약 6단계 (카카오계정 또는 휴대폰 인증 → 약관 동의 → 이름·주민번호 → 휴대폰 본인인증 → 인증비밀번호 6자리 → 패턴·생체 설정) | 이름, 주민번호, 휴대폰 번호, 카카오계정(선택) | 인증비밀번호(6자리), 패턴, 생체인증 | 약관 동의를 "전체 동의 + 필수/선택 구분"으로 한 화면에 처리. 가입과 계좌 개설이 분리되어 있음(가입 후 계좌 개설은 별도 흐름) |
| 신한 SOL / KB스타뱅킹 (전통 은행) | 약 4~5단계 (약관 동의 → 본인인증 → 아이디·비밀번호 설정 → 간편비밀번호 설정) | 이름, 주민번호, 휴대폰 번호, 아이디, 비밀번호 | 아이디·비밀번호 로그인 지원, 간편비밀번호(6자리), 패턴, 생체, 공동인증서 | **우리 프로젝트와 가장 가까운 형태.** 아이디·비밀번호로 로그인하고, 이체 등 중요 동작 전에 간편비밀번호를 한 번 더 묻는 2단계 구조 |

> 위 내용은 기억에 의존해 정리한 것이므로, 공유 전 실제 앱을 열어 단계 수와 입력 항목을 확인하고 수정한다.

### 2.1 우리 프로젝트에 반영할 것

- **로그인 구조는 전통 은행 앱 방식**: 휴대폰 본인인증과 기기 등록을 구현하지 않으므로, 아이디·비밀번호 로그인을 기본으로 한다.
- **가입 화면은 토스 방식**: 한 화면에 입력을 하나(또는 한 묶음)씩만 받는 단계형 UI로 구성해 모바일 앱 느낌을 낸다. 서버 렌더링이라면 단계별 페이지 또는 한 페이지 안의 단계 전환으로 구현한다.
- **약관 동의는 카카오뱅크 방식**: 전체 동의 체크박스와 필수·선택 항목 구분을 둔다.
- **본인인증은 흉내만 낸다**: 이름·생년월일·휴대폰 번호를 입력받되 실제 문자 인증은 하지 않는다. 필요하면 "인증번호 입력" 화면을 두고 고정값(예: 000000)으로 통과시키는 방식을 검토한다.
- **2차 인증(간편비밀번호)**: 세 앱 모두 이체 등 중요 동작 전에 숫자 PIN을 요구한다. 선택 기능으로 두고 계좌 담당과 협의해 결정한다(11장).
- **가입과 계좌 개설 분리**: 카카오뱅크처럼 회원가입만으로 끝내고, 계좌 개설은 계좌 파트의 별도 흐름으로 넘긴다.

## 3. 범위

### 3.1 구현하는 기능

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| AUTH-01 | 회원가입 | 단계형 화면에서 약관 동의, 아이디, 비밀번호, 이름, 생년월일, 휴대폰 번호를 입력받아 사용자를 생성한다. 아이디 중복과 비밀번호 규칙을 검증하고, 비밀번호는 해시로 저장한다. 가입 완료 시 자동 로그인 후 홈으로 이동한다. | 필수 |
| AUTH-02 | 로그인 | 아이디와 비밀번호로 인증한다. 실패 시 아이디 존재 여부를 노출하지 않는 공통 메시지를 보여주고, 연속 실패 횟수를 기록해 일정 횟수 초과 시 일시 잠금한다. 성공 시 세션을 만들고 마지막 로그인 시각을 갱신한다. | 필수 |
| AUTH-03 | 로그아웃 | 세션을 삭제하고 시작 화면으로 이동한다. 화면의 버튼과 자연어 요청("로그아웃 해줘") 양쪽에서 호출할 수 있다. | 필수 |
| AUTH-04 | 세션 유지 / 만료 | 서버 세션 쿠키로 로그인 상태를 유지한다. 일정 시간(예: 30분) 동작이 없으면 만료시키고, 만료 후 보호된 화면 요청은 로그인 화면으로 보낸다. 자연어 대화 맥락도 세션 단위로 묶는다. | 필수 |
| AUTH-05 | 본인 정보 접근 제어 | 로그인 필요 화면은 공통 보호 장치(데코레이터 또는 미들웨어)로 막는다. 계좌·카드·거래·대화 기록의 모든 조회와 변경은 세션의 user_id로 필터링하며, URL에 타인의 식별자를 넣어도 404 또는 403으로 응답한다. | 필수 |
| AUTH-06 | 내 정보 조회 / 수정 | 이름, 생년월일, 휴대폰 번호, 가입일을 보여주고 휴대폰 번호만 수정할 수 있게 한다. 자연어 "내 정보 보여줘"의 이동 대상 화면이다. | 선택 |
| AUTH-07 | 비밀번호 변경 | 현재 비밀번호 확인 후 새 비밀번호로 변경한다. 새 비밀번호는 가입 시와 같은 규칙을 적용하고, 현재 비밀번호와 같으면 거부한다. 변경 후 다른 세션은 그대로 둔다(단일 기기 전제). | 선택 |
| AUTH-08 | 2차 인증(간편비밀번호) | 가입 시 또는 내 정보 화면에서 숫자 6자리 간편비밀번호를 등록한다. 이체 등 중요 동작 직전에 입력을 요구하는 공통 확인 화면(또는 함수)을 제공하고, 계좌 파트가 호출해서 쓴다. | 선택 (계좌 담당과 협의) |

구현 순서는 AUTH-01 → 02 → 04 → 05 → 03 순으로 하고, 이 다섯 가지가 끝난 뒤 06 → 07 → 08을 진행한다. AUTH-05는 다른 파트가 자기 화면을 만들 때부터 필요하므로, 보호 장치의 사용법을 먼저 공유한다.

### 3.2 이번에 구현하지 않는 것

| 항목 | 제외 이유 | 대체 방식 |
|---|---|---|
| 비밀번호 찾기 / 재설정 메일 | 메일 발송 인프라가 필요하고 평가 범위 밖 | 잊어버린 경우 테스트 계정을 새로 만든다 |
| 소셜 로그인(카카오·네이버·구글) | OAuth 앱 등록과 콜백 처리가 과제 핵심과 무관 | 아이디·비밀번호 로그인만 제공 |
| 휴대폰 본인인증, 실명 확인 | 외부 인증 서비스 연동 불가 | 번호만 입력받고, 필요하면 고정 인증번호 화면으로 흉내만 낸다 |
| 생체인증, 패턴, 기기 등록 | 네이티브 앱 기능이라 웹에서 구현 범위 밖 | 간편비밀번호(AUTH-08)로 대체 |
| 공동인증서, OTP | 실제 은행 보안 매체라 재현 불가 | 2차 인증은 간편비밀번호로 통일 |
| 다중 기기 세션 관리, 강제 로그아웃 | 단일 기기 사용 전제 | 세션 하나만 유지 |
| 관리자 계정, 권한 등급 | 일반 사용자만 존재 | 모든 사용자는 동일 권한 |
| 회원 탈퇴 | 계좌·거래 데이터 정리 규칙이 필요해 범위가 커짐 | 시간이 남으면 마지막에 검토 |

## 4. 회원가입

### 4.1 입력 항목

| 항목 | 필수 | 형식 / 규칙 | 오류 메시지 |
|---|---|---|---|
| 아이디 | O | 영문 소문자·숫자 조합 5~20자, 영문으로 시작. 대소문자 구분 없이 저장 시 소문자로 통일 | "아이디는 영문 소문자와 숫자로 5~20자여야 합니다." / "이미 사용 중인 아이디입니다." |
| 비밀번호 | O | 8~20자, 영문·숫자·특수문자 중 2종류 이상 포함. 아이디와 같거나 아이디를 포함하면 불가. 같은 문자 4회 이상 연속 불가(예: 1111) | "비밀번호는 8~20자, 영문·숫자·특수문자 중 2종류 이상을 포함해야 합니다." / "아이디를 포함한 비밀번호는 사용할 수 없습니다." |
| 비밀번호 확인 | O | 비밀번호와 일치 | "비밀번호가 일치하지 않습니다." |
| 이름 | O | 한글 2~10자 또는 영문 2~30자, 공백·숫자 불가 | "이름을 정확히 입력해 주세요." |
| 생년월일 | O | YYYY-MM-DD, 실제 존재하는 날짜, 오늘 이전, 만 14세 이상 | "생년월일 형식이 올바르지 않습니다." / "만 14세 이상만 가입할 수 있습니다." |
| 휴대폰 번호 | O | 010으로 시작하는 숫자 10~11자리. 하이픈은 입력 시 허용하되 저장 시 제거 | "휴대폰 번호를 정확히 입력해 주세요." |
| 약관 동의 | O | 필수 약관(서비스 이용약관, 개인정보 수집·이용) 모두 체크. 선택 약관(마케팅 수신)은 미체크 허용 | "필수 약관에 동의해 주세요." |

### 4.2 검증 규칙

- **아이디 중복**: 입력 즉시 확인하지 않고, 해당 단계에서 "다음" 버튼을 눌렀을 때 서버에서 확인한다. 저장 직전(최종 제출)에도 한 번 더 확인해 동시 가입에 대비한다. 대소문자만 다른 아이디는 같은 아이디로 본다.
- **비밀번호 규칙**: 4.1의 규칙을 서버에서 검증한다. 브라우저의 입력 제한은 보조 수단으로만 쓰고, 최종 판단은 항상 서버가 한다. 비밀번호는 해시(예: werkzeug 또는 bcrypt)로 저장하며 평문은 로그에도 남기지 않는다.
- **나이 제한**: 생년월일 기준 만 14세 이상만 가입할 수 있다. 실제 은행은 만 19세 미만에게 보호자 동의를 요구하지만, 이 프로젝트에서는 나이에 따른 상품 제한만 계좌 파트가 판단하도록 생년월일을 넘겨준다.
- **휴대폰 번호 중복**: 허용한다. 실제 본인인증이 없어 한 번호로 여러 테스트 계정을 만들 수 있어야 한다.
- **입력값 정리**: 모든 문자열은 앞뒤 공백을 제거하고, 아이디는 소문자로, 휴대폰 번호는 숫자만 남겨 저장한다.
- **검증 실패 시**: 해당 단계에 머물며 오류 메시지를 입력란 아래에 표시한다. 이미 입력한 다른 값은 유지한다.

### 4.3 가입 흐름

| 단계 | 화면 | 입력 | 다음 단계 조건 |
|---|---|---|---|
| 1 | 약관 동의 | 전체 동의 체크박스, 필수 2개, 선택 1개 | 필수 약관 모두 체크 |
| 2 | 아이디 | 아이디 | 형식 통과 + 중복 아님 |
| 3 | 비밀번호 | 비밀번호, 비밀번호 확인 | 규칙 통과 + 두 값 일치 |
| 4 | 기본 정보 | 이름, 생년월일, 휴대폰 번호 | 형식 통과 + 나이 조건 |
| 5 | 확인 및 완료 | 입력 내용 요약(비밀번호 제외), "가입하기" 버튼 | 서버 최종 검증 통과 |

- 각 단계 상단에 진행 표시(예: 2/5)를 두고, "이전" 버튼으로 돌아가면 입력값이 유지되도록 한다.
- 단계 사이의 입력값은 서버 세션(임시 저장)에 보관하고, 최종 제출 시에만 users 테이블에 저장한다. 중간에 이탈하면 임시값은 세션 만료와 함께 사라진다.
- 서버 렌더링 구현 시 단계별로 별도 URL(/signup/1 ~ /signup/5)을 두는 방식과, 한 페이지에서 단계를 전환하는 방식 중 하나를 택한다. 단순한 쪽은 단계별 URL이다.
- 가입 완료 후 이동할 화면: 자동 로그인 후 홈(S-04). 홈에서 "첫 계좌를 만들어 보세요" 안내를 띄워 계좌 개설 흐름으로 연결한다(계좌 파트와 협의).
- 간편비밀번호(AUTH-08)를 구현하는 경우 5단계 뒤에 "간편비밀번호 설정" 단계를 추가한다. 건너뛰기를 허용하고, 내 정보 화면에서 나중에 등록할 수 있게 한다.

### 4.4 시드 사용자

테스트와 발표를 위해 가입 없이 바로 쓸 수 있는 사용자를 미리 넣어 둔다. 비밀번호는 README에 기록한다.

| 아이디 | 이름 | 용도 |
|---|---|---|
| user1 | 김하나 | 기본 시연용, 계좌·카드·거래 데이터 포함 |
| user2 | 이두리 | 타인 데이터 접근 차단 테스트용 |
| user3 | 박세나 | 가입 직후 상태(계좌 없음) 테스트용 |

## 5. 로그인 / 로그아웃

### 5.1 로그인

- **입력**: 아이디 + 비밀번호. 아이디는 소문자로 변환하고 앞뒤 공백을 제거한 뒤 조회한다.
- **처리 순서**:
  1. 아이디로 사용자 조회
  2. 잠금 상태(locked_until이 현재 시각 이후)면 잠금 메시지 표시 후 종료
  3. 비밀번호 해시 비교
  4. 실패: failed_login_count 1 증가, 5회 도달 시 locked_until을 10분 뒤로 설정
  5. 성공: failed_login_count 0, locked_until 비움, last_login_at 갱신, 세션 생성
- **성공 시 이동 화면**: 홈(S-04). 로그인 전에 보호된 화면에 접근하려다 돌아온 경우(next 파라미터)에는 그 화면으로 복귀한다. next 값은 우리 사이트 내부 경로("/"로 시작)만 허용하고, 외부 URL이면 무시하고 홈으로 보낸다.
- **실패 시 메시지**: 아이디 없음과 비밀번호 틀림을 **구분하지 않는다**. 둘 다 "아이디 또는 비밀번호가 올바르지 않습니다."로 통일해 아이디 존재 여부가 드러나지 않게 한다. 비밀번호 틀림일 때만 "(남은 시도 N회)"를 덧붙일지는 선택 사항이다.
- **연속 실패 처리**: 5회 연속 실패 시 10분간 잠금. 잠금 중에는 올바른 비밀번호를 넣어도 "비밀번호를 5회 이상 잘못 입력해 10분간 로그인할 수 없습니다. (HH:MM 이후 가능)"을 표시한다. 잠금은 시간이 지나면 자동 해제되고, 해제 후 첫 성공 로그인에서 카운트가 0이 된다. 실제 은행은 영업점 방문 또는 본인인증으로 해제하지만, 이 프로젝트는 시간 경과 방식만 둔다.
- **이미 로그인된 상태에서 로그인 화면 접근**: 홈으로 바로 보낸다.
- **로그인 화면 구성**: 아이디, 비밀번호, "로그인" 버튼, "회원가입" 링크. 아이디 저장 체크박스는 선택 사항(브라우저 localStorage 사용).

### 5.2 로그아웃

- **처리 방식**: POST 요청으로만 처리한다(GET 링크로 로그아웃되면 외부 링크 클릭만으로 로그아웃되는 문제가 있음). 서버 세션을 완전히 비우고(clear) 세션 쿠키를 만료시킨다. 자연어 대화 맥락도 세션에 있으므로 함께 사라진다.
- **호출 경로**: 홈·내 정보 화면의 로그아웃 버튼, 자연어 요청("로그아웃 해줘"). 자연어 경로에서는 "로그아웃할까요?" 확인 없이 바로 처리하고 결과만 알려준다(되돌리기 쉬운 동작이므로).
- **로그아웃 후 이동 화면**: 시작 화면(S-01)으로 이동하며 "로그아웃되었습니다." 안내를 한 번 표시한다.
- **로그인하지 않은 상태에서 로그아웃 요청**: 오류 없이 시작 화면으로 보낸다.

### 5.3 세션

- **저장 방식**: 프레임워크 기본 서버 세션 쿠키(Flask는 서명된 쿠키 세션, FastAPI는 starlette SessionMiddleware)를 쓴다. 토큰(JWT) 방식은 서버 렌더링 구조에서 이점이 없고 만료·무효화가 번거로워 쓰지 않는다. 별도 세션 테이블은 두지 않는다.
- **세션에 저장하는 값**: user_id, 로그인 시각, 마지막 활동 시각, 자연어 대화 맥락(최근 N턴), 가입 진행 중 임시값, 2차 인증 통과 시각(AUTH-08 구현 시).
- **쿠키 설정**: HttpOnly 켬, SameSite=Lax, 개발 환경에서는 Secure 끔(배포 시 켬). 세션 서명 키는 코드에 넣지 않고 환경 변수(.env)로 읽는다.
- **만료 시간**: 마지막 활동 기준 30분. 요청이 올 때마다 마지막 활동 시각을 갱신한다(슬라이딩 방식). 실제 은행 앱은 5~10분이지만, 시연 중 끊기지 않도록 30분으로 둔다.
- **만료 후 요청 시 동작**:
  - 화면 요청: 세션을 비우고 로그인 화면으로 보내며 "로그인 시간이 만료되었습니다. 다시 로그인해 주세요." 안내. 원래 요청 경로를 next로 넘겨 로그인 후 복귀한다.
  - 자연어 요청: 같은 안내와 함께 로그인 화면 링크를 응답으로 돌려준다. 대화 맥락은 세션과 함께 사라진 것으로 본다.
  - 폼 제출(POST) 중 만료: 입력값은 복구하지 않고 로그인 화면으로 보낸다.
- **로그인 시 세션 재생성**: 로그인 성공 시 기존 세션 값을 비우고 새로 만들어 세션 고정 공격을 막는다.
- **동시 로그인**: 같은 계정으로 다른 브라우저에서 로그인해도 막지 않는다(3.2의 단일 기기 전제대로 관리 기능은 두지 않음).

## 6. 접근 제어 규칙 (공통 규칙, 전원 적용)

| 규칙 | 내용 |
|---|---|
| R1 | 로그인 없이 접근 가능한 화면은 시작(S-01), 회원가입(S-02), 로그인(S-03), 상품 안내(금리·가입 조건 소개, 계좌 파트), 정적 파일뿐이다. 그 외 모든 화면과 API는 로그인이 필요하다. |
| R2 | 로그인 필요 화면에 미인증 접근 시 로그인 화면으로 보내고, 로그인 후 원래 화면으로 복귀한다(next 파라미터, 내부 경로만 허용). POST 요청이었다면 복귀하지 않고 홈으로 보낸다. |
| R3 | 모든 데이터 조회·변경은 세션의 user_id로 필터링한다. 쿼리에 user_id 조건이 빠진 조회는 버그로 본다. 폼이나 URL로 넘어온 user_id 값은 절대 신뢰하지 않고 세션 값만 쓴다. |
| R4 | URL이나 폼에 타인의 계좌번호·카드번호·거래 ID를 넣어도 조회·변경되지 않아야 한다. 존재하지 않는 것과 똑같이 404로 응답해 타인 데이터의 존재 여부도 노출하지 않는다. |
| R5 | 보호 장치는 한 가지로 통일한다. 로그인 필요 화면마다 공통 데코레이터(예: @login_required) 또는 미들웨어를 붙이고, 각자 자기 파트 화면에 빠짐없이 적용한다. 보호 여부는 7장 화면 목록의 "인증 필요" 열을 기준으로 한다. |
| R6 | 로그인한 사용자 정보는 요청마다 세션의 user_id로 DB에서 다시 읽어 쓴다(예: g.user 또는 request.state.user). 이름·잔액 등을 세션에 캐시하지 않아 값이 바뀌어도 바로 반영된다. |
| R7 | 상태를 바꾸는 요청(가입, 로그인, 로그아웃, 이체, 개설 등)은 반드시 POST로 받고, GET으로는 조회만 한다. 폼에는 CSRF 토큰을 넣는다(프레임워크 지원 범위 내에서). |
| R8 | 자연어 요청으로 실행되는 기능도 같은 규칙을 따른다. 자연어 처리기는 세션의 user_id를 받아 기능 함수를 호출하며, 사용자가 문장 안에 다른 사람의 이름이나 계좌를 넣어도 본인 데이터 범위 안에서만 동작한다. |
| R9 | 이체·해지 등 중요 동작은 2차 인증(AUTH-08)을 구현할 경우 통과 후 5분 안에만 실행할 수 있다. 미구현 시에는 확인 화면만 둔다. |

### 6.1 적용 방식 예시 (전원 공통)

```python
# 모든 파트가 같은 방식으로 사용
@app.route("/accounts")
@login_required                      # R2, R5
def account_list():
    accounts = Account.query.filter_by(user_id=g.user.id).all()   # R3
    ...

@app.route("/accounts/<int:account_id>")
@login_required
def account_detail(account_id):
    account = Account.query.filter_by(id=account_id, user_id=g.user.id).first_or_404()  # R3, R4
    ...
```

- login_required와 g.user(또는 request.state.user)는 회원·인증 파트가 제공하고, 다른 파트는 가져다 쓴다.
- 각자 구현 완료 후 "타인 계좌 URL 직접 입력" 테스트(F-06)를 전원이 돌려 R4를 확인한다.

```
                        └─ 5회 → 10분 잠금  │                              ├────────> [S-07 간편비밀번호 설정] ─> S-05
                                            │                              └─ "로그아웃"(POST) ──> [S-09] ──> S-01
                                            ├─ 계좌·카드 탭 ──> (계좌·카드 파트 화면)
                                            └─ 자연어 입력창 ──> (자연어 파트) ──"로그아웃 해줘"──> S-09

[미인증 상태에서 보호 화면 접근] ──> [S-03 로그인?next=원래경로] ──성공──> [원래 가려던 화면]
[세션 만료 후 요청]            ──> [S-03 로그인] "만료 안내"      ──성공──> [원래 가려던 화면]
[타인 데이터 URL 접근]          ──> [S-10 404]
[중요 동작(이체 등), AUTH-08 구현 시] ──> [S-08 2차 인증] ──통과──> 동작 실행 / ──취소──> 이전 화면
```

| 인증됨 | S-01, S-03 | S-04 홈으로 이동 |

## 8. DB 설계 (users)

### 8.1 users 테이블

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | INTEGER | PK, AUTOINCREMENT | 다른 모든 테이블이 참조하는 사용자 식별자 |
| login_id | TEXT | UNIQUE, NOT NULL | 아이디. 소문자로 정규화해 저장 (4.1) |
| password_hash | TEXT | NOT NULL | 해시 문자열. 평문 저장 금지 |
| name | TEXT | NOT NULL | 이름 |
| birth_date | DATE | NOT NULL | 생년월일. 나이 제한(4.2)과 상품 가입 조건(계좌 파트) 판단에 사용 |
| phone | TEXT | NOT NULL | 숫자만 저장(예: 01012345678). 중복 허용 |
| marketing_agree | INTEGER | DEFAULT 0 | 선택 약관 동의 여부 (0/1) |
| simple_pin_hash | TEXT | NULL 허용 | 2차 인증용 간편비밀번호 해시. 미등록이면 NULL |
| failed_login_count | INTEGER | DEFAULT 0 | 연속 로그인 실패 횟수. 성공 시 0 |
| locked_until | DATETIME | NULL 허용 | 잠금 해제 시각. NULL 또는 과거면 잠금 아님 |
| created_at | DATETIME | NOT NULL, DEFAULT now | 가입일시 |
| last_login_at | DATETIME | NULL 허용 | 마지막 로그인 성공 시각 |

- 주민등록번호 뒷자리, 비밀번호 평문, 간편비밀번호 평문은 어떤 형태로도 저장하지 않는다.
- 이메일은 받지 않으므로 컬럼을 두지 않는다. 나중에 필요하면 NULL 허용 컬럼으로 추가한다.
- SQLite 기준 타입으로 적었다. 다른 DB를 쓰면 DATE/DATETIME 타입만 맞춘다.

### 8.2 다른 테이블과의 관계 (DB 담당에게 전달)

| 테이블 | 연결 | 규칙 |
|---|---|---|
| accounts | accounts.user_id -> users.id (N:1) | 한 사용자가 여러 계좌. 계좌 조회·변경은 항상 user_id 조건 포함 (R3) |
| cards | cards.user_id -> users.id (N:1), 필요 시 cards.account_id -> accounts.id | 카드 소유자는 user_id로 직접 확인한다. 연결 계좌를 통해 간접 확인하지 않는다 |
| transactions | transactions.account_id -> accounts.id | user와 직접 연결하지 않고 계좌를 통해 연결. 조회 시 accounts와 조인해 user_id를 확인 |
| chat_logs | chat_logs.user_id -> users.id (N:1) | 자연어 대화 기록. session_key 컬럼을 두면 로그인 세션별로 맥락을 구분할 수 있음 (자연어 담당과 협의) |
| 추가 기능 테이블 (적금, 가계부 등) | *.user_id -> users.id | 사용자 소유 데이터는 예외 없이 user_id 컬럼을 가진다 |

- 외래키에는 ON DELETE 규칙을 두지 않는다(회원 탈퇴 미구현, 3.2).
- 시드 데이터 생성 순서: users → accounts → cards → transactions. 시드 사용자 3명(4.4)의 id는 1, 2, 3으로 고정해 다른 파트의 시드 스크립트가 참조할 수 있게 한다.

### 8.3 세션 저장

- **방식**: 프레임워크 기본 서버 세션(서명된 쿠키)을 사용한다. 5.3에서 정한 대로 세션에는 user_id와 활동 시각, 대화 맥락 등만 담는다.
- **테이블 필요 여부**: 세션 테이블은 두지 않는다. 쿠키 세션으로 충분하고, 강제 로그아웃이나 다중 기기 관리를 하지 않기 때문이다.
- **대화 맥락 저장 위치**: 세션에는 최근 5턴 정도만 두고, 전체 기록은 chat_logs에 남긴다. 세션 쿠키는 용량 제한(약 4KB)이 있으므로 긴 대화를 세션에 넣지 않는다.
- **로그인 실패 기록**: 세션이 아니라 users 테이블(failed_login_count, locked_until)에 둔다. 브라우저를 바꿔도 잠금이 유지되어야 하기 때문이다.

## 9. 자연어 입력과의 접점 (자연어 담당에게 전달)

### 9.1 인증 관련 의도(intent)

| 의도 | 예시 문장 | 처리 방식 (직접 실행 / 화면 링크) | 추가 질문 필요 여부 |
|---|---|---|---|
| auth.logout | "로그아웃 해줘", "로그아웃", "나갈래" | 직접 실행. 세션을 비우고 "로그아웃되었습니다." 응답 후 시작 화면으로 이동 | 없음 |
| auth.change_password | "비밀번호 바꾸고 싶어", "비번 변경" | 화면 링크(S-06). 비밀번호를 채팅에 입력하게 하지 않는다 | 없음. 채팅으로 새 비밀번호를 보내오면 "보안을 위해 화면에서 변경해 주세요"로 안내 |
| auth.my_info | "내 정보 보여줘", "내 전화번호 뭐야", "언제 가입했지?" | 직접 실행. 이름·아이디·휴대폰·가입일을 답하고 S-05 링크를 함께 제공 | 없음 |
| auth.update_phone | "전화번호 바꿔줘", "휴대폰 번호 010-1234-5678로 변경" | 번호가 문장에 있으면 직접 실행(형식 검증 후 변경, 변경 전 확인 질문 1회). 없으면 되묻기 | 있음: "변경할 번호를 알려주세요" |
| auth.signup_guide | "가입은 어떻게 해?", "회원가입 하고 싶어" | 화면 링크(S-02). 로그인 상태면 "이미 가입된 계정으로 로그인되어 있습니다" | 없음 |
| auth.login_guide | "로그인 하고 싶어", "로그인은 어디서 해?" | 미인증이면 S-03 링크, 인증 상태면 "이미 OOO님으로 로그인되어 있습니다" | 없음 |
| auth.who_am_i | "나 누구로 로그인돼 있어?", "지금 로그인 상태야?" | 직접 실행. 로그인한 사용자 이름과 아이디 응답 | 없음 |
| auth.set_pin | "간편비밀번호 설정할래", "핀번호 바꿔줘" | 화면 링크(S-07). 채팅에서 숫자를 받지 않는다 | 없음 |
| auth.lock_status | "왜 로그인이 안 돼?", "계정 잠겼어?" | 미인증 상태에서만 의미 있음. 잠금 정책 안내(5회 실패 시 10분)와 S-03 링크. 특정 아이디의 잠금 여부는 알려주지 않는다 | 없음 |
| auth.faq (RAG) | "비밀번호 규칙이 뭐야?", "만 14세 미만도 가입돼?" | RAG로 이 기획서·약관 문서에서 검색해 답변 | 없음 |

- 비밀번호, 간편비밀번호 같은 비밀값은 어떤 의도에서도 채팅 입력으로 받지 않고 화면으로 보낸다. chat_logs에 남기 때문이다.
- 의도 이름(auth.*)은 자연어 담당의 명명 규칙에 맞춰 바꾼다.
- 인증 파트는 각 의도에 대응하는 함수(logout(user), get_my_info(user), update_phone(user, phone))를 제공하고, 자연어 처리기가 세션의 user를 넘겨 호출한다 (R8).

### 9.2 미인증 상태의 요청 처리

- **로그인 안 한 상태에서 "내 계좌 보여줘" 입력 시**: 기능을 실행하지 않고 "로그인 후 이용할 수 있어요. [로그인하기]" 응답과 S-03 링크를 준다. 로그인 후 원래 요청을 자동 재실행할지는 하지 않는다(요청 문장을 세션에 보관해야 하고 복잡해짐). 대신 로그인 후 홈의 입력창에 안내만 띄운다.
- **미인증 상태에서 허용하는 의도**: auth.signup_guide, auth.login_guide, auth.lock_status, auth.faq(상품·규칙 안내 RAG). 그 외 모든 의도는 로그인 안내로 응답한다.
- **미인증 상태에서 자연어 입력창을 보여줄지**: 시작 화면(S-01)에 입력창을 두지 않는다. 자연어 입력창은 홈(S-04) 이후에만 있으므로, 미인증 요청은 사실상 세션 만료 경우에만 발생한다. 단, 자연어 담당이 시작 화면에도 상품 안내용 입력창을 원하면 위 허용 의도 목록으로 제한한다.
- **세션 만료 후 자연어 요청 시**: "로그인 시간이 만료되었습니다. 다시 로그인해 주세요. [로그인하기]" 응답. 세션이 사라졌으므로 대화 맥락도 초기화된 것으로 안내한다.
- **의도 판별 전 인증 확인 순서**: 자연어 처리기는 의도 분류보다 먼저 세션의 user를 확인하고, 미인증이면 허용 의도 목록만 분류 대상으로 한다. 이렇게 하면 미인증 상태에서 LLM이 계좌 조회 함수를 호출하는 일이 구조적으로 막힌다.

| F-09 | 로그인 상태에서 회원가입·로그인 화면 접근 | user1 로그인 후 /signup/1, /login 입력 | 홈으로 자동 이동 | |

| F-11 | GET으로 로그아웃 시도 | 로그인 상태에서 주소창에 /logout 입력 | 로그아웃되지 않음(405 또는 홈으로 이동). POST 버튼으로만 로그아웃 | |
| F-12 | 폼의 user_id 조작 | 개발자 도구로 휴대폰 번호 변경 폼에 user_id=2 필드를 추가해 제출 | 세션의 user_id(1)로만 처리되어 user2의 정보가 바뀌지 않음 | |
| F-13 | 채팅으로 비밀번호 전달 | 자연어 입력 "비밀번호 abcd1234!로 바꿔줘" | 변경하지 않고 화면 링크 안내. chat_logs에 남더라도 변경에 사용되지 않음 | |
| F-14 | 만 14세 미만 가입 | 4단계 생년월일에 올해 기준 13세 날짜 입력 | 4단계에 머물며 나이 제한 메시지 표시 | |

- README에는 F-01~F-07을 기본으로 싣고, 나머지는 시간이 되는 만큼 추가한다.
- 확인 결과 열에는 확인 날짜와 화면 캡처 파일명을 적는다.
