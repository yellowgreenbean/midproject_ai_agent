# 계좌 관리 서비스 기능 기획안

> **문서 버전:** v1.0  
> **작성일:** 2026-11-03  
> **대상 범위:** 계좌 관리(Account Management) 파트  
> **기획 상태:** 기능 범위 확정안(상세 정책은 개발 착수 전 협의)

---

## 1. 프로젝트 개요

### 1.1 목표
사용자가 계좌를 개설하고 보유 계좌의 잔액·거래 내역을 확인하며, 계좌 설정·상태·증명서·알림 등을 한곳에서 관리할 수 있는 계좌 관리 서비스를 구축한다.

### 1.2 범위 원칙
- **포함:** 계좌 개설·조회·관리·해지, 잔액 및 거래 내역 조회, 계좌 검색·통계, 문서 발급·내보내기, 활동 기록, 휴면 관리, 입출금 알림, 계좌 유형 관리.
- **제외:** 계좌 간·타행 이체 실행, 예약·자동이체, 이체 한도·수수료·인증 등 **이체 처리 파트 소관** 기능.
- 계좌 관리 파트는 다른 파트에서 확정한 거래 데이터와 잔액 변동 이벤트를 **조회 또는 구독**한다. 임의로 거래 원장이나 잔액을 수정하지 않는다.
- 실제 금융기관 서비스 수준의 규제 준수·본인확인·금융상품 약관은 별도 검토가 필요하다. 아래 상태명과 업무 정책은 **프로젝트용 설계 초안**이다.

### 1.3 사용자
- **일반 사용자:** 본인 명의 계좌의 생성·조회·설정·해지 및 알림 관리.
- **관리자/운영자(선택):** 장애 대응, 감사 로그 조회, 필요 시 계좌 상태 변경 승인(별도 권한·기록 필수).

## 3. 단계별 상세 기능 명세

### 3.1 1차 MVP — 기본 계좌 관리 (1~7)

#### F01. 계좌 개설
- **사용자 흐름:** 계좌 개설 화면 → 계좌 유형 선택 → 약관·필수 정보 확인 → 개설 요청 → 생성 결과 안내.
- **필수 데이터:** 사용자 ID, 계좌 ID, 고유 계좌번호, 계좌 유형, 개설일시, 상태.
- **처리 규칙:** 계좌번호 중복 방지, 인증된 사용자에게만 개설 허용, 요청 중복 시 중복 계좌 생성 방지.
- **완료 조건:** 개설 직후 본인 계좌 목록에서 확인 가능.

#### F02. 계좌 조회
- **사용자 흐름:** 내 계좌 목록 → 계좌 선택 → 상세 정보 확인.
- **표시 항목:** 별명(없으면 기본 계좌명), 계좌번호(필요 시 일부 마스킹), 유형, 잔액, 상태, 개설일.
- **처리 규칙:** 타인 계좌는 조회 불가. 해지 계좌는 활성 목록에서 분리하고, 필요 시 별도 이력 화면에 표시.
- **완료 조건:** 목록·상세 조회 결과가 일관됨.

#### F03. 잔액 조회
- **핵심:** 계좌별 현재 잔액 표시, 갱신 시점 표시(필요 시).
- **처리 규칙:** 잔액은 거래·원장 담당 시스템의 신뢰 가능한 값을 사용하며 계좌 관리 화면에서 임의 수정하지 않음.
- **완료 조건:** 거래 확정 후 갱신된 잔액을 조회할 수 있음.

#### F04. 거래 내역
- **핵심:** 입금·출금별 내역, 기간 조회, 상세 내역.
- **표시 항목 예시:** 거래 ID, 발생 일시, 거래 유형, 거래 금액, 거래 후 잔액(제공 시), 거래 상태, 적요.
- **처리 규칙:** 거래 원장 담당 시스템의 **확정된 내역**을 기준으로 조회. 미확정·취소 거래는 상태를 명확히 표시하거나 별도 구분.
- **완료 조건:** 사용자 계좌의 해당 기간 기록만 정확히 노출.

#### F05. 계좌 설정
- **핵심:** 계좌 별명 등록·수정·초기화, 즐겨찾기 등록·해제.
- **처리 규칙:** 별명 길이 제한 및 유효성 검증, 즐겨찾기는 사용자별 속성으로 관리.
- **완료 조건:** 변경 내용이 계좌 목록·상세 화면에 일관되게 반영됨.

#### F06. 계좌 상태 관리
- **핵심:** 정상 계좌 일시정지, 정지 해제, 계좌 해지 요청.
- **기본 상태:** `ACTIVE`(정상), `SUSPENDED`(일시정지), `CLOSED`(해지).
- **기본 전이:** `ACTIVE → SUSPENDED → ACTIVE`, `ACTIVE → CLOSED`.
- **해지 제한 조건(초안):** 잔액 0, 미완료 거래 없음, 연계 상품·제한 사유 없음. 실제 정책은 계좌 유형별 확정.
- **처리 규칙:** 해지는 물리적 DB 삭제가 아닌 상태 변경. 조회/감사 목적의 필수 기록 보존. **정지된 계좌의 거래 차단 범위는 이체 파트와 합의**.
- **완료 조건:** 상태 변경 이력이 남고, 타 파트가 최신 상태를 확인할 수 있음.

#### F07. 입출금 알림
- **핵심:** 입금·출금 확정 시 알림 생성, 기본 알림 ON/OFF.
- **처리 규칙:** 거래 파트의 `TransactionConfirmed` 등 확정 이벤트를 구독하여 알림을 생성. 동일 이벤트 재수신 시 중복 발송 방지.
- **완료 조건:** 사용자가 알림 설정을 켜 놓은 계좌에서 거래 확정 이벤트 발생 시 알림을 확인할 수 있음.

### 3.2 2차 확장 — 조회·문서 편의 (8~11)

#### F08. 계좌 검색·필터
- 계좌번호 일부·별명 검색, 정상/정지/해지 상태 및 계좌 유형별 필터.
- 정렬: 즐겨찾기 우선, 최근 개설순, 잔액순(선택).
- 해지 계좌는 기본 필터에서 제외하거나 별도 이력 탭으로 분리.

#### F09. 계좌 통합 대시보드
- 보유 계좌 수, 정상 계좌 수, 합산 잔액, 계좌별 잔액 및 비중.
- **합산 기준:** 동일 통화 계좌만 합산. 통화가 다르면 통화별 표시하거나 환율 기준과 시점을 명시.
- 휴면·해지 계좌의 합산 포함 여부는 화면에 명시하고 정책으로 고정.

#### F10. 계좌 증명서 발급
- 통장 사본 성격의 계좌정보 확인 문서와 계좌개설확인서의 조회·다운로드.
- 문서에 계좌 소유자, 계좌번호, 금융기관/서비스명, 발급일, 문서 종류를 표시.
- **주의:** 프로젝트에서 생성한 PDF를 실제 금융기관이 발급한 공인 증명서처럼 표시하지 않음. 실제 효력 있는 증명서는 금융기관 정책·권한에 따름.

#### F11. 거래 내역 내보내기
- 선택 계좌·조회 기간·거래 유형을 기준으로 **CSV / XLSX / PDF** 다운로드.
- 내보내기 데이터와 화면 조회 조건의 일치 여부 검증.
- 개인정보 마스킹, 파일 생성 권한, 대량 다운로드 제한·감사 기록 고려.

### 3.3 3차 고도화 — 이력·휴면·알림 (12~14)

#### F12. 계좌 활동 기록
- 기록 대상: 계좌 개설, 별명 변경, 즐겨찾기 변경, 알림 설정 변경, 일시정지·해제, 해지 등.
- 항목: 활동 ID, 계좌 ID, 변경 유형, 변경 시각, 변경 주체, 이전/변경 값(민감정보 제외).
- 거래 내역(F04)과 구분되는 **계좌 관리 행위 감사 로그**.

#### F13. 휴면 계좌 관리
- 프로젝트에서 정의한 미사용 기간을 초과한 계좌의 **장기 미사용 안내**.
- 휴면(또는 비활성) 표시, 사전 알림, 사용 재개 안내 및 필요 시 본인확인.
- **주의:** 이 기능의 `DORMANT`는 프로젝트용 비활성 상태 정의이며 법적 의미의 '휴면예금'과 동일하다고 단정하지 않음. 실제 금융기관 서비스에서는 관련 규정 및 상품 정책 별도 검토.
- 구현 권고: `lifecycle_status = ACTIVE/SUSPENDED/CLOSED`와 `inactivity_flag`를 분리하여 장기 미사용 표시가 수동 일시정지와 충돌하지 않게 설계.

#### F14. 알림 고급 설정
- 계좌별 알림 ON/OFF, 입금·출금별 알림, 최소 금액 기준.
- 알림 센터에서 수신 이력·읽음 상태 확인.
- 실패한 알림의 재시도, 중복 발송 방지, 알림 수신 채널(앱/이메일 등)은 실제 구현 환경에 맞춰 결정.

### 3.4 공통 확장 — 계좌 유형 관리 (15)

| 유형 | 예시 용도 | 주요 차이 | 초기 구현 원칙 |
|---|---|---|---|
| `CHECKING` / 입출금 계좌 | 일상적인 잔액 관리·입출금 | 거래 빈도 높음 | 기본 유형으로 제공 |
| `SAVINGS` / 저축 계좌 | 목적성 자금 저축 | 출금 조건·적립 규칙 등이 상품마다 다름 | 기본 분류와 화면 구분 먼저 제공, 복잡한 이자·만기 계산은 상품 정책 확정 후 구현 |

- 개설 시 유형을 선택하고, 목록·상세·검색·대시보드에 유형을 표시한다.
- 유형별 개설 요건, 해지 조건, 거래 허용 여부를 **설정 가능한 정책**으로 분리한다.
- 개설 후 계좌 유형 변경은 기본적으로 허용하지 않고, 필요 시 신규 계좌 개설 방식으로 안내한다(프로젝트 기본 정책).
- `CHECKING`/`SAVINGS`는 시스템 예시 코드이며 실제 금융상품 분류와 1:1로 대응한다고 가정하지 않는다.

## 5. 데이터 모델 초안

> 아래는 **논리 모델**이다. 컬럼명·타입·인덱스는 DB 설계 단계에서 확정한다. 계좌 잔액과 거래 원장은 각각의 책임 시스템이 관리한다.

### 5.1 주요 엔터티

| 엔터티 | 필드 예시 | 역할 |
|---|---|---|
| `accounts` | `id`, `user_id`, `account_number`, `account_type`, `lifecycle_status`, `opened_at`, `closed_at` | 계좌 기본 정보 및 상태 |
| `account_preferences` | `account_id`, `user_id`, `nickname`, `is_favorite` | 계좌별 사용자 설정 |
| `account_balances` *(조회 모델)* | `account_id`, `currency`, `available_balance`, `updated_at` | 원장/잔액 시스템 값의 조회용 표현. 원본 소유권은 별도 |
| `transactions` *(외부 조회)* | `transaction_id`, `account_id`, `type`, `amount`, `status`, `occurred_at` | 이체·거래 담당 파트가 제공하는 내역 |
| `account_activity_logs` | `id`, `account_id`, `actor_id`, `action`, `occurred_at`, `metadata` | 계좌 설정·상태 변경 감사 기록 |
| `notification_preferences` | `user_id`, `account_id`, `deposit_enabled`, `withdrawal_enabled`, `minimum_amount`, `channel` | 알림 설정 |
| `notifications` | `id`, `user_id`, `account_id`, `event_id`, `title`, `read_at`, `sent_at` | 알림 발송·수신 이력 |
| `account_inactivity` | `account_id`, `last_activity_at`, `is_inactive`, `flagged_at` | 장기 미사용 판단 및 안내 |
| `document_issuance_logs` | `id`, `account_id`, `document_type`, `issued_at`, `requested_by` | 증명서 발급 이력 |

### 5.2 필수 무결성·보안 원칙
1. `account_number`는 고유해야 하며 재사용 정책을 명시한다.
2. 모든 계좌 조회·변경 요청에서 **인증 및 소유권 검증**을 수행한다.
3. 계좌번호·고객정보·거래 내역은 전송/저장/로그에서 적절히 보호한다.
4. 중복 개설 요청, 계좌 상태 변경, 거래 이벤트 처리는 **중복 처리 방지**가 필요하다.
5. 계좌 상태 변경은 트랜잭션과 감사 기록을 함께 고려해 일관성을 확보한다.
6. DB 행 삭제 대신 해지 상태를 보존하고, 보존·파기 기간은 실제 적용 환경에 맞춘다.

## 6. 계좌 상태 및 휴면 처리

```text
[ACTIVE] 정상
   │  일시정지
   ▼
[SUSPENDED] 일시정지
   │  정지 해제
   └──────────────→ [ACTIVE]

[ACTIVE] ── 해지 조건 검증·확정 ──→ [CLOSED] 해지

[장기 미사용 여부] = 별도 플래그(inactivity_flag)
→ ACTIVE/SUSPENDED/CLOSED 상태와 혼동하지 않도록 별도 관리
```

**상태별 기본 정책 초안**

| 작업 | ACTIVE | SUSPENDED | CLOSED |
|---|---|---|---|
| 계좌 정보 조회 | 허용 | 허용 | 제한적 이력 조회 |
| 잔액·거래 내역 조회 | 허용 | 허용 | 보존 정책 범위에서 조회 |
| 별명·즐겨찾기 변경 | 허용 | 정책 확정 필요 | 불허 |
| 이체 실행 | 이체 파트 정책 적용 | 이체 파트에서 제한 반영 | 불허 |
| 계좌 해지 | 조건 충족 시 | 해제 후 처리 권장(초안) | 재해지 불허 |

> 특히 **일시정지 중 입금 허용 여부**, **정지 상태에서 출금/이체 제한 범위**, **해지 후 기록 열람 범위**는 파트 간 결정해야 할 사안이다. 구현 전에 명시적으로 확정한다.

## 7. 타 파트 연동 명세

### 7.1 이체·거래 파트와의 경계

| 구분 | 계좌 관리 파트 책임 | 이체·거래 파트 책임 |
|---|---|---|
| 계좌 상태 | 상태 조회·변경 API 제공 | 거래 전 계좌 상태 검증 |
| 거래 내역 | 조회 UI·조회 API 구성 | 원장 및 확정 거래 데이터 제공 |
| 잔액 | 읽기 전용 조회·표시 | 잔액 변경의 정합성 보장(원장 담당 시스템과 협업) |
| 입출금 알림 | 이벤트 수신·설정 적용·발송 | 거래 확정 이벤트 발행 |
| 계좌 해지 | 해지 요청·조건 검증·상태 반영 | 미완료 거래 유무 등 검증 데이터 제공 |

### 7.2 이벤트 연동 예시

```text
거래 확정 (이체·거래 파트)
    ↓
TransactionConfirmed 이벤트 발행
    ↓
계좌/알림 파트가 이벤트 수신
    ├─ 계좌·거래 유형·금액 기준 확인
    ├─ event_id로 중복 알림 검사
    ├─ 알림 저장·발송
    └─ 사용자 화면에 알림 이력 표시
```

- 이벤트 예시 필드: `event_id`, `transaction_id`, `account_id`, `transaction_type`, `amount`, `currency`, `confirmed_at`.
- 개인정보와 잔액 전체를 이벤트에 불필요하게 싣지 않는다.
- 알림 실패가 거래 자체를 취소하거나 중복 처리하게 해서는 안 된다.

### 7.3 API 초안 (예시, 확정 아님)

| Method | Endpoint | 용도 |
|---|---|---|
| POST | `/accounts` | 계좌 개설 |
| GET | `/accounts` | 본인 계좌 목록·검색·필터 |

| GET | `/accounts/{accountId}/balance` | 잔액 조회 |

## 8. 비기능 요구사항

- **권한:** 본인 계좌만 접근; 관리자 기능은 일반 사용자 기능과 분리.
- **정확성:** 잔액·거래 내역 불일치 금지, 중복 이벤트·중복 요청 대응.
- **추적성:** 중요 상태 변경·증명서 발급·알림 설정 변경은 감사 가능.
- **가용성:** 알림 전송 실패가 핵심 계좌 조회·거래 기능을 방해하지 않도록 비동기 분리.
- **UX:** 로딩·빈 목록·오류·계좌 정지·해지 상태를 명확하게 표시.
- **접근성:** 색상에만 의존하지 않는 상태 텍스트, 읽기 쉬운 금액과 날짜 표시.
- **개인정보:** 계좌번호 일부 마스킹, 다운로드 파일 접근 제어, 비밀정보 로그 기록 금지.

### 9.1 주요 테스트 시나리오
- [ ] 사용자가 계좌를 개설하면 고유 계좌번호가 발급되고 목록에 표시된다.
- [ ] 타인의 계좌 목록·상세·잔액·거래 내역에 접근할 수 없다.
- [ ] 거래 확정 후 화면에서 올바른 잔액·내역을 조회한다.
- [ ] 별명과 즐겨찾기 변경이 새로고침 후에도 유지된다.
- [ ] 일시정지·해제 상태가 이체 파트에도 전달된다.
- [ ] 잔액·미완료 거래 등 해지 제한 조건을 위반하면 해지되지 않는다.
- [ ] 해지 후에도 정책상 필요한 거래·감사 기록이 보존된다.
- [ ] 동일 거래 이벤트를 두 번 받더라도 입출금 알림은 중복되지 않는다.
- [ ] 검색·필터·대시보드 합산 조건이 일치한다.
- [ ] 내보낸 파일의 거래 기간·유형·금액이 화면 조건과 일치한다.
- [ ] 장기 미사용 표시가 수동 일시정지와 혼동되지 않는다.
- [ ] 계좌 유형별 설정·해지 정책이 올바르게 적용된다.

## 10. 개발 착수 전 결정할 항목

1. **서비스 성격:** 교육용 모의 금융 서비스인지, 실제 금융기관 연동 서비스인지.
2. **계좌 유형:** 입출금/저축 외 계좌 추가 여부, 저축 계좌 이자·만기 처리 범위.
3. **계좌 정지:** 사용자가 정지했을 때 입금 수신·출금·이체를 각각 허용할지.
4. **계좌 해지:** 잔액 처리, 미완료 거래, 해지 계좌 재조회·증명서 발급 정책.
5. **잔액 소유권:** 거래 파트와 원장/잔액 시스템 중 누가 최종 원본을 관리하는지.
6. **휴면 기준:** 미사용 기간과 판단 대상 활동, 사용자 복귀 절차.
7. **알림 채널:** 앱 내부 알림부터 구현할지, 이메일/푸시까지 확장할지.
8. **문서 효력:** 프로젝트 예시 문서인지, 실제 금융기관 확인 문서인지.
